第 2 讲 · 大模型时代 FDE 交付 vs 传统交付（讲师用讲义）

版本 v1.0 · 对象：C-Life 内部专业人员 · 时长 90′ · 实践蓝本：康养行业大模型及微康养生态运营平台 本讲义讲"怎么讲"；学员动手材料见 工作坊/02_大模型时代FDE交付vs传统交付_workshop.md，不重复。

一、一句话命题 + 能力位置

命题：从人月堆叠到认知杠杆。

传统交付靠堆人月——活变多就加人，加人就多接缝（见第 1 讲）。FDE 交付靠认知杠杆——一个人的结构化判断，被智能体编队和工程化平台放大数倍。关键要讲清：杠杆不来自"打字快"，来自"结构化能力 + 平台固化"。 打字快是线性的，结构化 + 平台是指数的。

**本讲在能力模型中的位置：**指向 C6 交付物工程（多智能体并行写作、锚定口径、装配质检）与 C2 结构建模（杠杆的支点是结构化能力）。本讲仍是"为什么/凭什么"，具体怎么建模从第 4 讲起训练。

三、认知输入

要点页 1 · 人力对比：一次真实的实证（10′）

【讲述脚本】

"上一讲我说'一个人贯通消除断层'，肯定有人心里嘀咕：一个人扛得动吗？还是嘴上好听、实际累死？今天我用康养项目的账，一笔一笔算给你看。

同一条交付链——从需求调研到 7 域数智本体建模、到 3835 行可运行插件骨架、到 100+ 页对客可研——两种模式的投入是这样：

传统模式：产品经理 + 架构师 + 行业顾问 + 方案经理 + 美工，5 人以上，数周。而且这 5 个人之间有至少 4 道接缝，每道接缝都在漏（第 1 讲讲过）。

FDE 模式：1 名 FDE + 智能体编队。0 接缝。

这不是'省了 4 个人'这么简单。是交付的组织形态变了——从'按工种分人、靠流程串起来'，变成'按认知链分给一个人、靠智能体扩手脚'。"

【板书/图】

图 2-1 传统交付流 vs FDE 交付流对比

图说：上半区"传统流"——5 个角色横向排开，中间 4 道接缝画漏斗（信息衰减），总工期"数周"；下半区"FDE 流"——1 个 FDE 居中，下挂智能体编队（事件风暴/建模/写作/制图并行分支），0 接缝，标注关键产出物节点。两区右端对齐同一个交付物（100+ 页可研），凸显"同样的结果，两种投入结构"。

【康养项目证据】

已在脚本中给出：传统 5+ 人 / 数周 vs 1 名 FDE + 智能体编队；交付物为 100+ 页可研（11 章 / ~11 万字 / 26 图）+ 2 份附录 docx，格式对齐客户既有模板。注意：这里不能只说"1 人"就完了——1 人扛得动的前提是后面三页要讲的杠杆机制。

要点页 2 · 交付物形态的根本变化（9′）

【讲述脚本】

"再看交出去的东西变了没有。很多人以为 AI 只是让你'写得快',交付物还是老三样。错。康养项目的交付物形态是传统模式根本产不出的：

第一，方案与代码同源。传统模式里，可研报告是方案经理写的 PPT/Word，跟真正的系统是两张皮。康养项目不是——11 章可研背后，是 3835 行可运行的 Python 插件骨架 + 21 个 YAML，7/7 py_compile 通过。方案里写的每个域，都有能编译的结构撑着。方案不再是"说说而已"，是"已经建好了骨架的说明书"。

第二，结构可校验。7 域五要素 OAG：Object 76 / Link 75 / Function 38 / Rule 47 / Action 54，A 结构校验 7/7 零悬空引用，B source 治理 7/7 零空 source。传统方案没有"校验"这个概念——你怎么校验一份 Word 的内部一致性？

第三，规模与深度同时在线：14 类知识库 / 8 个知识图谱 / 约 350 万三元组。这个体量,传统 5 人团队数周产不出，产出来也无法保证内部一致。"

【板书/图】

板书三行对照：「传统：Word 方案 ⟂ 系统（两张皮）」「FDE：11 章可研 ‖ 3835 行骨架（同源）」「传统：不可校验 / FDE：7/7 零悬空引用」。

【康养项目证据】

3835 行 Python + 21 YAML，7/7 py_compile ✓，只 import sdk 红线 ✓；五要素 Object 76 / Link 75 / Function 38 / Rule 47（声明式 18 + function 骨架 29）/ Action 54 / HIL 26；14 类知识库 / 8 图谱 / 约 350 万三元组。

要点页 3 · 节奏与质量控制的根本变化（9′）

【讲述脚本】

"节奏也变了。传统模式是串行接力：需求做完交设计，设计做完交开发，一棒接一棒，总时长是各段之和。FDE 模式是并行铺开：一个人在同一时间，指挥智能体编队并行跑多条支线。

康养项目可研的写作阶段就是活样本：35 个分节并行写作，不是一节一节写。制图 26 张与写作同步跑。7 个域同一天并行编译。这不是把串行加速，是把串行改成了并行——这是节奏上质的差别。

但并行有个致命风险：各写各的，口径会散。所以质量控制的方式也跟着变了。传统靠'评审会'事后抓错；FDE 靠锚定口径 + 结构校验事前防错。康养项目的做法是先立一份 _WRITING_BRIEF.md（术语表 + 核心数据表 + 观点主张 + 协作纪律）当唯一真相源，35 节全部引用不重算,再用结构校验器兜底。

我要诚实说一句：并行不是没代价的。散了口径就要收口。下一讲会讲到康养项目栽过的跟头——图目计数漂移、章节编号冲突——那都是并行的账。但账是可控的，靠的是纪律，不是靠不并行。"

【板书/图】

板书：「串行 Σ 各段 → 并行 max 各支线」+「事后评审 → 事前锚定口径(BRIEF)+ 结构校验」。

【康养项目证据】

35 节并行写作；26 图与写作同步；7 域同日并行编译；_WRITING_BRIEF.md 作唯一真相源统一口径；A/B 结构校验 7/7。并行代价的真实账：第 6 讲的 B-1（图目计数漂移，标题写 22 张实际 26 行）、B-2（章节编号冲突）——本讲点到，第 6 讲深讲。

要点页 4 · 杠杆到底来自哪里（8′）—— 核心，别讲偏

【讲述脚本】

"最后这页是全讲的钉子，钉不进去前面白讲。FDE 的杠杆，不来自打字快，来自两样东西：结构化能力 + 平台固化。

先说结构化能力。康养项目最难的一步是把 102 个乱糟糟的业务事件，收敛成 16 簇、压成 7 个域。这一步没有任何模型能替你做判断——模型可以帮你把 102 件事列出来、可以帮你写候选归类，但'该归成 16 簇还是 20 簇、这个域的边界划在哪'，是 FDE 的结构化判断。模型只能加速你做完，不能替你做对。这是杠杆的支点：你结构化能力越强，模型放大的倍数越大；你结构化能力是零，模型放大零还是零。

再说平台固化。7 个域能在同一天并行编译、7/7 零悬空引用，靠的不是个人手速，是 studio-planner（事件风暴）→ domain-model（限界上下文）→ clife-onto-engine（本体）→ citations 治理 → 可研报告生成 这一条固化管线（Astra Studio）。方法论一旦固化进平台，就不再依赖'这个人今天状态好不好'。没有工程化平台的 FDE，只是"更累的架构师"——他能做对，但做不快、做不稳、复制不了。

所以杠杆 = 结构化能力（决定能不能做对）× 平台固化（决定能不能做快做稳）。打字快，在这个乘式里连一项都不是。"

【板书/图】

板书公式：认知杠杆 = 结构化能力（做对） × 平台固化（做快做稳）；下方一行：打字快 ∉ 这个公式。

【康养项目证据】

结构化能力证据：102 事件 → 16 簇 → 7 域，模型不替你做判断（BRIEF 主张 1）。平台固化证据：7 域同日并行编译、7/7 零悬空引用，靠 studio-planner → domain-model → clife-onto-engine → citations → 可研 固化管线（BRIEF 主张 2）。

要点页 4·补 · Vibe Coding 的真相：AI 能干什么、不能干什么（reference/methodology 06，4′）

【讲述脚本】 "上一页那句'模型只能加速你做完、不能替你做对'，不是我编的口号，是我们方法论文集里一篇《AI 时代的 FDE》的第一手结论。作者用 AI 辅助，3 小时手搓了一个本体引擎原型；他复盘'这 3 小时里 AI 到底干了多少活'，得出一张清单——

  • AI 能干的：给了明确规格后，把伪代码变 Python、处理文件读写、生成测试、格式化输出——10 分钟搞定。共同特征：给明确规格，AI 快速生成代码。
  • AI 不能干的：规则写入前还是后执行？日志存快照还是只存改变？Schema 用 YAML 还是 Python？多规则违反时短路还是收集？——这些是工程判断，不是编码问题。AI 只会给'常见做法'，不一定符合你的设计原则。

一句话结论，请记死——'AI 能把"想清楚的事"快速变成代码，但不能代替"想清楚"这件事本身。' '想清楚'指的就是：数据规模 vs 决策治理、规则 vs 前置条件、可追溯性要什么、业务人员要审查什么、边界条件怎么处理——这些判断都发生在写代码之前。

所以'认知杠杆'的真相是：AI 把"实现"变便宜了，但没把"判断"变容易。 谁的判断力强，谁的杠杆就大；没有判断，AI 放大的是一堆能跑但错的代码（方法论 06 原话：没有蓝图的 Vibe Coding 会失控，一处改动带出三处 bug）。再补一句同篇的判断——'平台越来越便宜，本体模型越来越值钱；会建模型的人，不会被替代，而是被放大。'"

【板书】

Vibe Coding 真相（方法论 06）
  AI 能干：给明确规格 → 快速生成代码（伪代码→Python/测试/格式化，10 分钟）
  AI 不能干：工程判断（规则前/后校验、快照/日志、短路/收集…）
  ★ "AI 能把想清楚的事变成代码，不能代替'想清楚'本身"
  → 认知杠杆 = AI 让"实现"变便宜，但没让"判断"变容易

【呼应】 这条直接支撑本页公式的第一项"结构化能力（做对）"，也预告第 4 讲栈③（判断"想清楚"就是本体建模）与第 8 讲（判断力属 C1–C3，AI 替不了）。

四、现场演练导入（过渡话术）

"公式给你了，现在你自己套。别拿康养项目套——拿你自己经历过的一次交付套。接下来 36 分钟，你做一张人月/工序重估表：把那次交付原本花的人、花的工序列出来，逐条问'这一条，FDE + 智能体模式能压掉多少'，算出一个理论压缩比。

但我把话撂前头：这个练习真正的分，在你诚实标注哪些环节压不动。谁的表算出'压缩 10 倍、全能压'，谁就是没懂——一定有环节压不动，涉钱的判断、涉合规的取证、跟客户拍板的对话，这些第 3、6 讲会讲，智能体碰都不该碰。翻到 02_..._workshop.md。"

五、复盘研讨（18′）

  1. 你的压缩比里，最大的那一块压缩来自"结构化能力"还是"平台固化"还是"打字快"？如果主要来自打字快，说明什么？

    • 收口："主要来自打字快，说明你还没理解杠杆——打字快是线性的，最多快 2、3 倍；康养项目是 5+ 人到 1 人的结构性变化，那来自结构化 + 平台，是量级差别。"

  2. 你标注为"压不动"的环节，是真的压不动，还是你不敢让智能体碰？这两者的区别在哪？

    • 收口："真压不动=涉钱/涉合规/涉责任承担（第 3、6 讲的 HIL 硬判据）；不敢碰=你还没建立对平台的信任。前者是纪律，后者是能力缺口，别混为一谈。"

  3. 同样一份交付物，如果你没有 Astra Studio 这样的平台，只有 FDE 一个人 + 通用大模型，压缩比会掉到多少？

    • 收口："会掉很多，而且质量不可控。这正是主张 2：没平台的 FDE 只是更累的架构师。第 5 讲专门推演'无平台重做康养项目'的成本。"

六、本讲难听话 + 反例引用

难听话（1 句）

"你之所以觉得 AI 就是'帮你写得快一点'，是因为你自己的活里，就没有多少需要结构化判断的成分——你一直在做搬运，所以你只能想象一个'搬得更快'的 AI。杠杆放大的是判断力，你没有判断力，AI 放大的就是你的空白。"

反例引用 · B-7 的返工成本记在"人月账"上

本讲不强制配新反例（BRIEF 第四节），引第 1 讲的 B-7 补充人月视角：长者旅程初版做"夜间急救"过重、返工改会员飞轮——这笔返工在传统人月账里，是实打实的重做工时。这里要点破一个反直觉的事实：FDE 模式下，压缩比再高，也压不掉"方向错了导致的返工"。B-7 的返工不是打字慢造成的，是判断偏了造成的——正说明杠杆的支点是结构化判断：判断对，压缩比才成立；判断错，智能体只会让你更快地错更多。所以做人月重估时，别把"因方向错误产生的返工"算进"可压缩"里，它压不动，只能靠一开始想清结果来避免。
