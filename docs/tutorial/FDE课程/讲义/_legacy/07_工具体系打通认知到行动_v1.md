## 一、一句话命题 + 能力模型定位

**命题：工具体系的价值不在"有哪些工具"，而在"层与层如何咬合"——数据从认知无损流到行动。**

第 5 讲讲了平台的"固化"一面（纪律 → 校验器）。本讲讲同一个平台的**"咬合"一面**：Astra Studio 的 planner（认知萃取）/ insight（画像旅程流程）/ docs（文档生成装配）/ quality（校验）四层，如何把"客户嘴里的一句模糊话"一路传导成"可研报告里的一节字 + 一张图 + 一条校验通过记录"，中间**不掉数据、不断链**。

**能力模型定位**：本讲主打 **C6 交付物工程**，兼顾 C1→C2 的数据流理解。靶子是另一个误区：学员容易以为"工具各管一段就行"。本讲要点破——**层间的接口（产物契约）比工具本身更重要，而交付物的"格式质检"和"内容质检"是两条独立的线，FDE 都得自己走一遍**（这是 B-3/B-4 的主场）。

## 三、认知输入

### 要点页 1 · 四层地图：planner / insight / docs / quality 各管什么

**【讲述脚本】**
"先给你们一张全景，然后我们沿着一条数据流走一遍。Astra Studio 不是一个大工具，是一族插件，分四类职能：

- **planner（认知萃取）**：把人脑里的业务认知榨出来、结构化。它下面有 event-storm（事件风暴）、domain-model（限界上下文）、skill-design、spec-generate。康养项目的 **102 业务事件 → 16 事件簇 → 7 域 D1–D7**，就是这一层的产物。
- **insight（画像/旅程/流程）**：把事件变成'谁、在什么旅程、走什么流程、痛在哪'。它下面有 persona / journey / process / domain-canvas / behavior-matrix / opportunity。康养项目的 **7 画像（368 份问卷校准）/ 7 旅程 / 5 流程 / 10 热点**出自这里。
- **docs（文档生成装配）**：把前面所有认知产物，装配成对客交付物。blueprint / plan / write / assemble / export。康养项目 **11 章 / ~11 万字 / 26 图**的可研，是这一层吐出来的。
- **quality（校验）**：validate / wire-mcp，跨层守结构与合规。**7/7 结构校验、只 import sdk 红线**是它跑的。

再加一个运行时地基：**clife-onto-engine（本体运行时）**，把 insight/planner 的认知产物固化成 7 域数智本体（Object 76/Link 75/...），既是 docs 的数据源，也是 quality 的校验对象。

关键不是记住这些名字，是理解：**它们不是并列的四个工具箱，是一条流水线的四道工位。**"

**【板书 / 图】**

![图5-1 Astra Studio 工具栈分层与咬合](../figures/fig-5-1-平台分层.png)
**图 5-1  Astra Studio 工具栈分层与咬合**（第 5 讲同图复用）
本讲看它的"咬合"面：planner→insight→ontology→docs，四层间数据单向流转；quality 横切各层做校验。第 5 讲讲每层如何"固化纪律"，本讲讲层与层"如何交接数据不掉链"。

**【康养项目证据】**
- planner 产物：102 事件 → 16 簇 → 7 域。
- insight 产物：7 画像（368 份问卷 = 310 + 58）/ 7 旅程 / 5 流程 / 10 热点（P1–P5）。
- ontology 产物：Object 76 / Link 75 / Function 38 / Rule 47 / Action 54 / HIL 26。
- docs 产物：11 章 / ~11 万字 / 26 图 + 2 附录 docx。

### 要点页 1·补 · 两套 plugin 体系 + "认知到行动"就是 OAG（呼应第 5 讲）

**【讲述脚本】**
"上一页那四层，其实分属**两套 plugin（插件）体系**——这跟第 5 讲讲的是同一件事，你要在这一讲把它接上：
- **智能体 plugin 体系（建模端 / build-time）= Astra Studio**：planner / insight / docs / quality。它们是把 FDE 方法论固化的**技能插件**，帮你在'建的时候'把认知萃取、画像旅程、文档装配、质检跑通。对标 Palantir 的 **AIP 编排层（Agents·Skills·Tools·Workflows）**。
- **ontology plugin 体系（运行时 / run-time）= clife-onto-engine**：把建出来的 7 域本体，编译成能被智能体调用、能受治理写回的**本体插件**。对标 Palantir 的 **Ontology 本体层**。

为什么这一讲叫'打通**认知到行动**'？因为**这两套体系接起来，正好是一条从'认知'到'行动'的完整链**——planner/insight 把模糊认知榨成结构（**认知**），clife-onto-engine 的 Action 让智能体据此**受治理地做事、写回**（**行动**）。**这就是第 4 讲栈③讲的 OAG：让 AI 从'会查'升级到'会做且做得对、可追溯'。** 工具体系的终点不是'生成一份好看的文档'，是'让一个智能体能安全地按本体去改变世界'。"

**【板书】**
```
认知端(build)  智能体 plugin 体系 = Astra Studio       ← 对标 Palantir AIP 编排层
   planner(认知萃取) → insight(画像旅程) → docs(装配) · quality(校验横切)
        │  认知产物固化为本体
        ▼
行动端(run)    ontology plugin 体系 = clife-onto-engine  ← 对标 Palantir Ontology 层
   7 域本体(Object/Link/Function/Rule/Action) → 智能体受治理写回(Action)
"认知 → 行动" = OAG（从会查到会做），不是 RAG（只会查）
```

**【方法论出处】** `reference/methodology 07`（OAG 与 RAG 的分界）· `17`（我们在构建什么：一个 AI 原生 OS 内核）。工具体系不是"文档工厂"，是"AI 原生 OS 的建造与运行两端"。

### 要点页 2 · 一条数据流：从"义诊到店"这个事件，走到可研里的一节字

**【讲述脚本】**
"光看四层地图是抽象的。我带你们跟一条**真实的数据**从头走到尾，你就懂'咬合'是什么意思了。拿康养项目会员飞轮里一个具体事件：**E38 义诊（到店获客入口）**。

1. **planner / event-storm**：E38 作为 102 个事件之一被捕获，聚进营收簇。它旁边站着 E45 长者食堂、E03 老带新——三个到店入口。
2. **insight / journey + process**：这三个入口进入`会员转化与交叉复购飞轮`流程建模，触发态 = 义诊 E38 / 老带新 E03 / 食堂 E45 三入口到店；决策点 D1 命中试做、D2 转化 or 流失……**6+1 个决策点，每个决策点就是一个 skill 切分边界**。数据在这一步从'孤立事件'变成'带上下文的流程节点'。
3. **domain-model → ontology**：这些决策点归到 **D3 member-revenue-flywheel** 域，落成本体五要素——比如 D3 建成 10 Object / 11 Link / 6 Function / 6 Rule / 7 Action，其中`画像 canonical 在 D4 不分裂`是跨域纪律。E38 到此变成了 Object、Action、Rule。
4. **docs / blueprint→plan→write→assemble→export**：可研的营收章节写作时，作者从 D3 本体里取'三条营收线咬合（中医理疗 + 长者食堂 + 商城器械）'这个结构，写成正文，配一张流程图。
5. **quality / validate**：这一节引用的对象、这张图的 slug、这条规则挂的 citations，都要过校验。

看到没有——**同一个 E38，从'客户嘴里的一句义诊获客'，无损传导到了可研的一节字加一张图。**每一层的输出，是下一层的输入。这条链但凡断一环，前面的认知就白萃取了。**FDE 的核心工程能力，就是维护这条链不断。**"

**【板书】**
```
E38 义诊到店  一条数据流走 5 层：
event-storm(102事件之一) → journey/process(飞轮流程 6+1 决策点)
 → domain-model/ontology(归 D3, 落 Object/Action/Rule) → docs(写成营收章一节+配图)
 → quality(引用/slug/citations 过校验)
每层输出 = 下层输入；断一环，前面认知白萃取
```

**【康养项目证据】**
- 会员飞轮流程真实结构：触发 = 义诊 E38 / 老带新 E03 / 食堂 E45 三入口；6+1 决策点 = skill 切分边界；三条营收线咬合（中医理疗 E40 + 长者食堂 E45/E46 + 康养商城/器械 E52/E53/E54）。
- D3 本体规模：10 Object / 11 Link / 6 Function / 6 Rule / 7 Action，`画像 canonical 在 D4 不分裂`。

### 要点页 3 · 层间接口 = 产物契约：为什么"占位符即契约"

**【讲述脚本】**
"上一页讲了数据怎么流。这一页讲**层与层之间靠什么交接**——靠'产物契约'。什么叫产物契约？就是上一层交给下一层的东西，有一个双方都认的**格式约定**，不是随手扔个文件。

最典型的例子：**图片占位符**。docs 层写正文时，图还没画（图是并行制作的）。正文里先写一个占位：`![图N-M 图名](../figures/fig-N-M-<slug>.png)`。这个 `slug` 就是**正文层和制图层之间的契约**。正文说'我这里要一张 fig-5-1-平台分层'，制图那边就必须交一个文件名正好是 `fig-5-1-平台分层.png` 的图。两边对的是同一个 slug，图才能在导出时被 docx 正确嵌进去。

所以我们定了一条铁律：**slug 必须先定后画，一律用 figures 表已列的 slug，不自造、不事后改名。** 这不是龟毛，这是接口纪律。你把 slug 当成两个模块之间的 API 签名——签名一改，调用方全断。下一页的反例 B-3，就是这个契约被破坏后的惨状。"

**【板书】**
```
产物契约 = 层间接口的格式约定
图片占位 ![...](../figures/fig-N-M-<slug>.png) = 正文层↔制图层的 API 签名
铁律：slug 先定后画 · 用 figures 表已列 slug · 不自造不改名
占位符即契约，改 slug = 改 API 签名 = 调用方全断
```

**【康养项目证据】**
- BRIEF 配图约定：`![图N-M 图名](../figures/fig-N-M-<slug>.png)` + 下一行 `**图 N-M 图名**` + 2–4 句图说；"slug 必须先定后画（反例 B-3），一律用总纲 figures 表已列 slug，不自造新图名"。
- 康养项目 26 图全部走同一 slug 契约，本讲配图 fig-5-1-平台分层即遵此约。

### 要点页 4 · 反例主场：内容对了，交付物照样能崩（B-3 + B-4）

> 本讲反例 B-3（图片路径断裂）+ B-4（Word 主题色覆盖）。二者共同点：**内容层没错，是交付物的"格式/呈现"这条独立质检线出的事。** 核心原则：**交付物格式与内容是两条独立质检线，FDE 都得自己走一遍。**

**【讲述脚本 — B-3】**
"先讲 B-3，图片路径断裂。康养项目导出 docx 的时候，**丢图了**。正文里明明写了占位、图也画好了，导出的 Word 里就是有几张图不见了。查下去，原因很朴素：**正文占位的 slug 和实际图片文件名的 slug 对不上**——`../figures/fig-X-Y-slug.png` 里的 slug，和 figures 目录里真实文件的 slug，有出入。可能是有人事后改了图名，也可能是正文写占位时手抖。

这就是上一页'占位符即契约'被违反的直接后果。**契约一破，导出层照着断掉的路径去找图，找不到，就静默丢图。** 注意'静默'两个字——它不报错，docx 照样生成，你不逐张翻还发现不了。这是最阴险的一类 bug：**内容全对，管线全绿，交付物却是残的。**

教训：slug 先定后画（B-3 的直接对策）；而且导出后**必须人肉逐张验图**，不能信'管线跑通了'。"

**【讲述脚本 — B-4】**
"再讲 B-4，更微妙。导出 docx 的时候，我们用了对齐客户模板的 Word 主题。结果 **Word 的主题色把我们浅色系的配图给覆盖/冲突了**——图是按浅色系精心配的，套进 Word 模板一看，主题色一压，图文风格割裂，有的图直接看不清。

这里内容一个字没错、图一个像素没错、slug 也对得上。崩在**呈现层**：交付物的视觉规范和内容是两回事。B-4 告诉你一件残酷的事——**交付物的'格式质检'是一条和'内容质检'完全独立的线。** 内容质检问'字对不对、数对不对、引用断没断'；格式质检问'图显不显示、色冲不冲突、排版散没散、字体对不对'。两条线，两套检查动作，**都得 FDE 自己走一遍**，因为没有任何一个校验器会替你看'这张图套进 Word 好不好看'。

把 B-3 和 B-4 放一起你就看清了：**quality 层的自动校验能守结构（悬空、越界、红线），守不住呈现（丢图、串色）。呈现的最后一道闸，是 FDE 的眼睛。**"

**【板书】**
```
B-3 图片路径断裂：正文占位 slug ≠ 实际文件名 slug → docx 静默丢图
   对策：slug 先定后画（占位即契约）+ 导出后人肉逐张验图
B-4 Word 主题色覆盖：主题色压浅色系配图 → 图文风格割裂/看不清
   对策：格式质检独立于内容质检，FDE 亲自走呈现层
共同原则：交付物【格式】与【内容】是两条独立质检线，都得 FDE 自己走
        自动校验守结构，守不住呈现；呈现最后一道闸 = FDE 的眼睛
```

**【康养项目证据】**
- B-3：正文占位 `../figures/fig-X-Y-slug.png` 与实际文件名 slug 不一致 → docx 导出丢图。引出"占位符即契约；slug 必须先定后画，不可事后改名"。
- B-4：导出 docx 时模板主题色覆盖浅色系配图，图文风格割裂。引出"交付物格式与内容是两条独立质检线，都得 FDE 自己走一遍"。
- 交付规模：26 图 + 11 章需逐图逐节走两条线，非抽检。

### 要点页 5 · 收束：认知到行动，卡点永远在"层间"

**【讲述脚本】**
"把今天收成一句话。工具体系打通'认知到行动'，难点从来不在**单层内部**——event-storm 会不会用、export 命令怎么敲，那是操作，一学就会。真正的卡点永远在**层与层之间的交接**：

- 认知（planner）到结构（ontology）之间：会不会掉信息？102 事件归 7 域，归错一个簇，后面全歪。
- 结构（ontology）到交付（docs）之间：会不会断链？D3 本体里的规则，写进可研时引用对不对。
- 内容（docs write）到呈现（docs export）之间：会不会崩相？B-3 丢图、B-4 串色，全在这一交接口。

所以**FDE 是层间接口的维护者**。你不需要是每一层的顶尖专家，但你必须是**唯一一个对整条链负责的人**——因为每一层的工具都只对自己那段负责，没有任何工具对'端到端不掉链'负责。那个责任是你的，且**只能是你的**。

这也是为什么第 5 讲说'平台省人'，本讲要补一句：**平台省的是层内的力气，省不掉层间的责任。** 层间接口这道活，永远是 FDE 亲自扛，扛不动的人，交付物就在'最后一公里'崩给你看。"

**【板书】**
```
认知→行动的卡点永远在"层间"，不在"层内"
 planner→ontology：掉信息？（归错簇后面全歪）
 ontology→docs：断链？（规则引用错）
 docs write→export：崩相？（B-3 丢图 / B-4 串色）
FDE = 层间接口的唯一负责人：工具各管一段，端到端不掉链没人管，那是你的活
平台省层内力气，省不掉层间责任
```

**【康养项目证据】**
- 全链条：102 事件（planner）→ 7 域本体（ontology）→ 11 章可研（docs）→ 7/7 校验（quality），由 1 FDE 端到端维护接口。
- 层间事故实证：B-3 + B-4 均发生在 docs 内部 write→export 的交接口。

## 五、复盘研讨（24′，3 题 + 收口）

**研讨题 1（约 7′）**：你跑 mini 管线时，哪一个"层间交接口"最卡？是事件归流程、流程归本体、还是本体写成文？为什么层间比层内难？
> 收口导向：坐实"卡点在层间"这个本讲主命题。

**研讨题 2（约 8′）**：B-3 是"内容对、呈现崩"的静默故障。请各举一个你自己交付经历里"管线全绿但交付物是残的"例子。你当时是怎么发现的？是人肉逐张验出来的，还是客户替你发现的？
> 收口导向：逼出"格式质检必须 FDE 亲走、不能等客户发现"的痛感。

**研讨题 3（约 9′）**：B-4 说格式质检和内容质检是两条独立的线。请为你的交付物类型，各列一个"内容质检清单"和一个"格式质检清单"（各 3 条）。哪条线现在是你的盲区？

**【讲师收口话术】**
"今天记住三件事：**第一，工具体系的价值在层间咬合，不在单层功能。第二，层间靠产物契约交接，占位符即契约，slug 先定后画。第三，交付物有两条独立质检线——内容和格式，自动校验守内容结构，守不住呈现，B-3 丢图、B-4 串色都在提醒你：呈现层的最后一道闸，是你的眼睛。** 平台把你从层内的苦力里解放出来，就是为了让你有精力去当好那个'唯一对端到端负责的人'。"

## 六、本讲难听话 + 反例小结

**难听话**：
> **"你把可研跑出来了、管线全绿，就以为交付完了？B-3 丢了图你都不知道，因为它不报错——是客户翻到那一页替你发现的。工具能替你跑管线，替不了你逐张验图。那道活你不干，就等着在客户会议室里干。"**

**反例小结**：
- **B-3 图片路径断裂**：正文占位 slug 与实际文件名 slug 不一致 → docx 导出**静默**丢图。**原则：占位符即契约，slug 必须先定后画、不可事后改名；导出后人肉逐张验图。**
- **B-4 Word 主题色覆盖**：导出时模板主题色覆盖浅色系配图，图文风格割裂。**原则：交付物格式与内容是两条独立质检线，FDE 都得自己走一遍。**
