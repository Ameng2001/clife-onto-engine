**命题：没有平台的 FDE，只是一个更累的架构师；平台 = 方法论的固化物。**

## 三、认知输入

### 要点页 1 · 先算一笔账：康养项目这条链条，人到底省在哪

**【讲述脚本】**
"我先不讲平台，先给你们看一个数字，然后你们自己判断这数字是靠谁堆出来的。康养项目这个项目，最终交付了 100 多页可研（11 章、约 11 万字、26 图）加 2 份附录 docx，底下压着 7 个数智本体、3835 行可运行插件骨架、约 350 万条三元组的知识图谱。传统模式，这活儿是**产品经理 + 架构师 + 行业顾问 + 方案经理 + 美工，5 个人以上、干数周**。这次是**1 名 FDE + 智能体编队**。

现在关键问题来了：省下的那 4 个人、那几周，是被'AI 很聪明'省掉的吗？不是。是被**平台**省掉的。今天这堂课就论证这一句话。你要是听完还觉得是靠个人天赋，那你回去只能复制加班，复制不了康养项目。"

```
康养项目:  1 FDE + 智能体编队 · 平台管线              → 数日
省掉的 4 人不是 AI 省的，是【固化管线】省的
```

**【康养项目证据】**

### 要点页 2 · 平台 = 方法论的固化物（不是工具箱，是纪律的容器）

**【讲述脚本】**
"很多人对'平台'的理解停留在'一堆好用的工具'。错。平台不是工具箱，平台是**方法论被代码固化以后的样子**。

举个最硬的例子：DDD 说'限界上下文之间不能越界写对象'。这是一句方法论。方法论写在书上，靠人自觉。但在康养项目，这句话不是靠自觉——它变成了 `clife-onto-engine` 的一条**结构校验器规则**：任何 Action 想 `stage_write` 一个不属于本域的对象，编译期直接拦下来。方法论从'你应该'变成了'你做不到'。这就叫固化。

所以我给平台下的定义是：**平台把'资深 FDE 脑子里的纪律'变成了'新人也绕不过去的校验器'**。这句话是本讲的题眼。你没有平台的时候，那些纪律只活在你一个人脑子里，你请假纪律就崩了；有了平台，纪律活在管线里，谁来都得守。"

**【板书 / 图】**

![图5-1 Astra Studio 工具栈分层与咬合](../figures/fig-5-1-平台分层.png)
**图 5-1  Astra Studio 工具栈分层与咬合**
四层自上而下：planner（认知萃取）→ insight（画像/旅程/流程）→ ontology（clife-onto-engine 本体运行时）→ docs/quality（生成与校验）。方法论在每一层被固化成"产物契约 + 校验器"，数据沿层单向流转不倒灌。本图第 7 讲复用，届时讲层间数据咬合，本讲只讲"固化"这一面。

**【康养项目证据】**
- Astra Studio 实际插件族：studio-core / studio-planner（event-storm / domain-model / skill-design / spec-generate）/ studio-insight（persona / journey / process / domain-canvas / behavior-matrix / opportunity）/ studio-docs（blueprint / plan / write / assemble / export）/ studio-quality（validate / wire-mcp）/ studio-platform / clife-onto-engine（本体运行时）。
- 固化管线（术语表锁定写法）：studio-planner（事件风暴）→ domain-model（限界上下文）→ clife-onto-engine（本体）→ citations 治理 → 可研报告生成。

### 要点页 2·补 · 对照 Palantir 四层：C-Life 的"两套 plugin 体系"与工程化规范（8′）

**【讲述脚本】**
"给你们一个业界坐标，你就明白 Astra Studio 不是我们拍脑袋造的玩具。看 **Palantir 的平台架构——四层**：最底 **Foundry 数据底座层**（接入任何数据源、语义化数据服务）；往上 **Ontology 本体层**（业务语义中枢——实体建模 / 关系建模 / 权限与边界建模，'统一语义 · 业务规则 · 逻辑一致 · 权限边界'）；再往上 **AIP 编排层**（多智能体协同 / 自然语言交互 / 确定性运行时 / 安全治理——它的运行时就是 **Agents · Skills · Tools · Workflows**）；最顶 **应用层**（面向行业的智能应用）。右侧还横着一条 **跨层治理与安全**（统一身份 / 权限 / 审计追溯 / 数据安全 / 合规标准）和一列 **价值输出**（决策 / 优化 / 风控）。一句话：**Palantir 是'以本体为核心的企业智能操作系统'。**

现在关键——**C-Life 的工程化平台，本质上也是这套结构，而且它落成了两套可安装、可校验的 plugin（插件）体系**：
- **第一套：智能体 plugin 体系（对标 Palantir 的 AIP 编排层）** —— 就是 **Astra Studio**。studio-planner / insight / docs / quality 这些插件，每一个都是一组 **Skill**（SKILL.md），把'事件风暴 → 限界上下文 → 文档装配 → 质检'这套 FDE 方法论，固化成可被编排调用的技能。它对应 Palantir 的 Agents / Skills / Tools / Workflows。本会话启动时那句 '8 active plugin(s)'，就是这套体系在跑。
- **第二套：ontology plugin 体系（对标 Palantir 的 Ontology 本体层）** —— 就是 **clife-onto-engine 的本体插件**。康养项目 7 个域，每个域编译成一个**本体插件**，装进引擎运行。这是'业务语义中枢'的 C-Life 落地。

**为什么强调这个？因为这两套体系各自都有一套硬工程化规范——规范，才是平台的灵魂。** 平台值不值钱，不看它功能多，看它的**规范有多硬、校验器认不认**。"

**【板书 / 图】**

![图5-2 Palantir 四层 ↔ C-Life 两套 plugin 体系](../figures/fig-5-2-plugin体系.png)
**图 5-2  Palantir 四层架构 ↔ C-Life 两套 plugin 体系（以本体为核心）**
左列 Palantir 四层（应用层 / AIP 编排层 / Ontology 本体层 / Foundry 数据底座层 + 跨层治理与安全）；右列 C-Life 对照——① 智能体 plugin 体系（Astra Studio，对 AIP 编排层）② ontology plugin 体系（clife-onto-engine 本体插件，对 Ontology 层）③ 数智底座五引擎 / 数据中台（对 Foundry）④ HIL + citations + 等保合规（对跨层治理）。中间用箭头连"层层对应"。

**【两套 plugin 体系的工程化规范（本页重点，规范=可校验的约束）】**

| 维度 | 智能体 plugin 体系（Astra Studio） | ontology plugin 体系（clife-onto-engine） |
|---|---|---|
| **对标 Palantir** | AIP 编排层（Agents/Skills/Tools/Workflows） | Ontology 本体层（业务语义中枢） |
| **一个插件长啥样** | 一组 Skill（`SKILL.md`）+ `plugin.json` manifest | 一域一插件，四文件：`__init__.py`（五要素）+ `mappings/objects.yaml` + `cq/golden.yaml` + `plugin.yaml` |
| **规范/红线** | SKILL.md 结构规范、manifest 契约、命令与依赖声明 | **只 import `clife_onto_engine.sdk`**、`plugin.yaml`（plugin/ontology_id/version/engine_compat/provides）、跨域一律 ref/发布不越界 |
| **校验器** | `studio-quality:validate`（结构/合规/技能质量） | `py_compile` + `ontology-validate` 四段：**A 结构（零悬空）/ B 治理（citations/source）/ C 剩余 TODO / D 行为 CQ** |
| **康养项目实证** | 8 插件在跑、管线一键串联 | 7 域 7/7 py_compile、A 结构 7/7 零悬空、48 条 golden CQ（含 17 rejected） |

**【讲述脚本 · 收口】**
"看懂这张表你就懂了本讲的题眼：**规范 + 校验器，就是'平台把方法论固化成纪律'的物理形态。** 智能体插件那套规范，保证任何人写的 Skill 都能被编排、被质检；本体插件那套规范——'只 import sdk''四文件''零悬空'——保证任何人建的域都能被引擎装载、被静态校验。**Palantir 用四层架构把这件事做成了一个操作系统；C-Life 用两套 plugin 体系把它做成了你能安装、能校验、能复制的东西。** 这就是为什么 FDE 依赖平台：没有这两套规范，你的'方法论'永远只是你嘴上的叮嘱，落不成别人也能跑的资产。"

**【康养项目证据】**
- 智能体 plugin：SessionStart '8 active plugin(s)'；studio-* 插件族 + `studio-quality:validate` 校验。
- ontology plugin：`plugin.yaml`（plugin: kangyang-agent-core / ontology_id / version 0.1.0 / engine_compat / provides: schema+mappings+cq / generated_by: studio-ontology）；7 域 4 文件、只 import sdk 红线、7/7 py_compile、ontology-validate A/B/C/D 四段。

### 要点页 3 · 三个"同日"：平台省掉的不是打字，是一致性维护

**【讲述脚本】**
"平台到底省了什么？不是省你打字，是省你**维护一致性**。我给你们看三个'同日'。

第一，**7 个域同一天并行编译**。D1 建完，D2–D7 六个域照着 D1 这个范本并行建、机械编译，7 个插件骨架当天成型，统一校验 7/7 通过：py_compile 全过、每域 3 个 YAML 全过、'只 import sdk'红线全过，共 3835 行。

第二，**7/7 结构校验零悬空引用**。ontology-validate 静态跑 A 结构：7 个本体全部零悬空引用，跨域纪律守住；B source 治理 7/7，0 空 source。你想想手工干这个——7 个域、76 个 Object、75 个 Link 交叉引用，谁引谁、有没有引到一个不存在的对象，人眼查一遍要多久，错几处？

第三，**3835 行骨架自动生成**。这不是有人手写了 3835 行，是本体 IR 经编译器机械展开的。人手写 3835 行，光是把 76 个对象、54 个 Action 的命名保持一致就够呛，B-5（数据张冠李戴）就是人手维护一致性翻车的活证据——那还只是几个数字。

结论：**平台的价值密度，集中在'跨对象一致性维护'这件人类最不擅长、最容易疲劳出错的事上。**"

**【板书】**
```
三个"同日" = 平台省掉的不是打字，是一致性维护
① 7 域同日并行编译 · 7/7 校验通过（py_compile + YAML + 只import sdk 红线）
② 7/7 结构校验零悬空引用 · B source 治理 7/7（0 空 source）
③ 3835 行骨架机械生成（非手写）+ 21 YAML
人类弱项 = 跨 76 对象/75 链接的一致性维护 → 交给校验器
```

**【康养项目证据】**
- A 结构 7/7 ✅（零悬空引用）· B source 治理 7/7 ✅（0 空 source）· 3835 行 Python，7/7 py_compile ✓，只 import sdk 红线 ✓。
- 五要素跨域规模：Object 76 / Link 75 / Function 38 / Rule 47 / Action 54 / HIL 26。

### 要点页 4 · 反例主场：平台把纪律固化成校验器（B-8 + B-9）

> 本讲反例 B-8（越域写入冲动）+ B-9（SDK 能力想当然）。二者都是"编译期真实发生的冲动/存疑"，说明**即使是训练有素的 FDE，实操中也会想抄近道；靠自觉挡不住，靠校验器和显式挂账才挡得住。**

**【讲述脚本 — B-8】**
"讲个我们自己犯的冲动。编译 7 个域的时候，好几次都想让一个 Action **直接** `stage_write` 别的域的对象——比如 D1 的智能体链路，一个方案审核通过了，最省事的写法是直接去 D3 把销售订单写了、去 D2 把结算记一笔、去 D4 把画像更新了。一步到位，多爽。

但这是**越域写入**。DDD 的铁律是：跨域一律 ref / 发布，不能越界写别人家的对象。我们最后的处理是——**跨域发布（→D3 Order / →D2 结算 / →D4 画像）全部写成注释和 ref，不越界 stage_write**；整个 7 域'越域一律 ref/发布，不建越域 Link'。

注意，挡住这个冲动的不是我'觉悟高'。是 `clife-onto-engine` 的结构校验器：越域 stage_write 过不了 A 结构校验，会当场报悬空/越界。所以最后 7/7 零悬空引用，不是因为我们 7 次都自觉，是因为**校验器不给我们自觉的机会**。这就是平台把'跨域纪律'固化成校验器的实例。没有这个校验器，7 个域里哪怕有 1 处一时手滑越了界，你后面对账、追责、复现就是一场灾难。"

**【讲述脚本 — B-9】**
"再讲一个更微妙的坑：**SDK 能力想当然**。编译期我们要用 `PropertySpec.default`、要用 `Evaluation` 这些 SDK 能力，但当时**不确定引擎到底导没导出**这些符号。本机没有引擎仓库，只能 py_compile，验证不了运行时。

两种态度：一种是'应该支持吧'，直接往前写；另一种是我们最后选的——**不确定就显式挂账**。`Evaluation` 未导出→7 域统一落到 docstring 里，白纸黑字写明'此处依赖 X，待引擎仓库内确认'。这跟第 3 讲主张 3 是同一条脊椎：**敢说不知道**。'错文号比空缺更有害'，'错用一个没导出的 SDK 符号，比显式挂账更有害'。

这里的教训对平台的意义是：**平台会告诉你它保证什么（py_compile、只 import sdk），也会暴露它不保证什么（运行时符号导出）。成熟的 FDE 要能读懂平台校验的边界，在校验器覆盖不到的地方，用 docstring 手动补一道'诚实闸'。**"

**【板书】**
```
B-8 越域写入冲动：想让 Action 直接 stage_write 他域对象（图省事）
   → 挡它的是【校验器】不是【自觉】：越域 stage_write 过不了 A 结构校验
   → 结果：跨域全部 ref/发布写注释，7/7 零悬空引用
B-9 SDK 能力想当然：PropertySpec.default / Evaluation 是否导出，存疑
   → 不"应该支持吧"往前推 → 7 域统一 docstring 显式挂账
   → 校验器保证什么(py_compile/只import sdk) vs 不保证什么(运行时导出)
```

**【康养项目证据】**
- B-8：'跨域发布（→D3 Order/→D2 结算/→D4 画像）写为注释，不越界 stage_write'；'越域一律 ref/发布不建越域 Link'；最终 A 结构 7/7 零悬空引用。
- B-9：'Evaluation 未导出→落 docstring'；'PropertySpec.default、Evaluation 是否导出，编译期存疑未确认，7 域统一留 docstring'。

### 要点页 5 · 把纪律固化成校验器：一个可迁移的心智模型

**【讲述脚本】**
"我把前面收成一个你能带走的心智模型。任何一条你反复叮嘱新人的纪律，都要问自己三个问题：**能不能固化？固化成什么？谁来跑？**

- '跨域不许越界写' → 能固化 → 固化成 A 结构校验器 → clife-onto-engine 编译期自动跑（B-8）。
- '关键数字锚在单点、不重算' → 能固化 → 固化成 BRIEF 单一真相源 + 装配期一致性检查 → docs/quality 跑（B-5 就是没跑好的反例）。
- 'SDK 能力不确定就挂账' → 半固化 → 校验器管不到运行时，只能固化成 docstring 挂账约定 → FDE 人肉跑（B-9）。

看出来了吗：**纪律的固化程度，决定了它需要多少人力持续维护**。全固化的（越域校验），零人力、永不疲劳；半固化的（citations 挂账、SDK 挂账），需要 FDE 走一道人肉闸。你评估一个平台成不成熟，就看它把你多少条纪律固化进了校验器。**Astra Studio 之所以能让 1 个人干 5 个人的活，是因为它把资深 FDE 脑子里那批一致性纪律，绝大部分搬进了编译期和装配期的校验器。**

所以回到那句难听话：平台不是让你更快地打字，是让你**不必再靠意志力维持纪律**。你一个人靠意志力能守 3 天纪律，守不了 3 个月、守不了 7 个域同时。这就是为什么没有平台，你复制的只有加班。"

**【板书】**
```
固化三问：能不能固化？固化成什么？谁来跑？
全固化  → 校验器  → 零人力（越域校验 B-8、结构 7/7）
半固化  → 挂账约定 → FDE 人肉走一道（citations 30→已挂国标余11、SDK B-9）
未固化  → 全靠自觉 → 请假即崩（这是"更累的架构师"的默认状态）
平台成熟度 = 你多少条纪律进了校验器
```

**【康养项目证据】**
- 全固化：A 结构 7/7 零悬空、只 import sdk 红线 7/7、py_compile 7/7。
- 半固化挂账：citations 由"30 待补"→"已挂 18 处国标/法规，余 11 处 scoped 占位"；SDK 存疑统一 docstring（B-9）。

## 五、复盘研讨（18′，3 题 + 收口）

**研讨题 1（约 5′）**：你手上正在做的项目里，有哪一条纪律现在是"全靠你自觉守"的？它属于固化三问里的哪一档？能不能把它往"校验器"方向推一格？
> 收口导向：逼学员把抽象的"我很小心"翻译成"我应该固化成什么"。

**研讨题 2（约 5′）**：B-8 里挡住越域写入的是校验器不是自觉。如果你所在项目的平台**没有**这道校验器，你会用什么低成本手段替代？（提示：code review 清单、命名约定、pre-commit 钩子——都是"半固化"）
> 收口导向：让学员理解"没有成熟平台"不等于"没救"，而是"你要自己搭半固化的替代闸，成本记在你头上"。

**研讨题 3（约 8′）**：假设老板问你"我们为什么不直接让工程师用 ChatGPT 手撸，非要上 Astra Studio？"用今天的三个"同日"和固化三问，给一个 90 秒的回答。
> 收口导向：这是本讲的实战出口——FDE 必须能为平台投资做商业辩护。

**【讲师收口话术】**
"今天就一句话：**平台是方法论的固化物，它把纪律从你的意志力里搬进校验器里。** 你现在觉得自己不需要平台，是因为你还没同时扛过 7 个域。等你扛过，你会怀念那个当天报给你 7/7 的校验器。记住——**没有平台，你复制不了康养项目，你只能复制加班。**"

## 六、本讲难听话 + 反例小结

**难听话**：
> **"你以为康养项目是靠某个人手快？不。手快的人扛 7 个域，第 3 个域就开始出悬空引用了。你复制不了康养项目的手快，只能复制他的加班。"**

**反例小结**：
- **B-8 越域写入冲动**：编译期多次想让 Action 直接 `stage_write` 他域对象图省事 → 靠 A 结构校验器（而非自觉）挡住 → 跨域全部 ref/发布，7/7 零悬空引用。**原则：结构纪律靠校验器而非自觉。**
- **B-9 SDK 能力想当然**：`PropertySpec.default`/`Evaluation` 是否导出编译期存疑 → 不"应该支持吧"往前推，7 域统一 docstring 显式挂账。**原则：不确定就显式挂账，校验器保证什么/不保证什么都要读懂。**
