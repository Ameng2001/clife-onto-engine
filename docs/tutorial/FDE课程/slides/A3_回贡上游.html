① 为什么 · 不是为了做好人

理由
① 定制不再是孤儿留在自己项目里的专家，下次工具大改可能就不兼容了。进了上游，它跟着工具一起演进
② 别人替你维护合并之后，作者重构时会顺手改它。你不合并，每次升级都得自己适配
③ 别人不用再踩你在第五课发现的那六处「文档说 A、代码是 B」——提回去，后面所有人少踩六次
④ FDE 的信用一个被合并的 PR，比简历上写十行"精通 XX"有说服力

你在项目里踩过的坑，
提回去就成了别人的护栏。

【第 ① 条最实际，先说它】"你在 A1 写的那个专家，如果只留在自己项目里——工具下次大改，它可能就跑不起来了，而且没人告诉你。进了上游，作者重构时会顺手带上它。"

【第 ④ 条对年轻工程师有吸引力，但别讲成鸡汤】就一句带过。

③ 规范从哪来 · ⚠️ 一个诚实的现状

这个仓没有 CONTRIBUTING.md

也没有 .github/ 目录。所以没有官方明文告诉你怎么提——规范只能从 CLAUDE.md / AGENTS.md 反推。

⭐ 而这正好是你能提的第一个 PR

补一份 CONTRIBUTING.md——门槛最低、最容易被接受，
而且你刚上完 A1/A2，你比大多数人更清楚该写什么。

③ 规范 · ⚠️

⭐【坦率讲这个现状，别遮掩】"我查过了：没有 CONTRIBUTING.md、没有 .github/。所以我下面讲的规范是反推的，不是官方明文。"

【然后立刻把它转成机会】"这不是缺点，是一个机会。补一份 CONTRIBUTING，是最容易被接受的第一个 PR——而且你们刚上完 A1/A2，比大多数人更清楚该写什么。"

③ 四条原则

【第 7 条和 A1 直接连着】"A1 讲过：专家放 studio/agents/，不是插件目录。这在提 PR 时同样成立——你要贡献一个专家，是贡献到 studio-insight 的 agents/ 作为新的出厂件，而不是让用户放插件里。"

【三条自查让他们抄下来】一会儿实操第 5 步要用。

④ 提到哪里 · ⚠️ 本课的规矩

你的 PR 提到内部 fork，
不直接提到公开上游

第一段（你做，课上）
  内部 fork → 建分支 → 改 → 本地 --plugin-dir 测通 → commit → push
  → 向【内部 fork 的 main】开 PR          ← 你的交付到此为止

第二段（讲师做，课后）
  复核 + 脱敏检查 → 从内部 fork 向【公开上游】统一转提
  → 上游 PR 链接回传给你
为什么加这一段
① 脱敏不可逆上游是公开仓库。客户名、商务数字一旦推上去，删掉了也还在 git 历史和各种镜像里
② 第一个 PR 不该用来试错内部 fork 里可以随便改、随便重开，练手成本降到零
③ 讲师能合并同类项六个人可能提了同一处文档错，一起转提比六个重复 PR 对上游更友好

⚠️ 这不是"你的 PR 不算数"

转提时会在上游 PR 描述里写明原作者——
上游合并后的链接会回传给你，那才是你要收进简历的那个链接。

④ 两段式 · ⚠️

⚠️【这一页要讲得斩钉截铁，别留商量余地】"不要自己 fork 到个人账号再直提上游。内部 fork 的地址在白板上。"

【第 ① 条是唯一不可商量的理由，其他两条是附赠】"上游是公开仓库。你把客户名推上去，后面删掉也没用——git 历史、各种镜像、搜索引擎快照，都还在。"

⭐【立刻堵住"那我这算什么"的情绪】把最后那张卡念完："转提时写明原作者，上游合并的链接回传给你。"——不说这句，会有人觉得自己的活被截胡了。

④ PR 怎么写 · ⭐ 「为什么」决定命运

一个好的 PR 描述

内部 fork→建分支→改→ 本地测通→ commit / push→向内部 fork 开 PR
段写什么
改了什么一句话
⭐ 为什么最重要的一段——你在什么真实场景下需要它
怎么验证的你跑了什么、看到了什么
影响面动了哪些文件；会不会影响现有行为

❌ reviewer 不知道该不该收

"加了一个养老照护专家"

✅ 一看就知道该收

"我们在做养老机构的项目，内置的 product-manager 画出来的画像里把『助餐核销』和『膳食服务』混成一件事，业务方一眼就说不对。这个专家专门挑这类错。"

reviewer 判断的不是
"代码写得好不好"，
是"该不该进这个项目"。

④ PR · ⭐

⭐【两张对比卡是本页的全部】念一遍左边，再念一遍右边，让学员自己感受差别。

【为什么"为什么"最重要】"因为 reviewer 手上没有你的项目背景。他判断不了『这个专家好不好』，但他判断得了『有人在真实项目里被这个问题卡住了』。"

【实操时巡场就查这一段】"为什么"写得少于三句的，当场让他重写。

⑤ 实操 · 40′ · 今天不是模拟，是真的提

现在就提一个

序做什么时长
1盘素材——从第 3 页那张"你已经有的"表里挑一个5′
2克隆内部 fork（不是个人 fork）+ 建分支5′

把你在第五课发现的一处「文档说 A、代码是 B」写清楚提上去——
十分钟，而且一定被接受。

checkout 维度达标警示

脱敏过了没有客户名、没有商务数字把项目原文粘进 PR 描述
⑤ 实操

⭐【降级方案要提前说，别等有人卡住】"如果你的素材不成熟——提一个 issue 也算完成。第五课那六处落差，随便挑一处，十分钟写清楚。"

【巡场三个抓手】①还在纠结"我这个配不配"的——直接让他提 issue ②"为什么"只写了一句的——当场重写 ③没跑就想提的——按住，先跑。

【收尾时收链接】让每个人念一下自己的 PR / issue 链接。这是本课唯一的硬产出。

⑥ 被拒了怎么办

很正常，而且大多不是因为你写得差

常见原因怎么处理
范围不合（作者想放别处）问清楚该放哪，改了再提
太特化（只对你一家有用）改成可配置的，或转成文档 / 示例
没测补测试证据
没人看隔一两周礼貌地 ping 一次；别连着催

被拒的 PR 不是白写的。

它至少让你把那件事想清楚了一遍，
而且你的分支还在，下个项目接着用。

⑥ 被拒

【这一页是给心理预期的，别跳】"第一个 PR 被拒是常态。重要的是你知道被拒的原因通常不是『你写得差』。"

【"太特化"那条最常见，展开一句】"你的东西只对你一家有用——那就把可变的部分抽成配置，或者干脆转成一个示例文档。作者往往乐意收示例。"
