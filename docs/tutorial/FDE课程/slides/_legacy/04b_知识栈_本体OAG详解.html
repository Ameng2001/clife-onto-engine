本体是差异化

为什么本体是这门课的差异化，这页说透。传统的 ER 图是给人看的：它画清楚是什么、有什么、跟谁连，人读懂了去写代码，ER 图本身不会做任何事。我们要的本体是给智能体用的：它把语义和动能绑在一起，语义是"是什么"，动能是"能改什么、回写到哪"。关键差别在这——大模型只能在本体约束出来的合规候选集里生成，越权就直接 reject。这就是我们反复说的"防幻觉靠本体约束求解"的物理基础。传统信息化是人建图、人写逻辑、系统被动存数据；AI-Native 是本体既描述世界又约束智能体怎么改世界。你要建的是后者。

Palantir · 运营层

我们的五要素 OAG 不是我凭空造的，它的思想源头是 Palantir Foundry 的 Ontology 方法论。这也是为什么第九讲讲 Palantir FDE 时你会看到，他们交付的核心就是帮客户建一个 Ontology。据 Palantir 官方文档，Ontology 是架在已经接入的数据和模型之上、连接到现实世界实体的一层，他们叫它组织的运营层，或者数字孪生。注意这个定位——它不是又一个数据库 schema，不是给 IT 用的表结构，它是业务运营本身的镜像。最关键的一句：它要让本体能改世界，不只是描述世界。这个"能改世界"就是下一页要讲的动能层。来源我标在下面，是官方文档。

一句话：Palantir 把"语义（是什么）"和"动能（能改什么、回写哪）"绑在同一个本体里——这正是"给智能体用的本体"区别于"给人看的 ER 图"的根本。下面开始讲 C-Life 把这套语义 OS 做成的自有内核。

语义 + 动能

Palantir 的 Ontology 由两类元素构成，你把它记成两层。上面是语义层，Semantic，回答"是什么"：Object types 对象是什么、Properties 属性有什么、Link types 关系跟谁连。这一层其实 ER 图也有。真正拉开差距的是下面这层——动能层，Kinetic，回答"能改什么"：Action types 动作，用户或智能体的操作被捕获成新数据；Functions 函数，可以重算的派生计算；还有 writeback 写回，把动作的结果回写到业务系统、他们叫 system of record。一句话记住：Palantir 把语义和动能绑在同一个本体里，这就是给智能体用的本体和给人看的 ER 图的根本区别。ER 图只有上半层，本体两层都有。

五要素对照

把 Palantir 的概念对到我们的 OAG 五要素，就是这张表。Object 对象对 Object types，Link 关系对 Link types，这俩是语义层；Function 函数对 Functions，是只读派生、可重算、没有副作用；Action 动作对 Action types 加 writeback，是对外有副作用的、要写回本域或者发布到他域；Rule 规则对 Palantir 的动作校验和动态安全逻辑，是不变式和硬闸，还要挂国标 citations。前五个是一一对应的。第六项 HIL 人工闸是我们自己显式抽出来的——Palantir 里它散在 Action 的审批逻辑里，我们把它拎出来做成一等公民，意思是"人在关键动作上必须签字"这件事，不能藏在代码深处，要显式声明。后面每个要素我都给你看 D1 域里真实的代码。

C-Life 自有方法论 · clife-onto-engine

大模型负责理解，本体负责确立边界与错误拦截

LLM 是概率机器，给不了确定性。当 Agent 不只"回答问题"、而要"执行操作"（出方案 / 评级 / 签发凭证 / 派工单）时，必须有一层确定性边界在模型之外把关。

clife-onto-engine 就是这层边界的工程实现——一个坐在写路径上的运行时内核。

坐在写路径上的运行时内核

① 前置校验 ② 内存变更 ③ 全局规则校验 ④ 提交 / 确定性回滚 ⑤ 决策血统

对每次业务动作跑完这五步，才允许改世界。

C-Life 核心命题

从这一页开始，讲我们自己的方法论。记住这一句核心命题：大模型负责理解，本体负责确立边界与错误拦截。为什么需要它？因为 LLM 是概率机器，它给不了确定性。你让 Agent 只回答问题，错了顶多答案不准；可你一旦让它执行操作——出照护方案、给老人评级、签发凭证、派工单——错一次就是真实世界的状态被改错。所以必须有一层确定性的边界，站在模型之外把关。clife-onto-engine 就是这层边界的工程实现，它是一个坐在写路径上的运行时内核。看右边这五步：任何一次业务动作，都要走前置校验、内存变更、全局规则校验、提交或者确定性回滚、最后留决策血统。跑完这五步才允许改世界。这不是教科书概念，是我们一行行写出来、CI 强制的东西。

方法论内核一 · OAG（行动增强）≠ RAG（检索增强）

防幻觉在执行层，不在检索层

维度RAGOAG（行动增强）
增强的对象生成内容的依据行动的能力与边界
LLM 输出自然语言答案结构化操作调用
对世界的影响只读写操作（受规则约束）
出错后果答案不准状态被错误改变
追溯性难还原依据完整决策血统

GraphRAG / 知识图谱增强检索仍属"读"——帮模型理解关系，但不提供受治理的写回路径，挡不住"写错"。

防幻觉发生在执行层（LLM 提议、引擎回滚），不在检索层。概率推理在"选择层"，确定性约束在"执行层"。

⚠️ 给客户讲草业项目时曾用"Graph-RAG 约束求解防幻觉"话术贴近认知，但那把 OAG 的功劳记到了 RAG 头上——对内必须讲准（见 docs/02-oag-positioning.md 纠偏卡）。

OAG ≠ RAG

这一页最重要，你务必分清 OAG 和 RAG。本体语义层的本质是 OAG，行动增强，Ontology-Augmented Generation，它增强的不是"生成内容的依据"，而是"行动的能力与边界"。看这张对照表，一行行读：RAG 增强的是依据，OAG 增强的是行动边界；RAG 的输出是自然语言答案，OAG 的输出是结构化的操作调用；RAG 只读，OAG 是受规则约束的写；RAG 错了答案不准，OAG 错了世界状态被改错；RAG 难还原依据，OAG 有完整决策血统。这里最容易被搞混的一句——GraphRAG、知识图谱增强检索，它仍然属于"读"，它帮模型理解关系，但它不给你受治理的写回路径，挡不住"写错"。所以记死这句：防幻觉发生在执行层，是 LLM 提议加引擎回滚，不在检索层。概率推理在选择层，确定性约束在执行层。还有个诚实提醒：我们给客户讲草业项目时曾经用过"Graph-RAG 约束求解防幻觉"这个话术，那是为了贴近客户认知，但它把 OAG 的功劳记到 RAG 头上了，对内我们必须讲准，纠偏卡在 docs 零二那份里。

方法论内核三 · 五条设计红线

clife-onto-engine 的五条不可越

① 行业概念不进内核

内核源码禁止出现任何行业词（草 / 碳汇 / 辣椒 / 康养…），CI check_kernel_purity 强制。判缝准则："换成医疗大模型这段还成立吗？"

② enforced kernel，非 advisory schema

Rule 是"违反就拦截 + 回滚"，不是"希望遵守"。本体不是建议书，是强制内核。

③ 受治理的写

所有业务动作经 Action 引擎 guard→变更→写后校验→提交/回滚→审计，无旁路。

④ 开源优先、薄适配

自研只做"接缝"——五要素契约、SPI、Action 流水线；不重造轮子。

⑤ 多租户硬隔离

一个 ontology_id ↔ 一个图库 space + 租户作用域。租户之间物理隔离，不串门。

五条设计红线

我们这套内核有五条设计红线，越一条整个方法论就散了。第一条，行业概念不进内核——内核源码里禁止出现任何行业词，草、碳汇、辣椒、康养一个都不许有，我们用 CI 的 check_kernel_purity 强制卡。判缝的准则很简单：这段代码换成医疗大模型还成立吗？成立就进内核，不成立就得放插件。第二条，本体是 enforced kernel，不是 advisory schema——规则是"违反就拦截加回滚"，不是"希望你遵守"，它是强制内核不是建议书。第三条，受治理的写，所有业务动作必须走 Action 引擎那条 guard、变更、写后校验、提交或回滚、审计的流水线，没有旁路，谁都不能绕过去偷偷写。第四条，开源优先薄适配，我们自研只做接缝——五要素契约、SPI、Action 流水线，别的能用开源就用开源。第五条，多租户硬隔离，一个 ontology_id 对一个图库 space 加租户作用域，租户之间物理隔离不串门。

方法论内核四 · 三层架构（机制 / 策略 / 实例）

Kernel / Plugin / Tenant · 三层分离

层归属含行业词内容
Kernel 内核
（机制）		clife · 一次投入跨行业复用否（CI 强制）元模型、Action 内核、规则引擎、回滚、审计、置信度、意图编译
Plugin 行业插件
（策略）		clife + 行业专家 · 每行业一份是（隔离在插件内）五要素 Schema、映射、规则函数、Action handler、Agent、CQ

内核与插件只通过 clife_onto_engine/sdk/（Plugin SPI）通信——目录边界即红线。这就是第 5 讲 ontology plugin 体系的内部骨架；也印证"本体即基础设施"：内核只懂本体怎么运转、不懂任何行业，草业项目（草业）只是它的 tenant-zero，医疗 / 金融照样跑同一内核。

三层架构

五条红线怎么落地？靠三层架构，机制、策略、实例三层分离。第一层 Kernel 内核，是机制层，归 clife，一次投入跨行业复用，绝不含行业词、CI 强制，里面装的是元模型、Action 内核、规则引擎、回滚、审计、置信度、意图编译这些通用机制。第二层 Plugin 行业插件，是策略层，clife 加行业专家一起做，每个行业一份，行业词隔离在这一层，装的是五要素 Schema、映射、规则函数、Action handler、Agent、CQ。第三层 Tenant 租户配置，是实例层，客户自己的，每个客户一份，装私有物理映射、实例数据接入、密级授权。三层之间最关键的一条纪律：内核和插件只通过 clife_onto_engine 的 sdk 目录，也就是 Plugin SPI 通信，目录边界就是红线。这就是第五讲讲两套 plugin 体系时那个 ontology plugin 体系的内部骨架，也印证一句话——本体即基础设施：内核只懂本体怎么运转、不懂任何行业，草业项目只是它的 tenant-zero，第零号租户，换医疗换金融照样跑同一个内核。

方法论内核五 · 元模型五要素 = 内核 ↔ 插件唯一契约

五要素契约 · 受治理的写路径

内核只理解五种元类型，任何行业概念都是插件用它们声明的实例：

Object 业务实体（独立生命周期）· Link 有向关系（带边语义）· Function 只读派生量（无副作用）· Rule 全局不变式（违反则回滚）· Action 受审计业务动作（有前置 / 有副作用 / 需留痕）。

ctx 是受限 Capability，不是裸 context——插件拿到的是被内核授权限制过的能力句柄。

Action 写路径（这栈的灵魂）

guard（前置 declarative） stage_write（内存变更） post_rules（写后强制，违反即回滚） 提交 / 确定性回滚 审计快照 + set_confidence + add_evidence
五要素契约 · 写路径

三层架构里内核和插件的唯一契约，就是元模型五要素。内核只理解五种元类型，任何行业概念——健康洞察、碳汇、辣椒品种——都是插件用这五种去声明的实例。五种一句话定义：Object 是业务实体、有独立生命周期；Link 是有向关系、带边语义；Function 是只读派生量、无副作用；Rule 是全局不变式、违反则回滚；Action 是受审计的业务动作、有前置、有副作用、必须留痕。这栈的灵魂是 Action 的写路径，看右边这条链：先 guard，前置的声明式校验；再 stage_write，先在内存里变更、还没落库；然后 post_rules，写后强制校验，一旦违反立刻回滚；接着提交或者确定性回滚；最后留审计快照、set_confidence 记置信度、add_evidence 挂证据。还有一个细节很重要——插件 handler 里那个 ctx，它是受限的 Capability，不是裸 context，插件拿到的是被内核授权限制过的能力句柄，你只能做内核允许你做的事。这套写路径就是"Agent 以为自己成功了、引擎最后一刻回滚"那篇讲的核心。

方法论内核六 · 本体建模 SOP（reference/methodology 03）

起点不是"有哪些数据"，是"现在做法哪出了问题"

① 信息没法汇聚

散在多系统，Agent 拿到不同时间点的拼凑结果。

② 规则无法被执行

Agent 走后端接口绕过前端校验——规则没失效，只是从没在这条路径上被执行过。

③ 决策无法还原

日志记的是接口调用，看不出"为什么代采购经理下了这笔 28 万的单"。

先建模、再看数据（顺序不能反）

先看数据会被现有系统结构带偏，建出"系统长什么样"而非"业务是什么样"。基于业务语义推五要素，不是系统字段。

四阶段有先后、不并行

① 调研建模（业务专家必在场，产出文档/原型非代码）→ ② 数据盘点治理 → ③ 引擎搭建（这阶段才写代码）→ ④ 场景验证（Demo 价值在暴露边界，不是证明对）

三问验收：信息汇聚了没？规则真在执行没（警惕误拦截 > 漏拦截——持续误拦截会逼业务绕过本体）？决策能当天说清没？金句：本体建模是把业务知识变成可执行定义，不是软件开发本身。

建模 SOP · 先把建模做对

光有五要素概念还不够，我们方法论文集里最实操的一篇是建模 SOP，先把本体建模做对。第一个反直觉的点：起点不是"我们有哪些数据"，是"现在的做法在哪出了问题"。三类问题反复出现——信息没法汇聚，散在多系统、Agent 拿到的是不同时间点拼凑的结果；规则无法被执行，注意这个特别隐蔽，Agent 走后端接口把前端校验绕过去了，规则没失效、只是从没在这条路径上被执行过；决策无法还原，日志只记接口调用，你看不出为什么系统代采购经理下了这笔二十八万的单。先界定问题、划 MVP 边界。第二个反直觉的点：先建模、再看数据，顺序绝不能反，先看数据你会被现有系统结构带偏，建出来是"系统长什么样"不是"业务是什么样"，而且要基于业务语义推五要素、不是照抄系统字段。第三，四个阶段有先后不并行：调研建模、业务专家必须在场、这阶段产出的是文档和原型不是代码；然后数据盘点治理；再引擎搭建、到这一步才开始写代码；最后场景验证，记住 Demo 的价值在暴露边界、不是证明它对。三问验收：信息汇聚了没、规则真在执行没、决策能不能当天说清。这里有条硬经验——警惕误拦截大于漏拦截，持续误拦截会逼业务绕过本体，整套约束就失效了。金句记住：本体建模是把业务知识变成可执行定义，不是软件开发本身。

五要素逐个详解 · D1 kangyang-agent-core（10对象/13关系/5函数/6规则/6动作/2HIL）

① Object→ ObjectType

HealthInsight = ObjectType( primary_key="insight_id", properties=[ PropertySpec("severity", int, required=True), PropertySpec("detail", str, classification="confidential"), ], states=("new","triaged", "addressed","closed"), ) # 跨域共享根：只引用，不重复声明 Elder = ref(Elder)

primary_key 主键、PropertySpec 每属性一条（类型 / 是否必填 / 密级 classification / 单位）、states 状态机。

跨域共享根 Elder 一律 ref(Elder) 引用，不在本域重复声明全属性——这就是 Palantir "对象只有一个真相源"的纪律。

① Object

五要素逐个拆，就拿 D1 这个域，康养 agent 核心，它有十个对象、十三个关系、五个函数、六个规则、六个动作、两个 HIL。先看 Object 对象，它落成 SDK 里的 ObjectType。看这段真实代码，健康洞察 HealthInsight：primary_key 声明主键；properties 里每个属性一条 PropertySpec，带类型、是否必填、密级——比如 detail 标了 classification 等于 confidential，机密；还有单位。再看 states，这是状态机，new、triaged、addressed、closed，洞察从新建到分诊到处理到关闭。最关键一行在最下面：Elder 这个跨域共享根，一律用 ref 引用，绝不在本域把它的属性重新声明一遍。这就是 Palantir 说的"对象只有一个真相源"的纪律，也接上一册栈二讲的 Elder 单一写入点。

五要素逐个详解 · D1

② Link→ LinkType

root_caused_by = LinkType( source="HealthInsight", target="RootCause", cardinality="1:N", edge_semantics=("root_cause", "hypothesis", "derivation"), ) # 飞轮再入：指向待续假设 loops_back = LinkType(..., edge_semantics=("hypothesis",))

root_caused_by（洞察 → 根因，1:N）带 edge_semantics 语义化的边（root_cause / hypothesis / derivation）——不是一根裸箭头。

飞轮再入用 loops_back（hypothesis，指向待续假设）——闭环不是断头路，是回到"待验证"重新入链。

② Link

第二个要素，Link 关系，落成 LinkType。看这条 root_caused_by，从健康洞察指向根因，基数是一对多，一个洞察可能有多个根因。重点看 edge_semantics 这个参数——它给边标了语义：这条边到底是 root_cause 确证的根因，还是 hypothesis 待验证的假设，还是 derivation 推导出来的。这就是本体的边和 ER 图的边最大的不同：ER 图是一根裸箭头，只说"连了"，本体的边带语义，说清"以什么身份连"。下面还有一条 loops_back，飞轮再入，它的语义是 hypothesis，指向一个待续的假设。为什么重要？因为康养这套是要形成飞轮的，闭环不能是断头路，处理完一个洞察要能回到"待验证"重新入链，这条自指的边就是飞轮在本体里的样子。

五要素逐个详解 · D1

③ Function→ FunctionDef

plan_confidence = FunctionDef( returns=float, reads=["CarePlan","HealthInsight"], side_effects=None, # 只读 ) red_flag_count = FunctionDef(returns=int, ...) opportunity_estimate = FunctionDef(...) # 可重算；采纳才转 Action

只读派生、无副作用的计算：plan_confidence（方案置信度）、red_flag_count（红旗计数）、opportunity_estimate（机会估值）。

Function 只算不改——可重算；结果被采纳后，才由 Action 落成对世界的真实改动。算与改分离。

③ Function

第三个要素，Function 函数，落成 FunctionDef。它的定位就一句话：只读派生，无副作用的计算。看这几个真实的函数——plan_confidence 算方案置信度，red_flag_count 数红旗、就是危险信号有几个，opportunity_estimate 估增收机会。它们都只读，reads 声明它读哪些对象，side_effects 是 None，不改任何东西。这里有个特别重要的设计原则：算和改要分离。Function 只负责算，可以反复重算，算出来的置信度、红旗数只是候选建议；只有当这个建议被采纳了，才由下一个要素 Action 去落成对世界的真实改动。为什么要分离？因为算是安全的、可回溯的，改是危险的、要留痕要设闸的。把它俩混在一起，就没法管控智能体到底改了什么。

五要素逐个详解 · D1

④ Rule→ @spi.rule · 两类背书

Backing.DECLARATIVE · 自动放行

从 check 全自动、source="通用"、治理审计直接放行：方案须可解释 · HIL 必留痕 · 链路顺序不可逆。

Backing.FUNCTION · 硬规则

需查图谱/跨对象：置信度闸·防橡皮图章 · 药食/DIP 冲突拦截。

@spi.rule(backing=Backing.FUNCTION, severity=Severity.HARD, source="DIP 技术规范(医保办发〔2020〕50号)", citations=["某地级市 DIP 控费实施细则[本地待补文号]"]) def confidence_gate(insight, plan): ... # 防橡皮图章

每条带 severity / source / citations——挂得上的挂国标，挂不上留占位不编造（栈⑦合规在本体层的落点）。

④ Rule

第四个要素，Rule 规则，用 @spi.rule 装饰器声明，它分两类背书你要分得清。第一类 DECLARATIVE 声明式，规则体能从 check 全自动推出来，source 标"通用"，治理审计直接放行——比如"方案必须可解释""HIL 必须留痕""链路顺序不可逆"，这些是普适约束。第二类 FUNCTION，需要查图谱、跨对象判断的硬规则——比如置信度闸，专门防橡皮图章，防止智能体拿个低置信度的方案就往下走；还有药食同源和 DIP 医保的冲突拦截。看这段代码，每条规则都带 severity 硬约束、带 source、带 citations 挂国标——这条挂了 DIP 技术规范医保办发五十号。挂得上的挂国标，挂不上就留占位不编造，比如本地文号还没拿到就写"本地待补文号"。这就是栈七合规在本体层的落点。

五要素逐个详解 · D1

⑤ Action→ @spi.action · 写回 + 边界 + HIL 闸

@spi.action( writes=["CarePlan"], # 本域对象 guards=["confidence_gate"], # 引本域规则 hil=HilPolicy( reviewer_role="站长"), # 站长 HIL 增收闸 ) def adopt_plan(plan): # 跨域一律注释：发布到 D2/D3/D4 # 不越界 stage_write 他域 ...

对外副作用：writes 本域对象、guards 引本域规则。跨域一律注释"发布"、不越界 stage_write 他域（Palantir 写回 + 边界）。

审批类动作挂 hil=HilPolicy(reviewer_role="站长")——这就是站长 HIL 增收闸在代码里的样子。

⑤ Action

第五个要素，Action 动作，用 @spi.action 声明，它是唯一对外有副作用、能改世界的要素，所以管得最严。看这段：writes 声明它写哪个本域对象，这里写 CarePlan 照护方案；guards 声明它受哪些本域规则把守，这里挂了刚才那个 confidence_gate 置信度闸。三条纪律你必须记住。第一，写只能写本域对象。第二，跨域一律注释成"发布到 D2、D3、D4"，绝不越界直接 stage_write 别人的域——这就是 Palantir 的写回加边界。第三，审批类动作挂 HIL，你看 hil 等于 HilPolicy，reviewer_role 是站长，这一行就是我们讲的站长 HIL 增收闸在代码里的真实样子，意思是这个采纳方案的动作，必须站长签字才生效。这个 HIL 设点的四判据，第六讲 C3 会深讲，这里你先记住它是 Action 的一个显式参数。

显式挂账 · 121 处

这页讲工程纪律，很重要。康养项目这三千八百多行本体不是一次写完整的，它是骨架加显式挂账。什么意思？规则体、Action 的回写 handler、Function 的派生函数，很多地方先留一句 raise NotImplementedError 待实现，全七个域一共一百二十一处，加七个 seed，这些交给现场 FDE 在引擎仓库里去填。为什么这么做？核心一句话：可运行大于完美。先让七个域全部编译通过，骨架立住，再回头一处一处填规则体，而不是憋着一次写完美结果一个都跑不起来。还有一条更硬的纪律：不确定的东西要显式挂账，不能靠"应该支持吧"。比如你不确定 SDK 到底导没导出 Evaluation 这个类，就在 docstring 里显式写下来挂账，而不是想当然地用。这个坑第五讲 B-9 会专讲，就是 SDK 能力想当然。
