上一页那四层，其实分属两套 plugin 体系——这跟第五讲讲的是同一件事，你要在这一讲把它接上。第一套叫智能体 plugin 体系，是建模端、build-time，就是 Astra Studio：planner、insight、docs、quality。它们是把 FDE 方法论固化下来的技能插件，帮你在建的时候把认知萃取、画像旅程、文档装配、质检跑通，对标 Palantir 的 AIP 编排层。第二套叫 ontology plugin 体系，是运行时、run-time，就是 clife-onto-engine：把建出来的七域本体编译成能被智能体调用、能受治理写回的本体插件，对标 Palantir 的 Ontology 本体层。为什么这一讲叫打通认知到行动？因为这两套体系接起来，正好是一条从认知到行动的完整链——planner 和 insight 把模糊认知榨成结构，这是认知；clife-onto-engine 的 Action 让智能体据此受治理地做事、写回，这是行动。这就是第四讲栈三讲的 OAG：让 AI 从会查升级到会做、且做得对、可追溯，不是 RAG。工具体系的终点不是生成一份好看的文档，是让一个智能体能安全地按本体去改变世界。方法论出处是文集 07 和 17。

层间接口 = 产物契约："占位符即契约"

层与层靠产物契约交接——上一层交给下一层的东西有一个双方都认的格式约定，不是随手扔个文件。

最典型例子：图片占位符
![图N-M 图名](../figures/fig-N-M-<slug>.png)

docs 层写正文时图还没画（图并行制作）。这个 slug 就是正文层和制图层之间的契约：正文说"我要一张 fig-5-1-平台分层"，制图那边就必须交一个文件名正好是 fig-5-1-平台分层.png 的图。两边对同一个 slug，图才能在导出时被 docx 正确嵌进去。

铁律：slug 先定后画 · 一律用 figures 表已列 slug · 不自造不改名。改 slug = 改 API 签名 = 调用方全断。

上一页讲了数据怎么流，这一页讲层与层之间靠什么交接——靠产物契约。什么叫产物契约？就是上一层交给下一层的东西有一个双方都认的格式约定，不是随手扔个文件。最典型的例子是图片占位符。docs 层写正文时图还没画，图是并行制作的，正文里先写一个占位。这个 slug 就是正文层和制图层之间的契约，正文说我这里要一张 fig-5-1-平台分层，制图那边就必须交一个文件名正好是 fig-5-1-平台分层点 png 的图，两边对的是同一个 slug 图才能在导出时被 docx 正确嵌进去。所以我们定了一条铁律：slug 必须先定后画，一律用 figures 表已列的 slug，不自造、不事后改名。这不是龟毛，这是接口纪律。你把 slug 当成两个模块之间的 API 签名，签名一改调用方全断。下一页的反例 B-3 就是这个契约被破坏后的惨状。

反例 B-3 · 图片路径断裂

导出 docx 时丢图了——正文写了占位、图也画好了，Word 里几张图不见了

怎么发生的

正文占位的 slug 和实际图片文件名的 slug 对不上——../figures/fig-X-Y-slug.png 里的 slug 和 figures 目录真实文件的 slug 有出入。可能有人事后改了图名，也可能写占位时手抖。

最阴险的地方：静默

契约一破，导出层照断掉的路径找图，找不到就静默丢图——它不报错，docx 照样生成，你不逐张翻还发现不了。内容全对，管线全绿，交付物却是残的。

对策：slug 先定后画（占位即契约）；导出后必须人肉逐张验图，不能信"管线跑通了"。

先讲 B-3 图片路径断裂。康养项目导出 docx 的时候丢图了，正文里明明写了占位、图也画好了，导出的 Word 里就是有几张图不见了。查下去原因很朴素：正文占位的 slug 和实际图片文件名的 slug 对不上，占位路径里的 slug 和 figures 目录里真实文件的 slug 有出入，可能是有人事后改了图名，也可能是正文写占位时手抖。这就是上一页占位符即契约被违反的直接后果。契约一破，导出层照着断掉的路径去找图，找不到就静默丢图。注意静默两个字——它不报错，docx 照样生成，你不逐张翻还发现不了。这是最阴险的一类 bug：内容全对，管线全绿，交付物却是残的。教训：slug 先定后画是 B-3 的直接对策；而且导出后必须人肉逐张验图，不能信管线跑通了。

反例 B-4 · Word 主题色覆盖

用对齐客户模板的 Word 主题，主题色把浅色系配图给覆盖/冲突了

崩在哪

内容一个字没错、图一个像素没错、slug 也对得上。崩在呈现层：图按浅色系精心配，套进 Word 模板一看主题色一压，图文风格割裂，有的图直接看不清。

原则

交付物的"格式质检"是一条和"内容质检"完全独立的线。没有任何校验器会替你看"这张图套进 Word 好不好看"。呈现的最后一道闸，是 FDE 的眼睛。

把 B-3 和 B-4 放一起：quality 层自动校验能守结构（悬空、越界、红线），守不住呈现（丢图、串色）。

再讲 B-4，更微妙。导出 docx 的时候我们用了对齐客户模板的 Word 主题，结果 Word 的主题色把我们浅色系的配图给覆盖冲突了，图是按浅色系精心配的，套进 Word 模板一看主题色一压，图文风格割裂，有的图直接看不清。这里内容一个字没错、图一个像素没错、slug 也对得上，崩在呈现层：交付物的视觉规范和内容是两回事。B-4 告诉你一件残酷的事——交付物的格式质检是一条和内容质检完全独立的线。内容质检问字对不对数对不对引用断没断，格式质检问图显不显示色冲不冲突排版散没散字体对不对，两条线两套检查动作都得 FDE 自己走一遍，因为没有任何一个校验器会替你看这张图套进 Word 好不好看。把 B-3 和 B-4 放一起你就看清了：quality 层的自动校验能守结构，悬空越界红线，守不住呈现，丢图串色。呈现的最后一道闸是 FDE 的眼睛。

反例警示 · 别把外壳当交付

草业项目 demo「看着能用」——但它的 AI 是 Mock

外壳：真的很像

草业大模型有一个真实可点开的 11 页 Next.js demo：7 个角色可切换、每屏带证据溯源块。点起来顺、界面完整——看着就是个能用的产品。

内核：其实是壳

它的 AI 是 Mock：关键词路由 + 仿真数据。mock-ai.ts 自己注明「真实落地替换为草业项目本体 + RAG」。UI 跑通 ≠ 模型跑通。

FDE 的质检要能识破"看着能用其实是壳"。演示 demo 必须如实说"这是交互外壳、不是模型跑通"——把 demo 吹成产品 = 骗客户。

再给你们上一堂反面警示课，呼应本讲 B-3 B-4 那句"FDE 得自己质检"。草业大模型有一个真实可以点开的 demo，十三页 Next.js，七个角色能切换，每一屏还带证据溯源块，你点起来很顺、界面很完整，第一眼就觉得这是个能用的产品。但你要是信了这一眼，就中招了。翻开代码你会看到它的 AI 是 Mock——关键词路由加仿真数据，连它自己的 mock-ai.ts 文件里都写着一行字：真实落地时替换为草业项目本体加 RAG。也就是说 UI 跑通了，模型根本没跑通，这是两件事。这就是 B-3 B-4 教你的自己质检往前再走一步：格式质检看呈现，内容质检看数字，而这里你还要质检"这个能点的东西，内核到底是真模型还是关键词壳"。演示 demo 没问题，但你必须如实说这是交互外壳、不是模型跑通。你要是把这种 demo 吹成产品交给客户，那不是演示，是骗客户。
