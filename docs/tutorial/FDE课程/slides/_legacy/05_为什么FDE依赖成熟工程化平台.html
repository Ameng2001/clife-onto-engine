本讲题眼

平台不是工具箱，是纪律的容器

平台是方法论被代码固化以后的样子——它把"资深 FDE 脑子里的纪律"，变成"新人也绕不过去的校验器"。

最硬的例子：一句方法论 → 一条校验器规则
DDD 方法论（写在书上，靠人自觉）

"限界上下文之间不能越界写对象。"

→
clife-onto-engine 结构校验器

越域 stage_write → 编译期直接拦下。方法论从"你应该"变成"你做不到"。

很多人对平台的理解停在"一堆好用的工具"。错。平台是方法论被代码固化以后的样子。举个最硬的例子：DDD 说限界上下文之间不能越界写对象，这是一句方法论，写在书上靠人自觉。但在康养项目，这句话不靠自觉——它变成 clife-onto-engine 的一条结构校验器规则：任何 Action 想 stage_write 一个不属于本域的对象，编译期直接拦下来。方法论从"你应该"变成"你做不到"，这就叫固化。所以我给平台下的定义是：平台把资深 FDE 脑子里的纪律，变成新人也绕不过去的校验器。这句话是本讲题眼，你没有平台时那些纪律只活在你一个人脑子里，你请假纪律就崩了。

不是有人手写，是本体 IR 经编译器机械展开 + 21 YAML。人手维护 76 对象 / 54 Action 命名一致性 → B-5 就是翻车活证据。

平台的价值密度，集中在"跨对象一致性维护"——这件人类最不擅长、最容易疲劳出错的事上。

平台到底省了什么？不是省你打字，是省你维护一致性。三个"同日"。第一，七个域同一天并行编译，D1 建完 D2 到 D7 照范本机械编译，当天七个骨架成型，统一校验七比七通过，共三千八百三十五行。第二，七比七结构校验零悬空引用，七个本体、七十六个对象、七十五个链接交叉引用，谁引谁、有没有引到不存在的对象——你想手工查一遍要多久、错几处？第三，三千八百三十五行不是手写的，是本体 IR 经编译器机械展开的。人手写光是把七十六个对象、五十四个 Action 命名保持一致就够呛，B-5 数据张冠李戴就是人手维护一致性翻车的活证据。结论：平台的价值密度集中在跨对象一致性维护这件人类最容易疲劳出错的事上。
FDE 交付方法论
反例 B-8 · 越域写入冲动

"想让一个 Action 直接 stage_write 别的域的对象"

冲动怎么来的

编译 7 个域时，好几次想让 D1 的智能体链路：方案审核通过后直接去 D3 写销售订单、去 D2 记结算、去 D4 更新画像。一步到位，多爽。

谁挡住了它

不是"我觉悟高"，是 clife-onto-engine 结构校验器：越域 stage_write 过不了 A 结构校验，当场报悬空/越界。跨域发布（→D3 Order / →D2 结算 / →D4 画像）全部写成注释和 ref，不越界直写。

7/7 零悬空引用，不是因为我们 7 次都自觉，是因为校验器不给我们自觉的机会。

讲个我们自己犯的冲动。编译七个域的时候，好几次都想让一个 Action 直接 stage_write 别的域的对象——比如 D1 一个方案审核通过了，最省事的写法是直接去 D3 把销售订单写了、去 D2 结算记一笔、去 D4 画像更新了，一步到位多爽。但这是越域写入。DDD 铁律：跨域一律 ref 或发布，不能越界写别人家的对象。我们最后把跨域发布全部写成注释和 ref，不越界 stage_write。注意，挡住这个冲动的不是我觉悟高，是结构校验器：越域 stage_write 过不了 A 结构校验，会当场报悬空越界。所以最后七比七零悬空，不是我们七次都自觉，是校验器根本不给我们自觉的机会。这就是平台把跨域纪律固化成校验器的实例。

反例 B-9 · SDK 能力想当然

PropertySpec.default / Evaluation 到底导没导出？

两种态度

✗ "应该支持吧" → 直接往前写。

✓ 不确定就显式挂账：Evaluation 未导出 → 7 域统一落 docstring，白纸黑字写"此处依赖 X，待引擎仓库内确认"。

对平台的教训

平台会告诉你它保证什么（py_compile、只 import sdk），也会暴露它不保证什么（运行时符号导出）。校验器覆盖不到的地方，FDE 要用 docstring 手动补一道"诚实闸"。

与第 3 讲同一条脊椎：敢说不知道。"错用一个没导出的 SDK 符号，比显式挂账更有害。"

再讲一个更微妙的坑：SDK 能力想当然。编译期我们要用 PropertySpec.default、Evaluation 这些 SDK 能力，但当时不确定引擎到底导没导出这些符号，本机没有引擎仓库，只能 py_compile，验证不了运行时。两种态度：一种是"应该支持吧"直接往前写；另一种是我们最后选的——不确定就显式挂账，Evaluation 未导出就七域统一落到 docstring，白纸黑字写明此处依赖某某、待引擎仓库内确认。这跟第三讲主张三同一条脊椎：敢说不知道。错文号比空缺更有害，错用一个没导出的 SDK 符号，也比显式挂账更有害。教训是：成熟的 FDE 要读懂平台校验的边界，在校验器覆盖不到的地方，用 docstring 手动补一道诚实闸。

把纪律固化成校验器：一个可迁移心智模型

任何一条你反复叮嘱新人的纪律，都问三个问题：能不能固化？固化成什么？谁来跑？

固化程度固化成什么谁来跑康养项目实例
全固化结构校验器clife-onto-engine 编译期自动跑 · 零人力越域校验（B-8）、结构 7/7、只 import sdk 红线
半固化挂账约定FDE 人肉走一道闸citations 30 待补 → 已挂 18 国标、余 11 占位；SDK 挂账（B-9）
未固化全靠自觉请假即崩"更累的架构师"的默认状态

纪律的固化程度，决定它需要多少人力持续维护。平台成熟度 = 你多少条纪律进了校验器。

我把前面收成一个你能带走的心智模型。任何一条你反复叮嘱新人的纪律，都要问三个问题：能不能固化、固化成什么、谁来跑。跨域不许越界写，能固化，固化成 A 结构校验器，编译期自动跑，零人力永不疲劳。关键数字锚单点不重算，能固化，固化成 BRIEF 单一真相源加装配期检查。SDK 不确定就挂账，只能半固化，校验器管不到运行时，固化成 docstring 挂账约定，FDE 人肉跑。看出来了吗：纪律的固化程度，决定它需要多少人力维护。全固化的零人力，半固化的要 FDE 走一道人肉闸，未固化的全靠自觉、请假即崩。你评估一个平台成不成熟，就看它把你多少条纪律固化进了校验器。Astra Studio 之所以让一个人干五个人的活，就是因为它把资深 FDE 那批一致性纪律绝大部分搬进了编译期和装配期。
