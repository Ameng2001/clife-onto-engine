上半场 ② 启发 · 开场第一句

这不是编译器

运行时仓自己的文档写得很直白：map → compile → validate 三个技能是
"LLM-as-compiler" 的 prompt + spec，无确定性编译器、无代码、无测试。产出是插件骨架，内容 finishing 全靠人工。

机器负责把结构立起来，
人负责把判断填进去。

康养项目留了 121 处 NotImplementedError——
这不是没做完，是明确划出"机器到此为止、人从这里接手"的界线。

一个不敢留 NotImplementedError 的 FDE，会让模型把它猜的业务规则写成看起来能跑的代码——那才是灾难。

不是编译器

【为什么开场就说这句】学员看到 "compile" 会以为有个确定性编译器。本课的全部价值都建立在"没有"这个认知上。

"你们会看到编译产出一堆 raise NotImplementedError。第一反应是'这东西没做完'。不是——那 121 处是界线，是有人认真地说'这里机器不该猜，等人来填'。反过来想：如果一个工具把所有地方都填满了，那意味着它在猜你的业务规则，而且猜得看起来很像真的。那才可怕。"

上半场 ② 启发 · 栈③ 本体 OAG 1/4 · 技术分水岭

大模型负责理解，本体负责确立边界

维度RAGOAG
增强的对象生成内容的依据行动的能力与边界
LLM 输出自然语言答案结构化操作调用
对世界的影响只读写操作（受规则约束）
出错后果答案不准状态被错误改变
追溯性难还原依据完整决策血统

最容易搞混的一点：GraphRAG / 知识图谱增强检索仍属"读"——帮模型理解关系，但不提供受治理的写回路径，挡不住"写错"。

概率推理在"选择层"，
确定性约束在"执行层"。

OAG

【这一栈是 C-Life 真正的护城河】"别的方法论我们借业界经典，本体这一栈我们有自己成体系的方法论——对标 Palantir 本体语义 OS。下面讲的不是教科书概念，是我们自己一行行写出来、CI 强制、跨行业复用的东西。"

⚠️【诚实标注，课上必须说】"给客户讲草业项目时我们曾用'Graph-RAG 约束求解防幻觉'的话术贴近客户认知，但那把 OAG 的功劳记到了 RAG 头上。对外可以将就，对内必须讲准。"——这一段本身就是诚实边界的示范。

【这个角色原本是谁】知识工程师 / 本体工程师——把领域知识落成机器可推理、可执行、可追溯的本体，而不是给人看的 ER 图。

五要素 = 内核↔插件的唯一契约

要素定义判据（现场问学员）
Object业务实体，有独立生命周期有独立生命周期 / 独立属性 / 被引用？
Link有向关系，带边语义有方向吗？能带属性吗？
Function只读派生量，无副作用是算出来的，不是记下来的？
Rule全局不变式，违反则回滚所有入口都要成立、且是操作后校验
Action受审计业务动作有名字吗？要审计吗？带业务意图吗？
guard（前置 declarative）
  → stage_write（内存变更）
  → post_rules（写后强制，违反即回滚）
  → 提交 / 确定性回滚
  → 审计快照 + set_confidence + add_evidence

⚠️ 最容易讲漏的一条：Rule 与"前置条件"不是一回事。
前置条件只判本次调用；Rule 是全局不变式，在所有入口、操作之后都要成立，违反就回滚。
学员写规则段时经常把前置条件当规则写上去。

五要素

【写路径是这一栈的灵魂】指着那段代码逐行念。特别是 post_rules 那一行——"写后强制"是本课最反直觉的设计：先写进内存，再校验，违反就整个回滚。学员会问"为什么不先校验"？答案：有些规则只有在写完之后才能判（比如"该老人的总服务时长不得超过额度"——你得先把这次的加进去才知道超没超）。

【Rule vs 前置条件，实操时要抓】这是 §7 写规则段最高频的错。巡场时逐条问："这条规则，在别的入口进来也要成立吗？只在这一个动作前判的，那是 guard，不是 Rule。"

上半场 ② 启发 · 栈③ 3/4

五条设计红线，与三层架构

五条红线

① 行业概念不进内核——CI 强制。判缝准则："换成医疗大模型这段还成立吗？"
② 本体是 enforced kernel，不是 advisory schema——违反就拦截 + 回滚，不是"希望遵守"
③ 受治理的写——所有业务动作经 Action 引擎，无旁路
④ 开源优先、薄适配——自研只做"接缝"
⑤ 多租户硬隔离

三层架构

Kernel 内核（机制）　含行业词：否（CI 强制）
元模型 / Action 内核 / 规则引擎 / 回滚 / 审计 / 置信度

Plugin 行业插件（策略）　每行业一份
五要素 Schema / 映射 / 规则函数 / handler / Agent / CQ

Tenant 租户配置（实例）　每客户一份
私有物理映射 / 实例数据 / 密级与授权

内核只懂本体怎么运转，不懂任何行业。
两仓分工：plugins/{ontology_id}/（不是 {tenant}）放本体定义；tenants/{tenant}/ 放实例与名录数据。把名录数据写进 plugins/，违反的不是习惯，是红线。

红线 · 三层

【判缝准则最好用】"换成医疗大模型这段还成立吗？成立 → 内核，不成立 → 插件。这一句话能解决 90% 的'这段代码该放哪'的争论。"

【两仓分工必须讲，否则学员会把数据写进插件】grass 与 chili 在同一进程同一 registry 里按 namespace 共存——所以目录是按 ontology_id 分的，不是按租户分的。

上半场 ② 启发 · 栈③ 4/4

建模 SOP：可照做的四阶段

① 起点不是"有哪些数据"

是"现在的做法在哪出了问题"。三类症状：
信息没法汇聚 / 规则无法被执行（Agent 走后端接口绕过前端校验——规则没失效，只是从没在这条路径上被执行过）/ 决策无法还原

③ 先建模、再看数据

顺序不能反。
先看数据会被现有系统结构带偏，建出"系统长什么样"而非"业务是什么样"

⑤ 怎么判断建对了

① 信息汇聚实现没有？
② 规则真在执行没有？——警惕误拦截 > 漏拦截：持续误拦截会逼业务绕过本体，整套约束就失效
③ 决策能不能当天说清楚？

④ 四阶段有先后、不并行要点
① 调研与建模业务专家必须在场，工程师单独做必跑偏；产出文档 / 原型不是代码，业务逐条确认
② 数据盘点与治理—
③ 引擎搭建与数据接入这一阶段才开始写代码
④ 场景验证与调优Demo 的价值在暴露边界，不是证明对
建模 SOP

【金句，可直接板书】"本体建模是把业务知识变成可执行定义的过程，而不是软件开发本身。最难的环节不是选技术栈，而是和业务人员一起把'大家都知道但没有人写下来'的规则，变成能被系统执行的精确描述。"

【"规则无法被执行"这条症状要展开】"注意措辞——规则没失效，只是从没在这条路径上被执行过。前端有校验，Agent 走后端接口就绕过去了。这就是为什么约束必须下沉到写路径上，而不是留在界面层。"

【难听话】"建模只是七分之二（栈②DDD + 栈③OAG）。别以为会建模就等于会做 FDE。"

上半场 ② 启发 · 输入契约 · 本课最该背下来的东西

§7 的「规则三问」

① 违反了要不要
拦住并回滚？

→ severity
hard / soft

② 只看入参能判，
还是要去查别的数据？

→ backing
declarative / function

③ 依据是哪条标准 /
方法学 / 谁的经验？

→ source
没依据就写"待补依据"，不许猜

② 的一句话判据

判定所需的全部信息，是不是都在 ctx.params + ctx.actor 里？
是 → declarative（可从 check 全自动生成代码）　否 → function（只能生成骨架，你来填）

偷偷需要查名录 / 阈值 / 库存的，不是 declarative。

规则三问

【这三问要学员背下来】让他们当场对着自己 intake 的 §7 逐条问一遍。没答全三问的规则，就是没写完。

【规则工程师 agent 的原话可以直接念】"never mark a rule declarative if it secretly needs to look up a registry/threshold/inventory — that's function." "secretly"这个词用得好——学员标 declarative 时往往没意识到自己脑子里已经默认"去查一下名录"。

【偏好倾向】合规、安全、方法学类的规则，默认往 hard + post_write + function 三档靠。因为那才是回滚机制的用武之地。

上半场 ② 启发 · 七段 IR

三组关键取值域

edge_semantics 三值
（IR 里最难的一处判断）

root_cause　命中即终止追溯——找到根因了，别再往上查
hypothesis　继续查——这条边只是"可能相关"
derivation　纯结构派生——不参与因果推理

source 三态
（治理教学的关键）

具体标准号（GB 38600-2019）→ ✅ 通过
通用 → ✅ 通过，自明常识是合法值
TODO(FDE): 补依据 → ⚠️ 被拦，计入治理缺口

"通用"这个值的存在很重要：它让"我知道这是常识、不是我忘了查"能被表达出来。
留白和"承认这里是常识"是两件事。

⚠️ declarative 的取反逻辑（最容易写反的地方）

IR:    check = budget is None or budget >= 0        # 写"什么情况下是对的"
生成:  if not (budget is None or budget >= 0):     # 生成时取反
           return RuleResult.fail(...)
取值域

【取反逻辑必须现场演示一遍】写在白板上：先写 check，再写生成的代码。学员写 check 时最容易写反——记住口诀：写"什么情况下是对的"，不是"什么情况下要拦"。

【source 三态是下半场治理审计的伏笔】现在讲清楚，下半场讲 validate B 段时学员就懂为什么"通用"能放行、TODO(FDE) 会被拦。

上半场 ② 启发 · 本课最贵的实测资产

编译完成 ≠ 可用

FDE 收尾 6 项（机器帮不了的）

① 填 function-backed 规则体
② 填 Action handler 回写
③ 填 seed 参考数据
④ 把 CQ 翻成 Python——引擎只认 cq.py 的 CQ_SUITE，全仓没有代码读 cq/golden.yaml
⑤ 改 plugin.yaml 成引擎格式——引擎完全不认 provides，还要补 glossary + agents
⑥ 补 Evaluation 的 import——编译规则的固定头部漏了它，照抄会 NameError

六处「文档 vs 代码」落差

① README 说 11 段 → 实际 12 段
② 标题写「五段式」 → 正文 七段
③ 说"正好填满 SPI 7 槽位" → 槽位 5、6 完全不生成，3、4 只出骨架，7 格式不匹配
④ 产 cq/golden.yaml → 无代码读它
⑤ 产 provides: → 引擎不认
⑥ 固定 import 头部 → 漏了 Evaluation

这六条不是吐槽工具，是教学法。
唯一可靠的动作是去读代码、去跑一遍。

★★ 两道闸

你默认以为"HIL = 拦住不让写"。错的。

写入闸副作用闸（HIL）
谁触发hard 级 post_write 规则被违反HilPolicy.predicate 返回 true
效果overlay.clear() 确定性回滚，数据不落地，返回 StructuredRejection数据照常写入；decision 标记为 pending_hil

谁来兜底引擎（确定性，无人参与）人（reviewer_role）

写入闸拦的是"写错了"，
HIL 拦的是"这事该不该真的发出去"。

两道闸

⚠️【全课最容易混的一节，慢讲，讲两遍】第一遍讲机制表，第二遍用康养项目民政闸举例。

"康养项目的民政 DP-H 闸就是典型的副作用闸——数据可以先算出来，但'对外发布'这个动作必须人点头。注意：数据是写进去了的，只是通知、凭证、公告这些对外的副作用被冻结了。"

【预期提问】"那 HIL 的时候数据已经写了，人不同意怎么办？"——答：数据在库里是 pending 状态，人不同意就走撤销动作（那也是一个 Action，同样受治理）。关键是"对外发出去的东西"从来没发出去过。

下半场 ② 启发 · HIL 机制

⚠️ 三个必须知道的 HIL 陷阱

1. 光写 reviewer_role 等于没设闸

HilPolicy.predicate 的默认值是恒 False。
HilPolicy(reviewer_role="合规官") 不给 predicate，永远不会触发。

2. 置信度不会自己出现

编译只生成硬编码的 ctx.set_confidence(0.8)。真实插件的写法是：
ctx.set_confidence(ctx.params.get("_confidence", 0.82))
——上游意图编译器把 LLM 的置信度经 _confidence 参数注入。
插件文档完全没写这一句。不补这一步，你做出来的"置信度闸"是个永远不动的摆设。

3. severity_touched==hard 这个 predicate 基本不会触发

因为 touched_hard=True 时引擎先回滚 + 拒绝就返回了，走不到 HIL 判定那一行。需要组合条件（"低置信或碰了硬规则"）得手写 lambda——引擎允许，IR 语法没定义。这是表达力上限，也是逃生舱。

HIL 陷阱

【第 1 条是 checkout 的必查项】"只写角色不写条件——这是最常见的假设闸。学员会觉得'我写了 reviewer_role 就是设了闸'。没有。predicate 默认恒 False，那个闸永远不会触发。"

【第 2 条文档没写，这是我们实测出来的】强调这一点：插件文档完全没写这一句。不补这一步，学员做出来的置信度闸是个摆设。这又是一处"文档说 A、代码是 B"。

下半场 ② 启发 · 本课命门

⭐ 四条硬判据 + 一条置信度兜底闸

判据含义一句话测试康养项目实例
① 不可逆动作做了收不回来"撤销这个动作，代价大到不可接受吗？"急救四级联动升级（D4）、监管数据对外发布（D6）
② 涉钱直接产生 / 改变金钱流向"这一步之后有钱动了吗？"增收订单生成、DIP 结算入账、补贴拨付
③ 涉合规触发监管 / 法律义务"监管来查，这一步要留痕解释吗？"数据授权 / 最小必要、DIP 控费入账前阻断
④ 跨组织后果落到别的主体身上"做错了，是别人替我承担后果吗？"AI 方案转订单卖给会员、补贴发布

+ 置信度兜底闸（看模型把握 · 横切）

四条判据看动作性质；兜底闸看模型有多确定。
即便一个动作四条都不命中，只要模型对它的置信度低于阈值，同样落人工。
康养项目固化为 D1 的置信度闸：hard · function · pre，阈值占位 0.75，刻意设成 pre——在动作发生前拦，不是发生后补。

宁可多设几道闸拖慢一点，
不可漏一道闸出一次事。

四判据

⚠️【口径纪律，咬死】是 "四条硬判据 + 一条置信度兜底闸"，不是"五条硬判据"。旧讲义里有写成五条的，见到当场改口。四判据看动作性质，兜底闸看模型把握——两者不是同一类东西，混讲学员就学不会判断。

【为什么是"任一"不是"多数"】"因为这四条每一条单独成立就够伤。涉钱一条就够了——一笔错误增收决策，客户的钱亏了，赖不到模型头上，赖到你头上。所以是或，不是与。"

⚠️【但顺序不能反】"'任一即插人'必须先过一道筛：这个动作能不能固化成硬规则？ 先问"能不能自动"，再问"该不该插人"——顺序反了就会闸设满。"

【现场动作】让学员拿自己 IR 里的 Action 逐个过这四句测试。用问句，不要用名词——"有钱动了吗"比"是否涉钱"好用十倍。

下半场 ② 启发 · 方法论根据

闸为什么必须是两层

层次机制强度可绕过性
提示词层靠 LLM 自觉最弱高（注入即破）
API 网关层校验请求参数格式中中（参数可伪造）
本体层校验业务状态 + 全局不变式最强低（引擎强制，无旁路）

自觉遵守不是工程约束。

第一层 · 自动闸

引擎确定性回滚，机器把关。
被拒的 Agent 收到结构化拒绝三件套：triggered_rule（为什么不行）+ current_state（当时的世界快照）+ suggestion（可以怎么调整）
→ OAG 闭环：发现→调用→被拒→调整→重试，全程在约束内

能固化成硬规则的，就交给自动闸，别浪费人力。

第二层 · 人工闸（HIL）

两种情况才上：
① 机器判不了的价值判断——涉钱/涉合规/跨组织的拍板
② 机器"没把握"——每个断言都是概率的（balance_sufficient = (False, confidence=0.78)），置信度太低时基于它的决策不该是最终结论

这就是 0.75 阈值的方法论根据：不是拍脑袋，是"低置信必须转人"的工程共识

两层

【不讲这一节，学员会把 HIL 当成唯一的闸，闸设满、人变橡皮图章】

【软约束三个结构性缺陷，逐条念】会被遗忘（多轮对话后早期指令权重下降）、会被稀释（上下文塞满后约束被挤出）、会被绕过（提示词注入让模型"忘记"约束）。

【HIL 留痕 = 审计快照，不是日志】"留的不是操作日志，是决策快照——记录上下文，而不只是记录结果。康养项目强制留 signer_id / reviewed_at / decision / edits_before_after，就是为了回答那个问题：'三个月后，合规团队问 AI 当时凭什么觉得能下单，你能不能当天答上来。'"

【收口，可直接板书】"你能把多大的权力交给一个系统，取决于设计时边界定义在哪里，以及越界时——是被它自己拦下，还是被现实拦下。" 自动闸 + HIL 就是"被它自己拦下"；两样都没设，就是等着被现实拦下——那时赔的是钱、是合规、是客户关系。

下半场 ③ 沉浸 2/3 · 本课高潮

两大闸门，与按错的代价

闸门① · 站长 HIL（增收闸 · 置信度闸 0.75 防橡皮图章）

判据命中：涉钱 + 跨组织 + 置信度兜底　｜　机制：AI 生成增收方案后，必须站长点确认才能转订单
⚠️ 按错的代价：阈值调成 0 或站长养成"一律点同意"的习惯 → 闸门在，但等于没有。AI 给一个低置信的、对长者不合适的高价套包，站长机械点过，卖出去了——钱是长者的、口碑是客户的、责任是我们的。微康养做的是熟人生意（熟人获客 77.59%），卖错一单，毁的是整个片区的信任飞轮

闸门② · 民政 DP-H（监管发布闸）

判据命中：涉合规 + 涉钱 + 跨组织，三条全中　｜　机制：任何对外发布的监管数据 / 补贴决定，必须民政经办拍板留痕
⚠️ 按错的代价：AI 把未经核验的数据、或一笔补贴资格认定直接对外发布——违反数据授权最小必要（个保法）、可能错发/漏发补贴（涉公帑）、政府信用受损。而且不可逆：数据发出去收不回来；补贴发错了，追缴是政治事件

站长闸防的是"钱按错"，
民政闸防的是"合规越界"。

两大闸门

【本课高潮，讲情绪，别只讲机制】"卖错一单，毁的是整个片区的信任飞轮"——这句话要说得重。微康养是熟人生意，这不是抽象风险。

【两句话收口，让他们记住】闸门的价值不在"有没有"，在"会不会真拦"。置信度闸就是防止 HIL 退化成盖章仪式的技术保险。阈值是活的，谁调阈值谁负责。
跨组织 + 涉合规的动作，人工闸是法律义务不是可选项。谁发布谁签字，签字的人为这条数据的真实性背书。

你打算编一个让交付显得完整，还是留占位转取证清单？说出你会怎么跟客户解释这个空缺。

判断训练

【题 1 收口】好的 FDE 会为"高频低置信"动作设兜底闸，这是四判据之外最容易漏的一类——康养项目的 0.75 置信闸就是干这个的。

【题 2 收口】闸门的价值不在"有没有"，在"会不会真拦"。答案指向置信度闸 / 抽检 / 留痕追责——康养项目站长闸设 hard · pre + 0.75 阈值就是防退化的技术保险。

【题 3 收口，回收 B-10】"能对客户坦然说'这处我留了占位、给你一份取件清单'的 FDE，比交一份'看起来完整'的假件的 FDE 专业得多。"
题 3 要让每组都说一遍"我会怎么跟客户解释"——这是 C7 在本课唯一能练的地方。
