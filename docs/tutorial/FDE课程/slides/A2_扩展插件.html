① fund-review 是什么

一个"被工具链造出来"的插件

A1自定义智能体　二级台阶：不改代码，加一个 .md
A2扩展插件　三级台阶：← 今天
A3回贡上游　四级台阶
fund-review
干什么政府 IT 采购的报价优化 + 财评预审——按地方预算标准出优化建议、重写报价表、产带引用的评分报告
规模54 个文件：38 脚本（其中 12 个 scan_*.py）· 4 skill · 2 agent · 4 命令 · 5 reference
身份⭐ 不是 studio 工具链的一部分，是工具链产出的领域插件——只是搭同一个 marketplace 发布
fund-review所有 studio-*
运行时工作区stateful → .fund-review/{session-id}/　不在 studio/ 下用 studio/
外部依赖需要 openpyxl / python-docx一个都不需要第三方包

它证明的不是"这插件多厉害"，
是"这套工具链能造出这种量级的东西"。

⭐【"工具链产出的"这个身份要点破】"CLAUDE.md 里专门有一节叫 Vertical Plugins，说得很清楚。放在同一个仓只是为了搭同一个 marketplace 发布。"

【为什么这对学员重要】"你第五课产出的本体插件、以后要做的行业插件——都是这个身份。fund-review 就是你们的未来样本。"

① fund-review 是什么 · 续

四个 skill，一条流水线

init-session
初始化会话工作区→ quote-optimize
出优化建议→ 人批准方案→ quote-rewrite
按已批准的方案改表

另有 quote-review：对着标准打分，产带引用的评审报告。

⚠️ 注意 quote-rewrite 的措辞：「按已批准的方案」

改表这一步在人批准之后，不在 agent 手里。
这是下一页那条设计的伏笔——agent 提意见，人做决定，脚本执行。

四个 skill 里，
只有最后一个真的改东西——
而它不听 agent 的。

① 流水线

【这一页是第 4–5 页的引子，别讲长】重点就一句：改表在人批准之后。

【可以问一句】"如果让 agent 直接改表，会省一步。为什么不这么做？"——留 10 秒，下一页回答。

② 红蓝对抗 1/2 · ⭐

两个 agent，站在对立面

蓝方quote-optimizer　agents/quote-optimizer.md
"资深售前方案架构师，深谙政府 IT 采购报价"——站投标方，想让报价过审。拿扫描器发现 + 定价指引 + 标准条款索引，做筛选、排序、解释
原话：「同时说 投标商务 和 财评专家 两种语言」
红方financial-reviewer　agents/financial-reviewer.md
"政府财评专家"——站评审方，对每条 warn/fail 逐条挑战，要求页码引用
原话：「绝不批准一个你无法在标准公式里追溯出来的数字」

什么时候值得设红蓝：当一件事有明确的对立立场，而且两边都有专业性的时候。

✅ 适合

报价 vs 财评 · 开发 vs 安全 · 业务 vs 合规——两边都需要专业判断，盲区互补

❌ 不适合

只有一个正确答案的任务 · 只是想"多一个人看看"——那用一个复核专家就够（A1）
⚠️ 对抗的成本是双倍的推理

② 1/2 · ⭐

【读码：把两个 .md 的开头并排投出来】让学员自己读那两句原话。红方那句"绝不批准一个你无法在标准公式里追溯出来的数字"——把"可追溯"写进了角色人格。

【下一页才是这一节的重点】别在这里停太久。

② 红蓝对抗 2/2 · ⭐⭐ 最见功力的一处

两个 agent 都没有 Write 权限

allowed-tools: Read, Bash, Glob
scope: runtime

两份 agent 定义的 frontmatter 一模一样——都没有 Write。
它们只能查证与质询，不能改报价表。真正改表的是 quote-rewrite 里的确定性脚本，改什么由人批准的方案决定。

评审方要是能改报价，
它就不是评审方了。

课例子同一条判断
第五课ontology-validate 没有 Write校验器物理上不可能替你抹平不合格的地方
本课两个红蓝 agent 都没有 Write评审与优化只能提意见，不能自己动手

好的角色设计不是靠嘱咐
"你别乱改"，
是让它想改也改不了。

② 2/2 · ⭐⭐

⭐⭐【回答第 3 页留的问题】"为什么不让 agent 直接改表？因为那样它就同时是运动员和裁判。"

【「权限即职责」这条已经是第三次出现了】第五课 ontology-validate 无 Write、ontology-compile 无 Agent（纯机械翻译不许自由发挥）、今天这两个。这是 astra-studio 一以贯之的设计手法，值得学员带走。

【最后那句是本页落点】"好的角色设计不是靠嘱咐『你别乱改』，是让它想改也改不了。"——这也是第五课"纪律靠机制不靠自觉"的同一句话。

③ 确定性打底 1/3 · ⭐⭐ 本课重心

但红蓝对抗不是这个插件的重点

12 个确定性扫描器
scan_*.py→ findings.json→ agent 筛选·排序·解释→ 人批准方案→ 确定性脚本改表

数一下这个插件的构成：

能确定性算的，全写成了脚本；

③ 1/3 · ⭐⭐

⭐⭐【这一页比红蓝对抗重要，语气要转过来】"上两页那个红蓝设计很吸引眼球。但真正让这个插件能用的，是这一页——38 个脚本对 2 个 agent。"

【现场敲一下】ls scripts/*.py | wc -l 和 ls scripts/scan_*.py | wc -l——38 和 12，当场数给他们看。

③ 确定性打底 2/3 · 为什么它们该是脚本

12 个扫描器都在扫什么

扫描器扫什么
scan_subject科目对齐
scan_semantic平台 vs 大模型的语义重叠
scan_redundancy跨工作簿 / sheet 的重复内容
scan_labor · scan_workdays人工定价 · 人天极值
scan_caps比例守恒（标准里的硬上限）
scan_completeness · scan_summary_sheets9 大费用科目缺失 · 汇总 sheet 缺失
scan_brand_models设备品牌型号 ≥3（标准表 7 注 3 的硬要求）
scan_commercial商业组件识别（填补"软件产品购置费 = ¥0"缺口）
scan_evidence · scan_ops取值依据 · 大模型运维/运营行合规

⭐ 每一条都是"照规则一查就知道"的事——品牌型号够不够 3 个、比例有没有超上限、9 大科目缺了哪个、有没有跨表重复。

它们不需要判断，
所以它们该是脚本。

③ 2/3

【别逐个念完，挑三个最直观的】品牌型号 ≥3（标准白纸黑字写的）· 比例守恒（算术）· 9 大科目缺失（对照清单）。三个一说，学员就明白"这类事凭什么不该交给模型"。

【那 agent 干什么？】从一堆发现里挑出真正值得提的、排优先级、用标准条款解释为什么。——扫描是确定的，判断才是模型的。

③ 确定性打底 3/3 · ⭐⭐ 本课最该带走的一条

给你的判据

这一步能不能写成脚本？
能，就别交给模型。

模型是用来处理"规则说不清但人能判断"那一段的，
不是用来做你懒得写的计算。

① 确定性

脚本每次结果一样，模型不保证

② 可测

脚本能写单测，提示词不能

③ 成本

确定性脚本跑一万次成本不变，
agent 跑一万次要付一万次的钱

⭐ 这就是 S2/S3 讲的「确定性优先」，在插件层的活体

S3 讲 Deterministic Agent Runtime 时说：交易、库存、调度交确定性逻辑，只有意图识别和异常研判调大模型。
fund-review 就是这条原则在一个真实插件里的样子。

这一条不依赖 Astra Studio。
做任何 AI 应用都成立。

③ 3/3 · ⭐⭐

⭐⭐【全课最该板书的一句】"这一步能不能写成脚本？能，就别交给模型。"

【三个理由里第三个最容易被忽略】"很多人只想到准确率，没算成本账。一个每天跑几百次的扫描，写成脚本是一次性投入；交给 agent 是每天付费。"

【回扣 S2/S3】上过的人这里会有"原来如此"的反应——那条原则他们在引擎层听过，今天在插件层又见到一次。同一条判断，两个层次。

④ 插件骨架 1/2

一个插件长什么样 · Traits 是观察

plugin-name/
├── .claude-plugin/plugin.json   # 清单
├── commands/  skills/{name}/SKILL.md  agents/  hooks/  scripts/
├── references/                  # 按需加载 ← 就是第三课的渐进式披露
└── templates/
Trait意思会自动生成什么
stateful跨会话管理项目数据init-workspace skill + 运行时配置/状态模板
hil-gated流程里有人工审批关口SKILL.md 里的 ## Approval Gate 段
kb-dependent需要 LLM 之外的领域知识KB 集成说明
multi-pipeline2 个以上独立业务流按管线分别生成编排命令
expert-scoped运行时需要与规划期不同的专家agents/ 里的运行时 agent 定义

Traits are observations,
not configuration.

你不"配置" trait，是工具从你已经写下的规划产物里看出来的。没检测到的插件走标准路径，不多不少。

④ 1/2

⭐【那句英文留原文】"背后是一个设计立场：不给你一堆开关让你勾，而是从你已经写下的东西里推断。少一层配置，就少一层『配错了但没人发现』。"

⭐【fund-review 同时命中两个，把前面串回来】stateful → 第 2 页那个 .fund-review/{session-id}/；expert-scoped → 第 4 页那两个红蓝 agent。前面看到的两个特征，在这里找到了出处。

⭐【expert-scoped 是 A1 与 A2 的分界，一定要讲】"A1 你写的是规划期专家（做画像、域图时被叫，放 studio/agents/）；这两个红蓝是运行时专家（跟着插件跑在真实业务里，放插件自己的 agents/）。expert-scoped 这个 trait，就是这两者的分界。"

④ 插件骨架 2/2 · 设计与实现物理分开

同一件东西只存在于一个地方

studio/changes/{plugin}/   ← 只放设计文档：brief.md · skill-map.md · status.json · plugin.json.draft
{target_dir}/              ← 只放实现：SKILL.md · commands/ · scripts/ · agents/

status.json 里的 target_dir 字段，是这两边唯一的连线。

域工作区　type: "domain"

event-storm.md · domain-map.md · personas/ journeys/ processes/
⭐ 可被多个插件共享

插件工作区　type: "plugin"

只有设计文档。不含 SKILL.md 与 commands——那些在 target_dir；靠 domain 字段指回父域

为什么这样切：如果设计目录里也放一份 SKILL.md，它和实现里那份迟早不一致——而且你不知道该信哪份。

这是课程反复讲的 B-5，
写进了工具设计里。

⭐ 好的工具会替你守住纪律，而不是靠你自觉。

④ 2/2

【回扣第 2 页】"fund-review 的设计文档在另一个仓（fund-review-plugins）——就是这条原则的实例：设计和实现可以分在不同仓库，靠 target_dir 连起来。"

⭐【域工作区可共享，有实际价值】"一次事件风暴产出的域图和画像，可以喂给多个插件。别每个插件重做一次业务分析。"

⑤ 从零起一个插件

路径，与本地怎么调

plan→ build-skills
产可跑的初稿→ skill-creator 反复打磨
拿真实输入测→ validate→ promote
v0.1 → v0.2

「Initial fill, not final build」

build-skills 产的是能跑的初稿，不是成品。
指望它一次生成对，是用错了工具。

外循环 / 内循环

Astra Studio 管外循环（业务分析、领域建模、校验、发布）；
单个 skill 的编写打磨交给官方 skill-creator

promote 是版本化里程碑：v0.1 → v0.2，设计文档快照进归档但仍保持活跃——下一轮接着用，不是归档就冻结。

claude --plugin-dir ./studio-core --plugin-dir ./你的插件

改 SKILL.md 立刻生效。
不用发版，不用装。

⑤ 起插件

⭐【"Initial fill, not final build" 要说重】"设计原则第 10 条的原话。很多人跑完 build-skills 发现产物不完美就说『这工具不行』——它本来就没打算一次给你成品。和第五课那 121 处 NotImplementedError 是同一个态度：机器立结构，人填判断。"

⭐【最后那条命令是学员回去就能用的】"你不需要先想清楚整个插件。先跑起来一个能改的东西，比先设计完美强。这是三级台阶的入门动作。"
