① 缺的不是数据 1/4

一套承诺"消灭数据孤岛"的系统，
把公司送进了深渊

2018 年 2 月，露华浓（Revlon）上线新 ERP，要统一订单、库存、生产排期、财务，终结数据孤岛。

然后北卡罗来纳州牛津工厂的生产线出了问题：ERP 无法把订单信息传递给生产排程，也无法把库存状态传递回客户履约模块。多个系统业务规则不兼容，数据格式对不上。
当工人需要知道"现在该生产哪个 SKU、备多少料、发给哪个零售商"时——系统给不出一个可信的答案。

时间发生了什么
2018 Q4净亏损超过 7000 万美元
公告后股价单日暴跌超过 6%
同期因财务数据失真，无法按时向 SEC 提交年报
四年后申请破产保护
露华浓

【开场就用这个案例，别先讲定义】本体这个词太玄，先讲一个真实的、有代价的失败。7000 万美元、单日跌 6%、交不出年报、四年后破产保护——这几个数字要一个一个念出来。

【关键的反转在下一页】先不揭晓。让他们以为这是"数据没打通"的故事。

① 缺的不是数据 2/4

讽刺的是，露华浓的数据从来就不少

它知道它不知道
有一个 SKU 叫"超持久唇膏 210#"，库存 12,000 支这张订单是否已经触发了生产排程
沃尔玛有一张待履约的采购订单，数量 8,000 支生产排程需要哪条产线腾出来
如果那条产线正在跑另一个优先级更高的订单，应该由谁来决策插单还是延期

这些"知道"，分散在生产主管、供应链协调员、IT 管理员各自的脑子里，以及一套没人敢动的 Excel 排班表中。

系统记录了结果，没有记录"法则"。

数据治理困境的本质不是数据不够多，是缺少了描述"实体之间如何相互关联、如何相互约束、如何相互触发"的那一层——
哲学家把它叫做本体（Ontology）。

缺了哪一层

【这一页是反转，慢讲】"讽刺的是，露华浓的数据从来就不少。"——停一下。学员这时候会重新理解上一页。

【"没人敢动的 Excel 排班表"这句要说】每个企业都有那么一张表。它就是本体缺失的物证。

【收口】"这不是露华浓的特殊困境。这是几乎所有完成了'数字化第一阶段'的企业的共同症状。"

① 缺的不是数据 3/4 · 本课第一个心智模型

字典 vs 物理引擎

字典

有"员工"、"订单"、"设备"、"供应商"，每个词都有定义，精确无误。

但它不会告诉你：
· 员工有权限操作哪些订单？
· 订单超 10 万时必须经过谁审批？
· 设备故障应该触发哪个流程？

字典是死的。它只记录名词，不记录物理定律。

物理引擎

不仅定义名词（实体），还定义动词（操作）和物理约束（规则）：

"员工（实体）持有操作权限（关系），可以修改订单状态（行为），但金额不能超过 10 万（约束），超出则自动触发审批工作流（连锁反应）。"

这一段逻辑，在传统数据库里大概分散在五个不同的代码文件里，靠程序员的"约定"维持——
任何一个人离职或者某次迭代没跟上，这条规则就悄无声息地断掉了。

数据记录了世界是什么，
本体定义了世界如何运转。

字典 vs 物理引擎

⚠️【这一页是全课最该记住的一页】如果学员只带走一个心智模型，就是这个。讲慢，讲透，允许停顿。

【现场动作，效果最好】问一句："你们项目里，有没有一条规则是散在五个文件里、靠约定维持的？那条规则，如果写它的人明天离职，还成立吗？"——让他们想 10 秒。这个问题会让整节课落地。

【最后那句要板书】"数据是事实的存档，本体是现实的法则。没有法则，再多的事实也只是一堆彼此不相识的数字。"

① 缺的不是数据 4/4

为什么现在重提"本体"

语义网、知识图谱，这些概念已经炒了二十年。
因为大语言模型的出现，把这个问题从"技术债"升级成了生死线。

LLM 能力极强——能读懂需求、写代码、写报告、做分析。但它的本质，是一个基于概率的统计机器：
· 它没有你公司的私有业务逻辑　· 它没有现实世界的约束感知　· 它唯一会做的事，是根据概率"猜"

如果把露华浓那套割裂的数据直接喂给 LLM

让它决策"今天牛津工厂应该优先生产哪个 SKU"——
LLM 会给出一个看起来头头是道的答案，置信度 92%。
但它不知道沃尔玛订单有优先级协议、不知道某条产线今天在换模具、不知道某个原料供应商上周刚发来一封延期通知还没录入系统。

商业履约不接受 8% 的错误率，更不接受"我以为"。

大模型负责理解和推理（概率），
本体层负责确立边界和错误拦截（确定性）。

为什么是现在

【"置信度 92%"这个细节要念出来】它比"模型会出错"具体得多——模型很自信地错，而且看起来头头是道。

【最后那句是全课的总纲】后面所有章节都是在展开这一句。板书。

② 架构位置 1/5

幻觉的真正成因

模型给的答案，外行读起来头头是道，
内行读起来胡说八道。

一个例子

你让 AI 决策"明天哪批原材料可以优先入库"，它给出一份排序合理、逻辑自洽的清单。
但库管主管一眼看出问题：清单里第一位的供应商，合同上有一条"季度末不接收入库"的条款，今天恰好是季度末倒数第二天。

模型没有撒谎。它只是不知道那条合同条款的存在。

这类错误工程师通常归结为"幻觉"。但准确地说——
这不是幻觉，是因为大模型不懂业务规则。
模型的问题不在于它在概率上算错了，而在于它根本没有接触过那条约束它行为的"业务规则"。

所以需要的不是更大的模型，
而是一个不同的架构层。

幻觉

【这一页会改变很多人的判断】大部分人的第一反应是"幻觉 → 微调 / 换更大的模型 / 加 RAG"。这一页要把这条路堵死。

【一句可以补的话】"LLM 的边界是自然语言，业务的决策边界是规则空间。两者之间没有等价关系。 所以这和是否微调没什么关系——概率机器一定会有幻觉。"

② 架构位置 2/5

数据中台做了什么，没做什么

过去十年最流行的架构选择。它解决了一个真实且重要的问题，而且做成了——大多数完成数字化的企业今天都有一张能出实时报表的大屏。

但它有一个根本性的设计边界：
只管数据的流动，不管业务的逻辑。

它能告诉你它不知道
这个供应商今年交货了 1200 次这个供应商的合同当前是否处于合规状态
库存余量是 8000 件这 8000 件里哪些已经被预占、预占的优先级是什么、谁有权调整

把这张数据表直接喂给大模型，模型拿到的是一堆精确的数字，但没有数字背后的运转规则。

数据中台

【别把数据中台讲成错的】先肯定："这件事做成了。" 学员里很多人做过数据中台，上来否定他们会关闭。要讲的是边界，不是对错。

② 架构位置 3/5

传统数据中台 vs 本体平台

维度传统数据中台本体平台
设计目标数据的存储、加工与查询业务决策的建模与执行
核心单元表、列、行、指标Object（对象）、Link（关系）、Action（操作）
业务逻辑的位置散落在各种应用代码里集中在本体层，可查询、可治理
AI 接入方式直接读表，只读通过本体接口，可读可写
写回能力依赖人工或 ETL 流程Action 触发原生写回，支持事务
权限粒度表级 / 行级属性级 + 操作级（精确到每个 Action）
对 AI 的约束无约束，模型可以自由发挥前置条件拦截非法操作，后置规则确保操作合理

⭐ 最关键的是最后一行。 传统数据中台的设计假设是"AI 只负责分析，人负责决策和执行"。
但 Agentic AI 打破了这个假设——AI 开始执行操作，而不只是给出建议。
如果 AI 能直接写入系统，而系统没有业务规则层来约束它，出问题只是时间问题。

七维对照

【指着最后一行讲】前六行是"功能差异"，学员会觉得是产品对比。最后一行是"假设差异"——那才是分水岭。

"数据中台不是做错了，是它被设计出来的时候，AI 还不会写。"

② 架构位置 4/5

本体在哪一层

L4 业务消费层　AI Agent · 业务应用 · 决策看板
只通过本体接口交互，不直接访问底层数据库
L3 业务本体平台　Object（对象）· Link（关系）· Action（操作）
★ 数据层和应用层之间的语义枢纽。不重新存储数据，在数据之上建立语义模型
L2 数据仓库 / 数据湖　ODS → DWD → DWS
结构化的事实数据，但没有业务语义
L1 源系统　ERP · CRM · 生产控制 · IoT
原始数据的产生地，通常是割裂的、异构的

AI 看到的世界，
是被本体层"翻译"过的世界。

它看到的不是原始表，而是有名字、有关系、有规则的业务对象。

四层

【L3 那行的两个"不"要强调】不重新存储数据（它不是又一个数据库）、不直接访问底层（L4 必须走它）。学员最容易把本体理解成"又一层数据库"。

② 架构位置 5/5

本体为什么能解决幻觉

❌ 没有本体层时

用户问 AI → LLM 读供应商表和库存表 → 基于概率推断给出排序 → 排序里有一个条款异常的供应商 → 执行后违约

✅ 有本体层时

① 问题被转化为对 Supplier 和 InboundOrder 两个对象的查询
② AI 识别出需要执行 schedule_inbound 这个 Action
③ 前置条件检查：contract_status == 'active' 且 today NOT IN restricted_dates
④ 系统发现该供应商的 restricted_dates 包含今日 → Action 被阻断，AI 自动转向下一个候选
⑤ 最终执行的操作，已经通过了所有业务规则的校验

这个拦截发生在系统层面，不依赖 prompt 工程，不依赖模型的"理解能力"。
哪怕你用的是一个刚上线的小模型，只要它调用的是同一个 Action，就会经历同一套约束校验。

把业务规则从"模型应该知道的事"
变成"系统强制执行的约束"。

机制

【"哪怕你用的是一个刚上线的小模型"这句很重要】它说明这个方案不随模型能力波动——这是架构解，不是调参解。

【最后那句是本章落点】"前者依赖概率，后者是确定性的。"

【完整采购流程走查可以砍】Supplier A/B/C 三种结果那一段，超时就跳过，手册里有。

③ 五要素 1/3 · 一个纠偏

本体不是知识库，更像文件系统

工程师理解本体时，容易被"知识图谱""语义模型"这些词带偏。这些词没有错，但不够准确。

对一个要支撑 Agent 执行的系统，
本体首先要回答的是：
什么对象可以存在，怎么命名，怎么连接，
怎么被读取，怎么被写入，怎么过期，怎么追溯。

本体元素文件系统类比
ObjectType文件类型和 inode schema——定义系统里允许存在什么东西：约束、模式、决策记录、业务流程、反模式
LinkType文件系统的链接关系，但语义更强——不是"参见某某"的文本提示，而是可遍历、可审计、可治理的关系
derived_from 决策血缘 · contradicts 矛盾 · supersedes 替代 · impacts 影响传播

ObjectType 和 LinkType 不是知识库字段，
而是 AI 内存系统的 inode 和 link。

纠偏

【这一页专治"本体=知识图谱"的误解】"文件系统关心的是——这个对象是什么类型，和谁连接，谁能读，谁能写，何时失效，出了问题怎么修。知识库不关心后面四个。"

【LinkType 的例子要念一两个】contradicts（矛盾）和 supersedes（替代）最能说明"语义更强"——知识图谱里的边通常只是"相关"，这里的边是能驱动系统行为的。

③ 五要素 2/3

结构层与动力层

记忆层 · 让世界有结构

ObjectType + LinkType + 对象实例

保存企业世界的结构化状态，记录决策血缘，支持检索和注入，管理记忆生命周期

⚠️ 只有这一层，本体仍然只是一个结构化存储系统

动力层 · 让世界会运动

Action　受治理的写操作。它不是普通 tool calling——普通工具调用只描述函数签名，没有说明这个操作在业务世界里是否合法、是否需要审计、会影响哪些对象、失败时如何解释
Function　可计算的读路径。不一定改变状态，但定义了"系统如何理解当前世界"
Rule　边界。决定什么操作能执行、什么写回能晋升、什么记忆必须保护

ObjectType / LinkType 让世界有结构；
Action / Function / Rule 让世界会运动。

动力层回答的不是"世界是什么"，而是"世界如何合法地变化"。

结构 · 动力

⚠️【"Action 不是普通 tool calling"要讲透】这是学员最容易滑过去的一句。关键不是格式，而是语义：Action 改变的是一个受约束的企业世界。 一个普通的 function calling schema 描述"怎么调"，Action 描述"调了之后世界会怎样、允不允许"。

③ 五要素 3/3 · 建模时逐个问

五个判据

要素判据
Object有没有自己的生命周期？有没有独立的属性集？是否被其他对象引用？
Link有方向吗（依据"从哪边查更自然"来选）？能带属性吗？
Function是算出来的，不是记下来的？只读、无副作用？
Rule是必须始终成立的约束吗？
Action是需要被明确记录的操作吗？

采购场景的对象判定

业务概念独立对象判断依据
供应商✅有注册→合作→停用的生命周期，被采购订单引用
采购订单✅有草稿→审批→执行→完成的状态流转
合同✅有独立有效期，与采购订单是不同维度的关联
认证证书✅有过期日期和认证类型，独立于供应商主档
判据

【"认证证书"那一行最值得讲】新手会把认证做成供应商的一个字段。但它有自己的过期日期和类型，而且规则要单独引用它——所以是独立对象。这个判断直接决定了后面能不能写出"认证有效期不足 30 天"这条规则。

【Link 方向的判据很实用】"从哪边查更自然"——不用纠结业务上谁属于谁。

④ OAG ≠ RAG 1/2

一个客服场景暴露的分界

"我的订单 PO-2026-001 到哪了？"

RAG 能答。
检索订单文档，拼进提示词，生成流畅回复——
全程只读，世界状态没有任何改变。

"帮我把这笔订单取消，改从 ACME 重新下单。"

RAG 卡住了。
它可以生成"取消步骤说明"，甚至写出看起来像 API 调用的伪代码——
但它不能真正执行写操作，更无法保证执行后的状态仍符合业务规则。

差的不是模型能力，是架构层：
RAG 增强"生成内容的依据"，
OAG 增强"行动的能力与边界"。

RAG 的结构性边界：Embedding 是基于切片的，切片之间很难构建语义关系；检索和生成都发生在 LLM 的上下文里，不触及业务系统的写路径。
可以理解成"开卷考试"——书翻得再快，考生也不能改教科书里的内容。

分界

【"开卷考试"这个比喻很好用，念出来】它一句话说清了 RAG 的天花板。

【别贬低 RAG】"对问答、总结、分析类任务，这够了。 对'帮我把这笔采购批了'这类任务，不够。"——是分工，不是优劣。

⑤ 三层能力 1/3 · 操作发现

Schema 即能力清单

⑤ 三层能力 2/3 · 执行约束

为什么提示词工程不够

你在发起采购前，必须检查供应商认证有效期是否大于 30 天。

会被遗忘

多轮对话后，早期指令权重下降

会被稀释

上下文窗口塞满后，约束被挤出去

会被绕过

提示词注入攻击可以让 Agent"忘记"所有约束

自觉遵守不是工程约束。

层次机制强度可绕过性
提示词层靠 LLM 自觉最弱高（注入即破）
API 网关层校验 HTTP 请求参数中中（参数可伪造）
本体层校验业务状态 + 全局不变式最强低（引擎强制，无旁路）

API 网关能查"参数格式对不对"，但查不了"这笔采购加上去之后，未结金额会不会超过信用额度"——那需要看到写入后的新状态。只有本体层的全局规则能做到。

执行约束

【先讲反面：假设 Agent 能直连数据库】"它接到任务'补充 50 万备料'，选中一家认证还有 13 天到期的供应商，写入成功。数据库里多了一行记录。审批流没触发。信用额度没检查。业务规则全部绕过了——不是 Agent 有意为之，是它根本不知道这些规则的存在。"

【最后那句是本页最硬的论证】网关层为什么不够——因为它看不到写入后的新状态。这一句能挡住"我们有 API 网关就够了"的反驳。

⑤ 三层能力 2/3 · 结构化拒绝三件套

Agent 被拦的那一刻，收到了什么

{
  "status": "rejected",
  "triggered_rule": "certification_validity",          ← 为什么不行
  "message": "供应商认证有效期不足 30 天，订单已阻断",
  "current_state": {                                    ← 当时世界是什么样
    "Supplier/S-BETA-002": { "outstanding_amount": 120000 },
    "Certification/CERT-002": { "days_remaining": 13 }
  },
  "suggestion": "建议选择认证有效的备选供应商 S-ACME-001（ACME）"   ← 可以怎么调整
}

很多系统的拒绝长这样

{ "error": "操作失败" }

Agent 收到这个，只能盲试。

OAG 闭环

发现 → 调用 → 被拒 → 调整 → 重试成功
第 2 轮改选 ACME → 认证有效、额度充足 → 成功。
全程在本体层约束内完成，没有绕过。

这和"日志存快照"是同一哲学：记录上下文，而不只是记录结果。
区别是——日志给审计人员看，拒绝响应给 Agent 看。受众不同，但都需要完整的决策上下文。

三件套

【这一页是本课最有画面感的一页】"引擎内部发生了什么：前置条件通过 → 内存中创建订单 → 全局规则命中（剩余 13 天 < 30 天）→ 回滚，文件从未被写。"

【三个字段逐个指着讲】triggered_rule 让 Agent 理解失败原因；current_state 让它判断是临时状态还是结构性问题；suggestion 让它直接调整参数重试。Agent 不需要"猜"下一步。

⑤ 三层能力 3/3 · 决策追溯

三个月后，你能回答吗

"5 月 30 号那笔 28 万的采购，
AI 为什么觉得能下单？
当时供应商的认证状态是什么？"

这不是技术排查，是业务审计。

日志类型典型内容能回答不能回答
数据库日志INSERT INTO purchase_orders写了什么为什么写
应用日志POST /actions 200 OK调用成功没当时业务状态是什么

它存的不是"改了什么"，
而是"当时世界是什么样"。

一条记录里有：action_id · caller · params · snapshot · passed_rules · outcome。
不需要猜，不需要拼凑多个系统的日志。一行 JSON，一个完整的决策上下文。

决策追溯

【用这一条记录当场回答合规团队的四个问题】为什么选 ACME（认证剩余 365 天，合同有效）· 为什么金额没问题（未结 18 万 + 新单 8 万 = 26 万 < 额度 50 万）· 谁发起的（procurement-agent-v2）· 通过了哪些规则。

⑥ Software 3.0 1/2

Karpathy 的三代划分，少了一层

代人做什么
1.0人写显式代码
2.0人造数据集，程序学进权重矩阵
3.0人写 prompt、上下文、工具、记忆——上下文窗口就是程序，LLM 是解释器

这很像一个 OS 的内核：CPU 是 LLM，RAM 是 Context Window，外设是 MCP、API、CLI。

不过这里有一个问题：
文件系统在哪里？

交互层　自然语言或 API 接入意图。此时的输入尚未绑定对象，只是原始信号
逻辑内核（LLM OS Kernel）　128k–2M 的上下文适合"当前这轮"推理，不适合承载企业世界的完整约束与血缘。内核处理概率，不拥有业务真理
本体（Business Ontology）　持久的世界模型。实体与关系、业务规则、历史快照、不可违反的硬约束——Agent 的寻址空间
MCP 外设　数据库、向量库、外部 API 的标准化 I/O
Software 3.0

【"内核处理概率，不拥有业务真理"这句要念】它把 LLM 的位置说死了。

【引一句 Karpathy 的原话铺垫】"2026 年 4 月，Karpathy 在 Sequoia Ascent 上说：他从未像现在这样'落后'于编程。 不是不会写代码，是工作流变了——从逐行敲代码，变成向 Agent 委派整块任务。"

⑥ Software 3.0 2/2

三条边界，与一个关键分歧

① 上下文不是存储

RAM 易失、有长度上限；本体承担跨会话、跨 Agent、跨任务的一致性

② MCP 不是语义层

它是驱动；本体是 syscall 表——定义签名、前置条件、写回路径

③ 内核与外设必须经本体解耦

否则每个 Agent 都要重新"理解"一遍业务，锯齿状智能会在集成边界上放大

⭐ LLM 是 CPU，还是协处理器？

维度Karpathy行业共识本体论视角
内核是什么LLM语义内核规则执法者
LLM 的角色CPU（可信）大脑协处理器（不可信）
核心关切能力扩展用户体验决策正确性
信任模型LLM 可信LLM 是核心LLM 不可信

Karpathy 回答"如何让 LLM 更强大"，
本体论回答"如何让 LLM 的输出更可信"。

边界 · 分歧

【这一页要敢于表明立场】"我们和 Karpathy 的分歧不在技术，在信任模型。他把 LLM 当 CPU，我们把它当协处理器——一个能力很强但不可信的协处理器。"

【顺带一个很好用的类比表，超时可砍】传统 OS：用户程序不能直接操作硬件 → syscall；AI Native OS：LLM 不能直接改状态 → Action。内存保护（MMU）→ 规则校验；审计日志（auditd）→ 决策血统。
传统 OS 解决的是确定性计算的资源管理问题。当计算引擎从确定性变成概率性，传统 OS 没有任何机制能处理新出现的"语义正确性"问题。

⑦ Harness vs 本体

Harness 越多，越说明缺了一层

Harness、Loop、Agent 运行时、Workflow、Memory、Multi-Agent——名字不同，工程问题很接近：让模型能规划、执行、观察、验证、重试。
但它们最后都会撞到同一个边界：智能体到底运行在一个什么样的世界里？

如果这个世界只是提示词、聊天历史、向量库、工具 schema 和临时 JSON 的拼接，系统很快会出现：
规则没有强制性 · 记忆没有生命周期 · 写回没有血缘 · 多 Agent 之间没有共享语义 · 业务逻辑散落在提示词和工具代码里

Harness / Loop（运行层）

管控制流：谁先跑，谁后跑，失败回哪一步，重试几次，什么时候中止，什么时候升级

本体（世界层）

管世界：有哪些对象，哪些规则算数，哪些记忆能读，哪些结果能写回，什么经验能跨任务复用

放错地方后果
规则放在 prompt 里失败只能得到"模型觉得不对"
规则存在结构化约束里失败带规则 ID，系统知道是哪条约束被违反
成功经验只在 chat log 里下轮很难稳定复用

出问题时你必须能判断：是 Harness 路由错了、本体规则错了、上下文拼错了，还是 Agent 输出错了？
层次混在一起，排查成本会指数级上升，导致多智能体系统无法落地。

Harness vs 本体

【一句话记住】"Harness 框架是一套脚手架，它用来控制大模型怎么跑。本体相当于一个业务世界的数字孪生，它决定了大模型跑在哪个世界里。"

【最后那句是本章落点】排查成本指数级上升——这是很多多智能体项目死掉的真实原因，不是模型不行。

⑦ Harness vs 本体 · 补

多智能体是应用层，不是架构中心

企业里的多智能体有很多角色：采购、风控、财务、销售、运维、代码、测试。
分工很重要，但它们不应该各自维护一套私有的世界模型。

稳定的多智能体协作，
不来自"大家聊得更好"，
而来自共享的对象、规则、动作。

它们可以有不同的上下文清单、权限和 token 预算，但底层世界应该是一套。长期记忆如果只属于某个 Agent，就会变成角色私有笔记——企业系统需要的是共享内存：对象一致、血缘一致、规则一致、写回一致。
多智能体之间当然需要协议，但协议不是根，根是共享本体。

⭐ 本体自己也需要一套多智能体

应用线：Agent 使用本体

采购、风控、运维、编码 Agent——处理某张订单或修某个 bug

生产线：Agent 建设本体

Object Modeling · Link Modeling · Action Designer · Function Engineer · Rule Engineer · Memory Curator · Migration · Verifier（检查本体变更是否破坏已有流程）

企业本体不会一次建完——对象会拆分，链接会增加，规则会迁移，旧记忆会失效。
靠人手工维护全部变化，不现实；靠通用聊天 Agent 自动乱改，也不可靠。

两条线

【"两条线"是这一页的记忆点】"一条是应用线：Agent 使用本体。一条是生产线：Agent 建设本体。"——很多人只想到第一条。

【更合理的方式】让一组本体工程 Agent 在 Harness 约束下工作：提出变更，生成迁移，跑验证，经过晋升闸后再生效。

⑧ 建模 SOP + ⑩ 收口

建模四阶段，与一句收口

建模不能从"有哪些数据"开始。正确的起点是：现在的做法在哪里出了问题，这些问题集中在哪个业务范围内。
三类症状：信息没法汇聚（拿到的是不同时间点的拼凑结果）· 规则无法被执行（Agent 走后端接口绕过前端校验——规则没有失效，只是从来没有在这条路径上被执行）· 决策无法还原

阶段要点完成标志
① 调研与建模业务专家必须在场，工程师单独做往往跑偏。结果用文档呈现（不是代码），请业务人员逐条确认一份经业务确认的本体定义文档或原型
② 数据盘点与治理模型建完后再确认数据来源每个属性有明确来源和同步方式
③ 引擎搭建与接入前两个阶段产出文档或原型，这个阶段才开始写代码每次操作后留下可追溯的决策记录
④ 场景验证与调优贯穿全程，与业务人员走查规则边界业务团队确认：知道它会在什么情况下拦截，被拦截时能看到清晰原因

先建模、再看数据——顺序不能反。 先看数据会被现有系统结构带偏，建出"系统长什么样"而非"业务是什么样"。
三个判断：信息汇聚实现了吗 · 规则真在执行吗（警惕误拦截 > 漏拦截）· 决策能不能当天说清楚

本体建模是把业务知识变成可执行定义的过程，
而不是软件开发本身。

SOP · 收口

【"规则没有失效，只是从来没有在这条路径上被执行"——这句是全课最精准的一句诊断】它解释了为什么"我们有校验"和"规则被执行了"是两回事。

【金句板书】"最难的环节不是选技术栈，而是和业务人员一起把那些'大家都知道但没有人写下来'的规则，变成能被系统执行的精确描述。"

【全课收口，接第五课】"FDE 真正做的是世界建模——理解业务对象、理解对象关系、理解操作、构建应用，这四件事合起来就是本体建模。大模型负责生成候选，本体负责收敛候选：schema 校验合法性、rule 检查可执行、lineage 记录来源、分支/提案/评审让变更先在隔离环境验证。
AI FDE 的工作方式不是'一次生成正确答案'，而是'生成候选 → 放进本体和执行循环里验证 → 然后晋升'。
最后四句话记住：Harness 管循环，Ontology 管世界，Promotion Gate 管写回，Memory Pipeline 管下轮怎么读。
RAG 是读材料，AI FDE 是改世界。"
