动机 · 不做会怎样

为什么不直接手写插件？

运行时端的 plugins/grass/ 就是手写的。手写行不行？行。那为什么还要一个建模端？

① 手写的前提是"你已经知道要写什么"

而 FDE 面对新行业时，最贵的工作恰恰发生在写代码之前——把业务专家脑子里的东西挖出来、变成精确定义。
手写插件解决不了这一段。

② 业务专家看不懂 Python

五要素最终要由领域专家签字（否则规则没有出处）。
你不能把 @spi.rule 装饰器拿给他审。中间必须有一层他看得懂的东西——那就是 IR。

③ 手写没有一致性保证

第二个行业、第三个行业，结构会漂。
而 S2 讲过：内核靠 SPI 契约吃饭，插件结构不一致，"换行业零改内核"就是空话。

建模端解决的不是"写得快"，
是"业务专家能参与"和"结构不漂"。

动机

⭐【第②条是最重要的，展开讲】"S2 讲 Rule 的时候说过——规则要有 source，没有出处的规则不是规则，是某个人的意见。那么谁来提供出处？领域专家。可是领域专家看不懂 Python。所以必须有一份他能读、能改、能签字的中间物——这就是 IR 存在的全部理由。"

【第③条接 S2 的 SPI】"S2 那句『换行业零改内核』的前提是插件长得都一样。手写三个行业，三个人写，结构一定会漂。"

⚠️【别说成"提效工具"】"如果你在客户面前把它讲成'我们有个工具能自动生成代码'，客户会问『那准确率多少』，然后你就完了。正确的讲法是：它让业务专家能直接参与本体建模，并保证不同行业的产出结构一致。"

管线 ① · 业务分析（DDD）

两个入口，二选一

① 业务分析（DDD）事件风暴 · 限界上下文 · 行为矩阵 / Intake spec
入口适用来源
A. studio-planner 产物已跑过事件风暴 / 领域建模behavior-matrix · domain-canvas · process-flow · event-storm
B. 领域 Intake 标准 spec没跑过 planner——FDE 直接访谈，或交业务方填templates/domain-intake.md.tmpl

Intake spec = 给业务方 / 领域专家 / 规则工程师的标准输入契约

12 段（业务概述 · 角色 · 对象 · 关系 · 动作 · 指标 · 规则 · 决策点 · 数据源 · 能力问题 · 治理），
每段标注谁来填、编译成哪个本体要素，带示例 + 完成度自检。填完即可喂给 ontology-map。

填好的样例就在仓库里：examples/domain-intake-chili.md——一份填满的辣椒 intake， 对照运行时端的 plugins/chili。同一份模板、换个领域、填出来结构一致。

管线 ①

⭐【入口 B 才是 FDE 的主战场】"入口 A 是理想情况——客户已经做过事件风暴。现实是十次有八次没做过。所以入口 B（Intake spec）是你真正会用的那个。"

⭐【"每段标注谁来填"这一条极其重要】"这不是一份问卷，是一份责任分配表。§7 规则段标的是领域专家 + 规则工程师——不是 FDE 自己填。你自己填的规则没有出处，第五课的 checkout 会把它挑出来。"

⚠️【一处文档落差，实测记录】README 说 intake 是 11 段，模板实际是 §0–§11 共 12 段（README 没数 §0）。按 12 段。这是第五课实测出来的，又一处"文档说 A、代码是 B"。

【接第三、四课】"这份 Intake 的 §1–§9 怎么填？那正是第三课『采集信息』和第四课『认知萃取』的产出。这门课到这里和主干课接上了。"

管线 ① 续 · ⭐ 这个工具最聪明的地方

它不发明新语言，它做翻译

DDD / 事件风暴（业务团队已产出）本体五要素（运行时端）
聚合 / 实体Object
聚合间关系 / 上下文集成Link（带 root_cause / hypothesis / derivation 边语义）
命令 / 领域事件Action（受治理的写，带 guard / post-rule / HIL）
读模型 / KPIFunction（只读派生量）
不变式 / 策略 PolicyRule（写后强制，带 source / citations）
限界上下文namespace / ontology_id

你在客户那儿做的事件风暴，
不是白做的中间品，
是编译器的输入。

⭐ 注意第 5 行：Rule 带 source / citations——规则要有出处。
没有出处的规则，不是规则，是某个人的意见。（第四课认知萃取会反复讲这一条。）

⭐ 翻译表

⭐【这一页是本课的第一个高光，讲慢】"很多建模工具的做法是发明一套自己的建模语言，然后要求所有人来学。这个工具没有。它站在业务团队已经会的 DDD 上，做一层翻译。"

【对 FDE 的实际意义】"这意味着你在客户现场做的事件风暴、画的限界上下文，不是为了写文档，是为了喂给编译器。——你的每一小时都落到了产物上。"

【Link 那行的边语义是难点，点一下】root_cause / hypothesis / derivation——它决定多跳推理停在哪。第五课会细讲，今天知道"边是有语义的、不只是一根线"就够了。

【Action 带 HIL 也先埋着】HIL 是第五课下半场的主场。

管线 ② · 五要素 IR

IR：业务专家能读，编译器能吃

② 五要素 IRObject · Link · Function · Rule · Action　studio/changes/{id}/ontology-map.md
IR 段编译去向
§0 Header　Namespace & Sourceontology_id / namespace
§1 Objectsspi.registry.add_object(ObjectType(...))
§2 Linksspi.registry.add_link(LinkType(...))
§3 Functions@spi.function（骨架 + TODO）
§4 Rules　★ FDE 核心@spi.rule——declarative 全自动 / function 骨架
§5 Actions@spi.action（骨架）
§6 Mapping Hintsmappings/objects.yaml
§7 CQ　能力验证问题cq/golden.yaml

IR 是一份 Markdown——所以业务专家能读、能当场改、能签字；
同时它结构严格到编译器能逐行翻译。这两件事同时成立，是 IR 的全部设计目标。

管线 ②

⭐【§4 标着 ★FDE 核心，规范里原文就这么写的】"为什么规则段是核心？因为对象和关系业务方大多说得清，规则说不清——『大家都知道但没人写下来』的东西全在这一段。第五课的『规则三问』就是为这一段准备的。"

【规则三问预告一下，第五课细讲】① 违反了要不要拦住并回滚（severity: hard/soft）② 只看入参能判，还是要去查别的数据（backing: declarative/function）③ 依据是哪条标准/方法学/谁的经验（source）。

⭐【"declarative 全自动"这五个字要点出来】"注意 §4 那行——declarative 规则是唯一被全自动写完函数体的。所以规则三问的第二问答对了，机器就能替你写完。这是整条管线上自动化程度最高的一格。"

⚠️【又一处文档落差】规范标题写的是「五段式中间表示」，正文实际是 0 号 Header + 七段。按七段。

四类 NotImplementedError 的来源——它们不是 bug，是界线：

触发条件生成物
declarative 规则✅ 函数体全自动写完，不 raise
function-backed 规则装饰器 + docstring + TODO(FDE) + 可用方法提示 + raise
每一个 Action handlerstage_write 骨架注释 + set_confidence + raise
Function 口径不明TODO(FDE)：实现派生量计算（只读，无副作用）+ raise

机器负责把结构立起来，
人负责把判断填进去。

管线 ③

⭐【这一页要立住一个态度，第五课会反复用】"康养项目那个项目留了 121 处 NotImplementedError。这不是没做完，是明确划出了『机器到此为止、人从这里接手』的界线。"

⭐⭐【一句必须说出口的话】"一个不敢留 NotImplementedError 的 FDE，会让模型把它猜的业务规则写成看起来能跑的代码——那才是灾难。"

【绿色那一行是好消息，别只讲坏消息】"declarative 规则是唯一被全自动写完函数体的——这不是小事。真实项目里 declarative 规则往往占一半以上，这一半是白捡的。"

管线全貌 · ⭐ 四个命令只有一个有停点

那个 ⏸ 是整条管线的设计核心

业务分析 → ontology-map（IR 七段）→ ⏸ 你审 IR → ontology-compile（插件骨架）
        → FDE 收尾（填函数体 / 回写 / 参考数据）→ ontology-validate（结构 / 治理 / CQ）
命令干什么强制人审
/studio-ontology:map {id}业务分析 → 七段 IR无
/studio-ontology:compile {id}IR → 插件骨架无（已存在不覆盖，只告警）
/studio-ontology:validate {id}四段校验无（只诊断）
/studio-ontology:model {id}map → ⏸ 你审 IR → compile★ 唯一有

⏸ 停下来的时候，审四项

① 对象边界（是不是真的独立实体）　② edge_semantics（多跳推理停在哪）
③ 规则的 severity · backing · 出处　④ Action 的 writes · HIL
IR 是 Markdown，你可以直接改文件再继续。

⭐ 另一处"权限即职责"的设计：ontology-validate 没有 Write 权限—— 它物理上不可能改你的插件，只能告诉你哪里不合格。

⭐ 停点

⭐【那个 ⏸ 是本课第二个高光】"很多人会问：既然 LLM 能生成 IR，为什么还要人审一遍？因为本体是治理的锚点——一个没有人签字的治理基准，不是治理基准。"

⭐【这不是一句口号，是流水线上一个绕不过去的停点】"它被做成了工程约束，不是文档里的一句『建议人工复核』。——这和 S2 讲的『安全的默认值比安全的文档有用一百倍』是同一个思路。"

【校验器无权改代码，这个设计要夸一句】"纪律靠机制不靠自觉的又一个干净例子。校验器如果能改代码，早晚有人会让它'顺手修一下'——那时候它就不是校验器了。"

【课堂纪律，转告第五课】"用 model，不要分开跑 map 和 compile——那个停点是第五课最重要的教学时刻。"

⭐ 本课最该带走的一条职业习惯

README 里有一节，标题就叫「诚实边界」

编译只保证结构对、五要素齐、可 import。
function-backed 规则函数体、Action 回写逻辑、参考数据是 FDE 的手艺活，生成骨架 + TODO(FDE)， 由人在 clife-onto-engine 仓库内手填——这正是 FDE 不可替代之处，不假装全自动。

TODO(FDE) 这个做法值得单独说：它把"这里需要人"从一句原则， 变成了代码里一个可以被 grep 出来的标记。
→ 又是 S2 第 14 页那条方法论：重要但会被慢慢磨掉的东西，要想办法让它能被机器检查。

设计上的克制

核心语义决策留给人签字——这是主动选择，值得讲。

能力上的边界

function 体、Action 回写现在确实生成不了——这是做不到，不是不想做。

两件事在产品声明里写成了一句话，
在客户面前要分开讲。

⭐ 诚实边界

⭐⭐【这一页是本课道德重量最大的一页，讲慢】

【必须说出口的一段】"说『我们刻意把核心语义决策留给人』——没错，这是真的，而且值得讲。
但如果客户追问『那你们能不能生成 function 规则体』，答『目前生成不了』，别答『我们认为不该生成』。
把做不到包装成克制，是这一行最容易犯、也最伤信任的错。"

【客户问"你们是不是用 AI 自动建模"的标准答案】"AI 出初稿，业务专家签字。我们不接受一个没有人负责的本体。"——这句话既诚实，又恰恰是我们比『全自动』竞品更值得信任的地方。在这个赛道，承认边界是竞争优势，不是弱点。

【自查会考这一条】

⭐ 缺口 · 回答 S2 那张实测表的"为什么"

七段 IR，覆盖七槽位中的五格

IR 段落进 SPI 槽位自动化程度
§1 Objects · §2 Links① Schema 包✅ 全自动
§6 Mapping Hints② 映射注册表✅ 全自动
§3 Functions · §4 Rules③ Function / Rule⚠️ 只出骨架（declarative 除外）
§5 Actions④ Action handlers⚠️ 只出骨架
§7 CQ⑦ CQ 验收集⚠️ 格式与引擎不匹配
—— 没有对应的 IR 段 ——⑤ 记忆词典 / 术语表❌ 完全不生成
—— 没有对应的 IR 段 ——⑥ Agent 角色 + HIL 声明❌ 完全不生成

不是编译器没实现，
是 IR 里压根没有这两段。

如果是该怎么答客户
编译器没实现"这是个待补的功能"　← 那是欠债
IR 里没有这一段"这两块目前是人工产出的，不在自动化管线里"　← 那是设计边界，是坦荡
⭐ 缺口

【接 S2】"S2 第 6 页给了现象——七槽位只覆盖五格。这一页给结构性原因。"

⭐【那个区分决定你怎么答客户，必须讲透】"说错了，一个变成欠债，一个是坦荡。客户听到'待补的功能'会记在风险清单上；听到'不在自动化管线里、是人工产出'——那是一个清晰的交付边界。"

【这句话学员应该能原样说给客户听】"七段 IR 覆盖了七槽位中的五格"——诚实、精确、可交付。

【⑦ CQ 那行的细节，第五课会踩到】编译产 cq/golden.yaml，但引擎只认 cq.py 的 CQ_SUITE，全仓没有代码读那个 YAML。第五课收尾 6 项里就有这一项。

⭐ 验收 · 图上那行小字

产物与手写 plugins/grass 五要素同构

编出来的东西，
要和人手写的长得一样。

为什么这条标准立得住

plugins/grass 是手写的、跑通的、被真 Qwen 打过的（S2 第 15 页那六步就是它）。
拿一个已经被证明能跑的东西当靶子，比任何"生成质量评分"都硬。

它验的到底是什么

不是"代码写得好不好"，是结构齐不齐、契约对不对——
五要素都在吗？注册方式一致吗？能被内核 import 吗？
这正是 S2 说的：内核靠 SPI 契约吃饭。

已经跑通的实证：本插件已用真草业材料跑通，产物与 clife-onto-engine 手写的 plugins/grass 五要素同构。

⚠️ 交付纪律 · 最容易犯的一个错

产物落到哪里，是有红线的

建模仓（astra-studio 工作区）             运行时仓（clife-onto-engine）
studio/changes/{id}/ontology-map.md  →  plugins/{ontology_id}/  ← 本体定义/规则/动作（行业级，租户无关）
                                        tenants/{tenant}/       ← 该租户的实例与参考数据
规矩为什么
是 plugins/{ontology_id}/，不是 plugins/{tenant}/grass 与 chili 在同一进程同一 registry 里按 namespace 共存
名录数据、实例数据属于 tenants/它们是租户层的东西，不是行业层
IR 文件不在运行时仓跨仓复制过去

你把名录数据写进 plugins/，
违反的不是习惯，是红线。

这就是 S2 讲的三层切分 Kernel / Plugin / Tenant 在目录上的物理体现——
判缝准则的第三档（"具体数字 → 租户"）在这里变成了两个不同的文件夹。

⚠️ 红线

⚠️【这是第五课最高频的一个错，S3 先打预防针】"你编完插件，手里有一堆名录数据（哪些草种是乡土的、阈值是多少）。最自然的动作是把它们塞进插件里——错。那是租户数据。"

【回扣 S2 的判缝准则】"S2 说『换成医疗大模型还成立吗』分内核和插件，还有第三档：具体数字归租户。今天你看到那第三档在磁盘上长什么样了——它是另一个文件夹。"

【为什么是 ontology_id 不是 tenant】"因为 grass 和 chili 是跑在同一个进程、同一个 registry 里的，靠 namespace 分开。插件是按行业组织的，不是按客户组织的。"
