三、为什么要有建模端

运行时端的 plugins/grass/ 就是手写的。手写行不行？行。那为什么还要一个建模端？

三条理由，第二条最重要：

3.1 手写的前提是"你已经知道要写什么"

而 FDE 面对新行业时，最贵的工作恰恰发生在写代码之前—— 把业务专家脑子里的东西挖出来、变成精确定义。

手写插件解决不了这一段。

3.2 ⭐ 业务专家看不懂 Python

S2 讲 Rule 的时候说过：规则要有 source，没有出处的规则不是规则，是某个人的意见。

那么谁来提供出处？领域专家。 可是领域专家看不懂 @spi.rule 装饰器。

所以中间必须有一份他能读、能改、能签字的东西——这就是 IR 存在的全部理由。

3.3 手写没有一致性保证

第二个行业、第三个行业，结构会漂。 而 S2 讲过：内核靠 SPI 契约吃饭—— 插件结构不一致，"换行业零改内核"就是空话。

建模端解决的不是"写得快"，是"业务专家能参与"和"结构不漂"。

⚠️ 一条话术纪律： 如果你在客户面前把它讲成"我们有个工具能自动生成代码"， 客户会问"那准确率多少"，然后你就完了。

正确的讲法是：它让业务专家能直接参与本体建模，并保证不同行业的产出结构一致。

四、管线 ① · 业务分析：两个入口

入口 适用 来源
A. studio-planner 产物 已跑过事件风暴 / 领域建模 behavior-matrix · domain-canvas · process-flow · event-storm
B. 领域 Intake 标准 spec 没跑过 planner——FDE 直接访谈，或交业务方填 templates/domain-intake.md.tmpl

⭐ 入口 B 才是 FDE 的主战场： 入口 A 是理想情况——客户已经做过事件风暴。现实是十次有八次没做过。

4.1 Intake spec = 标准输入契约

12 段：业务概述 · 角色 · 对象 · 关系 · 动作 · 指标 · 规则 · 决策点 · 数据源 · 能力问题 · 治理。

⭐ 每段标注谁来填、编译成哪个本体要素，带示例 + 完成度自检。

这不是一份问卷，是一份责任分配表。 §7 规则段标的是领域专家 + 规则工程师——不是 FDE 自己填。 你自己填的规则没有出处，第五课的 checkout 会把它挑出来。

⚠️ 一处文档落差（第五课实测）： README 说 intake 是 11 段，模板实际是 §0–§11 共 12 段（README 没数 §0）。按 12 段。

4.2 填好的样例就在仓库里

examples/domain-intake-chili.md——一份填满的辣椒 intake，对照运行时端的 plugins/chili。

同一份模板、换个领域、填出来结构一致。

4.3 这一章和主干课的接缝

Intake 的 §1–§9 怎么填？那正是第三课「采集信息」和第四课「认知萃取」的产出。

五、⭐ DDD ↔︎ 五要素：这个工具最聪明的地方

它不发明新语言，它做翻译。

DDD / 事件风暴（业务团队已产出） 本体五要素（运行时端）
聚合 / 实体 Object
聚合间关系 / 上下文集成 Link（带 root_cause / hypothesis / derivation 边语义）
命令 / 领域事件 Action（受治理的写，带 guard / post-rule / HIL）
读模型 / KPI Function（只读派生量）
不变式 / 策略 Policy Rule（写后强制，带 source / citations）
限界上下文 namespace / ontology_id

很多建模工具的做法是发明一套自己的建模语言，然后要求所有人来学。 这个工具没有。它站在业务团队已经会的 DDD 上，做一层翻译。

对 FDE 的意义：

你在客户那儿做的事件风暴，不是白做的中间品，是编译器的输入。 ——你的每一小时都落到了产物上。

⭐ 注意第 5 行：Rule 带 source / citations——规则要有出处。 没有出处的规则，不是规则，是某个人的意见。（第四课认知萃取会反复讲。）

⭐ Link 那行的 root_cause / hypothesis / derivation 是边语义—— 它决定多跳推理停在哪。第五课细讲，今天知道"边是有语义的，不只是一根线"就够了。

六、管线 ② · 五要素 IR 七段

IR 是一份 Markdown（studio/changes/{id}/ontology-map.md）—— 所以业务专家能读、能当场改、能签字； 同时它结构严格到编译器能逐行翻译。

这两件事同时成立，是 IR 的全部设计目标。

IR 段 编译去向
§0 Header Namespace & Source ontology_id / namespace
§1 Objects spi.registry.add_object(ObjectType(...))
§2 Links spi.registry.add_link(LinkType(...))
§3 Functions @spi.function（骨架 + TODO）
§4 Rules　★ FDE 核心 @spi.rule——declarative 全自动 / function 骨架
§5 Actions @spi.action（骨架）
§6 Mapping Hints mappings/objects.yaml
§7 CQ 能力验证问题 cq/golden.yaml

6.1 为什么 §4 标着「★ FDE 核心」

因为对象和关系业务方大多说得清，规则说不清—— 「大家都知道但没人写下来」的东西全在这一段。

第五课的规则三问就是为这一段准备的：

① 违反了要不要拦住并回滚？ → severity: hard / soft ② 只看入参能判，还是要去查别的数据？ → backing: declarative / function ③ 依据是哪条标准 / 方法学 / 谁的经验？ → source；没依据就写"待补依据"，不许猜

⭐ 注意 §4 那行的「declarative 全自动」： declarative 规则是唯一被全自动写完函数体的。 所以规则三问的第二问答对了，机器就能替你写完—— 这是整条管线上自动化程度最高的一格。

⚠️ 又一处文档落差：规范标题写的是「五段式中间表示」， 正文实际是 0 号 Header + 七段。按七段。

七、管线 ③ · 编译产物：机器给你到哪一步

产出 4 个文件：

文件 内容
{target_dir}/__init__.py ONTOLOGY 常量 + Object/Link 注册 + Function/Rule/Action handler + seed 桩
mappings/objects.yaml ← IR §6，对象 → 物理表 / 列 / 物化策略
cq/golden.yaml ← IR §7
plugin.yaml 清单

7.1 四类 NotImplementedError 的来源

它们不是 bug，是界线：

触发条件 生成物
declarative 规则 ✅ 函数体全自动写完，不 raise
function-backed 规则 装饰器 + docstring + TODO(FDE) + 可用方法提示 + raise
每一个 Action handler stage_write 骨架注释 + set_confidence + raise
Function 口径不明 TODO(FDE)：实现派生量计算（只读，无副作用）+ raise

机器负责把结构立起来，人负责把判断填进去。

⭐ 康养项目那个项目留了 121 处 NotImplementedError。 这不是没做完，是明确划出了「机器到此为止、人从这里接手」的界线。

一个不敢留 NotImplementedError 的 FDE，会让模型把它猜的业务规则写成看起来能跑的代码——那才是灾难。

⭐ 别只讲坏消息：declarative 规则是唯一被全自动写完函数体的—— 真实项目里 declarative 规则往往占一半以上，这一半是白捡的。

八、⭐ 四个命令，一个强制停点

业务分析 → ontology-map（IR 七段）→ ⏸ 你审 IR → ontology-compile（插件骨架）
        → FDE 收尾（填函数体 / 回写 / 参考数据）→ ontology-validate（结构 / 治理 / CQ）
命令 干什么 强制人审
/studio-ontology:map {id} 业务分析 → 七段 IR 无
/studio-ontology:compile {id} IR → 插件骨架 无（已存在不覆盖，只告警）
/studio-ontology:validate {id} 四段校验 无（只诊断）
/studio-ontology:model {id} map → ⏸ 你审 IR → compile ★ 唯一有

8.1 ⏸ 停下来的时候，审四项

  1. 对象边界——是不是真的独立实体
  2. edge_semantics——多跳推理停在哪
  3. 规则的 severity · backing · 出处
  4. Action 的 writes · HIL

IR 是 Markdown，你可以直接改文件再继续。

8.2 ⭐ 那个 ⏸ 为什么必须存在

有人会问：既然 LLM 能生成 IR，为什么还要人审一遍？

因为本体是治理的锚点——一个没有人签字的治理基准，不是治理基准。

而且它不是一句口号，是流水线上一个绕不过去的停点： 它被做成了工程约束，不是文档里的一句"建议人工复核"。

这和 S2 讲的 「安全的默认值，比安全的文档有用一百倍」 是同一个思路。

8.3 另一处"权限即职责"的设计

skill allowed-tools 说明
ontology-map Read, Write, Glob, Grep, Agent 有 Agent → 能调专家做头脑风暴与复核
ontology-compile Read, Write, Glob, Grep 无 Agent → 纯机械翻译，不许自由发挥
ontology-validate Read, Glob, Grep, Bash 无 Write → 物理上不可能改你的插件；有 Bash → 能跑引擎

校验器无权改代码——纪律靠机制不靠自觉的又一个干净例子。 校验器如果能改代码，早晚有人会让它"顺手修一下"——那时候它就不是校验器了。

九、⭐ 诚实边界

studio-ontology 的 README 里有一节，标题就叫「诚实边界」：

编译只保证结构对、五要素齐、可 import。 function-backed 规则函数体、Action 回写逻辑、参考数据是 FDE 的手艺活， 生成骨架 + TODO(FDE)，由人在 clife-onto-engine 仓库内手填—— 这正是 FDE 不可替代之处，不假装全自动。

9.1 TODO(FDE) 这个做法值得单独说

它把"这里需要人"从一句原则，变成了代码里一个可以被 grep 出来的标记。

又是 S2 第十一章那条方法论： 重要但会被慢慢磨掉的东西，要想办法让它能被机器检查。 "哪些地方还没人填" → grep TODO(FDE)。

9.2 ⚠️ 但这里要分清两件事，否则就是自我美化

设计上的克制 核心语义决策留给人签字——这是主动选择，值得讲。
能力上的边界 function 体、Action 回写现在确实生成不了——这是做不到，不是不想做。

两件事在产品声明里写成了一句话，在客户面前要分开讲。

说"我们刻意把核心语义决策留给人"——没错，这是真的，而且值得讲。 但如果客户追问"那你们能不能生成 function 规则体"， 答"目前生成不了"，别答"我们认为不该生成"。

把做不到包装成克制，是这一行最容易犯、也最伤信任的错。

9.3 客户问「你们是不是用 AI 自动建模」

标准答案：

「AI 出初稿，业务专家签字。我们不接受一个没有人负责的本体。」

这句话既诚实，又恰恰是我们比"全自动"竞品更值得信任的地方。 在这个赛道，承认边界是竞争优势，不是弱点。

十、⭐ IR 七段 → SPI 七槽位：两个结构性缺口

S2 第三章（§3.4）给了现象（七槽位只覆盖五格）。这一章给结构性原因。

IR 段 落进 SPI 槽位 自动化程度
§1 Objects · §2 Links ① Schema 包 ✅ 全自动
§6 Mapping Hints ② 映射注册表 ✅ 全自动
§3 Functions · §4 Rules ③ Function / Rule ⚠️ 只出骨架（declarative 除外）
§5 Actions ④ Action handlers ⚠️ 只出骨架
§7 CQ ⑦ CQ 验收集 ⚠️ 格式与引擎不匹配
—— 没有对应的 IR 段 —— ⑤ 记忆词典 / 术语表 ❌ 完全不生成
—— 没有对应的 IR 段 —— ⑥ Agent 角色 + HIL 声明 ❌ 完全不生成

不是编译器没实现，是 IR 里压根没有这两段。

10.1 这个区分决定你怎么答客户

如果是 该怎么答
编译器没实现 "这是个待补的功能"　← 那是欠债
IR 里没有这一段 "这两块目前是人工产出的，不在自动化管线里"　← 那是设计边界，是坦荡

说错了，一个变成欠债，一个是坦荡。 客户听到"待补的功能"会记在风险清单上； 听到"不在自动化管线里、是人工产出"——那是一个清晰的交付边界。

「七段 IR 覆盖了七槽位中的五格」—— 这句话本身就是一个诚实、精确、可交付的技术回答，学员应该能原样说给客户听。

10.2 ⑦ CQ 那一行的细节（第五课会踩到）

编译产 cq/golden.yaml，但引擎只认 cq.py 的 CQ_SUITE， 全仓没有任何代码读那个 YAML。 → 第五课收尾 6 项里就有这一项。

十一、⭐ 验收标准：五要素同构

架构图右下角那个框，最后一行小字就是建模端的验收标准：

产物与手写 plugins/grass 五要素同构。

编出来的东西，要和人手写的长得一样。

11.1 为什么这条标准立得住

plugins/grass 是手写的、跑通的、被真 Qwen 打过的—— S2 第十一·补章那六步跑的就是它（碱茅在巴彦淖尔是乡土、在锡林郭勒不是，那条规则就在 grass 里）。

拿一个已经被证明能跑的东西当靶子，比任何"生成质量评分"都硬。

验收一个生成器最难的地方是"定义什么叫好"。 这里的做法很聪明：不定义"好"，定义"和那个已经被证明能跑的东西一样"。

11.2 它验的到底是什么

不是"代码写得好不好"，是结构齐不齐、契约对不对—— 五要素都在吗？注册方式一致吗？能被内核 import 吗？

这正是 S2 说的：内核靠 SPI 契约吃饭。

11.3 对 FDE 的用处

已经跑通的实证：本插件已用真草业材料跑通，产物与手写的 plugins/grass 五要素同构。

⭐ 第五课你编完插件卡住的时候，不要猜——去对照 plugins/grass。 它是这条管线上唯一的标准答案。

十二、⚠️ 两仓红线：产物落到哪里

建模仓（astra-studio 工作区）             运行时仓（clife-onto-engine）
studio/changes/{id}/ontology-map.md  →  plugins/{ontology_id}/  ← 本体定义/规则/动作（行业级，租户无关）
                                        tenants/{tenant}/       ← 该租户的实例与参考数据
规矩 为什么
是 plugins/{ontology_id}/，不是 plugins/{tenant}/ grass 与 chili 在同一进程同一 registry 里按 namespace 共存
名录数据、实例数据属于 tenants/ 它们是租户层的东西，不是行业层
IR 文件不在运行时仓 跨仓复制过去

你把名录数据写进 plugins/，违反的不是习惯，是红线。

这就是 S2 讲的三层切分 Kernel / Plugin / Tenant 在目录上的物理体现—— 判缝准则的第三档（"具体数字 → 租户"）在这里变成了两个不同的文件夹。

⚠️ 这是第五课最高频的一个错： 你编完插件，手里有一堆名录数据（哪些草种是乡土的、阈值是多少）。 最自然的动作是把它们塞进插件里——错。那是租户数据。

十三、行业参照（⚠️ 二档来源）

⚠️ 来源：中国信通院 / CCSA TC601 数标委对 Palantir 2026 AIPCon 的公开分析。 二手来源，非 Palantir 官方文档。

他们的观察 我们这边的对应
传统本体建模：6–12 个月周期、8–15 人专职团队、无法跨板块复用 这三个数字是行业公开的成本基线——客户觉得"不就是画个数据模型吗"的时候拿出来
把建模从定制项目变成标准化工程能力 正是 studio-ontology 在做的事（第三章三条动机）
LLM 是「建模加速器」而非「建模替代者」，核心语义决策人工最终审核 我们把它做成了流水线上一个绕不过去的 ⏸（第八章）+ 代码里的 TODO(FDE)（第九章）

第三行是这一节存在的全部理由： 一个市值千亿的产品把它写成产品原则，我们把它做成了流水线上的一个停点。 同一条工程判断，在两个产品里各自长了出来。这比我们自己说自己对有力得多。

第五课要你做的事：

用 /studio-ontology:model 跑通 map → ⏸ 审 IR → compile， 亲手填掉机器帮不了的 6 项收尾，然后： ① 落位 plugins/{ontology_id}/ → ② 补齐 → ③ smoke_cq 绿 → ④ /viz/{你的 id}

你交的不是模型文档，是一个能跑的插件。

这个工作坊里，唯一一个「交付物是系统不是报告」真正兑现的地方，就是第五课。

十五、自查

1. 建模端的产物落到运行时仓的哪个目录？为什么不是 plugins/{tenant}/？名录数据该放哪？

2. 为什么不直接手写插件？说出三条理由里最重要的那条，并解释为什么。

3. 「你在客户那儿做的事件风暴，不是白做的中间品」——这句话什么意思？

4. IR 七段里哪一段标着「★ FDE 核心」？为什么是它？

5. 四个命令里只有一个有强制停点，是哪个？那个 ⏸ 为什么必须存在？

6. 客户问「你们这个建模工具能不能自动生成规则的实现代码」。 用「设计上的克制 vs 能力上的边界」这个区分来答。

7. IR 有七段，SPI 有七个槽位，但编译只覆盖了五格。 为什么这是"结构性缺口"而不是"编译器没实现"？这个区分对你答客户有什么影响？

8. 建模端的验收标准是什么？为什么这条标准立得住？

参考答案

1. 落到 plugins/{ontology_id}/。 不是 {tenant} 是因为 grass 与 chili 在同一进程同一 registry 里按 namespace 共存—— 插件是按行业组织的，不是按客户组织的。 名录数据、实例数据属于 tenants/{tenant}/。 把名录数据写进 plugins/，违反的不是习惯，是红线（S2 三层切分在目录上的物理体现）。

2. 最重要的是 ② 业务专家看不懂 Python。 因为规则必须有 source，而出处只能由领域专家提供； 他看不懂 @spi.rule 装饰器，所以中间必须有一份他能读、能改、能签字的东西——那就是 IR。 （另两条：手写解决不了"写代码之前"那段最贵的工作；手写在第二、三个行业会结构漂， 而结构不一致，"换行业零改内核"就是空话。）

3. 因为 studio-ontology 不发明新建模语言，它做 DDD → 五要素的翻译： 聚合→Object、上下文集成→Link、命令/领域事件→Action、读模型/KPI→Function、不变式/策略→Rule、限界上下文→namespace。 所以你在现场做的事件风暴是编译器的输入，你的每一小时都落到了产物上。

4. §4 Rules。 因为对象和关系业务方大多说得清，规则说不清—— 「大家都知道但没人写下来」的东西全在这一段。 （第五课的「规则三问」就是为它准备的。）

5. /studio-ontology:model。 那个 ⏸ 必须存在，因为本体是治理的锚点——一个没有人签字的治理基准，不是治理基准。 而且它被做成了工程约束，不是文档里一句"建议人工复核"—— 安全的默认值比安全的文档有用一百倍。 停下来审四项：对象边界 / edge_semantics / 规则的 severity·backing·出处 / Action 的 writes·HIL。

6. 分两句答： ① declarative 规则能全自动生成函数体——只看入参就能判的，机器写完（真实项目里往往占一半以上）。 ② function-backed 规则、Action 回写只出骨架 + TODO(FDE)——这是能力边界，目前生成不了。 ⚠️ 不要把 ② 说成"我们刻意留给人"。 "核心语义决策留给人签字"是设计上的克制（真的，值得讲）； "function 体生成不了"是能力上的边界（也真的，别包装）。 把做不到包装成克制，是这一行最伤信任的错。

7. 因为 IR 里压根没有"记忆词典"和"Agent 角色"这两段—— 不是编译器读了却没生成，是输入契约里就没有这两项。 影响：如果是编译器没实现，该说"这是个待补的功能"——那是欠债，客户会记在风险清单上； 如果是 IR 里没有，该说"这两块目前是人工产出的，不在自动化管线里"——那是设计边界，是坦荡。

8. 产物与手写 plugins/grass 五要素同构。 立得住是因为 grass 是手写的、跑通的、被真 Qwen 打过的—— 拿一个已经被证明能跑的东西当靶子，比任何"生成质量评分"都硬。 它验的不是"代码写得好不好"，是结构齐不齐、契约对不对（五要素都在吗？注册方式一致吗？能 import 吗？）—— 因为内核靠 SPI 契约吃饭。

DDD ↔︎ 五要素：聚合→Object ｜ 上下文集成→Link（边语义）｜ 命令/事件→Action（HIL）｜ 读模型/KPI→Function ｜ 不变式/策略→Rule（source/citations）｜ 限界上下文→namespace

IR 七段 → SPI 七槽位：覆盖五格 ①② ✅ 全自动 ｜ ③④ ⚠️ 只出骨架（declarative 除外，全自动）｜ ⑦ ⚠️ 格式不匹配 ⑤ 记忆词典 / ⑥ Agent 角色 ❌ —— IR 里没有对应段

A. 四层架构

应用层        面向业务端的成品与工作流 · 按量计费
AIP 编排层    Agent 运行时 · 确定性优先
⭐ 本体层     业务语义与治理的锚点   ← 2026 从"平台内置能力"跃升为产品线战略锚点
Foundry      数据底座：接入 / 治理 / 血缘

对照 S1 讲的四层（L1 源系统 / L2 数仓 / L3 业务本体平台 / L4 消费层）——是同一张图。

B. 确定性优先（Deterministic Agent Runtime）

交给确定性逻辑 才调大模型
交易 · 库存 · 调度 · 权限判定 · 规则校验 意图识别 · 异常研判 · 非结构化理解

在一个以 AI 为卖点的产品里，核心链路刻意不用 AI。 理由与 S1 一致：LLM 是协处理器（不可信），不是 CPU（可信）； 把交易逻辑交给模型，等于把一个需要 100% 正确的东西交给一个 95% 正确的组件—— 而那 5% 不是随机分布的，它集中在罕见、复杂、高价值的场景。

对照 S2：Action 内核六步全是确定性的，intent/compiler.py 只负责把自然语言编译成 Action 申请。

C. 其他三条架构取舍

维度 做法 对我们的参考
治理 对象级 + 字段级权限沿本体继承，Agent 和人走同一套 S2 的 authz.py 在内核、guard 阶段生效——同一条思路
供给 不迁数据，Snowflake / Databricks / Oracle / SAP 经标准 API 对接 S2 的「遥测读只产计划不当 TSDB」是同一姿态
消费 按量计费（AIP 实操频次 / 智能体调用量），弱化席位订阅 敢转按量制，说明产品相信自己会被高频使用

D. 五阶段交付方法论

阶段 名称 周期 产出
零 对齐 — 场景选定、成功标准、数据可达性确认

Bootcamp（"带资进组"）：客户带真实数据和真实场景来，1–5 天出一个能跑的东西。

Day 干什么

E. FDE 角色与飞轮

三栖 = 销售 + 产品 + 工程——不是三个技能会一点，是在客户现场同时承担这三个职责 （因为 Bootcamp 只有 5 天，没时间做"工程师→产品→销售"的往返）。

维度 传统咨询 FDE
交付物 报告 可运行的系统 ← 根
项目结束 退出 持续运营
经验沉淀在 人（顾问离职就带走） 平台
收入 一次性 长期订阅

这四条互相支撑：交付系统 → 能持续运营 → 经验沉淀进平台 → 下个客户更快 → 订阅收入滚起来。 抽掉第一条，后面三条全塌。

飞轮：

do things that don't scale — at scale.　规模化地做那些无法规模化的事。

定制交付（贵、慢、不可复制）
     ↓  沉淀  ← 关键在这个箭头，它不会自动发生
标准能力（建模端工具、SPI、模板）
     ↓  复用
规模化（下一个客户更快、更便宜）
     ↓  释放出的人力
去做更多定制交付（进入更难的行业）

⭐ 对照 S2 第三章：Plugin SPI 七槽位，就是"沉淀"这个动作的工程形态。 它规定了"一次定制交付里，哪些东西必须以可复用的形式产出"。 没有 SPI，每个项目的产出就是一堆散落的代码，飞轮转不起来。
