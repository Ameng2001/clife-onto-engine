读完这一课，你应该能做到：

  • 说出能提什么，以及四档门槛各自的成本

一、为什么要回贡

不是为了做好人。

理由 说明
① 你的定制不再是孤儿 留在自己项目里的专家，下次工具大改可能就不兼容了。进了上游，它跟着工具一起演进
② 别人替你维护 合并之后，工具作者会在重构时顺手改它。你不合并，每次升级都得自己适配
③ 你踩的坑别人不用再踩 你在第五课发现的那六处「文档说 A、代码是 B」——提回去，后面所有人少踩六次
④ 这是 FDE 的信用 一个被合并的 PR，比简历上写十行"精通 XX"有说服力

你在项目里踩过的坑，提回去就成了别人的护栏。

二、能提什么：四档门槛

档 提什么 成本 被接受的可能
① 一处文档更正 / 一个 issue 十分钟 最高——事实清楚，无争议
② 一个行业专家 agents/xxx-expert.md 半小时 高——出厂就有儿童营养、老年康复，它本来就预期按行业扩充
③ 一个映射包 / 参考数据 半天 中——如 fund-review 只带了一个地方的预算标准映射包，换个地方就要一份新的
④ 一个完整插件 数天起 看质量——像 fund-review 那样的垂直插件

⭐ 从第 ① 档开始。 提 PR 不一定要提一整个插件—— 一处文档更正、一个专家 .md，都是贡献。

三、⚠️ 一个诚实的现状

这个仓目前没有 CONTRIBUTING.md，也没有 .github/ 目录。

所以没有官方明文告诉你怎么提。 规范只能从 CLAUDE.md / AGENTS.md 反推。

⭐ 而"补一份 CONTRIBUTING.md"，正好就是你能提的第一个 PR—— 门槛最低、最容易被接受，而且你刚上完 A1/A2，你比大多数人更清楚该写什么。

3.1 从代码约定反推出来的三条

① 照 Plugin Structure 摆文件

plugin-name/
├── .claude-plugin/plugin.json   # 清单（name / description / version）
├── commands/                    # 斜杠命令（.md）
├── skills/{skill-name}/SKILL.md
├── agents/                      # 子智能体角色定义
├── hooks/                       # 事件驱动自动化
├── scripts/                     # Python 辅助脚本
├── references/                  # 按需加载的参考文档
└── templates/                   # 脚手架模板

摆错位置的 PR，reviewer 第一眼就会打回。

② 守住 Design Principles 里最容易违反的几条

11 条里，提 PR 时最容易踩的是这四条：

# 原则 违反的样子
1 设计与实现分离 把 SKILL.md 也放进 studio/changes/ —— 两份，迟早不一致
5 标准 Claude Code 插件规范，无私有扩展 自己发明一个字段、一个目录约定
6 平台中立产出 生成的 SKILL.md 里写死 Claude 特有的引用
7 专家存 studio/agents/（git 跟踪、团队共享） 把专家塞进插件目录 —— 下次更新被覆盖

③ 本地测通再提

claude --plugin-dir ./studio-core --plugin-dir ./你改的插件
  • 改 SKILL.md 立刻生效，不用发版
  • 用 /plugin:command-name 测命令
  • skill 会在描述匹配用户意图时自动触发

⚠️ 别提没跑过的东西。

这是所有开源项目最基本的一条，也是最常被违反的一条。

四、提 PR 的动作

4.1 ⚠️ 本课走两段式：你提到内部 fork，讲师统一转提上游

你今天不直接向公开上游仓提 PR。

第一段（你做，课上）
  内部 fork → 建分支 → 改 → 本地 --plugin-dir 测通 → commit → push
  → 向【内部 fork 的 main】开 PR          ← 你的交付到此为止

第二段（讲师做，课后）
  复核 + 脱敏检查 → 从内部 fork 向【公开上游】统一转提
  → 上游 PR 链接回传给你

内部 fork 的地址由讲师在开课前给出（T-1 天通知里）。不要自己 fork 到个人账号再直提上游。

为什么加这一段：

① 脱敏是不可逆的 上游是公开仓库。客户名、商务数字一旦推上去，删掉了也还在 git 历史和各种镜像里。多一道人工复核，成本很低
② 你的第一个 PR 不该用来试错 内部 fork 里可以随便改、随便重开。练手的成本降到零
③ 讲师能合并同类项 六个人可能提了同一处文档错。一起转提比六个重复 PR 好看得多，对上游也更友好

⚠️ 这不是"你的 PR 不算数"。 转提时讲师会在上游 PR 描述里写明原作者， 上游合并后的链接会回传给你——那才是你要收进简历的那个链接。

4.2 流程细节

fork（用内部 fork，不是个人 fork）
  → 建分支
  → 改
  → 本地 --plugin-dir 测通      ← 这一步不能省，讲师转提时不会替你测
  → commit → push
  → 向内部 fork 的 main 开 PR

4.3 一个好 PR 描述包含什么

段 写什么
改了什么 一句话
为什么 ⭐ 最重要的一段——你在什么真实场景下需要它
怎么验证的 你跑了什么、看到了什么
影响面 动了哪些文件；会不会影响现有行为

⭐ 「为什么」那一段决定 PR 的命运。

「加了一个养老照护专家」—— reviewer 不知道该不该收。 「我们在做养老机构的项目，内置的 product-manager 画出来的画像里把『助餐核销』和『膳食服务』混成一件事，业务方一眼就说不对。这个专家专门挑这类错」—— 一看就知道该收。

4.4 提之前的三条自查

  • 本地 --plugin-dir 跑过了吗？
  • 文件位置符合 Plugin Structure 吗？
  • 有没有私有扩展 / 平台绑定？（Design Principles 第 5、6 条）

五、实操（40′）

今天不是模拟，是真的提。

序 做什么 时长
1 盘素材——从第二章那张"你已经有的"表里挑一个 5′
2 克隆内部 fork（不是个人 fork）+ 建分支 5′
3 改 / 加文件（照 Plugin Structure 摆） 10′
4 本地 --plugin-dir 测通 10′

如果时间不够 / 素材不成熟：在内部 fork 提一个 issue 也算完成。 把你在第五课发现的一处「文档说 A、代码是 B」写清楚提上去——十分钟，而且一定被接受。

⚠️ 提交前自己先过一遍脱敏：不带客户名、不带商务数字。 讲师转提时会再查一次，但第一道关是你——上游是公开仓库，推上去就删不干净了。

checkout 硬指标

维度 达标 警示
真的提了 有内部 fork 上的 PR / issue 链接 只在本地改了没提；或直接提到了公开上游

六、被拒了怎么办

很正常，而且大多数时候不是因为你写得差。

常见原因 怎么处理
范围不合（这个功能作者想放别处） 问清楚该放哪，改了再提
太特化（只对你一家有用） 改成可配置的，或转成文档/示例
没测 补测试证据
没人看 隔一两周礼貌地 ping 一次；别连着催

⭐ 被拒的 PR 不是白写的——它至少让你把那件事想清楚了一遍， 而且你的分支还在，下个项目接着用。

七、自查

1. 回贡上游对你自己有什么好处？说出至少两条。

2. 四档门槛里，你现在手上已经有哪一档的素材？

3. 这个仓的贡献规范写在哪？⚠️ 这是个陷阱题。

4. 提 PR 前必须自查的三件事是什么？

5. 一个好的 PR 描述里，哪一段决定它的命运？为什么？

6. PR 被拒了，最常见的原因是什么？

7. 本课的 PR 提到哪里？为什么不直接提到公开上游？

参考答案

1.（任两条）① 你的定制不再是孤儿——进了上游会跟着工具一起演进，不用每次升级自己适配； ② 别人替你维护；③ 你踩的坑别人不用再踩；④ 一个被合并的 PR，比简历上十行"精通 XX"有说服力。

2. 至少两档：① 第五课发现的六处「文档说 A、代码是 B」——那是六个现成的 issue； ② A1 写的那个行业专家 .md。 ⭐ 别去想"我能贡献什么"，先盘你已经有的。

3. ⚠️ 陷阱题——它没写在任何地方。 该仓目前没有 CONTRIBUTING.md，也没有 .github/。 规范只能从 CLAUDE.md / AGENTS.md 反推：照 Plugin Structure 摆文件 · 守 Design Principles · 本地测通。 而"补一份 CONTRIBUTING.md"正好是你能提的第一个 PR。

4. ① 本地 --plugin-dir 跑过了吗（⚠️ 别提没跑过的东西） ② 文件位置符合 Plugin Structure 吗 ③ 有没有私有扩展 / 平台绑定（Design Principles 第 5、6 条）

5. 「为什么」那一段。 因为 reviewer 判断的不是"这段代码写得好不好"，是"这个东西该不该进这个项目"—— 而只有你说清了真实场景，他才判断得了。 「加了一个养老照护专家」他不知道该不该收； 「我们做养老项目，内置 product-manager 把『助餐核销』和『膳食服务』混成一件事，业务方一眼说不对」——一看就知道该收。

6. 范围不合（作者想放别处）和太特化（只对你一家有用）。 都不是"写得差"。前者问清该放哪再提；后者改成可配置的，或转成文档 / 示例。 ⭐ 被拒的 PR 不是白写的——你把那件事想清楚了一遍，分支还在，下个项目接着用。

7. 提到内部 fork，讲师复核后统一转提公开上游。 三条理由：① 脱敏不可逆——上游是公开仓，客户名 / 商务数字推上去，删了也还在 git 历史里； ② 第一个 PR 不该用来试错——内部 fork 里可以随便重开； ③ 讲师能合并同类项——六个人可能提了同一处文档错。 ⚠️ 这不是"你的 PR 不算数"：转提时会写明原作者，上游合并后的链接回传给你。
