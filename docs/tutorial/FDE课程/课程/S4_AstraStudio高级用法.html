一、四级台阶

级 动作 说明
一级 用内置的 跑 /studio-insight:persona-insight，用它自带的产品经理、架构师……
L3 / L4 / L5 都停在这一级。绝大多数人也停在这一级。
二级 自定义专家 不改一行代码，加一个 .md 文件，让它带上你这个行业的判断（第二章）
三级 写自己的插件 像 fund-review 那样：40 个脚本 + 4 个 skill + 2 个对抗 agent（第三~五章）
四级 回贡上游 把插件 / 专家 / 修复提 PR 进 astra-studio-plugins（第六章）

⭐ 二级的性价比高得离谱：一个 .md 文件，不改代码、不发版，而且跟着 git 走、全团队共享。 今天如果只带走一件事，带走这个。

工具不改造，你就只能做它预设的那类项目。

二、二级台阶：自定义智能体

2.1 ⭐ 查找顺序就是设计

1. 项目级   studio/agents/{name}.md      ← 你团队的定制专家（git 跟踪）
2. 内置     插件自带 agents/{name}.md    ← studio-insight 出厂的 11 个

同名覆盖：项目级赢。

这不是一个查找细节，是一条产品决策： 定制点被放在用户项目的 git 仓库里，而不是插件配置里。

意味着——你的专家跟着项目走、跟着团队走，换台机器 clone 下来就在。

这一条规则给了你三种改法，都不用碰插件源码：

改法 什么时候用
① 加一个新专家 行业里有个角色内置没有 → 写一个新 .md
② 覆盖一个内置的 内置的产品经理说的话不像你们公司 → 同名写一份，换成你们的术语与流程
③ 从模板起手 抄 _domain-expert-template.md 改

⭐ 第 ② 种最容易被忽略。 很多人以为只能加新的—— 其实你可以同名覆盖内置的产品经理。内置那个是通用的，你们的是对的。

出厂 11 个专家 + 1 个模板：

类别 专家
通用 6 个 产品经理 · 架构师 · UX 研究 · 数据分析 · 合规官 · 运营经理
健康域 4 个 儿童营养 · 儿童运动 · 老年营养 · 老年康复运动
美护域 1 个 女性护肤

⭐ 注意出厂专家里有"儿童营养""老年康复运动"这种细分角色—— 这说明它本来就预期你按行业往里加。 你的行业专家没在里面，不是遗漏，是等你写。

创建命令：/studio-core:create-expert

2.2 动态专家发现：它是怎么被找到并用上的

studio-insight 的 6 个 skill 全部使用动态专家发现。以 persona-insight 为例，每次运行做五步：

# 做什么
1 主角色必载——product-manager.md（由它主导画像产出）
2 扫项目级——Glob studio/agents/*.md，把团队自定义的全部载入
3 扫内置——跳过已从项目级载入的同名（覆盖就发生在这一步）
4 按相关性选 1–3 个——拿专家的 ## Your Domain 段与本次主题比对
5 跳过模板——_domain-expert-template.md 只用于造专家，不参与咨询

2.3 ⭐ 关键：专家是复核者，不是生成者

主角色先产出初稿，专家在 Expert Review 步骤逐个复核纠错。

给每个专家的指令原文是：

"从你的领域专长审这份画像。标出不正确、过度简化、遗漏的地方； 注意我们漏掉的领域痛点、影响这个画像的现实约束、以及从业者实际会用的术语。"

一个专家的价值，在于它能挑出你没想到的错，而不是替你写。

这决定了你写专家时该写什么： 不是写它"懂什么"，是写它"会挑什么错"。

2.4 什么时候值得造一个专家

✅ 该造 ❌ 不该造
这个行业有只有从业者才知道的坑，通用角色挑不出来 只是想让输出"更专业一点"——那是提示词问题，不是专家问题
有成文的标准 / 规程 / 禁忌可以写进它的判断 一次性项目，下次用不到
同一类错在多个项目里反复出现 你自己也说不清它该挑什么错——说不清就写不出 ## Your Domain
内置角色的术语和你们不一样 → 同名覆盖 已有专家改两句就够用 → 覆盖，别新建

⚠️ 别给每个角色都造一个专家。 第 4 步只选 1–3 个——专家多了会互相稀释。

2.5 ⚠️ 最常见的失效模式

## Your Domain 写得含糊，你的专家永远不会被选中。

因为第 4 步的相关性匹配就靠这一段。

而且它失效得悄无声息：不报错、不警告，它只是从来没被载入过， 你以为专家在起作用，其实一次都没跑。

这和 S2 讲的**"记忆塞满不报错，只是慢慢变笨"**是同一类故障：静默失效。 这类故障最贵，因为你不会去查一个"看起来正常"的东西。

三、三级台阶：fund-review 是什么

干什么 政府 IT 采购的报价优化 + 财评预审——按地方预算标准出优化建议、重写报价表、产带引用的评分报告
规模 54 个文件：40 个脚本 · 4 个 skill · 2 个 agent · 4 个命令 · references/ 映射包
身份 ⭐ 不是 studio 工具链的一部分，是工具链产出的领域插件——只是搭同一个 marketplace 发布
trait stateful → 会话落在用户项目的 .fund-review/{session-id}/，不在 studio/ 下
依赖 唯一需要第三方包的插件（openpyxl / python-docx）——所有 studio-* 都不需要

它的设计文档不在这个仓，在单独的 fund-review-plugins 仓的 studio/changes/fund-review/—— 这正是"设计与实现分离"的实例（第五章）。

它证明的不是"这个插件多厉害"，是"这套工具链能造出这种量级的东西"。

你第五课产出的本体插件、以后要做的行业插件——都是这个身份。fund-review 就是你们的未来样本。

四、⭐ 红蓝对抗，以及它为什么不是重点

4.1 两个 agent，站在对立面

蓝方 quote-optimizer 红方 financial-reviewer
人设 "资深售前方案架构师，深谙政府 IT 采购报价" "政府财评专家"
立场 站投标方，想让报价过审 站评审方，逐条质询
干什么 拿扫描器发现 + 定价指引 + 标准条款索引，做筛选、排序、解释 对每条 warn/fail 逐条挑战，要求引用页码
原话 「同时说 投标商务 和 财评专家 两种语言」 「绝不批准一个你无法在标准公式里追溯出来的数字」

4.2 ⭐ 最见功力的一处：两个 agent 都没有 Write 权限

allowed-tools: Read, Bash, Glob
scope: runtime

它们只能查证与质询，不能改报价表。 真正改表的是确定性脚本，改什么由人批准的方案决定。

这是**「权限即职责」的又一次出现—— 第五课讲过 ontology-validate 没有 Write，所以它物理上不可能**替你抹平不合格的地方。 这里同理：评审方要是能改报价，它就不是评审方了。

什么时候值得设红蓝：

当一件事有明确的对立立场，而且两边都有专业性的时候。 报价 vs 财评、开发 vs 安全、业务 vs 合规。 不是所有任务都需要，别滥用——对抗的成本是双倍的推理。

4.3 ⭐⭐ 但红蓝对抗不是这个插件的重点

14 个确定性扫描器  →  findings.json  →  agent 筛选·排序·解释  →  人批准方案  →  确定性脚本改表
   scan_*.py

数一下构成：40 个脚本 · 4 个 skill · 2 个 agent。

能确定性算的，全写成了脚本；agent 只处理"需要判断"的那一段。

交给确定性脚本 才交给 agent
科目对齐 · 语义重叠 · 人工定价 · 工作日 · 冗余 · 品牌型号 · 完整性 · 证据 · 商务条款……（14 个扫描器） 从一堆发现里挑出真正值得提的、排优先级、用标准条款解释为什么
解析报价表 · 解析标准 · 公式引擎 · 重写表格 · 生成报告与交付件 逐条质询、要求引用页码

这就是 S2/S3 讲的「确定性优先」，在插件层的活体。

S3 讲 Deterministic Agent Runtime 时说：交易、库存、调度交确定性逻辑，只有意图识别和异常研判调大模型。 fund-review 就是这条原则在一个真实插件里的样子——扫描是确定的，判断才是模型的。

⭐ 给你的可迁移判据：

这一步能不能写成脚本？能，就别交给模型。 模型是用来处理"规则说不清但人能判断"那一段的，不是用来做你懒得写的计算。

顺带一条成本账：确定性脚本跑一万次成本不变，agent 跑一万次要付一万次的钱。

五、进阶模型：Traits · 工作区 · 迭代

5.1 Plugin Traits：观察，不是配置

skill-design 阶段会从规划产物里**"看出"**插件的横切特征，这些特征驱动 spec-generate 生成不同的脚手架：

Trait 意思 会自动生成什么
stateful 跨会话管理项目数据 init-workspace skill + 运行时配置/状态模板（fund-review 的 .fund-review/ 就是靠它）
hil-gated 流程里有人工审批关口 相关 SKILL.md 里的 ## Approval Gate 段
kb-dependent 需要 LLM 之外的领域知识 KB 集成说明；可能配一个知识库插件
multi-pipeline 2 个以上独立业务流 按管线分别生成编排命令
expert-scoped 运行时需要与规划期不同的专家 agents/ 里的运行时 agent 定义（那两个红蓝 agent 就是这么来的）

Traits are observations, not configuration.

你不"配置" trait，是工具从你已经写下的东西里推断出来的。 没检测到 trait 的插件，走标准生成路径，不多不少。

这背后是一个设计立场：不给你一堆开关让你勾，而是从产物里推断—— 少一层配置，就少一层"配错了但没人发现"。

⭐ fund-review 同时命中 stateful 和 expert-scoped—— 第三、四章看到的那两个特征，在这里找到了出处。

5.2 两级工作区 + 设计与实现分离

studio/changes/{plugin}/   ← 只放设计文档：brief.md · skill-map.md · status.json · plugin.json.draft
{target_dir}/              ← 只放实现：SKILL.md · commands/ · scripts/ · agents/

status.json 里的 target_dir 字段，是这两边唯一的连线。
域工作区 type: "domain" 插件工作区 type: "plugin"
装什么 event-storm.md · domain-map.md · personas/ journeys/ processes/ 只有设计文档
特点 可被多个插件共享 不含 SKILL.md 与 commands——那些在 target_dir；靠 domain 字段指回父域

为什么要这样切——单一真相源，不重复。

如果设计目录里也放一份 SKILL.md，它和实现里那份迟早不一致，而且你不知道该信哪份。

同一件东西只存在于一个地方——

这是这门课程反复讲的 B-5，在工具设计上的同一条判断。

⭐ 好的工具会替你守住纪律，而不是靠你自觉。

⭐ 域工作区可共享有实际价值：一次事件风暴产出的域图和画像可以喂给多个插件， 别每个插件重做一次业务分析。

5.3 迭代模型：初稿不是成品

plan → build-skills（产可跑的初稿）→ skill-creator 反复打磨（拿真实输入测）→ validate → promote（v0.1 → v0.2）
「Initial fill, not final build」 build-skills 产的是能跑的初稿，不是成品。指望它一次生成对，是用错了工具。
外循环 / 内循环分工 Astra Studio 管外循环（业务分析、领域建模、校验、发布）；单个 skill 的编写打磨交给官方 skill-creator
版本化 promote v0.1 → v0.2，设计文档快照进归档但仍保持活跃——下一轮迭代接着用，不是归档就冻结

这和第五课那 121 处 NotImplementedError 是同一个态度：机器立结构，人填判断。

本地开发（回去就能用）：

claude --plugin-dir ./studio-core --plugin-dir ./你的插件

改 SKILL.md 立刻生效，不用发版、不用装。这是三级台阶的入门动作。

六、四级台阶：回贡上游

6.1 能提什么（按门槛从低到高）

提什么 说明
一个行业专家 你写的 agents/xxx-expert.md——出厂那 11 个里有儿童营养、老年康复，说明它本来就预期按行业扩充
一个 bug 修复 / 文档更正 比如你在第五课发现的那几处「文档说 A、代码是 B」
一个映射包 fund-review 只带了一个地方的预算标准映射包，换个地方就要一份新的
一个完整插件 像 fund-review 那样的垂直插件

6.2 ⚠️ 一个诚实的现状

这个仓目前没有 CONTRIBUTING.md，也没有 .github/ 目录。

所以贡献规范只能从 CLAUDE.md / AGENTS.md 反推：

  1. 照 Plugin Structure 摆文件 
    plugin-name/
├── .claude-plugin/plugin.json   # 清单
├── commands/                    # 斜杠命令
├── skills/{skill-name}/SKILL.md
├── agents/                      # 子智能体角色定义
├── hooks/                       # 事件驱动自动化
├── scripts/                     # Python 辅助脚本
├── references/                  # 按需加载的参考文档
└── templates/                   # 脚手架模板
  2. 遵守 11 条 Design Principles（设计实现分离 · 插件优先 · git 跟踪工作区 · 标准 Claude Code 插件规范无私有扩展 · 平台中立产出 ……）
  3. 本地用 --plugin-dir 测通——别提没跑过的东西

⭐ 而"补一份 CONTRIBUTING.md"，本身就是你能提的第一个 PR。

6.3 降低心理门槛

提 PR 不一定要提一整个插件。 一个专家 .md、一处文档更正，都是贡献。

第五课你们发现的那六处「文档说 A、代码是 B」——那本身就是六个可以提的 issue。

你在项目里踩过的坑，提回去就成了别人的护栏。

八、自查

1. 自定义专家放哪、和内置的冲突时谁赢？为什么这么设计？

2. 专家在流程里是生成者还是复核者？这决定你写它时该写什么？

3. 自定义专家不报错但完全不起作用，最可能是什么原因？

4. fund-review 两个 agent 都没有 Write 权限，为什么？

5. 40 个脚本对 2 个 agent，这个比例说明什么？

6. 为什么设计文档和 SKILL.md 要物理分在两处？

参考答案

1. 放 studio/agents/{name}.md（用户项目里，git 跟踪）；同名时项目级赢。 这么设计是因为定制点应该跟着项目和团队走——换台机器 clone 下来就在，而不是散落在各人的插件配置里。 ⚠️ 答"放插件目录里"就错了——那样定制会在下次更新插件时被覆盖掉。

2. 复核者。 主角色（如 product-manager）先产出初稿，专家在 Expert Review 步骤逐个挑错： 标出不正确、过度简化、遗漏的地方。 所以写专家时要写的是"它会挑什么错"，不是"它懂什么"。 （一个专家的价值，在于它能挑出你没想到的错，而不是替你写。）

3. ## Your Domain 那一段写得太含糊——动态发现第 4 步的相关性匹配就靠它， 写不准就永远不会被选中。 ⚠️ 而且它不报错、不警告，只是从来没被载入过——你以为专家在起作用，其实一次都没跑。 这是静默失效，和 S2 讲的"记忆塞满只是慢慢变笨"同类。

4. 因为评审方要是能改报价，它就不是评审方了。 两个 agent 只能查证与质询（Read, Bash, Glob），改表交给确定性脚本，改什么由人批准的方案决定。 这是「权限即职责」——和第五课 ontology-validate 没有 Write 是同一个设计。

5. 说明能确定性算的都写成了脚本，agent 只处理需要判断的那一段。 14 个扫描器先出 findings.json，agent 才做筛选、排序、解释。 这就是 S2/S3 讲的"确定性优先"在插件层的活体。 （顺带：确定性脚本跑一万次成本不变，agent 跑一万次要付一万次的钱。）

6. 单一真相源。 如果设计目录里也放一份 SKILL.md，它和实现里那份迟早不一致，而且你不知道该信哪份。 studio/changes/ 只放设计文档，实现全在 target_dir/，靠 status.json 的 target_dir 字段连接。 这是这门课程反复讲的 B-5，在工具设计上的同一条判断——好的工具会替你守住纪律，而不是靠你自觉。
