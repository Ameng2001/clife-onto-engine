## 先立一条规矩

你做出能点开的界面会很兴奋，然后就开始拿它当"产品"演示。
**这是本课程唯一一条"路演一票警示"的红线。**

> **demo 跑通的是 UI，不是模型。**
> **把外壳当成"产品跑通了"去演示，就是骗客户。**

**所以本课的验收标准有两条，缺一不可**：

1. 做出 **3–6 屏可点开的原型**
2. **白纸黑字写清哪些是 Mock**

**你要交出什么**：3–6 屏可点开原型 + **一句诚实说明** + **Mock 清单**

## 一、三步流水线

```
/studio-design:design <截图路径>
  ① screenshot-to-pencil  → docs/design/screens.pen      ⏸ 你确认
  ② pencil-to-openspec    → openspec/changes/{id}/       ⏸ 你确认

```

**可从任意阶段切入**：给 `.png/.jpg` → 从①开始；给 `.pen` → 从②；给 change-id → 从③。

> ⚠️ 判定算法插件文档没写明（是按参数形态推断的）。
> **建议显式指定要跑哪一步，别赌它猜对。**

三个薄命令 `screenshot-to-pencil` / `pencil-to-openspec` / `openspec-to-code` 也可单独调用。

## 二、① 截图 → .pen

### .pen 到底是什么（实测澄清）

> **实测结论**：本地三份真实 `.pen`（含一份 1.7MB 的）**都是明文 UTF-8 JSON**，
> 顶层键 `children / variables / version`，`version: 2.10`，首节点 `type: frame`。
>
> 所以 **studio-design 把 .pen 当普通 JSON 直接读写的路子是成立的**。
> **插件的 `CLAUDE.md` 里"需要 Pencil MCP"的说法与本地实际文件不符。**

**结构四层**：`frame`（屏）→ 布局区 → 组件组 → `text` / `icon_font` / `ellipse`
**节点 ID**：5 位字母数字随机
**尺寸标准**：桌面 1440×900、移动 390×844

### 转换四步

| 步 | 做什么 |
|---|---|
| ① 视觉分解 | 整体布局 → 主区块 → 组件（导航/按钮四型/输入/卡片列表表格/模态下拉提示/图标）→ 字号字重层级 → 取色板 → 间距 → 尺寸 |
| ② **令牌抽取** | 背景 `$bg/$bg-sidebar/$bg-card/$bg-input/$bg-muted`；文本 `$text-primary/secondary/muted`；强调 `$accent/$destructive/$green/$blue/$red`；边框 `$border/$border-light` |
| ③ 结构生成 | 四层节点树；`layout`+`gap`+`padding`+`alignItems`；图标映射到 Lucide 名；**重复出现的模式标 `reusable: true`**，其他帧用 `type: "ref"` 引用 |
| ④ 输出 | 新建写完整 JSON；追加则 push frame 并 merge 令牌 |

**⏸ "已存在"交互**：若 `docs/design/` 下已有 `.pen`，会问你**"向其追加一个新 frame"还是"新建文件"**。
选追加时它会：**复用设计令牌 · 复用 `reusable:true` 的组件 · 确定下一帧序号 · 避免 ID 冲突**。

> ⭐ **教学点**：颜色**必须走 `$variable`，不许写死色值**——这就是为什么追加帧能自动统一风格。
>
> **令牌就是设计层的"口径单点"**，和第六课的 BRIEF 数字单点**是同一个思想**。

**它明确不做**：不生成代码 · 不建 OpenSpec · **不需要 Pencil 桌面端** · 不处理动效交互

## 三、② .pen → OpenSpec

产物落在 `openspec/changes/{change-id}/`：

| 文件 | 内容 |
|---|---|
| `proposal.md` | `## Why`（从帧名/内容反推设计意图）· `## What Changes`（每能力一条）· `## Impact` |
| `specs/{capability}/spec.md` | **每能力一份**，五类需求各写成 `### Requirement:`（用 SHALL/MUST）+ `#### Scenario:` + `- **WHEN** / **THEN** / **AND**` |
| `tasks.md` | 5 组带编号复选框：1.Setup · 2.Components · 3.Shared Components · 4.Styling · 5.Integration |
| `design.md` | **条件产出**：仅当涉及多能力 / 有共享架构决策 / 状态管理不显然时才生成 |

**五类需求**：①Layout 布局（含具体像素）②Component 组件（**占位符文案直接取自 .pen 的 content**）③State 状态 ④Navigation 导航（含 active 高亮）⑤Visual 视觉（深色主题令牌一致性）

### ⭐ 帧 → 能力的映射规则（本步最需要理解的一条）

| .pen 里 | → OpenSpec 里 |
|---|---|
| **同一页的不同状态帧**（"1. 空状态"、"1a. 下拉展开"、"1b. 已提交"） | **一个能力，多个 Scenario** |
| 不同页 | 不同能力 |
| `reusable` 组件 | 共享能力或横切需求 |

> 命名一律 kebab-case 动宾式：新增 `add-{capability}`、改版 `update-{capability}`。

> ⚠️ **已知不一致**：`openspec-guide.md` 规定 spec delta 要分 `## ADDED / MODIFIED / REMOVED Requirements` 三段，
> 但模板**没写这层包裹**。**按 guide 补上。**

## 四、③ OpenSpec → 代码

**读取顺序**：`proposal.md` → `tasks.md` → `design.md` → 全部 `specs/` → 扫项目（现有路由、已装 shadcn、tailwind 配置、package.json）→ **回读 .pen 取精确尺寸与颜色**

**⭐ 它不按 `tasks.md` 的原序做**，而是重排成固定 6 级实现顺序：

```
layouts → shared components → feature components → pages → routes → integration
```

**逐条 Scenario 心算校验 WHEN/THEN/AND**，不满足就补逻辑。最后**回写 `tasks.md`，把 `- [ ]` 改成 `- [x]`**。

**技术栈**：Next.js App Router · TanStack Query · Tailwind CSS 4 · shadcn/ui · Zustand · React 19 · LangGraph SDK
**已装 shadcn 组件 14 个**：Button/Input/Textarea/Card/Dialog/DropdownMenu/Sidebar/Tooltip/Tabs/Badge/Separator/ScrollArea/Avatar/Skeleton
**样式硬约束**：只用 Tailwind + `cn()`，**禁内联样式 / CSS Modules / styled-components**；禁 `useEffect+fetch` 取数；禁超 2 层 prop drilling

### ⭐ 缺信息时的兜底约定（这条直接关系诚实边界）

| 缺什么 | 它怎么做 |
|---|---|
| 缺 API | **mock 数据 + `TODO: connect to API`** |
| 缺状态管理 | 本地 useState + `TODO: lift state` |
| 缺鉴权 | `TODO: add auth guard` |
| 缺错误态 | 基础 error boundary + `TODO: improve error handling` |

> **这些 TODO 就是你的 Mock 清单。**
> 演示前把它们 grep 出来，就是一份现成的"哪些是假的"说明。
>
> **别删掉它们。删了 TODO 不等于实现了功能，只等于你看不见了。**

**一条硬纪律**：**未经询问不得新增 npm 依赖。**

> ⚠️ **目录前缀坑**：真实结构是 `frontend/src/app/...`，但生成的路径和扫描都用无前缀的 `app/`、`components/`。
> **落到你的仓库时要人工对齐前缀，工具不会自动加。**

## 五、⭐⭐ demo 可信度分级（本课的灵魂）

你会说"我们的 demo 是 Mock"。**但 Mock 不是一档。**

把这两个真实案例并排放：

| | **教育督导项目** | **草业大模型** |
|---|---|---|
| 页数 | **47 个 `page.tsx`** + 18 张成品截图 | **11 页**（README 标题写"13 个页面"，但其自身表格与代码都是 11） |
| AI | Mock（关键词路由） | Mock（`mock-ai.ts` 12.6KB，正则分支 + `setTimeout(550)` **假装思考延时**） |
| **数据** | **真的** —— `lib/data.ts` 用 `fs.readFileSync` 直接读 **79 园真实 CSV**（7 张表），还支持多城市切换 | **全仿真** —— `lib/data.ts` 写死 |
| **分级** | **壳假 · 数据真** | **壳假 · 数据也假** |

> **同样一句"这是 Mock demo"，含金量差一个量级。**

### 更值得学的一点

**草业项目的 `mock-ai.ts` 自己在文件头写着**：

> "Mock AI 引擎 — 关键词路由到五大智能体，注入仿真数据 / **真实落地替换为 草业项目本体大模型 + RAG 三通道**"

README 结尾也标了"数据为仿真演示数据"。

> **它的诚实标注做得很好，可以直接当正面教具。**

### ⚠️ 同时纠正一个常见误引

**辣椒没有 demo**（`demo-app/` 只有一个 0 字节 `.gitkeep`）。
**别顺口说成"三个农业案例都有 demo"。**

### 你的三档自评

| 档 | 你的 demo 是 | 演示时必须说 |
|---|---|---|
| **A** | 壳真 + 数据真 + 模型真 | （**还没有人到这一档**） |
| **B** | 壳假 + **数据真** | "界面是原型，**数据是客户真实数据**，AI 回答是预设的" |
| **C** | 壳假 + 数据假 | "这是交互外壳，**数据和 AI 回答都是演示用的**，不是模型跑通" |

> **说不出自己在哪一档 → 路演一票警示。**

## 六、实操（70′）

| 序 | 做什么 | 时长 |
|---|---|---|
| 1 | 准备输入：一张参考截图 / 手绘图 / 或直接描述屏 | 10′ |
| 2 | `screenshot-to-pencil`，⏸ 确认 .pen | 20′ |
| 3 | `pencil-to-openspec`，⏸ **看 spec 的 Scenario 写得对不对** | 15′ |
| 4 | `openspec-to-code` 出代码 | 15′ |
| 5 | **grep 所有 `TODO:` 写成 Mock 清单** | 10′ |

### 按交付模式分形态

- **模式一（SaaS 应用）** → 做**应用主界面几屏**（工作台 / 会员 / 督导 / 证据溯源）
- **模式二（大平台）** → 做**关键几屏**（一张图 / 驾驶舱 / 核心闭环）

### 🔔 强烈建议做的一屏：HIL 确认界面

把第五课设的闸**画出来**——**谁在审、审什么、按错的代价是什么**。

> 现成参考：`Plugins/courses-workshop-plugins/apps/teaching-workshop-ui*/hil-confirm.html`，
> 那个仓有 **v1→v3 四代 UI 原型**，可以做 before/after 对照。
>
> **能把闸画出来的方案，客户才相信你真的想过责任归属。**

## 八、⚠️ 四个翻车点

### 1. 别把外壳当交付（**一票警示**）

demo 跑通的是 UI 不是模型。演示时**必须先说清哪些是 Mock**（哪屏的"AI 回答"是写死的、哪块数据是假的），**再展示交互**。
**顺序不能反。**

### 2. 目录前缀要人工对齐

生成的路径是 `app/`、`components/`，而技术栈规定的是 `frontend/src/app/`。**工具不会自动加前缀。**

### 3. spec delta 缺 ADDED/MODIFIED/REMOVED 包裹

模板没写，按 `openspec-guide.md` 补。

### 4. 端到端尚未实测（诚实标注）

> 本手册的 `.pen` 格式结论来自对**现存文件**的实测（明文 JSON、version 2.10、结构吻合规范）。
> **但"跑一次 `screenshot-to-pencil` 然后用 Pencil 编辑器打开产物"这条端到端链路还没实测过。**
>
> —— **把这条写在手册里，本身就是本课要教的东西。**
