# 一、fund-review 是什么

| | |
|---|---|
| **干什么** | 政府 IT 采购的**报价优化 + 财评预审**——按地方预算标准出优化建议、重写报价表、产带引用的评分报告 |
| **规模** | **54 个文件**：**38 个脚本**（其中 **12 个 `scan_*.py`**）· 4 个 skill · **2 个 agent** · 4 个命令 · 5 个 reference |
| **身份** | ⭐ **不是 studio 工具链的一部分，是工具链产出的领域插件**——只是搭同一个 marketplace 发布 |

## 1.1 ⭐ "Vertical Plugin"这个身份

`CLAUDE.md` 专门有一节说这件事，两点区别：

| | fund-review | 所有 `studio-*` |
|---|---|---|
| **运行时工作区** | `stateful`，会话落在用户项目的 `.fund-review/{session-id}/`——**不在 `studio/` 下** | 用 `studio/` |
| **外部依赖** | 需要 `openpyxl` / `python-docx` | **一个都不需要第三方包** |

**它的设计文档不在这个仓**，在单独的 `fund-review-plugins` 仓的 `studio/changes/fund-review/`——
**这正是"设计与实现分离"的实例**（第四章）。

> **它证明的不是"这个插件多厉害"，是"这套工具链能造出这种量级的东西"。**
>
> ⭐ **你第五课产出的本体插件、以后要做的行业插件——都是这个身份。**
> **fund-review 就是你们的未来样本。**

## 1.2 四个 skill 是一条流水线

| skill | 干什么 |
|---|---|
| `init-session` | 初始化会话工作区，解析输入 |
| `quote-optimize` | 对着预算标准 + 全局定价指引，**出优化建议** |
| `quote-review` | 对着标准**打分，产带引用的评审报告** |
| `quote-rewrite` | **按已批准的方案**改写原始报价表 |

⚠️ **注意 `quote-rewrite` 的措辞：「按已批准的方案」。**
**改表这一步在人批准之后，不在 agent 手里**——这是第二章那条设计的伏笔。

# 二、⭐ 红蓝对抗

## 2.1 两个 agent，站在对立面

| | **蓝方 `quote-optimizer`** | **红方 `financial-reviewer`** |
|---|---|---|
| 人设 | "资深售前方案架构师，深谙政府 IT 采购报价" | "政府财评专家" |
| 立场 | **站投标方**，想让报价过审 | **站评审方**，逐条质询 |
| 输入 | 扫描器发现 + 全局定价指引 + 标准条款索引 | 每一条 `warn` / `fail` 的行数据 |
| 干什么 | **筛选、排序、解释**——为什么这条该改，引哪一条标准 | **挑战每一条**，要求页码引用 |
| 原话 | 「同时说 **投标商务** 和 **财评专家** 两种语言」 | 「**绝不批准一个你无法在标准公式里追溯出来的数字**」 |

## 2.2 ⭐⭐ 最见功力的一处：两个 agent 都没有 Write

```yaml
allowed-tools: Read, Bash, Glob
scope: runtime
```

**两份 agent 定义的 frontmatter 一模一样——都没有 Write。**

**它们只能查证与质询，不能改报价表。**
真正改表的是 `quote-rewrite` 里的确定性脚本，**改什么由人批准的方案决定**。

> ### **评审方要是能改报价，它就不是评审方了。**

这是**「权限即职责」**的又一次出现：

| 课 | 例子 | 同一条判断 |
|---|---|---|
| **第五课** | `ontology-validate` **没有 Write** | 校验器**物理上不可能**替你抹平不合格的地方 |
| **本课** | 两个红蓝 agent **都没有 Write** | 评审与优化**只能提意见，不能自己动手** |

> **好的角色设计不是靠嘱咐"你别乱改"，是让它想改也改不了。**

## 2.3 什么时候值得设红蓝

> **当一件事有明确的对立立场，而且两边都有专业性的时候。**

| ✅ 适合 | ❌ 不适合 |
|---|---|
| 报价 vs 财评 · 开发 vs 安全 · 业务 vs 合规 | 只有一个正确答案的任务 |
| 两边都需要专业判断，而且**盲区互补** | 只是想"多一个人看看"——**那用一个复核专家就够（A1）** |

⚠️ **别滥用**——**对抗的成本是双倍的推理**。

# 三、⭐⭐ 但红蓝对抗**不是**这个插件的重点

## 3.1 数一下构成

| | 数量 |
|---|---|
| **脚本** | **38 个**（其中 **12 个 `scan_*.py`** 扫描器） |
| skill | 4 个 |
| **agent** | **2 个** |

```
12 个确定性扫描器 → findings.json → agent 筛选·排序·解释 → 人批准方案 → 确定性脚本改表
    scan_*.py
```

> ### **能确定性算的，全写成了脚本；agent 只处理"需要判断"的那一段。**

## 3.2 12 个扫描器都在扫什么

| 扫描器 | 扫什么 |
|---|---|
| `scan_subject` | 科目对齐 |
| `scan_semantic` | 平台 vs 大模型的**语义重叠** |
| `scan_redundancy` | **跨工作簿 / sheet 的重复内容** |
| `scan_labor` | 人工定价 |
| `scan_workdays` | **人天极值** |
| `scan_caps` | **比例守恒**（标准里的硬上限） |
| `scan_completeness` | 9 大费用科目**缺失情况** |
| `scan_summary_sheets` | 汇总 sheet 缺失 |
| `scan_brand_models` | **设备品牌型号 ≥3**（标准表 7 注 3 的硬要求） |
| `scan_commercial` | 商业组件识别（填补"软件产品购置费 = ¥0"缺口） |
| `scan_evidence` | **取值依据** |
| `scan_ops` | 大模型运维 / 运营行合规 |

⭐ **每一条都是"照规则一查就知道"的事**——
**品牌型号够不够 3 个、比例有没有超上限、9 大科目缺了哪个、有没有跨表重复。**

**这些交给脚本，因为它们不需要判断。**

## 3.3 那 agent 干什么

| 交给确定性脚本 | 才交给 agent |
|---|---|
| 上面 12 类扫描 | 从一堆发现里**挑出真正值得提的** |
| 解析报价表 · 解析标准 · 公式引擎 | **排优先级** |
| 重写表格 · 生成报告与交付件 | **用标准条款解释为什么** |
| | 逐条质询、要求引用页码 |

> ### **这就是 S2/S3 讲的「确定性优先」，在插件层的活体。**
>
> S3 讲 Deterministic Agent Runtime 时说：
> **交易、库存、调度交确定性逻辑，只有意图识别和异常研判调大模型。**
> **fund-review 就是这条原则在一个真实插件里的样子——扫描是确定的，判断才是模型的。**

## 3.4 ⭐ 给你的可迁移判据

> ### **这一步能不能写成脚本？能，就别交给模型。**
>
> 模型是用来处理"**规则说不清但人能判断**"那一段的，
> **不是用来做你懒得写的计算。**

**三个理由**：

| # | |
|---|---|
| 1 | **确定性**——脚本每次结果一样，模型不保证 |
| 2 | **可测**——脚本能写单测，提示词不能 |
| 3 | **成本**——**确定性脚本跑一万次成本不变，agent 跑一万次要付一万次的钱** |

> **这一条不依赖 Astra Studio。做任何 AI 应用都成立。**

# 四、插件的骨架

## 4.1 Plugin Structure：一个插件长什么样

```
plugin-name/
├── .claude-plugin/plugin.json   # 清单（name / description / version）
├── commands/                    # 斜杠命令（.md）
├── skills/{skill-name}/SKILL.md # 具体任务
├── agents/                      # 子智能体角色定义（.md）
├── hooks/                       # 事件驱动自动化（hooks.json）
├── scripts/                     # Python 辅助脚本
├── references/                  # 按需加载的参考文档
└── templates/                   # 脚手架模板
```

⭐ **注意 `references/`——"按需加载"**。
这就是第三课讲的**渐进式披露**：`SKILL.md` 是入口，长东西放 `references/`，**用到才读**。

## 4.2 Plugin Traits：观察，不是配置

`skill-design` 阶段会从**规划产物**里"看出"插件的横切特征，这些特征驱动 `spec-generate` 生成不同的脚手架：

| Trait | 意思 | 会自动生成什么 |
|---|---|---|
| `stateful` | 跨会话管理项目数据 | **`init-workspace` skill + 运行时配置/状态模板** |
| `hil-gated` | 流程里有人工审批关口 | 相关 SKILL.md 里的 `## Approval Gate` 段 |
| `kb-dependent` | 需要 LLM 之外的领域知识 | KB 集成说明；可能配一个知识库插件 |
| `multi-pipeline` | 2 个以上独立业务流 | 按管线分别生成编排命令 |
| `expert-scoped` | **运行时需要与规划期不同的专家** | **`agents/` 里的运行时 agent 定义** |

> ### **Traits are observations, not configuration.**
>
> **你不"配置" trait，是工具从你已经写下的东西里推断出来的。**
> 没检测到 trait 的插件，走标准生成路径，**不多不少**。

**这背后是一个设计立场**：不给你一堆开关让你勾，而是从产物里推断——
**少一层配置，就少一层"配错了但没人发现"。**

⭐ **fund-review 同时命中两个**：

| Trait | 在 fund-review 里的样子 |
|---|---|
| `stateful` | `.fund-review/{session-id}/`（第一章那个运行时工作区） |
| `expert-scoped` | **那两个红蓝 agent**（第二章）——**它们是运行时专家，不是规划期专家** |

> ⭐ **A1 你写的是规划期专家**（做画像、域图时被叫）；
> **这两个是运行时专家**（跟着插件跑在真实业务里）。
> **`expert-scoped` 这个 trait，就是这两者的分界。**

## 4.3 两级工作区 + 设计与实现分离

```
studio/changes/{plugin}/   ← 只放设计文档：brief.md · skill-map.md · status.json · plugin.json.draft
{target_dir}/              ← 只放实现：SKILL.md · commands/ · scripts/ · agents/

status.json 里的 target_dir 字段，是这两边唯一的连线。
```

| | **域工作区** `type: "domain"` | **插件工作区** `type: "plugin"` |
|---|---|---|
| 装什么 | event-storm.md · domain-map.md · personas/ journeys/ processes/ | **只有设计文档** |
| 特点 | ⭐ **可被多个插件共享** | **不含 SKILL.md 与 commands**——那些在 `target_dir`；靠 `domain` 字段指回父域 |

**为什么要这样切——单一真相源，不重复。**

> 如果设计目录里也放一份 SKILL.md，**它和实现里那份迟早不一致**，而且你不知道该信哪份。
>
> ### **同一件东西只存在于一个地方**——
> **这是这门课程反复讲的 B-5，在工具设计上的同一条判断。**

⭐ **好的工具会替你守住纪律，而不是靠你自觉。**

⭐ **域工作区可共享**有实际价值：一次事件风暴产出的域图和画像可以喂给多个插件，
**别每个插件重做一次业务分析。**

# 五、从零起一个插件

## 5.1 路径

```
plan → build-skills（产可跑的初稿）→ skill-creator 反复打磨（拿真实输入测）→ validate → promote（v0.1 → v0.2）
```

| | |
|---|---|
| **「Initial fill, not final build」** | `build-skills` 产的是**能跑的初稿**，不是成品。**指望它一次生成对，是用错了工具。** |
| **外循环 / 内循环分工** | Astra Studio 管**外循环**（业务分析、领域建模、校验、发布）；单个 skill 的编写打磨交给官方 `skill-creator` |
| **版本化 promote** | v0.1 → v0.2，**设计文档快照进归档但仍保持活跃**——下一轮迭代接着用，**不是归档就冻结** |

> **这和第五课那 121 处 `NotImplementedError` 是同一个态度：机器立结构，人填判断。**

## 5.2 本地开发：改完立刻生效

```bash
claude --plugin-dir ./studio-core --plugin-dir ./你的插件
```

| 步骤 | |
|---|---|
| 1 | **直接改 `SKILL.md`**——通过 `--plugin-dir` 加载时**立刻生效**，不用发版、不用装 |
| 2 | 用 `/plugin:command-name` 测命令（如 `/studio-core:init`） |
| 3 | skill 会在**描述匹配用户意图时自动触发** |

⭐ **这是三级台阶的入门动作。** 你不需要先想清楚整个插件——
**先跑起来一个能改的东西，比先设计完美强。**

**这就是 S2/S3 讲的"确定性优先"在插件层的活体。**

**4.** 都是**"照规则一查就知道"**的事——品牌型号够不够 3 个、比例有没有超上限、9 大科目缺了哪个、有没有跨表重复。

**5.** 意思是**你不配置 trait，是工具从你已经写下的规划产物里推断出来的**——
**不给你一堆开关让你勾，少一层配置就少一层"配错了但没人发现"。**

**6.** **单一真相源。** 如果设计目录里也放一份 SKILL.md，**它和实现里那份迟早不一致，而且你不知道该信哪份**。

**这是课程反复讲的 B-5，在工具设计上的同一条判断——好的工具会替你守住纪律，而不是靠你自觉。**

**7.** A1 写的是**规划期专家**（做画像、域图时被叫，放 `studio/agents/`）；
fund-review 那两个是**运行时专家**（跟着插件跑在真实业务里，放插件自己的 `agents/`）。

> 三个理由：**确定性** · **可测** · **成本**（脚本跑一万次成本不变）

---

**Plugin Structure**：`.claude-plugin/plugin.json` · `commands/` · `skills/{name}/SKILL.md` · `agents/` · `hooks/` · `scripts/` · **`references/`（按需加载 = 渐进式披露）** · `templates/`

**Traits（观察，不是配置）**：`stateful` · `hil-gated` · `kb-dependent` · `multi-pipeline` · **`expert-scoped`（← 规划期专家 vs 运行时专家的分界）**

**两级工作区**：`studio/changes/` 只放设计 ｜ `{target_dir}/` 只放实现 ｜ 靠 `status.json` 的 `target_dir` 连接
→ **单一真相源，就是 B-5**

---

**从零起一个插件**：`plan` → `build-skills`（**可跑的初稿，不是成品**）→ `skill-creator` 打磨 → `validate` → `promote` v0.1→v0.2

**本地开发**：`claude --plugin-dir ./你的插件` —— **改 SKILL.md 立刻生效，不用发版**
