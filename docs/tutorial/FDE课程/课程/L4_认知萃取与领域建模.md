## 这一课干什么

**把项目描述压成人 / 路径 / 机会，再切成限界上下文。**

- **上半场学"零件"**：六个工具各跑一遍，看清每个产物长什么样、为什么这么长
- **下半场学"装配线"**：一条命令串起五步，体会流水线里到底发生了什么

| | 上半场 · 认知萃取 | 下半场 · 领域建模 |
|---|---|---|
| **目的** | 把第三课的项目描述压成**人、路径、机会** | 把认知产物切成**限界上下文**，顺手产出 `skill-map` |
| **前置** | 第三课的 `_INPUT.md`；第二课的 `/studio-core:init` | 上半场的画像 / 旅程 / 流程 |
| **工具** | `studio-insight` 六件套（**手动单跑**） | `studio-planner` 五步流水线（**一条命令**） |
| **产出** | ② 画像 ≥3 · 旅程 ≥2 · 流程 ≥2 · 热点分层 | ③ `domain-map.md` + `skill-map.md` |
| **能力位** | **C1 认知萃取** | **C2 结构建模**（上半） |

### 会做两遍吗？不会，但会碰同一批产物

`/studio-planner:plan` 的事件风暴步骤，内部**会调用**上半场那三个工具（画像 / 旅程 / 流程）。

**上半场先手动跑一遍，是为了让你知道下半场那条流水线里到底发生了什么**——否则流水线跑完，你只会说"它自己生成了一堆文件"。

# 上半场 · 认知萃取

## 一、你要交出什么

**画像 ≥3、旅程 ≥2、流程 ≥2、热点分层一份**——这就是下半场切域的原料。

> **FDE 的核心资产不是"会用 AI"，是把客户的模糊意图压成可执行的结构。**
> 证据：康养项目 **102 个业务事件 → 16 事件簇 → 7 域限界上下文**。
> **这一步没有任何模型能替你做判断，模型只能加速你做完。**

---

## 二、方法论：产品设计这一栈

> **这个角色原本是谁**：产品经理 / 产品设计师——负责把模糊的客户意图变成"要做什么"。
> 传统模式里他一个人占着这个位置，**交接给架构师时信息就衰减一次**。
> **FDE 把这套方法论装进自己脑子**，从事件一路跑到机会矩阵，中间不换人。

### 核心命题

产品设计**不是"画原型"**。它在这门课里的定义只有一句：

> **一条把"客户想要点什么"逼成可归域结构的方法论管线**：
> `事件 → 画像 → 旅程 → 机会矩阵`

管线的出口，**直接插进下半场的限界上下文**。

### 五个把模糊意图变结构的方法

| 方法 | 要点 | 对应工具 |
|---|---|---|
| **Persona 用户画像** | 按**行为 / 目标 / 动机 / 痛点**定义真实用户，**不是人口属性堆砌**。画像是整条旅程的地基 | `persona-insight` |
| **User Journey Map 用户旅程图** | 五要素：① 用户 ② 场景与目标 ③ **旅程阶段** ④ **行为·态度·情绪**（每阶段的正负情绪）⑤ **机会点**（从摩擦 / 痛点里长出来） | `journey-map` |
| **Opportunity Matrix 机会矩阵** | 把旅程里暴露的痛点**排优先级**——影响 × 可行性 × 频率，ROI 排序，决定先做哪个 | `opportunity-brief` |
| **Event Storming 事件风暴** | 把业务事件全量铺开、再归簇，**喂给限界上下文** | 下半场 `event-storm` |
| **产品思维（梁宁）** | 补一层"人和情绪"：① **同理心**——把需求分成痛点 / 痒点 / 爽点 ② **点线面体**——别做一个没有势能的孤点 ③ **用户体验五层**——产品不止"感知层好看"，底下四层才决定成败 | 贯穿六件套 |

> **画像 → 旅程 → 机会矩阵是有先后的**：
> **画像不真，旅程就是编的；旅程不暴露痛点，机会矩阵就没有原料。**
> **这条顺序不能倒。**

### ⚠️ 一处方法论与工具的差异

机会矩阵在方法论上是**三因子**（影响 × 可行性 × 频率），但 `opportunity-brief` 这个工具**只算两轴**：

```
Score = Impact × Feasibility        5×5 星阵，频率不进公式
```

**不是工具做错了。** 频率信息在旅程里（"每天都遇到" vs "一年一次"），**工具把它留给你做最后判断**。

> 所以工具给的排序**本来就该被你以业务理由推翻**。
> **别对着两个数字发懵，也别自己动手改工具的算法。**

### 要补这一栈，啃这几本

| 来源 | 补什么 |
|---|---|
| 《设计冲刺 Sprint》（Jake Knapp, Google Ventures） | 五天从问题到可测原型；HMW、用户测试 |
| Figma User Journey Map 资源库 | 旅程图五要素与五步做法的权威框架 |
| 梁宁《产品思维 30 讲》 | 同理心 / 点线面体 / 用户体验五层 |
| **内部《场景化产品设计》**（刘亚蒙，2018） | 它的"建立共同的认知约定"**就是本课程锚定口径机制的原型**；**"场景七要素"就是第五课五要素里 Action 的前身** |

> ⭐ **产品栈和本体栈本是一条血脉。**
> 你到第五课会以为五要素是凭空长出来的本体概念——**不是**，它在产品栈的"场景七要素"里就有雏形。
> **这也是为什么认知萃取做得糙，第五课一定难受。**

### 康养项目完整链条（量级标尺，背下来）

```
102 业务事件 → 16 事件簇 → 7 角色画像（368 份问卷校准）
    → 7 条用户旅程 → 5 条业务流程 → 10 个热点（P1–P5 分层）→ 7 域限界上下文
```

**每一段都有一个工具对应。这条链就是你今天要复刻的东西，只是规模小一号。**

## 三、三件必须讲透的事

### ① 画像的真假之分（上半场唯一的核心教学点）

| ❌ 假画像 | ✅ 真画像 |
|---|---|
| 人口统计："60 岁以上、退休、有慢病" | **行为倾向 + 证据**："熟人获客接受度 **77.59%**"、"智能监护接受但要简单式 **84.48%**" |
| **从常识就能编** | **必须去问** |

康养项目那 7 个画像背后是 **368 份问卷校准**，**每条特征都能指回一份数据来源**。

> **判据**：两个画像如果目标、痛点、使用频率**没有显著差异，就不该拆成两个**。
> 建议 **2–3 个起步**，超过 4 个说明你的范围划大了。

### ② 旅程要选"最暴露痛点"的场景，不是最典型的场景

**典型场景大家都顺，看不出机会在哪。**

### ③ 热点分层是给决策者看的，不是给自己看的

打分的意义不在于分数本身，在于**逼你说清"凭什么这个先做"**。

而且工具**明确允许你以业务理由否决它的排序**——

> **这正是 C7「价值判断」不可外包的具体落点**：
> 模型能算 Impact×Feasibility，但"**这个季度必须先啃硬骨头给客户看到东西**"这种判断，只能人做。

### ⚠️ 反例 B-7 · 旅程建模过重

康养项目长者旅程的初版做的是**"夜间急救"**——场景很戏剧、很打动人，但**过重且偏离营收主线**，最后返工改成会员飞轮。

> **落到你身上**：选旅程场景之前，**先回头看第三课写的商业模式**——
> **那三条收入线在哪条旅程上？就做那条。**

## 四、insight 六件套：命令、产物、确认点

| 命令 | 参数 | 产物路径 | 确认点 |
|---|---|---|---|
| `/studio-insight:persona-insight` | `[用户描述 或 工作区路径]` | `studio/changes/{name}/personas/{slug}.md` | **2** |
| `/studio-insight:journey-map` | `[persona + 场景描述]` | `journeys/{persona}-{scenario}.md` | 1 |
| `/studio-insight:process-flow` | `[流程描述]` | `processes/{slug}.md` | **2** |
| `/studio-insight:domain-canvas` | `[领域描述 或 工作区路径]` | `domain-canvas.md` | 1 |
| `/studio-insight:behavior-matrix` | `[领域描述 或 工作区路径]` | `behavior-matrix.md` | 1 |
| `/studio-insight:opportunity-brief` | `[领域描述 或 工作区路径]` | `opportunity-brief.md` | 1 |

### 六个工具内部结构完全同构，都是这五段

```
① 专家发现（五步）
     ↓
② 主体分析（各自不同）
     ↓
③ 专家评审（派子代理逐个评审草稿）
     ↓
④ 向你提 3–4 个问题
     ↓
⑤ 这时才落盘
```

> **关键：先评审、再问你、最后才写文件。**
> 你看到"它在反复确认"**不是卡住了，是设计如此**。

### 专家发现机制（不懂这个会被"静默覆盖"坑）

**五步查找顺序**：

1. **固定加载主角色** —— 画像 / 旅程 / 机会三个用 `product-manager.md`；流程 / 画布 / 矩阵三个用 `architect.md`
2. 扫 `studio/agents/*.md` —— **项目级自定义专家，先扫**
3. 扫插件内置 `agents/*.md` —— **"skip any already loaded from project"**
4. 按相关性匹配，选 1–3 个
5. 跳过 `_domain-expert-template.md`（它是模板不是专家）

**第 3 步那句 skip 就是覆盖生效点**：`studio/agents/product-manager.md` 存在时，**内置那份根本不会被加载**。

**内置的 11 个专家**：

| 通用 6 个 | 领域 5 个 |
|---|---|
| `product-manager` 用户视角，是否解决真问题 | `child-nutrition-expert` 0–12 岁营养 |
| `architect` 结构、边界、可持续性 | `child-exercise-expert` 0–12 岁运动发育 |
| `ux-researcher` 人**实际**怎么做，而非嘴上怎么说 | `elderly-nutrition-expert` 60+ 慢病膳食 |
| `data-analyst` 可度量性、指标与基线 | `elderly-rehab-exercise-expert` 60+ 康复与防跌倒 |
| `compliance-officer` 规则、风险与问责 | `skincare-expert` 护肤 |
| `operations-manager` 日常怎么落地、能否规模化 | |

> 老年营养 + 老年康复运动这两个内置专家，**正是康养项目沉淀下来的**。
> **这就是"平台=固化物"在专家层的体现**——上一个项目的领域知识，变成了下一个项目开箱可用的评审视角。

**⚠️ 翻车点 · 同名专家静默覆盖**

你在 `studio/agents/` 放了个自己写的 `product-manager.md`，内置那份就不加载了。
**产出的画像会走味，而且没有任何报错。**

> **处置**：跑之前先 `ls studio/agents/`，心里有数。
> 要定制就用 `/studio-core:create-expert customize product-manager`，**别手搓同名文件**。

**⚠️ 一个文档错误，两处都会撞上**：插件文档里有处写 `/studio-insight:create-expert`——**这个命令不存在**，正确的是 **`/studio-core:create-expert`**。下半场的事件风暴文档里**同样有两处这么写**。

## 五、六个产物长什么样

**画像卡**
Role / Age range / Tech level / Context / **Goals(1–3)** / **Pain points(1–3，带 高·中·低 severity)** / Current tools / Success looks like
\+ 共情图四象限：**Thinks / Sees / Hears / Does**
\+ 结尾两行 `Pain:` / `Gain:`

**旅程**
元数据（persona、scenario、trigger、end state）
\+ 逐阶段表：`Stage / Actions / Touchpoints / Thoughts / Emotion / Pain points`，**4–7 个阶段**
\+ 情绪曲线
\+ **痛点机会表 5 列**：`# | Stage | Pain Point | Severity | Opportunity`

**流程**
元数据（name / trigger / end states / frequency）
\+ 文字流程图，五种符号：`[事件]` `◇ 问题？` `→` `├─` `(Actor)`
\+ **决策点表 5 列**：`ID | Decision | Condition | True path | False path`
\+ 并行说明 + 泳道图

**域画布**
每域一张卡：**Owns / Does NOT own / Key actors / Key events**
\+ 分类表（Core / Support / Generic）+ 关系表 + ASCII 图

> **`Does NOT own` 这一行是精华**：定义一个域最有效的方式，是说清它**不管什么**。
> 这条直接喂给下半场的域切分。

**行为矩阵**
Actor 清单 + 动作表 / 事件表 / 数据表
\+ **主矩阵 5 列**：`Actor | Action | Event | Data In | Data Out`
\+ Gaps + Automation opportunities

> 主矩阵是**第五课五要素的直接前身**：Actor→Action 的 actor，Action→Action，Data In/Out→Object 与 Link。

**机会简报**
证据来源表 + 候选表（`OP-1`…）
\+ **Impact × Feasibility 5×5 星阵**：★★★ Build first / ★★ Build next / ★ Consider / 空 Defer
\+ 工作量表 + 排名块 + Recommendation

> ⚠️ 它**明确拒绝给工期估算**（"Do NOT give time estimates"）。
> "那什么时候能做完"——**这不是这个工具该回答的**，工期要等域切分和技能拆解之后才谈得上。

## 六、沉浸：教育督导项目三件套

> 素材：`Plugins/kindergarten-bench-plugins/studio/changes/saihan-preschool/`
> **成熟度诚实标注**：已完成建模 + 方案 + **47 页 Mock demo**——**AI 是 Mock，但数据是 79 园真实 CSV**；**本体未编译**。
> 它是全部项目里画像 / 旅程 / 流程**三件唯一齐全**的。

| 类型 | 文件 | 看点 |
|---|---|---|
| 画像 | `p1-li-keke`（区教育局科长）/ `p2-zhang-yuanchang`（园长）/ `p3-wang-laoshi`（教师） | **三层视角**：监管者 / 管理者 / 执行者。同一件事在三个人眼里完全不同 |
| 旅程 | `j1-li-gap-to-okr` / `j2-zhang-task-to-class` / `j3-wang-upload-qc` | **三条旅程首尾相接**：李科长的产出是张园长的输入，张园长的产出是王老师的输入 |
| 流程 | `pf1-district-gap-okr` / `pf2-park-task-decompose` / `pf3-upload-qc-loop` | 与旅程一一对应，把"人的体验"翻译成"系统的流程" |

> ⭐ **最值得学的一点**：三个画像**不是并列的三类用户，而是一条责任链上的三环**。旅程也因此能首尾相接。

**问你自己**：你的命题里，那几个角色是**并列**的，还是有**责任传递关系**的？
**如果是链，就按链来做旅程。**

### ⚠️ 同时带一个 B-5 活体

教育督导项目的园所数在源材料里**不一致**：事件风暴写 **99 所**、热点评估写 **124 园**、数据样本是 **79 园**。

> **正确处置是三个数都标"待区教育局核实"，不替它选一个。**
> 你最想做的动作是"挑一个看起来最靠谱的写上去"——**那就是编造的开始。**

### ⚠️ 反面对照 · 学前教育项目

那个项目交出了 653KB 可研和完整送审报价包，**但它没有画像、没有旅程**。

> **说明什么**：可研写得出来，**不等于认知萃取做过了**。
> **跳过认知萃取也能交付，但交付的是"我们理解的业务"，不是"客户实际在做的业务"。**
>
> ⚠️ 正因为它没有画像 / 旅程，**它不能拿来教认知萃取**——在本课它只作反面对照。

## 七、上半场实操

### 先做一件事：把第三课的输入包喂进去

六件套的第一个输入，**就是你第三课产出的 `_INPUT.md`**——不是现场再口述一遍命题。

> ⭐ **这是对第三课的一次真实验收**：
> 如果跑出来的画像很空洞、或者术语每次都不一样，**回去看输入包的 ② 口径层缺了什么，别怪工具。**

### 任务与时间盒

**任务**：用本组命题跑完六件套，产出 **画像 ≥3、旅程 ≥2、流程 ≥2、热点分层一份**。

| 序 | 命令 | 时长 | 输出 |
|---|---|---|---|
| 1 | `persona-insight` | 20′ | ≥3 张画像卡 + README 索引 |
| 2 | `journey-map` ×2 | 20′ | 2 条旅程（选**最能暴露痛点**的场景） |
| 3 | `process-flow` ×2 | 15′ | 2 个流程（含决策点表） |
| 4 | `opportunity-brief` | 15′ | 热点排名（**可当场推翻评分**） |

> `domain-canvas` 与 `behavior-matrix` **本步不强制跑**——下半场的流水线完整模式会自动带出来。
> 时间充裕的组可以跑 `behavior-matrix`，提前感受一下第五课五要素的雏形。

### 三个注意

**① 画像必须按「行为」切，不能按「人口属性」切。**
判据见上面"画像的真假之分"。

**② `opportunity-brief` 的评分可以推翻。**
**但推翻的时候必须说出业务理由**，checkout 会查这一条。

**③ 没有工作区时产物会散落。**
六个工具都能脱离 `studio/` 独立跑，此时会写到**当前目录**。**先确认 `/studio-core:init` 跑过**，否则文件会撒得到处都是。

## 八、⭐ 实操之后立刻回收：你刚才体验到的就是认知杠杆

> 概念与公式第一课讲过。这 10 分钟只干一件事：**把那个抽象公式，钉在你刚做完的事情上。**

**第一步 · 自己报数**
刚才 55 分钟，你们组产出了几张画像、几条旅程、几个流程？
> 通常是 **3 画像 + 2 旅程 + 2 流程 + 1 份热点排名**。

**第二步 · 换算成传统模式**
| 动作 | 传统模式耗时 |
|---|---|
| 产品经理访谈 + 整理画像 | 2–3 天 |
| 旅程与流程建模 | 再 2 天 |
| 机会矩阵排序 | 1 天 |
| **合计** | **约一周，还不含来回确认** |

**第三步 · 指回公式**

```
产出 = 结构化能力 × 平台固化 × 模型算力
```

刚才那 55 分钟里——

- **模型算力**是买来的（第三个因子，唯一能花钱买到的）
- **平台固化**是六件套给的（第二个因子）
- 但**画像该按行为切还是按年龄切、这条旅程选哪个场景、热点排序该不该推翻工具的打分**——

> **这三件事没有一件是模型替你做的。那是第一个因子，是你自己出的。**
>
> ⭐ **所以杠杆不是"AI 帮我干活"，是"我的判断被放大了 N 倍"。**
> 判断错了，放大的就是错的——**这也是为什么第三课要花一整课把信息问准。**

> ⚠️ 这一节讲完，你该有的感受不是"AI 真厉害"，
> 而是**"原来我刚才做的那几个判断这么值钱"**。

## 十一、方法论：领域驱动设计这一栈

> **这个角色原本是谁**：领域架构师——负责把大系统切成边界清晰、各自内聚的域。
> 传统模式里，他拿到产品经理递过来的需求，切完再递给知识工程师；
> **FDE 是同一个人从事件切到域，中间不换脑子**——这就是为什么上半场的产物在这里可以直接复用，不必重跑。

### 前置：切域之前，先把"事件"写对

> **事件是过去式的既成事实**——"材料已上传""质检已通过"，
> **不是**"支持材料上传""实现质检模块"。

为什么它是前置？因为**限界上下文是按"谁推进了这个既成事实"聚出来的**。

你写成功能清单，聚出来的就只能是"查询模块""管理模块"——**那是系统的形状，不是业务的形状。**

> **事件写歪，域必然切歪，而且到第五课才会疼。**

### DDD 三件核心

| 概念 | 一句话 | 康养项目的物理落点 |
|---|---|---|
| **统一语言** | 业务方和工程师用同一套词，且这套词**直接出现在代码里** | 共享根 `Elder` **单一写入点**——同一个"老人"只有一个真相源 |
| **限界上下文** | 一个词在一个边界内只有一个含义；**出了边界就是另一个概念** | 102 事件 / 16 簇切成 **7 域 D1–D7** |
| **上下文映射**（含防腐层） | 两个域之间是"引用"还是"发布"，**必须说得出来**；跨语义的地方加防腐层翻译 | 两处防腐层：**D6↔D5**、**D4↔D5**；跨域一律 **ref / 发布，不越界写入** |

### 三个判据（对着你的域图问）

**① 同一个词在两个地方含义不同 → 该切开**
康养项目的"老人"在 D4 居家照护里是"**被照护对象**"，在 D3 会员飞轮里是"**消费者**"。
同一个人，两套属性、两套规则 → **两个域**。

**② 状态机不共享 → 该切开**
一个对象的生命周期如果在两处被不同的人推进，**说明它其实是两个对象**。

**③ 能独立发布 → 该切开**
D6 民政治理有 8 个 HIL 闸、要对监管负责；把它和 D3 会员营收捆在一起，**一次发布要同时说服民政局和市场部**。

### 要补这一栈，啃这两本

| 来源 | 补什么 |
|---|---|
| 《领域驱动设计》Eric Evans（蓝皮书） | 概念体系的源头 |
| 《实现领域驱动设计》Vaughn Vernon（红皮书） | 落地版，概念怎么变成代码 |

> **别通读。** 重点啃**"限界上下文"**与**"上下文映射"**两章——这门课用到的就是这两章。

### ⚠️ 反例 B-8 · 越域写入冲动

康养项目编译期**多次想让 Action 直接写他域的对象**——因为"就改一个字段，绕一圈太麻烦"。

> **原则**：跨域一律走 ref / 发布，不越界直写。
> **两个域之间只能是"引用"或"发布"，没有第三种。**
>
> **关键的一句**：**结构纪律靠校验器，不靠自觉。**
> 你在赶工期的凌晨三点是不会守纪律的，**但校验器会**。

这条在第五课有物理对应：引擎的能力检查脚本会直接拦住摸内核私有方法的代码，**CI 挂给你看**。

### ⚠️ 反例 B-9 · SDK 能力想当然

编译期不确定某两个符号是否导出，**7 个域统一留了 docstring 挂账**，没有靠"应该支持吧"往前推。

> **这个判断在第五课被验证是对的**：编译规则的固定头部**确实漏了一个 import**，照着生成会报错。
> **当初挂账的人是对的。**
>
> **原则**：不确定就显式挂账，别赌。

## 十二、先纠正一个误解：`plan` 不是编排引擎

你会以为 `/studio-planner:plan` 是个自动化流水线。**它不是。**

> `plan` 本身**只是一段串行提示词**——它按顺序点名 5 个工具，并写明"每步之后暂停、把结果交给用户确认"。
> **真正的衔接靠"文件 + `status.json`"，不靠内存传参。**

三个直接后果：

1. **随时可以中断**，下次接着跑——因为状态都在磁盘上
2. **每一步都能单独跑**，只要前一步的文件在
3. **可以人工改产物再继续**——比如 `domain-map.md` 你改完，下一步读的就是你改过的版本

> 这正是 FDE 与"点一下按钮等结果"的分野：
> **管线是给你用的，不是替你做主的。**

### 五步流水线：读什么、写什么

| 步 | 读（前置） | 写（交棒物） | 确认点 |
|---|---|---|---|
| **event-storm** | `studio/`、`studio/agents/*.md` | `event-storm.md`、`changelog.md`、`status.json`、`personas/`、`journeys/`、`processes/` | **≈8**（精细）/ **3**（快速） |
| **domain-model** | `event-storm.md`（**缺失即拦截**） | `domain-map.md`；为每个候选插件建 status.json + 空脚手架 | 2–5 |
| **skill-design** | `status.json`；父域 `domain-map.md` | `skill-map.md`；status.json 的 skills 全填 `draft` | **2** |
| **spec-generate** | `skill-map.md`（**必需**） | `brief.md`、`plugin.json.draft`、骨架；phase `planning→building` | **0（纯自动）** |
| **build-skills** | phase **必须 == `building`** | 就地填充 `skills/*/SKILL.md` | 1 |

**单步续跑口令**（卡在哪一步就从哪接）：

```
/studio-planner:event-storm   <domain>
/studio-planner:domain-model  <domain>
/studio-planner:skill-design  <plugin>
/studio-planner:spec-generate <plugin>
/studio-planner:build-skills  <plugin>
```

> ⚠️ 这五个是 **skill 触发，没有对应的命令文件**（studio-planner 只有 `plan.md` 一个命令）。
> **你的环境里 `/` 补全不出来是正常的**，改用自然语言 `use skill: spec-generate for xxx` 同样生效。

### phase 状态机（贯穿本课 → 第八课）

```
planning ──spec-generate──▶ building ──validate──▶ approved ──promote──▶ shipped（归档副本）
                                                                  └─▶ 活动区重置回 planning，iteration+1
```

> ⚠️ `studio/config.yaml` 的 lifecycle 里列了 `testing` 一档，但**全链路没有任何工具会写入它**——
> validate 直接从 building 跳到 approved。**别等一个永远不会出现的状态。**

### ⏱️ 时间盒的头号杀手：确认点

精细模式下跑完一次完整 `plan`，**用户停顿点 ≈20+ 次**。

**课堂必须用快速模式，能压到 6–8 次。** 两处开场都会问你：

| 工具 | 精细（默认） | 快速 |
|---|---|---|
| `event-storm` | 🔍 每步暂停 | ⚡ **仅 3 个确认点**：①专家角色+事件清单 ②画像+旅程+流程一起看 ③热点排名 |
| `domain-model` | 🔍 完整分析（含域画布 / 行为矩阵 / 机会简报） | ⚡ **跳过这三个分析**，从事件聚类直达插件提案 |

> **选快速模式不是偷懒**——被跳过的三个分析，**你在上半场已经手动跑过了**。
> 这里跳过是**避免重复**，不是省略步骤。

> ⚠️ 但要知道：`domain-model` 完整模式的判据是"**事件 > 15 个或预期多插件**"。
> 你的命题若真的复杂，**该选完整就选完整**，只是要预留时间。

### traits：整条流水线的分叉开关

`skill-design` 的 **Step 1.5 是本半场的核心确认点**：

| trait | 含义 | 下游影响（第八课会生成什么） |
|---|---|---|
| `stateful` | 有持久运行时状态 | 额外生成 `init-workspace` skill + 两个 runtime 模板 |
| `hil-gated` | 有人工审批闸 | 给相关 skill 插入 `## Approval Gate` 段（✅确认 / ✏️修改 / ❌拒绝） |
| `kb-dependent` | 依赖知识库 | 影响 skill 的数据依赖设计 |
| `multi-pipeline` | 有多条编排流水线 | 每条流水线一个 `commands/{pipeline}.md` |
| `expert-scoped` | 需要领域专家 agent | 生成 `agents/` 目录 |

> **traits 是整条流水线的"分叉开关"**——它在 `skill-design` 被确认，到第八课 `spec-generate` 才兑现成不同的骨架。
> **现在选错，第八课生成的东西就不对。**
>
> 特别注意 `hil-gated`：**它和第五课本体层的 HIL 是两回事**（一个是 skill 层的审批段，一个是 Action 层的策略），第五课会讲清楚。

**四档复杂度**：Simple / Moderate / Script-heavy / MCP-dependent——决定 `allowed-tools` 和要不要建 `scripts/` 目录。

## 十四、下半场实操

### 阶段一 · 事件风暴（25′）

```
/studio-planner:event-storm <你的 domain-slug>
```

**命名规则**：lowercase、kebab-case、**2–3 个词**（`children-health`、`trading-ops`、`linxi-edutech`）。

#### 🔔 最容易错的一步：什么是"业务事件"

| ❌ 这不是事件（这是功能） | ✅ 这才是事件（过去式的既成事实） |
|---|---|
| 提供订单查询功能 | **订单已提交** |
| 支持材料上传 | **材料已上传** |
| 实现质检模块 | **质检已通过** / **质检已驳回** |

> **判据**：能不能加"已"字、并且它**已经发生过、不可撤销**？能，才是事件。
>
> **你一上来必写功能清单。这是整个下半场最关键的一次纠偏，写错了后面全歪。**

**产物 `event-storm.md` 的固定 7 个 H2**：
`Domain Context` · `Events` · `Artifacts Produced` · `Hotspots` · `Knowledge Base Dependencies` · `Expert Scope` · `Decision Points`

其中 **KB 依赖表**（`热点 | 需要的领域知识 | 知识类型 | 更新频率`）值得单看：
知识类型四选一（参考文档 / 结构化数据 / 历史案例 / 实时数据），**≥3 个知识源且更新频繁 → 建议做一个伴生知识库插件**。

> 康养项目的 D7「康养大模型知识库」**就是这么长出来的**。

**增量模式**：检测到 `event-storm.md` 已存在 → 自动走 delta 模式，**原地更新 + 追加 changelog + iteration+1**。

> ⚠️ **修订是就地覆盖的，`git diff` 就是你的修订历史**。
> 所以 `studio/` **必须 git-tracked**——第二课 init 那句 "Consider running `git init` first" 的告警**不是走过场**。

### 阶段二 · 域建模（25′）

```
/studio-planner:domain-model <domain-slug>
```

**产物 `domain-map.md` 的 5 个 H2**：
`Analysis Mode` · `Artifacts` · `Plugin Candidates` · `Generic Capabilities` · `Collection Structure`

**Plugin Candidates 表 7 列**：`Plugin | Domain | Role | Action | Description | Dependencies | Priority`
（Role = core / add-on；Action = create / modify）

#### `## Generic Capabilities` 这一段是精华

它列的是"**不需要定制插件**的能力"。

> 你最容易犯的错是**什么都想自己建**。这一段逼你回答：
> **"这个能力买现成的行不行？"** 答案常常是行。
>
> 康养项目 D7 定位 Generic-Support、草业项目 / 辣椒共用底座，**都是这个判断的产物**。

**Collection Structure 三种模式**：
1 个插件 = 不建 collection；2–5 个相关 = 一个 collection 且**必须有明确的 core**；不同领域的独立插件 = 分开 collection。

> ⚠️ **增量模式下有一个硬确认点**（文档明写 "This is a key decision point"）：
> 会给你一张"插件影响评估"表，**必须显式确认才继续**。
> 这是整条流水线上**唯一被标为"关键决策点"的地方**。

### 阶段三 · 技能设计（20′）

```
/studio-planner:skill-design <plugin-name>
```

**产物 `skill-map.md`**：`Skills`（每个含 Description / Inputs / Outputs / Out of scope / Complexity / allowed-tools / Preconditions 七个字段）· `Data Flow` · `Complexity Summary` · `Plugin Traits` · `Implementation Order`

**Step 1.5 五个 traits 逐个判过——不要直接回车接受默认。**

### 🛑 跑到 `skill-map.md` 就停

`spec-generate` 和 `build-skills` **属于第八课**。

> 别一路跑下去——那会把第八课的内容提前消耗掉，而且**在没做第五课本体的情况下就去建插件骨架，顺序就乱了**。

### ⚠️ 四个翻车点

**1. `spec-generate` 找不到模板（会在第八课撞上）**
它的 Pre-check 让它读 `../../templates/brief.md.tmpl`，但 **studio-planner 根本没有 `templates/` 目录**——那两个模板住在 **studio-core** 下。
**后果**：模型找不到模板，会按内嵌结构生成（结果可用，但可能与预期不同）。**知道就行，不用修。**

**2. 文档里的 `/studio-insight:create-expert` 是错的**
**正确的是 `/studio-core:create-expert`**（同一个错在上半场文档里也有）。

**3. `build-skills` 的 phase 硬门**
phase 不是 `building` 会直接报错退出。**这是设计，不是 bug。**

**4. 别在本课就跑 `spec-generate`**
它是**零确认点的纯自动化**，一跑就把骨架全生成了。
**在没做第五课本体、没想清 traits 的情况下生成的骨架，等于白生成。**

## 十五、⭐ 本课结束时必须知道的一件事：后面是分叉，不是流水线

跑完 `domain-map` + `skill-map`，路分成三条：

```
                    ┌──▶ 第五课 本体建模   ← 要"可执行的规则与闸"
   domain-map ──────┼──▶ 第六课 文档工程   ← 要"可评审的文书"
   + skill-map      └──▶ 第八课 技能插件   ← 要"可发版的插件"
                    （第七课 原型基本独立，随时可插）
```

**它们并行、不互为前置。**

**活证据 · 学前教育项目**：那个项目**没做本体建模、没有画像 / 旅程**，照样交出了 **653KB 可研 + 完整送审报价包 + 单一来源论证**。

> **别以为"不编译本体就不能写方案"。** 交付模式决定你走哪条分支：
> - **模式二 To-G 大盘、赢单靠评审** → 第六课那条优先
> - **模式一 SaaS 应用、赢单靠能用** → 第五 + 第七课优先
> - **要做可复用能力沉淀** → 第八课

## 十六、下半场 checkout

| 维度 | 达标 | 警示 |
|---|---|---|
| 事件写法 | 全是过去式既成事实（"材料已上传"） | 写成功能清单（"支持材料上传"）→ **一票警示** |
| 域切分理由 | 每个域能说清"谁对它负责"+ 至少一条切分判据 | 按功能模块切（"查询域""管理域"） |
| Generic 判断 | `Generic Capabilities` 非空，能说清什么不用自建 | 什么都要自己建 |
| core 明确 | collection 里有且仅有一个明确的 core | 2–5 个插件平级、无 core |
| skill-map 溯源 | **每个插件都能在第三课项目描述里找到出处** | 有凭空想出来的插件 |
| traits | 五个逐个判过，说得出为什么选 / 不选 | 直接回车接受默认 |
| 越域 | 无跨域直写设计 | 有"就改一个字段"的越界冲动（**B-8**） |
| 停在正确的位置 | 跑到 `skill-map.md` 停 | 一路跑到 build-skills（**抢了第八课**） |

## 附 · 一页纸速查

**上半场顺序不能倒**：画像 → 旅程 → 机会矩阵。画像不真，旅程就是编的。

**画像判据**：按行为切，不按人口属性切。目标/痛点/频率无显著差异 → 不该拆成两个。

**事件判据**：能加"已"字、已发生、不可撤销 → 才是事件。

**切域三判据**：同词不同义 / 状态机不共享 / 能独立发布 → 该切开。

**跨域只有两种关系**：引用（ref）或发布。**没有第三种。**

**结构纪律靠校验器，不靠自觉。**

**跑到 `skill-map.md` 停。**
