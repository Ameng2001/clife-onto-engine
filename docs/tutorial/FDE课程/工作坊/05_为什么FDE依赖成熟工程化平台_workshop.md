## 〇、开场（教练宣读，4′）

> 📌 **本环节为研讨环节（不产交付包物件）**——本讲就本组命题做启发式研讨，产出记进工作簿的"思考"区即可，不强塞交付物。下方的 💡 启发范例是**标尺、不是模板**：康养项目/教育督导项目/辣椒/草业项目做对了长这样，帮你把研讨聊到点子上、照结构想，别抄数字。

**🎯 本坊目标**：就本组命题研讨清楚 **① 没有平台、纯手工维护跨域一致性，会慢且必错到什么量级** + **② 平台到底替我们扛了什么风险**（能说成向老板辩护平台投资的一句话）——产出是**研讨观点 / 一句话共识**，记进工作簿"思考"区，不必成表。

**🧭 过程方法论（本坊用的 FDE 方法）**：一致性维护成本推演 · 五类校验动作清单 · **发现成本曲线**（错误发现越晚越贵）· 手工 ÷ 平台 倍率 · 平台 = 方法论固化物。

**📏 工作坊纪律（教练宣读）**
1. **启发-执行**：每步先点开"💡启发"看康养项目范例，再动手；不空想。
2. **时间盒**：铃响即停，个人估算/分组核对都守时。
3. **终止铃**：教练铃响，讨论立即停，进下一步。
4. **停车场**：争不出的挂 parking lot，会后再议，不占时间盒。
5. **checkout**：每阶段末对照输出与验收。

**🙌 工作坊宣言（齐读）**：完成大于完美 · 团队大于个人 · 共识大于对错。

> 本坊的核心不是算出精确工时，是让你**亲手撞到那堵墙**：人类做跨对象一致性维护，慢且必错——而这正是平台真正的价值密度所在。

## 二、输入材料（可直接发学员）

### 2.1 康养项目 7 域真实规模清单（本推演的"工作量底数"）

| 项 | 数量 | 说明 |
|---|---|---|
| 数智本体（域） | **7** | D1–D7，限界上下文 |
| Object | **76** | 跨域对象总数（含 3 个跨域共享根 Elder/Member、ServiceOrder、Station） |
| Link | **75** | 域内 + 跨域 12 条承重 Link |
| Function | **38** | 只读派生（风险分级/支付拆分/DIP 报销/补贴测算等） |
| Rule | **47** | 声明式 18 + function 骨架 29 |
| Action | **54** | 写操作（含 26 处需 HIL） |
| HIL 闸 | **26** | 站长 HIL + 民政 DP-H 等 |
| 代码骨架 | **3835 行** Python + 21 YAML | 机械编译产物 |

### 2.2 平台实际达成的基线（你要拿自己的推演跟它比）

- **编译**：7 域**同一天**并行编译成插件骨架；统一校验 **7/7 通过**（py_compile ✓ + 每域 3 个 YAML ✓ + "只 import sdk"红线 ✓）。
- **结构校验**：ontology-validate 静态 A 结构 **7/7 零悬空引用**；B source 治理 **7/7，0 空 source**。
- **人力**：**1 名 FDE + 智能体编队**（传统对照：产品经理 + 架构师 + 行业顾问 + 方案经理 + 美工，5+ 人 / 数周）。

### 2.3 两个真实"冲动/存疑"现场（推演时要把它们的返工成本算进去）

- **B-8 越域写入冲动**：编译期多次想让 Action 直接 `stage_write` 他域对象（图省事）。平台靠 A 结构校验器当场拦下，最终跨域全部 ref/发布写注释。**问自己：手工模式下，这个越界谁来发现？多久发现？**
- **B-9 SDK 能力想当然**：`PropertySpec.default`/`Evaluation` 是否导出编译期存疑，7 域统一 docstring 显式挂账。**问自己：手工模式下，你会不会"应该支持吧"往前写，然后在集成期集体返工？**

### 2.4 研讨要点（围绕这些点估量级，不必成表）

研讨"手工重做"的成本时，围绕这七个点估个量级、感受平台价值——不追求精确工时，追求撞到那堵墙：

- **① 悬空引用检查**：每条 Link/Action 的 ref 是否指向真实存在的 Object（底数：75 Link + 54 Action）。
- **② 跨域越界检查（B-8）**：有没有 Action 越域 stage_write（底数：54 Action）。
- **③ 命名一致性**：76 对象跨 7 域命名不冲突不漂移。
- **④ 红线检查**：每个插件"只 import sdk"。
- **⑤ SDK 能力核实（B-9）**：每处存疑符号是否真被导出/支持。
- **⑥ 返工放大**：一处错误连累多少下游（改一处牵一串）。
- **⑦ 沟通损耗**：手工必然多人，跨人一致性再打折。

再拿它对照 **2.2 平台基线**（当天 / 7 域 / 1 FDE / A 结构 7/7 零悬空 / B source 7/7），感受"手工 ÷ 平台"的量级差；最后用一句话说清 **平台替我们扛了什么风险、代价是什么、值不值**。

## 三、分阶段脚本（每步：🔔任务 / 🔔输出 / 🔔难点 + 💡启发范例）

### 阶段一 · 手工成本个人估量讨论（10′）

#### 步骤① · 锚定五类校验动作（3′）
> 🔔 **任务**：就本组命题想清"手工重做"必须人肉完成的一致性校验动作，至少数出五类：① 悬空引用检查（每个 Link/Action 的 ref 是否指向真实存在的 Object）；② 跨域越界检查（有没有 Action 越域 stage_write，B-8）；③ 命名一致性（76 对象跨 7 域命名不冲突不漂移）；④ 红线检查（只 import sdk）；⑤ SDK 能力核实（B-9）。
> 🔔 **输出**：*能数清这五类校验动作的研讨观点*，认到"哪些是人肉最易疲劳出错的活"。
> 🔔 **难点/注意**：别把"打字/写代码"当校验动作——3835 行是机械生成的，真正的成本在**一致性维护**，不是敲键盘。

<details><summary>💡 启发 · 点开看平台把这五类校验做成了什么</summary>

康养项目平台里，这五类不是靠人肉，是靠**确定性校验器**一次跑完：① 悬空引用 = ontology-validate 的 A 结构校验（结果 7/7 零悬空）；② 越界 = A 结构校验器当场拦 B-8；③ 命名一致性 = 编译期跨域符号解析；④ 红线 = "只 import sdk" 静态检查；⑤ SDK 能力 = docstring 显式挂账 + 编译核实。**你要推演的，是把这一整套"当天 7/7"的确定性保证，换成人肉一条条核，要花多少工时、必然漏多少。**

</details>

#### 步骤② · 个人估个量级（7′）
> 🔔 **任务**：围绕 2.4 研讨要点，对每个校验动作心里估个"单位工时"和"错误率"的量级，说得出你的假设（比如"1 个人查 1 条 Link 的引用完整性约 X 分钟"）。不必成表，形成对量级的个人观点即可。
> 🔔 **输出**：*对手工成本量级的个人观点*，每个错误率/工时判断都带一句可辩护的假设。
> 🔔 **难点/注意**：**错误率别给太低**。谁说"我很仔细所以错误率 1%"，要能被 B-8 反问顶回去。数字取自 2.1 清单，不拍脑袋另造。

<details><summary>💡 启发 · 点开看仅"悬空引用"一项的量级</summary>

只算校验动作①：75 Link + 54 Action = **129 条引用**，每条人工核需交叉查"这个 ref 指的 Object 到底存不存在"约 2–3 分钟，单人跑一遍就是 **4–6 小时**，且必然有漏。这还只是一个域一遍、一类校验。乘上 7 域、多轮迭代、返工放大后，手工达到"零悬空"的成本是平台"当天 7/7"的**一到两个数量级**。重点不是这个数，是让你自己撞到"人类做跨对象一致性维护慢且必错"这堵墙。

</details>

### 阶段二 · 分组研讨 + 与平台基线对照（20′）

#### 步骤③ · 分组研讨（12′）
> 🔔 **任务**：4 人一组就本组命题研讨。重点吵三件事：谁的错误率最乐观、谁漏了"返工放大"（一处越界改动会连累多少下游）、谁忘了"沟通损耗"（手工模式必然多人，跨人一致性还要再打折）。让研讨把⑥返工放大、⑦沟通损耗都聊进去。
> 🔔 **输出**：*组内对手工成本量级的研讨共识*，明确⑥⑦两项不能漏。
> 🔔 **难点/注意**：**手工模式的致命点不是"会错"，是"错误发现得晚"**。B-8 在平台里编译期发现（便宜），手工里可能对账期才发现（昂贵，还要追责复现）。这条"发现成本曲线"必须在研讨里被点出来。

<details><summary>💡 启发 · 点开看返工放大与发现成本曲线</summary>

- **返工放大**：命名一致性是 **B-5（数据张冠李戴）的放大版**——76 个对象跨 7 域，一处命名漂移可能连累所有引用它的 Link/Action，改一处牵一串。
- **发现成本曲线**：训练有素的 FDE 在**有校验器兜底**的情况下，编译期还**多次**想越域写入（B-8）。没有校验器兜底，凭什么相信自己 99% 不越界？而且越界若在集成/对账阶段才暴露，成本比编译期发现高一到两个数量级。把这条曲线套到你自己的项目上，就是研讨题 2。

</details>

#### 步骤④ · 与平台基线对照（8′）
> 🔔 **任务**：把你组研讨出的手工成本量级 vs 平台的"当天 7/7、零悬空"摆一起，研讨出对**倍率量级**（手工 ÷ 平台）的一句话共识。
> 🔔 **输出**：*对倍率量级的一句话共识* + 一句"这个倍率里多少来自打字、多少来自一致性维护"。
> 🔔 **难点/注意**：不追求精确值，追求意识到"**倍率主要不来自打字**"。若你组研讨落在"倍率主要是打字工时"，说明还没识别一致性维护才是主成本。

<details><summary>💡 启发 · 点开看平台基线的"当天 7/7"意味着什么</summary>

平台基线是：**7 域同一天并行编译、7/7 统一校验通过、A 结构 7/7 零悬空、B source 7/7 零空 source，1 名 FDE 完成**。传统对照是 5+ 人 / 数周。你的手工推演倍率，量级上应落在"一到两个数量级"这个区间——不是因为平台打字快，是因为平台把"人类最易疲劳出错、且错误发现越晚越贵的一致性维护"固化成了确定性校验器。

</details>

### 阶段三 · 研讨平台价值（6′）

#### 步骤⑤ · 研讨出一句话共识（6′）
> 🔔 **任务**：就本组命题研讨收口——"平台替我们承担了 ___ 风险，代价是 ___ 投入，值/不值因为 ___"，聊出一句能向老板辩护平台投资的话。
> 🔔 **输出**：*平台价值的一句话共识*，量级站得住、值/不值有据。
> 🔔 **难点/注意**：结论别空洞、别与研讨量级脱节。"平台承担的风险"要具体到"7 域跨 76 对象/75 链接的一致性维护与越界防护"，不是"提高效率"。

<details><summary>💡 启发 · 点开看标准三句结论骨架</summary>

1. 平台替我们承担了 **7 域跨 76 对象 / 75 链接的一致性维护与越界防护** 风险（B-8 靠校验器而非自觉挡住）；
2. 代价是 **平台建设 + 学习 + 管线维护** 的一次性与持续投入；
3. **值**，因为一致性维护是人类最易疲劳出错、且错误发现越晚越贵的环节，把它固化进校验器，等于把"复制加班"变成"复制能力"——**没有平台，你复制不了康养项目的 7/7，只能复制那个人的加班。**

</details>

## 四、checkout（研讨深度对照 · 不看交付物，看想没想透）

> 每阶段末 + 收尾各对照一次。四维，每维看"研讨到位没"与"一票警示"。

| 维度 | ✅ 研讨到位 | ⚠️ 警示（没聊到点上） |
|---|---|---|
| **D1 落到本组命题** | 用本组命题的规模底数（对照 76/75/38/47/54/26、3835 行、7 域）来研讨，不空谈 | 脱离本组命题，或自造数字、严重偏离规模清单 |
| **D2 识别一致性维护是主成本（核心）** | 研讨数清五类校验动作，且**点出 B-8 越界的下游放大**和多人沟通损耗 | **只盯"打字工时"，没认到一致性维护是主成本**（把成本当"打字慢"而非"一致性维护"） |
| **D3 诚实不乐观** | 错误率量级不糊弄、说得出可辩护的假设；含 B-9 式"不确定就挂账"的态度 | 判断无假设支撑，或错误率乐观到不可信；对 SDK 能力想当然"假设都支持"（撞 B-9） |
| **D4 说得清平台价值** | 能用一句话说清平台替我们扛了什么风险、值不值，量级站得住 | 说不出平台价值密度，或与研讨量级脱节 |

**评级参照**：四维都聊透 = 真懂了平台的价值密度在"一致性维护"；D2 只盯打字 = 没听懂本讲。
**一票警示**：**D2 把成本当成"打字慢"而非"一致性维护"** —— 视为没听懂本讲，需重听要点页 3；对 SDK 能力想当然"假设都支持"即撞 B-9，同样警示。

## 五、复盘研讨（3 题，教练收口，18′）

1. **（价值密度）** 你组算出的"手工 ÷ 平台"倍率是多少？这个倍率里，有多少来自"打字慢"，有多少来自"一致性维护 + 返工 + 沟通损耗"？哪一块是平台真正的价值密度所在？
2. **（发现成本曲线）** B-8 的越界，在平台里是编译期当场报错（零成本发现）；在手工模式里可能要到集成/对账阶段才暴露（高成本发现）。请把"错误发现得越晚越贵"这条曲线，套到你自己正在做的项目上举一个例子。
3. **（无平台怎么办）** 如果你所在的项目**没有** Astra Studio 这样的成熟平台，你打算用哪些"半固化"手段（review 清单 / 命名约定 / pre-commit 钩子 / docstring 挂账）替代校验器？这些替代手段的持续维护成本记在谁头上？

> 教练收口锚点：题 1 指向"倍率主要不来自打字"——价值密度在一致性维护；题 2 回收 B-8 的发现成本曲线（编译期便宜 vs 对账期昂贵）；题 3 引 B-9 纪律——"不确定就显式挂账（docstring），把存疑留成白纸黑字，而不是'应该支持吧'往前推"，与第 3 讲"错文号比空缺更有害"同一条纪律。

## 六、参考答案要点（讲师版 · 标"讲师专用勿发学员"）

> ⚠️ 讲师专用，勿发学员。下面是引导标尺，不是唯一正解——学员的绝对数字可以不同，关键看结构对不对。

**关于推演倍率的合理区间**：不追求精确值，追求学员意识到"倍率主要不来自打字"。一个可引导的参照：仅悬空引用检查一项，75 Link + 54 Action = 129 条引用，每条人工核 2–3 分钟且需交叉查对象是否存在，单人一遍就是 4–6 小时且必然有漏；7 域 × 多轮 × 返工放大后，手工达到"零悬空"的成本是平台"当天 7/7"的**一到两个数量级**。重点不是这个数，是让学员自己撞到"人类做跨对象一致性维护，慢且必错"这堵墙。

**必须点破的三个常见错误**：
- **只算打字工时**：最典型的失分。要追问"3835 行是机械生成的，手写才是问题；但手写更大的问题是 76 个对象命名跨 7 域保持一致——这是 B-5（数据张冠李戴）的放大版"。
- **错误率给太低**：谁写"我很仔细所以错误率 1%"，直接用 B-8 反问："训练有素的 FDE 在有校验器兜底的情况下，编译期还**多次**想越域写入。没有校验器兜底，你凭什么相信自己 99% 不越界？"
- **漏掉发现成本曲线**：手工模式的致命点不是"会错"，是"错误发现得晚"。B-8 在平台里编译期发现（便宜），手工里可能对账期才发现（昂贵，且要追责、复现）。

**收口给标准答案骨架（三句结论范例）**：
1. 平台替我们承担了 **7 域跨 76 对象/75 链接的一致性维护与越界防护** 风险（B-8 靠校验器而非自觉挡住）；
2. 代价是 **平台建设 + 学习 + 管线维护** 的一次性与持续投入；
3. **值**，因为一致性维护是人类最易疲劳出错、且错误发现越晚越贵的环节，把它固化进校验器，等于把"复制加班"变成"复制能力"——**没有平台，你复制不了康养项目的 7/7，只能复制那个人的加班。**

**与 B-9 的联动提醒**：若有学员在 ⑤ SDK 能力核实里写"假设 SDK 都支持"，当场纠正——这正是 B-9 的错误姿势。正解是"不确定就显式挂账（docstring），把存疑留成白纸黑字，而不是'应该支持吧'往前推"，与第 3 讲"错文号比空缺更有害"同一条纪律。
