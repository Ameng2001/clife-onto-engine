## 〇、开场：这一步为什么值 60 分钟

学员的心理预期是"装个软件而已"。要先把预期扭过来：

> **你装的不是工具，是别人已经走通的方法论。**
> 康养项目 7 个域能在同一天并行编译、7/7 结构校验零悬空引用，靠的不是个人手速，是 `studio-planner → domain-model → studio-ontology` 这条**固化下来的管线**。没有它，同样的活要一个人在脑子里维持 7 套上下文——那不叫 FDE，叫更累的架构师。

**这也是为什么 T2 排在最前面**：后面七步全部依赖这一步装对。而更重要的是，**T2 本身就在示范一条 FDE 纪律——上客户现场前先跑冒烟测试。** 别在客户会议室里第一次执行安装命令。

## 五、翻车点（全部实测踩出来的）

### ⚠️ 1. 装完当前会话看不到新 skill —— 最真实的课堂翻车点

**现象**：`plugin install` 明确回报 `✔ Successfully installed`，但技能列表里就是没有 `/studio-ontology:*`。
**原因**：插件在会话启动时加载，装完不会热更新。
**后果**：学员判定"装失败了"，开始反复卸载重装，浪费十分钟还越搞越乱。
**处置**：**T2 收尾统一重启一次 Claude Code**，重启后逐个确认命令可见。

> 💡 这条是本次备课**实测撞上的**：装好 studio-ontology 后当前会话仍看不到，重启后 4 个 command + 5 个 skill + 2 个 agent 全部出现。

### ⚠️ 2. 不跑 `marketplace update` 就装不到 studio-ontology

**原因**：studio-ontology 是后加进 marketplace 的，旧快照里根本没有它。实测本机快照停在 4 月 12 日，只有 7 个插件；`update` 之后变成 9 个（新增 studio-ontology + fund-review）。
**正常现象**：update 时会打印 `Found stale directory, cleaning up and re-cloning…` —— 这是陈旧缓存被清理重克隆，**不是报错**，别慌。

### ⚠️ 3. 升级不能靠重装

改版后必须 `marketplace update` + `plugin update X@astra-studio`；**再跑一次 `install` 是无效的**。远端如果没有 bump 版本号，本地也识别不到更新。兜底手段：`claude plugin install --force`。

### ✅ 4. 两个仓库 URL 都能用（曾经以为是坑，已澄清）

插件文档里写的是 `github:Ameng2001/astra-studio-plugins`，而 marketplace 记录的是 `VanLengs/astra-studio-plugins`。**实测 `git ls-remote` 两个 URL 返回同一个 commit** —— 是同一仓库改名后 GitHub 自动重定向，两条都能拉通。讲义统一用 `VanLengs` 即可，**不必当成故障排查**。

## 六、知识（讲什么）· 平台=方法论的固化物

装完之后立刻回答学员心里那个问题：**"这一堆插件到底替我做了什么？"**

### 核心命题

> **没有平台的 FDE，只是一个更累的架构师；平台 = 方法论的固化物。**
> **推论（难听话，讲的时候要撂下来）：没有平台，你复制不了康养项目，你只能复制加班。**

**这一讲真正的靶子是一个认知误区**：学员会把康养项目的成绩归功于"某个人手快 / AI 强"。要把功劳掰回到**管线**上——`studio-planner → domain-model → clife-onto-engine → citations 治理 → 可研生成`，这条固化管线才是"7 域同日并行编译、7/7 零悬空引用"的真实原因。

### ① 先算一笔账：人到底省在哪（5′）

| | 投入 | 接缝 |
|---|---|---|
| **传统模式** | 产品经理 + 架构师 + 行业顾问 + 方案经理 + 美工 → **5+ 人 · 数周** | ≥4 道 |
| **康养项目** | **1 名 FDE + 智能体编队** · 平台管线 → **数日** | 0 |

同一批交付物：**100+ 页可研（11 章 / ~11 万字 / 26 图）+ 2 份附录 docx**，底下压着 **7 个数智本体、3835 行可运行插件骨架（纯 .py）+ 21 个 YAML、约 350 万条三元组**。

```
省掉的那 4 个人，不是"AI 很聪明"省的，是【固化管线】省的
```

> **这就是 T2 值 60 分钟的理由**：学员现在敲的这几条 `plugin install`，装的正是那条管线。

### ② 三层固化（讲清这三层，学员才知道自己在装什么）

| 层 | 固化了什么 | 体现在 |
|---|---|---|
| **工具层** | 做事的步骤顺序 | studio-planner 的 5 步流水线，不用每次想"先干哪个" |
| **结构层** | 产物的形状 | 每个 skill 的产出路径与章节结构固定，下游能直接消费 |
| **纪律层** | 什么不许做 | validate 的治理审计（每条规则必须有 source）、编译红线（只 import sdk） |

**第三层最值钱**：工具能省时间，纪律能防事故。

**最硬的一个例子**：DDD 说"限界上下文之间不能越界写对象"——这是一句写在书上、靠人自觉的方法论。在康养项目，它变成了 `clife-onto-engine` 的一条**结构校验器规则**：任何 Action 想 `stage_write` 一个不属于本域的对象，编译期直接拦下。

> **方法论从"你应该"变成了"你做不到"。这就叫固化。**
> 一句话定义：**平台把"资深 FDE 脑子里的纪律"，变成了"新人也绕不过去的校验器"。**

### ③ 业界坐标：Palantir 四层 ↔ C-Life 两套 plugin 体系（延展段，时间紧可略）

先给学员一个坐标，免得他们以为 Astra Studio 是我们拍脑袋造的玩具。**Palantir 的平台架构分四层**：最底 **Foundry 数据底座层** → **Ontology 本体层**（业务语义中枢：实体/关系/权限与边界建模）→ **AIP 编排层**（运行时就是 Agents · Skills · Tools · Workflows）→ 最顶 **应用层**；右侧横着一条**跨层治理与安全**（身份/权限/审计追溯/合规）。一句话：**以本体为核心的企业智能操作系统。**

**C-Life 本质上也是这套结构，而且落成了两套可安装、可校验的 plugin 体系**：

| 维度 | 智能体 plugin 体系（Astra Studio） | ontology plugin 体系（clife-onto-engine） |
|---|---|---|
| **对标 Palantir** | AIP 编排层（Agents/Skills/Tools/Workflows） | Ontology 本体层（业务语义中枢） |
| **一个插件长啥样** | 一组 Skill（`SKILL.md`）+ `plugin.json` manifest | 一域一插件，四文件：`__init__.py`（五要素）+ `mappings/objects.yaml` + `cq/golden.yaml` + `plugin.yaml` |
| **规范/红线** | SKILL.md 结构规范、manifest 契约、命令与依赖声明 | **只 import `clife_onto_engine.sdk`**、`plugin.yaml` 五字段、跨域一律 ref/发布不越界 |
| **校验器** | `studio-quality:validate`（结构/合规/技能质量） | `py_compile` + `ontology-validate` 四段：**A 结构（零悬空）/ B 治理（citations/source）/ C 剩余 TODO / D 行为 CQ** |
| **康养项目实证** | 8 插件在跑、管线一键串联 | 7 域 7/7 py_compile、A 结构 7/7 零悬空、48 条 golden CQ（含 17 rejected） |

> **本页题眼**：**规范 + 校验器，就是"平台把方法论固化成纪律"的物理形态。**
> 平台值不值钱，**不看它功能多，看它的规范有多硬、校验器认不认。**
> **学员现在装的这一排插件，装的就是左列那一套；T5 编译出来的本体插件，是右列那一套。**

### ④ 三个"同日"：平台省的不是打字，是一致性维护（7′）

```
三个"同日" = 平台省掉的不是打字，是一致性维护
① 7 域同日并行编译 · 7/7 校验通过（py_compile + YAML + 只 import sdk 红线）
② 7/7 结构校验零悬空引用 · B source 治理 7/7（0 空 source）
③ 3835 行骨架机械生成（非手写）+ 21 YAML + 121 处 NotImplementedError 显式挂账
人类弱项 = 跨 76 对象 / 75 链接的一致性维护 → 交给校验器
```

- **第一个同日**：D1 建完，D2–D7 照着 D1 这个范本并行建、机械编译，7 个插件骨架当天成型，统一校验 7/7 通过。
- **第二个同日**：手工干这件事试试——7 个域、**Object 76 / Link 75** 交叉引用，谁引谁、有没有引到一个不存在的对象，人眼查一遍要多久、错几处？
- **第三个同日**：3835 行不是有人手写的，是本体 IR 经编译器机械展开的。人手写，光是把 **76 个 Object、54 个 Action** 的命名保持一致就够呛。

**五要素跨域规模（量级标尺，背下来）**：`Object 76 / Link 75 / Function 38 / Rule 47 / Action 54 / HIL 26`。

> **结论**：**平台的价值密度，集中在"跨对象一致性维护"这件人类最不擅长、最容易疲劳出错的事上。**

### ⚠️ 反例 B-8（越域写入冲动）

编译 7 个域的时候，好几次都想让一个 Action **直接** `stage_write` 别的域的对象——比如 D1 的智能体链路，方案审核通过了，最省事的写法是直接去 D3 把销售订单写了、去 D2 记一笔结算、去 D4 更新画像。一步到位，多爽。

最后的处理是：**跨域发布（→D3 Order / →D2 结算 / →D4 画像）全部写成注释和 ref，不越界 `stage_write`**；整个 7 域"越域一律 ref/发布，不建越域 Link"。

> **挡住这个冲动的不是"觉悟高"，是校验器**——越域 `stage_write` 过不了 A 结构校验，会当场报悬空/越界。
> **所以 7/7 零悬空，不是因为我们 7 次都自觉，是因为校验器不给我们自觉的机会。**
> **原则：结构纪律靠校验器，不靠自觉。** 这条在 T4（域切分）和 T5（`check_plugin_capabilities.py`）都会回收。

### ⚠️ 反例 B-9（SDK 能力想当然）

编译期要用 `PropertySpec.default`、`Evaluation` 这些 SDK 能力，但当时**不确定引擎到底导没导出**。本机没有引擎仓库，只能 `py_compile`，验证不了运行时。

两种态度：一种"应该支持吧"直接往前写；另一种——最后选的——**不确定就显式挂账**，`Evaluation` 未导出 → **7 域统一落到 docstring**，白纸黑字写明"此处依赖 X，待引擎仓库内确认"。

> **这个判断在 T5 被验证是对的**：`compile-rules.md` 的固定头部确实漏了 import `Evaluation`，照着生成会 NameError。**当初挂账的人是对的。**
> **对平台的意义**：平台会告诉你它**保证什么**（py_compile、只 import sdk），也会暴露它**不保证什么**（运行时符号导出）。**成熟的 FDE 要读懂校验边界，在校验器覆盖不到的地方，用 docstring 手动补一道"诚实闸"。**

### ⑤ 固化三问：一个可迁移的心智模型（收口）

任何一条你反复叮嘱新人的纪律，都问三个问题：**能不能固化？固化成什么？谁来跑？**

| 纪律 | 能不能固化 | 固化成什么 | 谁来跑 |
|---|---|---|---|
| 跨域不许越界写 | 全固化 | A 结构校验器 | clife-onto-engine 编译期（B-8） |
| 关键数字锚在单点、不重算 | 全固化 | BRIEF 单一真相源 + 装配期一致性检查 | docs/quality（**B-5 就是没跑好的反例**） |
| SDK 能力不确定就挂账 | **半固化** | docstring 挂账约定 | **FDE 人肉走一道**（B-9） |

```
固化三问：能不能固化？固化成什么？谁来跑？
全固化  → 校验器   → 零人力、永不疲劳（越域校验 B-8、结构 7/7）
半固化  → 挂账约定 → FDE 人肉走一道（citations 挂账、SDK B-9）
未固化  → 全靠自觉 → 请假即崩（这就是"更累的架构师"的默认状态）
平台成熟度 = 你有多少条纪律进了校验器
```

> **纪律的固化程度，决定了它需要多少人力持续维护。**
> **Astra Studio 之所以能让 1 个人干 5 个人的活，是因为它把资深 FDE 脑子里那批一致性纪律，绝大部分搬进了编译期和装配期的校验器。**

### 活证据 · fund-review（现成的、可点开的）

`Plugins/fund-review-plugins/` 是政府采购报价优化 + 财评预审插件，**首发案例就是学前教育项目**——某工业城市仓 `配置清单/内部包/_原始工作区/*.json` 就是它跑出来的会话产物。

> **一个真实交付项目里反复做的动作，被沉淀成了可复用插件，下一个项目直接调用。** 这就是"平台=方法论固化物"最直白的样子。T8 会再回收一次。

### 💡 启发 · 顺带指出固化也发生在"输入端"（B-11 正面）

学员容易以为固化只发生在工具和代码里。其实**调研模板本身就是可固化的资产**：辣椒的调研件是照着草业项目那份换领域填的——第二个项目不必从零想"该问客户什么"。

> ⚠️ 但这条要**只讲正面、点到为止**：它的反面（模板会把上一个项目的数字一起带过来）是 **B-11**，主场在 T1，别在这里抢。

### 🔔 现场小推演（可选，5′；时间不够就留作课后）

> **残忍的问题**：如果没有平台，你自己手工重做康养项目这 7 个域的一致性校验，**要多久？会错几处？**

别拍脑袋说"挺快的"。给学员这份规模清单去推演：**7 域 · Object 76 · Link 75 · Rule 47 · Action 54 · 3835 行**，然后把推演结果和平台的"当天 7/7 通过"摆在一起。

### 口播 · 开场：先算一笔账（对应 §六 ①）

"我先不讲平台，先给你们看一个数字，然后你们自己判断这数字是靠谁堆出来的。康养项目这个项目，最终交付了 100 多页可研（11 章、约 11 万字、26 图）加 2 份附录 docx，底下压着 7 个数智本体、3835 行可运行插件骨架、约 350 万条三元组的知识图谱。传统模式，这活儿是**产品经理 + 架构师 + 行业顾问 + 方案经理 + 美工，5 个人以上、干数周**。这次是**1 名 FDE + 智能体编队**。

现在关键问题来了：省下的那 4 个人、那几周，是被'AI 很聪明'省掉的吗？不是。是被**平台**省掉的。今天这堂课就论证这一句话。你要是听完还觉得是靠个人天赋，那你回去只能复制加班，复制不了康养项目。"

### 口播 · 平台不是工具箱，是纪律的容器（对应 §六 ②）

"很多人对'平台'的理解停留在'一堆好用的工具'。错。平台不是工具箱，平台是**方法论被代码固化以后的样子**。

举个最硬的例子：DDD 说'限界上下文之间不能越界写对象'。这是一句方法论。方法论写在书上，靠人自觉。但在康养项目，这句话不是靠自觉——它变成了 `clife-onto-engine` 的一条**结构校验器规则**：任何 Action 想 `stage_write` 一个不属于本域的对象，编译期直接拦下来。方法论从'你应该'变成了'你做不到'。这就叫固化。

所以我给平台下的定义是：**平台把'资深 FDE 脑子里的纪律'变成了'新人也绕不过去的校验器'**。这句话是本讲的题眼。你没有平台的时候，那些纪律只活在你一个人脑子里，你请假纪律就崩了；有了平台，纪律活在管线里，谁来都得守。"

### 口播 · Palantir 四层与两套 plugin 体系（对应 §六 ③，延展段）

"给你们一个业界坐标，你就明白 Astra Studio 不是我们拍脑袋造的玩具。看 **Palantir 的平台架构——四层**：最底 **Foundry 数据底座层**（接入任何数据源、语义化数据服务）；往上 **Ontology 本体层**（业务语义中枢——实体建模 / 关系建模 / 权限与边界建模，'统一语义 · 业务规则 · 逻辑一致 · 权限边界'）；再往上 **AIP 编排层**（多智能体协同 / 自然语言交互 / 确定性运行时 / 安全治理——它的运行时就是 **Agents · Skills · Tools · Workflows**）；最顶 **应用层**（面向行业的智能应用）。右侧还横着一条 **跨层治理与安全**（统一身份 / 权限 / 审计追溯 / 数据安全 / 合规标准）和一列 **价值输出**（决策 / 优化 / 风控）。一句话：**Palantir 是'以本体为核心的企业智能操作系统'。**

现在关键——**C-Life 的工程化平台，本质上也是这套结构，而且它落成了两套可安装、可校验的 plugin（插件）体系**：
- **第一套：智能体 plugin 体系（对标 Palantir 的 AIP 编排层）** —— 就是 **Astra Studio**。studio-planner / insight / docs / quality 这些插件，每一个都是一组 **Skill**（SKILL.md），把'事件风暴 → 限界上下文 → 文档装配 → 质检'这套 FDE 方法论，固化成可被编排调用的技能。它对应 Palantir 的 Agents / Skills / Tools / Workflows。本会话启动时那句 '8 active plugin(s)'，就是这套体系在跑。
- **第二套：ontology plugin 体系（对标 Palantir 的 Ontology 本体层）** —— 就是 **clife-onto-engine 的本体插件**。康养项目 7 个域，每个域编译成一个**本体插件**，装进引擎运行。这是'业务语义中枢'的 C-Life 落地。

**为什么强调这个？因为这两套体系各自都有一套硬工程化规范——规范，才是平台的灵魂。** 平台值不值钱，不看它功能多，看它的**规范有多硬、校验器认不认**。"

### 口播 · 两套体系收口（对应 §六 ③ 表格之后）

"看懂这张表你就懂了本讲的题眼：**规范 + 校验器，就是'平台把方法论固化成纪律'的物理形态。** 智能体插件那套规范，保证任何人写的 Skill 都能被编排、被质检；本体插件那套规范——'只 import sdk''四文件''零悬空'——保证任何人建的域都能被引擎装载、被静态校验。**Palantir 用四层架构把这件事做成了一个操作系统；C-Life 用两套 plugin 体系把它做成了你能安装、能校验、能复制的东西。** 这就是为什么 FDE 依赖平台：没有这两套规范，你的'方法论'永远只是你嘴上的叮嘱，落不成别人也能跑的资产。"

### 口播 · 三个"同日"（对应 §六 ④）

"平台到底省了什么？不是省你打字，是省你**维护一致性**。我给你们看三个'同日'。

第一，**7 个域同一天并行编译**。D1 建完，D2–D7 六个域照着 D1 这个范本并行建、机械编译，7 个插件骨架当天成型，统一校验 7/7 通过：py_compile 全过、每域 3 个 YAML 全过、'只 import sdk'红线全过，共 3835 行。

第二，**7/7 结构校验零悬空引用**。ontology-validate 静态跑 A 结构：7 个本体全部零悬空引用，跨域纪律守住；B source 治理 7/7，0 空 source。你想想手工干这个——7 个域、76 个 Object、75 个 Link 交叉引用，谁引谁、有没有引到一个不存在的对象，人眼查一遍要多久，错几处？

第三，**3835 行骨架自动生成**。这不是有人手写了 3835 行，是本体 IR 经编译器机械展开的。人手写 3835 行，光是把 76 个对象、54 个 Action 的命名保持一致就够呛，B-5（数据张冠李戴）就是人手维护一致性翻车的活证据——那还只是几个数字。

结论：**平台的价值密度，集中在'跨对象一致性维护'这件人类最不擅长、最容易疲劳出错的事上。**"

### 口播 · 反例 B-8 越域写入冲动（对应 §六 B-8）

"讲个我们自己犯的冲动。编译 7 个域的时候，好几次都想让一个 Action **直接** `stage_write` 别的域的对象——比如 D1 的智能体链路，一个方案审核通过了，最省事的写法是直接去 D3 把销售订单写了、去 D2 把结算记一笔、去 D4 把画像更新了。一步到位，多爽。

但这是**越域写入**。DDD 的铁律是：跨域一律 ref / 发布，不能越界写别人家的对象。我们最后的处理是——**跨域发布（→D3 Order / →D2 结算 / →D4 画像）全部写成注释和 ref，不越界 stage_write**；整个 7 域'越域一律 ref/发布，不建越域 Link'。

注意，挡住这个冲动的不是我'觉悟高'。是 `clife-onto-engine` 的结构校验器：越域 stage_write 过不了 A 结构校验，会当场报悬空/越界。所以最后 7/7 零悬空引用，不是因为我们 7 次都自觉，是因为**校验器不给我们自觉的机会**。这就是平台把'跨域纪律'固化成校验器的实例。没有这个校验器，7 个域里哪怕有 1 处一时手滑越了界，你后面对账、追责、复现就是一场灾难。"

### 口播 · 反例 B-9 SDK 能力想当然（对应 §六 B-9）

"再讲一个更微妙的坑：**SDK 能力想当然**。编译期我们要用 `PropertySpec.default`、要用 `Evaluation` 这些 SDK 能力，但当时**不确定引擎到底导没导出**这些符号。本机没有引擎仓库，只能 py_compile，验证不了运行时。

两种态度：一种是'应该支持吧'，直接往前写；另一种是我们最后选的——**不确定就显式挂账**。`Evaluation` 未导出→7 域统一落到 docstring 里，白纸黑字写明'此处依赖 X，待引擎仓库内确认'。这跟第 3 讲主张 3 是同一条脊椎：**敢说不知道**。'错文号比空缺更有害'，'错用一个没导出的 SDK 符号，比显式挂账更有害'。

这里的教训对平台的意义是：**平台会告诉你它保证什么（py_compile、只 import sdk），也会暴露它不保证什么（运行时符号导出）。成熟的 FDE 要能读懂平台校验的边界，在校验器覆盖不到的地方，用 docstring 手动补一道'诚实闸'。**"

### 口播 · 固化三问收口（对应 §六 ⑤）

"我把前面收成一个你能带走的心智模型。任何一条你反复叮嘱新人的纪律，都要问自己三个问题：**能不能固化？固化成什么？谁来跑？**

- '跨域不许越界写' → 能固化 → 固化成 A 结构校验器 → clife-onto-engine 编译期自动跑（B-8）。
- '关键数字锚在单点、不重算' → 能固化 → 固化成 BRIEF 单一真相源 + 装配期一致性检查 → docs/quality 跑（B-5 就是没跑好的反例）。
- 'SDK 能力不确定就挂账' → 半固化 → 校验器管不到运行时，只能固化成 docstring 挂账约定 → FDE 人肉跑（B-9）。

看出来了吗：**纪律的固化程度，决定了它需要多少人力持续维护**。全固化的（越域校验），零人力、永不疲劳；半固化的（citations 挂账、SDK 挂账），需要 FDE 走一道人肉闸。你评估一个平台成不成熟，就看它把你多少条纪律固化进了校验器。**Astra Studio 之所以能让 1 个人干 5 个人的活，是因为它把资深 FDE 脑子里那批一致性纪律，绝大部分搬进了编译期和装配期的校验器。**

所以回到那句难听话：平台不是让你更快地打字，是让你**不必再靠意志力维持纪律**。你一个人靠意志力能守 3 天纪律，守不了 3 个月、守不了 7 个域同时。这就是为什么没有平台，你复制的只有加班。"
