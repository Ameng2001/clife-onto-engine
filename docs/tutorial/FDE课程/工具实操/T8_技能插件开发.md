## 二、spec-generate：唯一零确认点的一步

```
/studio-planner:spec-generate <plugin-name>
```

**前置**：`skill-map.md` **必需**（缺则打回 T4）

**产物严格分家**：

| 落到 `studio/changes/{plugin}/` | 落到 `{target_dir}/` |
|---|---|
| `brief.md`（H2：Business Context / Plugin Candidates / Success Criteria / Notes） | `skills/{skill}/SKILL.md` 骨架 |
| `plugin.json.draft`（默认 version `0.1.0`） | `commands/{skill}.md` |
| `status.json`（phase → `building`） | Moderate 及以上另建 `scripts/.gitkeep` |

**SKILL.md 骨架的 6 个 H2**：`## Intent` · `## Expected Inputs` · `## Expected Outputs` · `## Preconditions` · `## Workflow` · `## Out of Scope`

### ⭐ traits 在这里兑现（T4 选的开关，现在看到结果）

| trait | 生成什么 |
|---|---|
| `stateful` | 额外生成 `init-workspace` skill + command + **两个 runtime 模板**（生成的运行时工作区形如 `.{plugin}/config.yaml`、`projects/`、`agents/custom/`、`archive/`） |
| `hil-gated` | 给标了 HIL 的 skill，在 `## Out of Scope` **之前**插入 `## Approval Gate` 段，内含固定三选一：**✅确认 / ✏️修改 / ❌拒绝** |
| `multi-pipeline` | 每条流水线一个 `commands/{pipeline}.md` |
| `expert-scoped` | 生成 `agents/` 目录 |
| `kb-dependent` | 影响 skill 的数据依赖设计 |

> ⚠️ **注意区分两个 HIL**：
> - **T4/T8 的 `hil-gated`** → skill 层的**审批段**（人在对话里点确认）
> - **T5 的 `HilPolicy`** → Action 层的**副作用闸**（引擎冻结 effects 等人审）
> 一个在交互层，一个在执行层。**同一件事的两层落点，别混。**

### 失败处理：全是"不覆盖 + 打警告"

SKILL.md 已存在 → 不覆盖；templates 已存在 → 不覆盖；`modify` 模式下命令一律不覆盖只警告。
**最重要的一条**：本轮 `skill-map` 未列出的 skill —— **不得创建、不得删除、不得重写**。

> **这条纪律值得单讲**：工具不会"顺手帮你清理"没在计划里的东西。**边界之外一律不动**，这正是可预测性的来源。

## 三、build-skills：初稿不是成品

```
/studio-planner:build-skills <plugin-name>
```

**硬门**：`phase` 必须 == `building`，否则直接报错退出——
`planning` → 先跑 spec-generate；`approved` → 已构建校验过；`shipped` → 活动区已被 promote。

**它做什么**：不新建设计文档，**就地改写** `{target_dir}/skills/*/SKILL.md`，把骨架填成能跑的初稿。内部委托 `skill-creator`，**不由学员手动跑**。

### ⭐ 期望管理：SKILL 里有张 "Initial Fill, Not Final Build" 对照表

> **"scaffolding with substance"——有内容的脚手架，初稿不是成品。**
> 要用 **2–3 个真实场景**测试后再迭代。**需要迭代不是构建失败。**

**失败模式**：单个 skill 构建失败 → 该 skill 保持 `draft` 或标 `building-failed`；**phase 一律保持 `building`，绝不自动进入 validation**。

> **这个设计要点出来**：工具**不会自己给自己发合格证**。从 building 到 approved 必须过校验器那一关。

## 四、⭐ validate：校验器到底查什么（本步最有教学价值的部分）

```
/studio-quality:validate <插件目录路径>
```

三个 Python 脚本，**逐项列出来给学员看**——因为这张清单就是"什么叫做完了"的操作定义：

### A. 结构（`validate_plugin.py`，7 类）

| 检查 | 不过的后果 |
|---|---|
| `.claude-plugin/plugin.json` 存在（找不到退而找 `plugin.json.draft`） | 都没有 → **failed** 并提前返回；**用 draft 会产生 warning**："这是开发工作区，不是最终插件" |
| JSON 可解析 | failed |
| 必填 `name` / `version` / `description` 非空 | failed |
| name 匹配 `^[a-z][a-z0-9-]*$` | **failed** |
| name == 目录名 | **warning**（不是 failed） |
| version 匹配 `^\d+\.\d+\.\d+` | failed |
| 声明的 `skills`/`commands`/`hooks`/`mcpServers` 路径能 resolve | failed |

### B. 技能（`validate_skills.py`，逐 skill 9 类）

| 检查 | 说明 |
|---|---|
| `skills/` 存在、每个子目录有 `SKILL.md` | failed |
| **行数 ≤ 500** | 超出 = warning（含实际行数） |
| frontmatter 可解析、`name` 存在 | failed |
| **`description` ≤ 1024 字符** | 超出 = **failed** |
| name == 目录名 | warning |
| **未知 frontmatter key** | warning。**白名单只有 7 个**：`name, description, allowed-tools, user-invocable, disabled, trigger, model` —— 注意 `argument-hint` 之类都会被判 unknown |
| **正文引用的 `scripts/xxx.py`、`references/xxx.md` 必须真实存在** | **failed**；例外：引用前 50 字符内出现 `${CLAUDE_SKILL_DIR}` 则跳过 |

> ⭐ **最后这条是 B-3（图片路径断裂）的同类机制**：**占位符即契约**——你在文档里写了要引用的文件，它就必须存在。
> 康养项目当年是 docx 导出丢图，这里是校验器直接判 failed。**同一条纪律，两个场景。**

### C. 依赖（`check_dependencies.py`，3 组）
`.mcp.json`（每个 server 必须有 `command`，重名 failed，env 含 `${` 给 warning 提醒写文档）· `hooks.json`（**事件名白名单 6 个**：SessionStart, SessionEnd, PreToolUse, PostToolUse, Notification, Stop）· `dependencies[]`（找不到 = warning）

### 报告

**终端**：三行汇总 `Structure: / Skills: / Dependencies:` + `Errors:` 段（前缀 `[structure]` / `[skill:{name}]` / `[dependency]`）+ `Warnings:` 段 + 末行 `Overall:`
**文件**：`{plugin-dir}/.validation-report.json`，**verdict 只有 PASS / FAIL 两值，warning 不影响 verdict**。FAIL 时退出码 1。

> ⚠️ SKILL.md 的示例用 ✅/⚠️ emoji，**实际脚本输出的是纯文本 `PASS`/`WARN`/`FAIL`**。以脚本为准。

**⏸ 唯一确认点**：通过后问你要不要更新工作区的 `status.json`。同意则：skill `built → tested`、phase → `approved`。
**规则是"只前进不倒退"**——不会把已 tested 的降级。

## 五、wire-mcp：给你做的插件配 MCP

```
/studio-quality:wire-mcp <插件目录>  [--merge]
```

**它扫什么**：每个 `SKILL.md` 的 ① `allowed-tools:` 行里的 `mcp__*` ② 正文里的完整工具名 ③ **9 条能力关键词**（database / postgresql / mysql / sqlite / web search / browser / slack / github api / filesystem access）

**匹配**：7 条 server 正则，**首个命中即 break**；没命中的进 `unmatched` 报给你
**自动补默认 env**：github → `GITHUB_PERSONAL_ACCESS_TOKEN`、slack → `SLACK_BOT_TOKEN`、brave-search → `BRAVE_API_KEY`、postgres → `POSTGRES_CONNECTION_STRING`
**`--merge`**：已存在的同名 server **不覆盖**
**一个都没匹配** → 打印"不需要 MCP"并**不写文件**

> ⚠️ **它是"给你做的插件配 MCP"，不是"给 studio 自己装 MCP"**。studio-* 自身除 studio-design 存疑外无 MCP 依赖。

## 六、promote：发版与归档

```
/studio-core:promote <plugin-name>  [v0.2.0]
```

**6 条硬前置**：① status.json 存在 ② **phase == `approved`** ③ 能拿到 `target_dir` ④ 目标目录存在且 `skills/` 下有 SKILL.md ⑤ **所有在范围内的 skill 状态为 `tested`** ⑥ 目标目录非空（空则 abort）

**版本推进规则**：
1. 已有 `plugin.json` → 读现有 version，**patch +1**（`0.1.0 → 0.1.1`）
2. 命令行给了显式版本 → 用它（覆盖上一条）
3. 无 manifest → 用 `plugin.json.draft` 的版本（默认 `0.1.0`）

**归档规则**：`studio/archive/{plugin}/{YYYY-MM-DD}-iteration-{N}/`，同名已存在则加后缀 `-1`、`-2`。
**是 copy 不是 move** —— 活动工作区保留。
归档副本：`phase=shipped` + shipped_at/version/to/archive_path。
活动副本：**`iteration+1`、phase 重置为 `planning`** + last_shipped_*。

**⭐ promote 明确不做的事**（这张"不做"清单比"做"更值得讲）：
> 不拷贝实现文件 · **不 `git add/commit`** · 不删实现文件 · **不跑校验** · 不删活动工作区 · **不把 promote 当终态**

> **为什么不自动 commit**：因为**提交是人的决定**。工具把状态推进到位，**但"我认可这个版本"这句话必须由人说出口**。
> 顺带：`git diff studio/` 是唯一的迭代历史来源——这也是 T2 强调 `studio/` 必须 git-tracked 的原因。

## 七、实操（90′）

| 序 | 做什么 | 时长 |
|---|---|---|
| 1 | `spec-generate`，看 traits 兑现成了什么 | 20′ |
| 2 | `build-skills`，读 1–2 份生成的 SKILL.md | 25′ |
| 3 | `validate`，**故意制造一个 failed 再修好** | 25′ |
| 4 | `promote`，看归档目录与版本号 | 10′ |
| 5 | 对照"不做清单"，手动 `git add` 并写 commit | 10′ |

**🔔 交付物**：一个通过校验、可发版的插件 v0.1

**🔔 强烈建议的一个动作：故意让校验失败一次**
比如把某个 SKILL.md 里引用的 `scripts/foo.py` 删掉，跑 validate 看它报 failed，再修好。
> **学员亲眼看到校验器抓住自己**，比听十遍"纪律靠机制"都管用。

## 九、知识（讲什么）· 三层固化回收 + 团队编成（30′）

> ⚠️ **与 T2 的分工，先说清楚**：T2 讲的是**平台是什么、省了什么**（平台=方法论固化物、Palantir 四层对照、三个"同日"）。
> **T8 只讲一件事：纪律是怎么被固化的，以及校验器怎么在你想抄近道的时候替你守住。** 别在这里重讲一遍 T2，学员会走神。

### 9.1 讲 5 回收：三层固化，走完八步才集齐

T2 讲过三层，那时它还是三个抽象名词。走完八步后回来看，每一层都有了具体落点：

| 层 | 固化了什么 | 在哪见到的 |
|---|---|---|
| **工具层** | 做事的步骤顺序 | T4 的 5 步流水线、T6 的 plan→write→assemble |
| **结构层** | 产物的形状 | 七段 IR、蓝图 structure、skill-map 的 H2、SKILL.md 的 6 个 H2 |
| **纪律层** | **什么不许做** | **T5 的 CI 红线执法、T6 的编号权归装配、T8 的校验器 + "不做清单"** |

> **第三层最值钱**：工具能省时间，**纪律能防事故**。
> 而且纪律有个特点：**它在你最想违反的时候生效**——凌晨三点赶工期时，你不会守纪律，但 `validate_skills.py` 会。

### 9.2 ⭐ 固化三问：这一节是学员唯一要带走的心智模型

任何一条你反复叮嘱新人的纪律，都问它三个问题：**能不能固化？固化成什么？谁来跑？**

| 档 | 例子 | 固化成什么 | 谁来跑 | 人力成本 |
|---|---|---|---|---|
| **全固化** | "跨域不许越界写" | A 结构校验器 | 编译期自动 | **零人力，永不疲劳** |
| **全固化** | "SKILL.md 引用的脚本必须存在" | `validate_skills.py` | `/studio-quality:validate` | 零人力 |
| **半固化** | "关键数字锚在单点、不重算" | BRIEF 单点 + 装配期一致检查 | docs/quality 跑，人复核 | FDE 走一道人肉闸 |
| **半固化** | "SDK 能力不确定就挂账" | docstring 显式挂账约定 | **人肉跑** | FDE 走一道人肉闸 |
| **未固化** | 只活在你脑子里的那条 | 无 | 全靠自觉 | **请假即崩** |

> **纪律的固化程度，决定了它需要多少人力持续维护。**
> **评估一个平台成不成熟，就看它把你多少条纪律固化进了校验器。**
> 康养项目能做到 **1 名 FDE + 智能体编队**顶掉传统 **5+ 人 / 数周**，不是因为手快，是因为绝大部分一致性纪律被搬进了编译期和装配期。

**现场提问（30″，效果比讲十分钟好）**：
> "你本组命题里，现在还有哪一条纪律是**全靠你自觉守**的？它能不能往校验器方向推一格？"

### 9.3 校验器替你守纪律：两个真实的"想抄近道"（B-8 / B-9）

这两条不是设想出来的教学案例，是康养项目编译期真实发生的冲动与存疑。**它们证明的是：训练有素的 FDE 也会想抄近道，靠自觉挡不住。**

| | **B-8 越域写入冲动** | **B-9 SDK 能力想当然** |
|---|---|---|
| 冲动是什么 | 让一个 Action 直接 `stage_write` 别的域的对象（一步到位，省事） | `PropertySpec.default` / `Evaluation` 到底导没导出，不确定但"应该支持吧" |
| 谁挡住了它 | **A 结构校验器**——越域 `stage_write` 过不了校验，当场报悬空/越界 | **没人挡**——校验器管不到运行时符号导出 |
| 最终处置 | 跨域发布（→D3 Order / →D2 结算 / →D4 画像）**全部写成注释和 ref**，不越界 | 7 域统一在 docstring 里**显式挂账**："此处依赖 X，待引擎仓库内确认" |
| 结果 | **7/7 零悬空引用** | 存疑白纸黑字留在代码里，不被遗忘 |
| 档位 | **全固化** | **半固化** |

> ⭐ **B-8 的教学点**：7/7 零悬空**不是因为我们 7 次都自觉**，是因为校验器不给我们自觉的机会。
> ⭐ **B-9 的教学点**：**平台会告诉你它保证什么（py_compile、只 import sdk），也会暴露它不保证什么（运行时符号导出）。** 成熟的 FDE 要能读懂平台校验的**边界**，在校验器覆盖不到的地方，用 docstring 手动补一道"诚实闸"。

**接回本步实操**：T8 §七让学员**故意制造一次 failed**，就是让每个人亲身体验一次 B-8——**被校验器抓住一次，胜过听十遍"纪律靠机制"。**

### 9.4 讲 8：三级能力锚（这是结课定级的口径，T9 直接用）

| 级 | 判据 |
|---|---|
| **L1 见习** | 能在 FDE 指导下**承接单一环节** |
| **L2 胜任** | 能**独立完成认知侧全链条**，交付物**需一次复核** |
| **L3 主理** | 能**主持项目、设 HIL 闸、对客户承诺负责**，并**能带 L1** |

**硬口径两条，讲师必须原话说出来**：

> ① **C1–C6 可训练，C7（客户关系 / 责任承担 / 价值判断 / 政治敏感度）只能筛选。**
> 这八步教的全是 C1–C6。**C7 教不了——但这八步走一遍，能照出你在 C7 上缺什么。**

> ② **多数人第一次会停在 L1，这是正常的，装作 L2 才是危险的。**

**所以结课不发"合格证"**：发的是**能力等级 + 差距清单**。T9 结课定级用的就是这三级锚，学员在 T8 就该知道自己会被怎么量。

**C7 的锚点，全在这门课里出现过**：
- **客户关系 / 政治敏感度** → 康养项目 **11 处地方文号**查不到，**坚决留占位不编造**，转成向机关逐项取件的清单。原话：**"错文号比空缺更有害。"**
- **价值判断** → 站长 HIL 的 **0.75 置信度阈值**：不是算出来的，是权衡出来的。
- **责任承担** → 对外一律写"赋能优化"而非"替代"——**因为承担说错话后果的是人。**

### 9.5 讲 8：团队编成随交付模式变

| | **模式一（Token-SaaS）** | **模式二（平台建设 + 运营）** |
|---|---|---|
| 编成 | **轻**：1 FDE + 平台/运行时组 | **重**：1 主理 FDE(L3) + N 见习(L1) + 平台组 |
| FDE 吃重 | T3 快 + T5 设闸 + T7 产品化；T6 轻 | 全链，尤重 T5 合规 / T6 可研 / 商业建模 |
| 半径要求 | 快跑快迭代 | 扛得起可研、财务测算、监管合规——**商业与合规半径宽得多** |

**三个角色各自提供什么**（这句是编成的本质）：
> **L3 提供判断和责任（C7 + 高阶 C1–C6），L1 提供手数和成长通道，平台组提供杠杆。三者缺一，康养项目都不可复制。**

**平台组不是 FDE**，是让 FDE 不必"更累"的人。**没有平台组，L3 就退化成一个更累的架构师。**

> ⚠️ **一句冷水**：能做模式二的大平台，**不代表**你能做模式一的 SaaS 应用，反之更是。
> 真正的分水岭是 **C1 认知萃取的跨行业迁移力**——换个你不熟的行业，沉淀归零、**只剩方法**，你还压得出可归域的结构吗？**这就是 L2 和 L3 的分界。**

### 口播 · B-8 越域写入冲动：挡住它的是校验器不是自觉

"讲个我们自己犯的冲动。编译 7 个域的时候，好几次都想让一个 Action **直接** `stage_write` 别的域的对象——比如 D1 的智能体链路，一个方案审核通过了，最省事的写法是直接去 D3 把销售订单写了、去 D2 把结算记一笔、去 D4 把画像更新了。一步到位，多爽。

但这是**越域写入**。DDD 的铁律是：跨域一律 ref / 发布，不能越界写别人家的对象。我们最后的处理是——**跨域发布（→D3 Order / →D2 结算 / →D4 画像）全部写成注释和 ref，不越界 stage_write**；整个 7 域'越域一律 ref/发布，不建越域 Link'。

注意，挡住这个冲动的不是我'觉悟高'。是 `clife-onto-engine` 的结构校验器：越域 stage_write 过不了 A 结构校验，会当场报悬空/越界。所以最后 7/7 零悬空引用，不是因为我们 7 次都自觉，是因为**校验器不给我们自觉的机会**。这就是平台把'跨域纪律'固化成校验器的实例。没有这个校验器，7 个域里哪怕有 1 处一时手滑越了界，你后面对账、追责、复现就是一场灾难。"

### 口播 · B-9 SDK 能力想当然：读懂校验器的边界

"再讲一个更微妙的坑：**SDK 能力想当然**。编译期我们要用 `PropertySpec.default`、要用 `Evaluation` 这些 SDK 能力，但当时**不确定引擎到底导没导出**这些符号。本机没有引擎仓库，只能 py_compile，验证不了运行时。

两种态度：一种是'应该支持吧'，直接往前写；另一种是我们最后选的——**不确定就显式挂账**。`Evaluation` 未导出→7 域统一落到 docstring 里，白纸黑字写明'此处依赖 X，待引擎仓库内确认'。这跟第 3 讲主张 3 是同一条脊椎：**敢说不知道**。'错文号比空缺更有害'，'错用一个没导出的 SDK 符号，比显式挂账更有害'。

这里的教训对平台的意义是：**平台会告诉你它保证什么（py_compile、只 import sdk），也会暴露它不保证什么（运行时符号导出）。成熟的 FDE 要能读懂平台校验的边界，在校验器覆盖不到的地方，用 docstring 手动补一道'诚实闸'。**"

### 口播 · 固化三问：一个可迁移的心智模型

"我把前面收成一个你能带走的心智模型。任何一条你反复叮嘱新人的纪律，都要问自己三个问题：**能不能固化？固化成什么？谁来跑？**

- '跨域不许越界写' → 能固化 → 固化成 A 结构校验器 → clife-onto-engine 编译期自动跑（B-8）。
- '关键数字锚在单点、不重算' → 能固化 → 固化成 BRIEF 单一真相源 + 装配期一致性检查 → docs/quality 跑（B-5 就是没跑好的反例）。
- 'SDK 能力不确定就挂账' → 半固化 → 校验器管不到运行时，只能固化成 docstring 挂账约定 → FDE 人肉跑（B-9）。

看出来了吗：**纪律的固化程度，决定了它需要多少人力持续维护**。全固化的（越域校验），零人力、永不疲劳；半固化的（citations 挂账、SDK 挂账），需要 FDE 走一道人肉闸。你评估一个平台成不成熟，就看它把你多少条纪律固化进了校验器。**Astra Studio 之所以能让 1 个人干 5 个人的活，是因为它把资深 FDE 脑子里那批一致性纪律，绝大部分搬进了编译期和装配期的校验器。**

所以回到那句难听话：平台不是让你更快地打字，是让你**不必再靠意志力维持纪律**。你一个人靠意志力能守 3 天纪律，守不了 3 个月、守不了 7 个域同时。这就是为什么没有平台，你复制的只有加班。"

### 口播 · 三类"看起来最像 FDE"的人，为什么都不是

"我们先把三个候选人请上台，因为你们中的大多数，简历上写的正是这三个词之一。

**解决方案架构师**——他从'一个技术方案'开始工作，交给客户一份架构图。他很强，但他的起点是'系统怎么搭'，不是'客户的模糊话到底是什么意思'。康养项目这条链的第一步不是画架构，是把客户一句'帮站长管好老人'拆成 102 个业务事件——这一步架构师通常直接跳过，因为他默认需求已经有人整理好了。

**交付架构师**——他从'一个已经定型的方案'开始，负责把它落地、集成、上线，交付一套跑得起来的系统。他的价值在'把定好的东西做出来'，可 FDE 的价值恰恰在'定'之前那一段——从 16 事件簇收敛到 7 域限界上下文，那是判断，不是集成。

**需求分析师**——他离 FDE 最近，也最容易自我感觉良好。他会做访谈、写需求文档。但他的交付物是'一份需求清单'，交给下游就结束了；他不为'这份需求能不能编译成 7 域、38 个 Function、47 条 Rule、54 个 Action'负责，更不为'哪个 Action 要设 HIL 闸、按错了谁赔'负责。

三个人都真、都强、都有用。但他们各自只握住 FDE 这条链的一段。**FDE 不是这三个人里最好的那个，FDE 是这三段本来就不该切开的那条链。**"

### 口播 · 六维对照表：失败归因是最见人品的一维

"现在我把这张对照表逐维讲透。你们招人、内部选拔，就用这六维当尺子。我一维一维过，每一维你都对号入座——你自己现在站在哪一列。"

"看第 4 维'失败归因'——这是最见人品的一维。三类角色出了问题，话术都是'别人的锅'；FDE 没有这个话术，因为**全链是他一个人走的，接缝数为零，断层无处推**。这不是道德要求，是结构决定的：你把四段合成一段，就再也找不到'上一棒没交好'这个借口了。"

### 口播 · 硬能力矩阵 C1–C6：可训练的六维

"好消息先说：FDE 的六维硬能力，**都能训练**。坏消息随后：训练它们，比你想的贵、慢、且必须在真实项目上磨。我把 C1–C6 逐维给你判定基线——达到哪个程度算过关。这张矩阵你在工作坊里就要拿来给自己打分。"

"注意最后一列——三类角色**各有一两维起点不低，但没有一类六维齐全**。这正是'像 FDE 但不是 FDE'的结构原因。训练 FDE，不是把某一维练到顶，是**把六维的短板逐一补齐到 L2 以上**。"

### 口播 · 软能力 C7：只能筛选，不能训练

"现在讲最扎心的一维——C7，人的部分：客户关系、责任承担、价值判断、政治敏感度。总纲里那句话是全课程的支点：**C1–C6 可训练，C7 只能筛选。**

什么意思？C7 不是'练一练会变好'的技能，是'你这个人是不是这种人'的底色。我给你们四个具体切片：

**客户关系**——不是会说话，是客户信不信你敢对他说'这个我不知道'。康养项目 11 处地方文号查不到，FDE 的处理是坚决保留 `[本地待补文号]` 占位、锚定上位国标、转成向医保局/民政局逐项取件的清单，而不是编一个像模像样的假文号糊过去。内部原话——**'错文号比空缺更有害。'** 一个改不掉'不能在客户面前露怯'这个本能的人，永远做不到这一步。

**责任承担**——第 2 维对照里那个'无处甩锅'，能不能扛得住，是天性不是培训。

**价值判断**——康养项目那条红线：表述一律用'赋能优化'而非'替代'，因为涉及民政、就业、政治敏感。什么时候该踩刹车，是价值观在做判断，不是流程在做判断。

**政治敏感度**——To-G 项目里，一句话措辞不当就可能引火烧身。这个雷达，有的人天生有，有的人怎么教都装不上。

所以选拔 FDE，**C1–C6 看能不能补，C7 看是不是这块料**。C7 不合格，前六维再强也不能给他 L3、不能让他对客户承诺负责。"

### 口播 · 团队编成：1 主理 + N 见习 + 平台组

"最后一页最实际。你现在知道 FDE 稀缺、C7 筛不出几个，那怎么组队干活？答案不是'招一堆全能 FDE'——那是幻想。答案是**一个非对称编队**：

**1 名主理 FDE（L3）**——C7 过关、C1–C6 齐全，主持项目、设 HIL 闸、对客户承诺负责。康养项目就是这个角色一个人带编队走完的。一个 L3 是整个编队的'判断中枢'和'甩锅终点'。

**N 名见习 FDE（L1）**——C7 有潜质、C1–C6 在补齐中。他们在 L3 指导下承接**单一环节**：比如专攻 C1 主持事件风暴、或专攻 C6 写并行章节。L1 不独立对客户承诺，但在真实项目里练六维。康养项目若要复制，第二个项目就应该配 2–3 个 L1 在 L3 身边过手。

**平台组**——不是 FDE，是让 FDE 不必'更累'的人。他们维护 Astra Studio 建模管线（planner/domain-model/clife-onto-engine/citations/可研生成），把方法论固化成工具，让 7 域能同日并行编译。**没有平台组，L3 就退化成一个更累的架构师**（第 5 讲主张二）。

记住这个编队的本质：**L3 提供判断和责任（C7 + 高阶 C1–C6），L1 提供手数和成长通道，平台组提供杠杆。三者缺一，康养项目都不可复制。**"

### 口播 · 能力半径 + 团队编成随"交付模式"变

"六维里最容易被高估的是 **⑤ 能力半径**，而它跨**交付模式**才见真章。有人在康养项目做完一个康养大平台，就以为自己是 L3 了。我泼盆冷水：**能做模式二的大平台，不代表你能做模式一的 SaaS 应用，反之更是。**

两种模式的团队编成根本不同——**模式一（Token-SaaS，如教育督导项目）编成轻**：1 个 FDE + 平台/运行时组，快跑快迭代；**模式二（大平台建设运营，如康养项目/草业项目/辣椒）编成重**：1 个主理 FDE（L3）+ N 个见习 + 平台组，而且要扛得起可研、财务测算、监管合规——商业和合规的能力半径要宽得多。你擅长哪种模式，直接决定你能主理哪种项目。

而真正的分水岭是 **C1 认知萃取的跨行业迁移力**：教育督导项目能用和康养项目同一套管线做出来，证明**方法能迁移**；但你能不能在一个**你不熟的行业**（学前督导、辣椒育种、草原修复）里，快速把模糊意图压成可归域的结构？康养你可能靠沉淀蒙对了，换个行业沉淀归零、**只剩方法**——这就是 L2 和 L3 的分界。

最后一句诚实话：辣椒/草业项目目前只到方案、草业项目 demo 还是 Mock，所以我讲它们只敢讲'定位与结构'，不敢讲交付实测——**知道自己在哪个模式、哪个行业、哪个阶段还没有发言权，本身就是能力半径的一部分。**"
