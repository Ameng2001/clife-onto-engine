T4 · 领域建模（studio-planner）

目标：把 T3 的认知产物切成限界上下文，并顺手产出 skill-map——它是 T8 的输入。120′（知识注入 30′ + 实操 70′ + checkout 20′） 知识（讲什么）：栈② 领域驱动设计——统一语言 / 限界上下文 / 上下文映射（讲义已并入本手册第六节，讲师不必另开文件） 主案例：康养项目 7 域 / HR项目 9 插件切分 工具：studio-planner v0.2.0，依赖 studio-core + studio-insight

〇、先纠正一个误解：plan 不是编排引擎

学员会以为 /studio-planner:plan 是个自动化流水线。它不是。

commands/plan.md 本身只是一段串行提示词——它按顺序点名 5 个 skill，并写明“每步之后暂停、把结果交给用户确认”。 真正的衔接靠“文件 + status.json”，不靠内存传参。

这个设计事实带来三个直接后果，必须在开跑前讲：

  1. 随时可以中断，下次接着跑——因为状态都在磁盘上
  2. 每一步都能单独跑，只要前一步的文件在
  3. 可以人工改产物再继续——比如 domain-map.md 你改完，下一步读的就是你改过的版本

这正是 FDE 与“点一下按钮等结果”的分野：管线是给你用的，不是替你做主的。

一、五步流水线：读什么、写什么

步 读（前置） 写（交棒物） 确认点
event-storm studio/、studio/agents/*.md studio/changes/{domain-slug}/：event-storm.md、changelog.md、status.json、personas/、journeys/、processes/ ≈8（精细）/ 3（快速）
domain-model event-storm.md（缺失即拦截） domain-map.md；为每个候选插件建 status.json + 空脚手架；回写 domain 的 plugins[] 2–5
skill-design status.json 的 action/domain；父域 domain-map.md skill-map.md；status.json 的 skills{} 全填 draft 2

单步续跑口令（学员卡在哪一步就从哪接）：

/studio-planner:event-storm   <domain>
/studio-planner:domain-model  <domain>
/studio-planner:skill-design  <plugin>
/studio-planner:spec-generate <plugin>
/studio-planner:build-skills  <plugin>

⚠️ 这五个是 skill 触发，没有对应的命令文件（studio-planner 只有 plan.md 一个命令）。学员环境里 / 补全不出来是正常的，改用自然语言“use skill: spec-generate for xxx”同样生效。

phase 状态机（贯穿 T4→T8）

planning ──spec-generate──▶ building ──/studio-quality:validate──▶ approved ──/studio-core:promote──▶ shipped(归档副本)
                                                                                        └─▶ 活动区重置回 planning, iteration+1

⚠️ studio/config.yaml 的 lifecycle 里列了 testing 一档，但全链路没有任何 skill 会写入它——validate 直接从 building 跳到 approved。别等一个永远不会出现的状态。

二、⏱️ 时间盒的头号杀手：确认点

精细模式下跑完一次完整 plan，用户停顿点 ≈20+ 次：

event-storm 8 次 + 每个 persona/journey/process 子技能各 1–2 次
+ domain-model 5 次 + skill-design 2 次 + spec-generate 0 次 + build-skills 1 次

课堂必须用快速模式，能压到 6–8 次。 两处开场都会问你：

技能 精细（默认） 快速
event-storm 🔍 每步暂停 ⚡ 仅 3 个确认点：①专家角色+事件清单 ②Persona+Journey+Process 一起看 ③热点排名
domain-model 🔍 完整分析（含 domain-canvas / behavior-matrix / opportunity-brief） ⚡ 跳过这三个分析，从事件聚类直达插件提案

教练口径： > “选快速模式不是偷懒——被跳过的三个分析，你在 T3 已经手动跑过了。这里跳过是避免重复，不是省略步骤。”

⚠️ 但要提醒：domain-model 完整模式的判据是“事件 > 15 个或预期多插件”。学员命题若真的复杂，该选完整就选完整，只是要预留时间。

三、实操（70′）

阶段一 · event-storm（25′）

/studio-planner:event-storm <你的 domain-slug>

domain-slug 命名规则：lowercase、kebab-case、2–3 个词（children-health、trading-ops、linxi-edutech）。

🔔 最容易错的一步：什么是“业务事件”

❌ 这不是事件（这是功能） ✅ 这才是事件（过去式的既成事实）
提供订单查询功能 订单已提交
支持材料上传 材料已上传
实现质检模块 质检已通过 / 质检已驳回

判据：能不能加“已”字、并且它已经发生过、不可撤销？能，才是事件。 学员一上来必写功能清单，教练要当场纠偏——这是整个 T4 最关键的一次纠偏，写错了后面全歪。

产物 event-storm.md 的固定 7 个 H2： ## Domain Context · ## Events · ## Artifacts Produced · ## Hotspots · ## Knowledge Base Dependencies · ## Expert Scope · ## Decision Points

其中 KB 依赖表（列：热点 | 需要的领域知识 | 知识类型 | 更新频率）值得单讲：知识类型四选一（参考文档 / 结构化数据 / 历史案例 / 实时数据），≥3 个知识源且更新频繁 → 建议做一个伴生知识库插件。康养项目的 D7「康养大模型知识库」就是这么长出来的。

增量模式：检测到 event-storm.md 已存在 → 自动走 delta 模式，原地更新 + 追加 changelog + iteration+1。 changelog.md 是 append-only，每次一个 ## {日期}，下含 **Summary** + ### Added / ### Revised / ### Impact on Plugins。

⚠️ 这里有个取舍要讲明：修订是就地覆盖的，git diff 就是你的修订历史。所以 studio/ 必须 git-tracked——T2 里 init 那句 “Consider running git init first” 的告警不是走过场。

阶段二 · domain-model（25′）

/studio-planner:domain-model <domain-slug>

产物 domain-map.md 的 5 个 H2： ## Analysis Mode · ## Artifacts · ## Plugin Candidates · ## Generic Capabilities (no custom plugin needed) · ## Collection Structure

Plugin Candidates 表 7 列：Plugin | Domain | Role | Action | Description | Dependencies | Priority - Role = core / add-on - Action = create / modify

## Generic Capabilities 这一段是精华 —— 它列的是“不需要定制插件的能力”。 > 学员最容易犯的错是什么都想自己建。这一段逼你回答：“这个能力买现成的行不行？” 答案常常是行。 > 康养项目 D7 定位 Generic-Support、草业项目/辣椒共用 smart-agriculture 底座，都是这个判断的产物。

Collection Structure 三种模式：1 个插件 = 不建 collection；2–5 个相关 = 一个 collection 且必须有明确的 core；不同领域的独立插件 = 分开 collection。

⚠️ 增量模式下有一个硬确认点（插件文档明写 “This is a key decision point”）：会给你一张“插件影响评估”表（插件 | 动作 | 原因，动作用 🆕新建 / ✏️修改），必须显式确认才继续。 > 这是整条流水线上唯一被标为“关键决策点”的地方——因为它决定了要动哪些既有插件。

阶段三 · skill-design（20′）

/studio-planner:skill-design <plugin-name>

产物 skill-map.md 的 H2：## Skills（每个 skill 一个 H3，含 Description/Inputs/Outputs/Out of scope/Complexity/allowed-tools/Preconditions 七个字段）· ## Data Flow · ## Complexity Summary · ## Plugin Traits · ## Pipelines（仅 multi-pipeline）· ## Implementation Order

⚠️ Step 1.5 是本步的核心确认点：五个插件特征（traits）

trait 含义 下游影响（T8 会生成什么）
stateful 有持久运行时状态 额外生成 init-workspace skill + 两个 runtime 模板
hil-gated 有人工审批闸 给相关 skill 插入 ## Approval Gate 段（✅确认/✏️修改/❌拒绝 三选一）
kb-dependent 依赖知识库 影响 skill 的数据依赖设计
multi-pipeline 有多条编排流水线 每条流水线一个 commands/{pipeline}.md
expert-scoped 需要领域专家 agent 生成 agents/ 目录

traits 是整条流水线的“分叉开关”——它在这里被确认，到 T8 的 spec-generate 才兑现成不同的骨架。现在选错，T8 生成的东西就不对。 特别注意 hil-gated：它和 T5 本体层的 HIL 是两回事（一个是 skill 层的审批段，一个是 Action 层的 HilPolicy），T5 会讲清楚。

四档复杂度：Simple / Moderate / Script-heavy / MCP-dependent —— 决定 allowed-tools 和要不要建 scripts/ 目录。

本步到此为止

跑到 skill-map.md 就停。 spec-generate 和 build-skills 属于 T8。

教练必须明说这句话，否则学员会一路跑下去，把 T8 的内容提前消耗掉，而且在没做 T5 本体的情况下就去建插件骨架，顺序就乱了。

四、⭐ T4 结束时必讲：后面是分叉，不是流水线

跑完 domain-map + skill-map，路分成三条：

                    ┌──▶ T5 本体建模（studio-ontology）  ← 要"可执行的规则与闸"
T4 domain-map ──────┼──▶ T6 文档工程（studio-docs/platform）← 要"可评审的文书"
   + skill-map      └──▶ T8 技能插件（planner 续跑 + quality）← 要"可发版的插件"
                    （T7 界面原型基本独立，随时可插）

它们并行、不互为前置。

活证据 · 学前教育项目：那个项目没做本体建模、没有 persona/journey，照样交出了 653KB 可研 + 完整送审报价包 + 单一来源论证。

别让学员以为“不编译本体就不能写方案”。 交付模式决定你走哪条分支： - 模式二 To-G 大盘、赢单靠评审 → T6 优先 - 模式一 SaaS 应用、赢单靠能用 → T5 + T7 优先 - 要做可复用能力沉淀 → T8

HR项目「HR项目」· 9 插件切分（本步最佳教具）

素材：~/Codes/hr-dlink-plugins/studio/changes/linxi-edutech/

从一份 event-storm 切出 9 个插件的 skill-map： linxi-core（核心）· policy-parser（政策解析）· data-harvester（数据采集）· talent-matcher（人才撮合）· training-recommender（培训推荐）· employment-monitor（就业监测）· major-advisor（专业规划顾问）· outreach-optimizer（访企拓岗优化）· insight-report（洞察报告）

六、知识（讲什么）· 栈② 领域驱动设计（领域架构师的方法论，30′）

这一节是讲 4「七角色知识栈」里的 栈②，能力位 C2 结构建模（上半）。 【这个角色原本是谁】 领域架构师——负责把大系统切成边界清晰、各自内聚的域。传统模式里，他拿到产品经理递过来的需求，切完再递给知识工程师；FDE 是同一个人从事件切到域，中间不换脑子——这就是为什么 T3 的产物在这里可以直接复用，不必重跑。

6.1 核心命题

限界上下文的边界，不是按功能划的，是按“谁对这件事负责”划的。

6.2 前置：切域之前，先把“事件”写对

栈②的输入是栈①（T3 + 本步 event-storm）的事件集。这里必须回扣第三节那条纪律：

事件是过去式的既成事实——“材料已上传”“质检已通过”，不是“支持材料上传”“实现质检模块”。 为什么它是 DDD 的前置？因为限界上下文是按“谁推进了这个既成事实”聚出来的。你写成功能清单，聚出来的就只能是“查询模块”“管理模块”——那是系统的形状，不是业务的形状。事件写歪，域必然切歪，而且到 T5 才会疼。

6.3 方法论内核：DDD 三件核心

核心概念 一句话 康养项目的物理落点
统一语言 Ubiquitous Language 业务方和工程师用同一套词，且这套词直接出现在代码里 共享根 Elder 单一写入点——同一个“老人”只有一个真相源
限界上下文 Bounded Context 一个词在一个边界内只有一个含义；出了边界就是另一个概念 102 事件 / 16 簇切成 7 域 D1–D7
上下文映射 Context Mapping（含防腐层 ACL） 两个域之间是“引用”还是“发布”，必须说得出来；跨语义的地方加防腐层翻译 两处防腐层：D6↔︎D5、D4↔︎D5；跨域一律 ref / 发布，不越界写入

6.4 业界经典（要补这一栈，就啃这两本）

来源 补什么
《领域驱动设计》Eric Evans（蓝皮书） DDD 开山之作，概念体系的源头
《实现领域驱动设计》Vaughn Vernon（红皮书） 落地版，告诉你概念怎么变成代码

别通读。重点啃 “限界上下文” 与 “上下文映射” 两章——这门课用到的就是这两章，其余章节等你真的要写聚合根再说。

6.5 三个判据（现场对着学员的域图问）

  1. 同一个词在两个地方含义不同 → 该切开 康养项目的“老人”在 D4 居家照护里是“被照护对象”，在 D3 会员飞轮里是“消费者”。同一个人，两套属性、两套规则 → 两个域。（这就是“限界上下文”最朴素的用法。）
  2. 状态机不共享 → 该切开 一个对象的生命周期如果在两处被不同的人推进，说明它其实是两个对象。
  3. 能独立发布 → 该切开 D6 民政治理有 8 个 HIL 闸、要对监管负责；把它和 D3 会员营收捆在一起，一次发布要同时说服民政局和市场部。

6.6 方法论 → 工具：这一栈也已经被固化了

栈②的管线是 事件簇 → 限界上下文 → 上下文映射，对应的固化工具就是本步在跑的这几个：domain-model（切域、出 domain-map.md）· domain-canvas（域画布，Owns / Does NOT own 就是边界定义）· behavior-matrix（行为矩阵）。

切得对不对不靠自觉，靠校验兜底：康养项目 7 域最终跑出 A 结构 7/7、零悬空引用。这就是“结构纪律靠校验器”在 DDD 层的证据——T5 会把这条校验真正跑给你看。

6.7 ⚠️ 反例 B-8（越域写入冲动）

康养项目编译期多次想让 Action 直接 stage_write 他域的对象——因为“就改一个字段，绕一圈太麻烦”。

原则：跨域一律走 ref / 发布，不越界直写。这就是上下文映射：两个域之间只能是“引用”或“发布”，没有第三种。 关键的一句：结构纪律靠校验器，不靠自觉。 你在赶工期的凌晨三点是不会守纪律的，但校验器会。 这条在 T5 有物理对应：clife-onto-engine 的 check_plugin_capabilities.py 会直接拦住摸内核私有方法的代码，CI 挂给你看。

6.8 ⚠️ 反例 B-9（SDK 能力想当然）

编译期不确定 PropertySpec.default、Evaluation 是否导出，7 个域统一留了 docstring 挂账，没有靠“应该支持吧”往前推。

这个判断在 T5 被验证是对的：compile-rules.md 的固定头部确实漏了 import Evaluation，照着生成会 NameError。当初挂账的人是对的。 原则：不确定就显式挂账，别赌。

6.9 自学 / 自评到“能独立交付”

练法：把 T3 + event-storm 的事件集按“谁拥有这个决策”切域；切完自查一遍——有没有一个对象被两个域同时写？ 有，就是切错了。

自评三条（够到就是能交付）： - 能独立完成 1 个域的 ontology-map 并通过结构校验（这条要到 T5 才验收，但判断力在本步就要有）； - 能说清任意两个域之间是“引用”还是“发布”，说不清就是边界没想透； - 每个域都能回答“谁对它负责”——答不上来的域，多半是按功能模块切的。

七、checkout（20′）

维度 达标 警示
事件写法 全是过去式既成事实（“材料已上传”） 写成功能清单（“支持材料上传”）→ 一票警示
域切分理由 每个域能说清“谁对它负责”+ 至少一条切分判据 按功能模块切（“查询域”“管理域”）

core 明确 collection 里有且仅有一个明确的 core 2–5 个插件平级、无 core
skill-map 溯源 每个插件都能在 T1 项目描述里找到出处 有凭空想出来的插件
traits 五个 traits 逐个判过，说得出为什么选/不选 直接回车接受默认
越域 无跨域直写设计 有“就改一个字段”的越界冲动（B-8）
停在正确的位置 跑到 skill-map.md 停 一路跑到 build-skills（抢了 T8）

八、翻车点

⚠️ 1. spec-generate 找不到模板（会在 T8 撞上）

它的 Pre-check 让它读 ${CLAUDE_SKILL_DIR}/../../templates/brief.md.tmpl，但 studio-planner 根本没有 templates/ 目录——那两个模板住在 studio-core 下。 后果：模型找不到模板，会直接按 SKILL.md 内嵌的结构生成（结果可用，但可能与预期不同）。知道就行，不用修。

⚠️ 2. 文档里的 /studio-insight:create-expert 是错的

event-storm 的 SKILL.md 有两处这么写，正确的是 /studio-core:create-expert。

⚠️ 3. build-skills 的 phase 硬门

phase 不是 building 会直接报错退出（planning→让你先 spec-generate；approved→已校验过；shipped→已 promote）。这是设计，不是 bug。

⚠️ 4. 别在 T4 就跑 spec-generate

它是零确认点的纯自动化，一跑就把骨架全生成了。在没做 T5 本体、没想清 traits 的情况下生成的骨架，等于白生成。

九、给讲师的时间盒

口播 · 栈②的角色定位与三件核心

（用在：第六节 6.1–6.3，进入三判据之前。讲述要点（非原话稿），出自讲义 04 §3.2）

“这一栈原本是领域架构师的活——负责把大系统切成边界清晰、各自内聚的域。DDD 就三件核心：统一语言、限界上下文、上下文映射（含防腐层 ACL）。业界经典是两本：Eric Evans 的《领域驱动设计》，蓝皮书，DDD 的开山之作；Vaughn Vernon 的《实现领域驱动设计》，红皮书，落地版。别通读，重点啃’限界上下文’和’上下文映射’这两章，这门课用到的就是这两章。”

口播 · 康养项目是怎么切的

（用在：第六节 6.3 表格与 6.6，或第五节康养项目 7 域范例讲完时。讲述要点（非原话稿），出自讲义 04 §3.2 康养项目段）

“康养项目是怎么落的？102 个事件、16 个簇，切成 7 个域的限界上下文 D1 到 D7。跨域一律走 ref、走发布，不越界写入；有两处防腐层——D6 和 D5 之间、D4 和 D5 之间——那就是 DDD 里的 ACL。共享根 Elder 只有一个写入点，那就是’统一语言 + 单一真相’。那么怎么知道切得对不对？不靠自觉，用结构校验兜底——康养项目最后跑出来的是 A 结构 7 比 7，零悬空引用。”

口播 · 这一栈的自评标准

（用在：第六节 6.9，转入 checkout 之前。讲述要点（非原话稿），出自讲义 04 §3.2 自学自评段）

“怎么练？把事件集按’谁拥有这个决策’切域，切完自查一遍：有没有一个对象被两个域同时写？ 有，就是切错了。什么叫补到能交付？两条：第一，能独立完成一个域的 ontology-map，并且通过结构校验；第二，能说清任意两个域之间到底是’引用’还是’发布’。说不清，就是边界没想透。越域写入的冲动是真实存在的坑，不是我吓唬你们——康养项目编译期就反复冒出来过。”

口播 · 难听话（收口用）

（用在：本步最后、第四节“后面是分叉不是流水线”讲完之后，压一句。原话稿，出自讲义 04 §6 难听话）

“你以为 FDE 就是会建模？建模只是七分之二。你能交出 7 域本体、3835 行骨架——很好，那是栈②栈③。客户翻到可研最后一章问你’总投资多少、功能点怎么算的、IRR 几年回本’，你答不出某工业城市那样的’27,056 功能点 / 4,839 万’、答不出’15.2% 第 9 年回本’，你就只是个更贵的建模师，不是 FDE。缺的那五个角色，不会因为你建模漂亮就自动长出来。”

讲师提示：这段是为第四节那张分叉图服务的——学员刚学完切域，最容易产生“我已经会 FDE 了”的错觉。念完这段，再指着分叉图说一句“T6 那条线上的账，栈②替你算不出来”，效果最好。
