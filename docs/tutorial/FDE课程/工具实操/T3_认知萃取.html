〇、先说清楚一件事：T3 和 T4 会“做两遍”吗

不会重复，但确实会碰同一批产物，先讲明白，否则学员到 T4 必困惑：

T3（本步） T4（下一步）

三、六个产物长什么样（手册要给学员看样子）

persona 卡

ASCII 卡片：Role / Age range / Tech level / Context / Goals(1–3) / Pain points(1–3，带 高·中·低 severity) / Current tools / Success looks like + 共情图四象限：Thinks / Sees / Hears / Does + 结尾两行 Pain: / Gain:

journey

元数据（persona、scenario、trigger、end state） + 逐阶段表，行标签固定：Stage / Actions / Touchpoints / Thoughts / Emotion(带 emoji) / Pain points，4–7 个阶段列 + 情绪曲线文字图 + 痛点机会表 5 列：# | Stage | Pain Point | Severity | Opportunity + Key insights

process

元数据（name / trigger / end states / frequency） + 文字流程图，五种符号：[事件] ◇ 问题？ → ├─ (Actor) + 决策点表 5 列：ID | Decision | Condition | True path | False path + 并行说明 + 泳道图 + Key observations

domain-canvas

每域一张卡：Owns / Does NOT own / Key actors / Key events + 分类表：Domain | Type | Rationale（Type = Core / Support / Generic） + 关系表（──▶ 喂入 / ◀──▶ 共享 / · · · 独立 / ══▶ 编排） + 整张 canvas ASCII 图 + build strategy 建议

Does NOT own 这一行是精华：定义一个域最有效的方式是说清它不管什么。这条直接喂给 T4 的域切分。

behavior-matrix

Actor 清单（Type = User / AI Agent / System / External） + 动作表 / 事件表 / 数据表 + 主矩阵 5 列：Actor | Action | Event | Data In | Data Out + 数据实体表 + Gaps + Automation opportunities + Skill mapping hints

主矩阵是 T5 五要素的直接前身：Actor→Action 的 actor，Action→Action，Data In/Out→Object 与 Link。T5 会回来用它。

opportunity-brief

证据来源表 + 候选表（ID 形如 OP-1） + Impact × Feasibility 5×5 星阵：★★★ Build first / ★★ Build next / ★ Consider / 空 Defer + 工作量表 + 排名块（Score = 两轴相乘）+ Recommendation

⚠️ 它明确拒绝给工期估算（“Do NOT give time estimates”）。学员问“那什么时候能做完”——这不是这个工具该回答的，工期要等 T4 域切分和 T8 技能拆解之后才谈得上。

四、实操（70′）

🔔 任务

用本组命题跑完六件套，产出：画像 ≥3、旅程 ≥2、流程 ≥2、热点分层一份。

建议顺序与时间盒

序 命令 时长 输出

2 journey-map ×2 20′ 2 条旅程（选最能暴露痛点的场景，不是最典型的）

🔔 难点/注意

① 画像必须按「行为」切，不能按「人口属性」切。

康养项目基线：7 个画像不是“60 岁以上老人”“空巢老人”这种切法，而是 “熟人获客接受度 77.59%”、“智能监护接受但要简单式 84.48%” ——按行为倾向切，且每条都有 368 份问卷校准。 判据：两个画像如果目标、痛点、使用频率没有显著差异，就不该拆成两个。建议 2–3 个起步，超过 4 个说明你的范围划大了。

② opportunity-brief 的评分可以推翻。 skill 明确允许你以业务理由否决它的排序。这正是 C7「价值判断」不可外包的具体落点——模型能算 Impact×Feasibility，但“这个季度必须先啃硬骨头给客户看到东西”这种判断，只能人做。

③ 没有工作区时产物会散落。 六个 skill 都能脱离 studio/ 独立跑，此时会写到当前目录或让你选路径。先确认 /studio-core:init 跑过，否则文件会撒得到处都是。

六、知识（讲什么）· 栈① 产品设计（产品经理的方法论，30′）

这一节是讲 4「七角色知识栈」里的 栈①，能力位 C1 认知萃取。 【这个角色原本是谁】 产品经理 / 产品设计师——负责把模糊的客户意图变成“要做什么”。传统模式里他一个人占着这个位置，交接给架构师时信息就衰减一次。FDE 把这套方法论装进自己脑子，从事件一路跑到机会矩阵，中间不换人。

6.1 核心命题

FDE 的核心资产不是“会用 AI”，是把客户的模糊意图压成可执行的结构。 证据：康养项目 102 个业务事件 → 16 事件簇 → 7 域限界上下文。这一步没有任何模型能替你做判断，模型只能加速你做完。

产品设计不是“画原型”。它在这门课里的定义只有一句：一条把“客户想要点什么”逼成可归域结构的方法论管线——事件 → 画像 → 旅程 → 机会矩阵。管线的出口直接插进 T4 的限界上下文。

6.2 方法论内核：五个把模糊意图变结构的具体方法

方法 要点 本步对应的 skill
Persona 用户画像 按行为 / 目标 / 动机 / 痛点定义真实用户，不是人口属性堆砌。画像是整条旅程的地基——Figma 的说法是 persona 让旅程“反映真实用户视角” persona-insight
User Journey Map 用户旅程图 Figma 五要素框架：① 用户（persona）② 场景与目标 ③ 旅程阶段（通用 awareness→consideration→decision→purchase→retention，可按业务定制）④ 行为·态度·情绪（每阶段的正负情绪）⑤ 机会点（从摩擦/痛点里长出来）。五步做法：研究数据定 persona 与目标 → 找触点 → 可视化阶段 → 逐阶段记录行为与情绪 → 用真实反馈校验迭代 journey-map
Opportunity Matrix 机会矩阵 把旅程里暴露的痛点排优先级——按影响 × 可行性 × 频率打分、ROI 排序，决定先做哪个 opportunity-brief

⚠️ 方法论与工具实现有一处差异，要当场说明：机会矩阵在方法论上是三因子（影响 × 可行性 × 频率），但 opportunity-brief 这个 skill 只算两轴——Score = Impact × Feasibility，5×5 星阵，频率不进公式。 不是工具做错了：频率信息在旅程里（“每天都遇到” vs “一年一次”），工具把它留给你做最后判断。所以工具给的排序本来就该被你以业务理由推翻——这正是下面第三条要讲的。 别让学员对着两个数字发懵，也别自己动手改工具的算法。 | Event Storming 事件风暴 | 把业务事件全量铺开、再归簇，喂给后面的限界上下文（栈②/T4） | T4 event-storm | | 产品思维（梁宁） | 给上面这些方法补一层“人和情绪”：① 同理心——看懂用户情绪、把需求分成痛点/痒点/爽点（画像和旅程里的“痛点”就从这来）② 机会判断·点线面体——别做一个没有势能的孤点 ③ 用户体验五层（战略存在/能力圈/资源结构/角色框架/感知层）——产品不止“感知层好看”，底下四层才决定成败 | 贯穿全部六件套 |

画像 → 旅程 → 机会矩阵是有先后的：画像不真，旅程就是编的；旅程不暴露痛点，机会矩阵就没有原料。这条顺序不能倒，也是本步实操时间盒的排法依据。

6.4 方法论 → 工具：这一栈已经被固化了

这些方法在 C-Life 不是靠手画白板，是固化成 studio 技能：persona-insight · journey-map · process-flow · opportunity-brief · behavior-matrix · domain-canvas，加上 T4 的 event-storm。

这跟 T5 本体锚到 clife-onto-engine 是对称的：产品栈锚到 Astra Studio planner/insight 工具链——方法论被平台固化（呼应 T2 讲的“平台 = 方法论的固化物”）。 记住因果方向：工具是果，管线是因。不是因为有了这六个 skill 才这么做事，是因为先有这条管线，工具才长成这个样子。

6.5 康养项目完整链条（背下来，这是量级标尺）

102 业务事件 → 16 事件簇 → 7 角色画像（368 份问卷校准）
    → 7 条用户旅程 → 5 条业务流程 → 10 个热点（P1–P5 分层）→ 7 域限界上下文

每一段都有一个 skill 对应：event-storm 出 102 事件 / 16 簇 → persona-insight 定 7 画像 → journey-map 画 7 旅程 → process-flow 出 5 流程 → opportunity-brief 排 10 热点 P1–P5。这条链就是本步实操要复刻的东西，只是规模小一号。

6.6 三件事讲透

  1. 画像的真假之分（本步唯一的核心教学点） —— 假画像是人口统计（“60 岁以上、退休、有慢病”），真画像是行为倾向 + 证据（“熟人获客接受度 77.59%”“智能监护接受但要简单式 84.48%”）。前者从常识就能编，后者必须去问——康养项目那 7 个画像背后是 368 份问卷校准，每条特征都能指回一份数据来源。 > 判据：两个画像如果目标、痛点、使用频率没有显著差异，就不该拆成两个。
  2. 旅程要选“最暴露痛点”的场景，不是最典型的场景 —— 典型场景大家都顺，看不出机会在哪。
  3. 热点分层是给决策者看的，不是给自己看的 —— Impact × Feasibility 打分的意义不在于分数本身，在于逼你说清“凭什么这个先做”。

6.7 同一套方法跨行业成立 · 教育督导项目的印证

教育督导项目用的是完全同一套 planner/insight 方法：3 画像（李科长 / 张园长 / 王老师）+ journey + opportunity-brief ROI 排序（material-qc / standard-decode / gap-diagnose 排 P0）。

康养和幼教，行业不同、交付模式不同，认知萃取这一栈的做法一模一样。 这就是 C1 认知萃取迁移力的底座——也是为什么这一栈值得单独花 30 分钟：它是你换一个行业还带得走的东西。

6.8 ⚠️ 反例 B-7（旅程建模过重）

康养项目长者旅程的初版做的是“夜间急救”——场景很戏剧、很打动人，但过重且偏离营收主线，最后返工改成会员飞轮。

原则：建模要服务于业务优先级，不是求全。返工成本要记在方法论账上，不能假装没发生过。 落到本步：选旅程场景之前，先回头看 T1 写的商业模式——那三条收入线在哪条旅程上？ 就做那条。

6.9 自学 / 自评到“能独立交付”

练法：对一个熟悉业务，限时做一张含五要素（persona / 阶段 / 情绪 / 痛点 / 机会）的旅程图，再从痛点排一张机会矩阵。

自评三条（够到就是能交付）： - 能独立主持一场事件风暴，产出可归域（不是流水账）的事件集； - 能做一张情绪与机会点齐全的 journey map； - 每个画像特征都能指到一份数据来源——康养项目 368 份问卷就是这条纪律的样板，指不出来源的特征就是编的（这正是 B-5「数据张冠李戴」的上游防线）。

七、知识（讲什么）· 认知杠杆：为什么工具能顶几个人（15′）

讲这一节的时机很关键：放在实操之后。 学员刚亲手用六件套在 55 分钟里产出了传统要几天的东西——这时候讲「认知杠杆」他有实感；开课就讲，他只当是口号。 本节吸收讲义「第 2 讲 · 大模型时代 FDE 交付 vs 传统交付」。口播稿在末节讲师包，5 段可照读。

认知杠杆 = 结构化能力 × 平台固化（这一页是钉子，钉不进去前面白讲）

认知杠杆 = 结构化能力（决定能不能做对） × 平台固化（决定能不能做快做稳）
                    ★ 打字快 ∉ 这个公式
  • 结构化能力：把 102 个乱糟糟的业务事件收敛成 16 簇、压成 7 个域，没有任何模型能替你做判断。模型能帮你把 102 件事列出来、写候选归类，但“该归成 16 簇还是 20 簇、边界划在哪”是 FDE 的判断。模型只能加速你做完，不能替你做对。 你结构化能力越强，模型放大的倍数越大；你结构化能力是零，模型放大零还是零。
  • 平台固化：7 域同日并行编译、7/7 零悬空，靠的是 studio-planner → domain-model → clife-onto-engine → citations 治理 → 可研生成 这条固化管线（详见 T2 §六）。没有工程化平台的 FDE，只是“更累的架构师”——能做对，但做不快、做不稳、复制不了。

顺带把“交付物形态”讲了（学员以为 AI 只是让你写得快，交付物还是老三样，错）：

传统 FDE
方案与系统 Word 方案 ⟂ 系统（两张皮） 11 章可研 ‖ 3835 行骨架（同源，7/7 py_compile）
一致性 不可校验（你怎么校验一份 Word 的内部一致性？） A 结构 7/7 零悬空、B source 治理 7/7 零空 source
规模与深度 5 人数周产不出，产出来也无法保证内部一致 14 类知识库 / 8 个知识图谱 / 约 350 万三元组

节奏也变了：传统是串行接力（总时长 = 各段之和），FDE 是并行铺开（35 个分节并行写作、26 图与写作同步、7 域同日编译）。

⚠️ 并行有代价，要诚实说：各写各的，口径会散。康养项目的处置是先立一份 _WRITING_BRIEF.md（术语表 + 核心数据表 + 观点主张 + 协作纪律）当唯一真相源，35 节全部引用不重算，再用结构校验器兜底。 这条纪律就是本手册 §四 B-11 的上位规则——“数字锚在单点、引用不重算”，在写作期叫 BRIEF，在调研期就叫“换模板必须清空所有数字”。

🎯 Vibe Coding 的真相（一句话记死）

AI 能干 AI 不能干
给了明确规格后，把伪代码变 Python、处理文件读写、生成测试、格式化输出——10 分钟搞定 工程判断：规则写入前还是后执行？日志存快照还是只存改变？Schema 用 YAML 还是 Python？多规则违反时短路还是收集？

“AI 能把’想清楚的事’快速变成代码，但不能代替’想清楚’这件事本身。” AI 把“实现”变便宜了，但没把“判断”变容易。 没有蓝图的 Vibe Coding 会失控，一处改动带出三处 bug。 落到 T1：这份项目描述，就是那份“蓝图”。你在这一步偷的懒，AI 会在后面七步替你放大。

口播 · 开场：为什么是“角色合体”，不是“技能清单”

（用在：全课第一次讲“知识栈”时——本步是七栈的第一站，这段开场只在 T3 讲一次，T4/T5a/T6 不再重复。原话稿，出自讲义 04 §3.0）

“上一版这一讲我讲’五维知识栈’，讲浅了。今天换个讲法，也是更真实的讲法：你要成为 FDE，本质上是要一个人干完过去七个岗位的活。传统模式做康养项目这种项目，会议室里坐七种人——产品经理定需求、架构师切系统、知识工程师建图谱、商业顾问搭模式、财评专家算功能点、方案经理写标书、法务把红线。他们各说各的行话，交接处全是信息衰减（这就是第 1 讲的交付断层）。FDE 消除断层的办法，不是协调这七个人，是把这七套方法论装进自己脑子，一个人从头跑到尾。所以这一讲不是七个技能点，是七个角色的方法论体系，每一个我都给你一本业界压舱的经典——你补哪一栈，就去啃那一本。”

口播 · 栈①的角色定位与内核

（用在：第六节 6.1–6.2，进入方法表之前。讲述要点（非原话稿），出自讲义 04 §3.1）

“这一栈原本是谁的活？产品经理、产品设计师——负责把模糊的客户意图变成’要做什么’。但产品设计不是’画原型’，它的核心是四件可照做的方法，一步步把’客户想要点什么’逼成可归域的结构：Persona 按行为、目标、动机、痛点定义真实用户，不是人口属性堆砌；User Journey Map 有五要素——用户、场景与目标、旅程阶段、行为态度情绪、机会点，机会点是从摩擦和痛点里长出来的；机会矩阵把痛点按影响乘可行性乘频率排出优先级；事件风暴把业务事件全量铺开再归簇，喂给后面的限界上下文。再加梁宁那套产品思维，补上’人和情绪’这一层——痛点、痒点、爽点，点线面体，用户体验五层。这五样合起来，才是这一栈。”

口播 · 画像必须按行为切（本步唯一的核心教学点）

（用在：第六节 6.6 第 1 条 + 实操第①个难点，学员开始跑 persona-insight 之前。讲述要点（非原话稿），出自讲义 04 §3.1 康养项目段）

“康养项目 persona-insight 定出 7 个画像，是 368 份问卷校准过的，而且是按行为聚类的——不是按’60 岁以上老人’这种人口属性切，是按’熟人获客接受度 77.59%’’智能监护接受但要简单式 84.48%’这种行为倾向切。差别在哪？人口属性那种画像，你坐在办公室里凭常识就能编出来，编出来还看不出错；行为倾向这种，你必须去问，问完还得留下数据来源。所以我给你们的验收标准只有一条：每个画像特征，都要能指到一份数据来源。 指不出来的，就是你编的。”

口播 · 同一套方法跨行业成立

（用在：第六节 6.7 或第五节教育督导项目范例讲完时。讲述要点（非原话稿），出自讲义 04 §3.1 教育督导项目段）

“教育督导项目用的是同一套——3 个画像：李科长、张园长、王老师，加 journey，加 opportunity-brief 的 ROI 排序，material-qc、standard-decode、gap-diagnose 排 P0。康养和幼教，行业不同、交付模式也不同，但认知萃取这一栈的做法一模一样。这就是为什么这一栈值得单独花三十分钟：它是你换一个行业还带得走的东西。”

口播 · 人力对比，一次真实的实证（对应 §六 ③ 开场）

"上一讲我说’一个人贯通消除断层’，肯定有人心里嘀咕：一个人扛得动吗？还是嘴上好听、实际累死？今天我用康养项目的账，一笔一笔算给你看。

同一条交付链——从需求调研到 7 域数智本体建模、到 3835 行可运行插件骨架、到 100+ 页对客可研——两种模式的投入是这样：

传统模式：产品经理 + 架构师 + 行业顾问 + 方案经理 + 美工，5 人以上，数周。而且这 5 个人之间有至少 4 道接缝，每道接缝都在漏（第 1 讲讲过）。

FDE 模式：1 名 FDE + 智能体编队。0 接缝。

这不是’省了 4 个人’这么简单。是交付的组织形态变了——从’按工种分人、靠流程串起来’，变成’按认知链分给一个人、靠智能体扩手脚’。"

口播 · 交付物形态的根本变化（对应 §六 ③ 的对照表）

"再看交出去的东西变了没有。很多人以为 AI 只是让你’写得快’,交付物还是老三样。错。康养项目的交付物形态是传统模式根本产不出的：

第一，方案与代码同源。传统模式里，可研报告是方案经理写的 PPT/Word，跟真正的系统是两张皮。康养项目不是——11 章可研背后，是 3835 行可运行的 Python 插件骨架 + 21 个 YAML，7/7 py_compile 通过。方案里写的每个域，都有能编译的结构撑着。方案不再是“说说而已”，是“已经建好了骨架的说明书”。

第二，结构可校验。7 域五要素 OAG：Object 76 / Link 75 / Function 38 / Rule 47 / Action 54，A 结构校验 7/7 零悬空引用，B source 治理 7/7 零空 source。传统方案没有“校验”这个概念——你怎么校验一份 Word 的内部一致性？

第三，规模与深度同时在线：14 类知识库 / 8 个知识图谱 / 约 350 万三元组。这个体量,传统 5 人团队数周产不出，产出来也无法保证内部一致。"

口播 · 节奏与质量控制的根本变化（对应 §六 ③ “节奏也变了”）

"节奏也变了。传统模式是串行接力：需求做完交设计，设计做完交开发，一棒接一棒，总时长是各段之和。FDE 模式是并行铺开：一个人在同一时间，指挥智能体编队并行跑多条支线。

康养项目可研的写作阶段就是活样本：35 个分节并行写作，不是一节一节写。制图 26 张与写作同步跑。7 个域同一天并行编译。这不是把串行加速，是把串行改成了并行——这是节奏上质的差别。

但并行有个致命风险：各写各的，口径会散。所以质量控制的方式也跟着变了。传统靠’评审会’事后抓错；FDE 靠锚定口径 + 结构校验事前防错。康养项目的做法是先立一份 _WRITING_BRIEF.md（术语表 + 核心数据表 + 观点主张 + 协作纪律）当唯一真相源，35 节全部引用不重算,再用结构校验器兜底。

我要诚实说一句：并行不是没代价的。散了口径就要收口。下一讲会讲到康养项目栽过的跟头——图目计数漂移、章节编号冲突——那都是并行的账。但账是可控的，靠的是纪律，不是靠不并行。"

口播 · 杠杆到底来自哪里（对应 §六 ③ 公式，全讲的钉子，别讲偏）

"最后这页是全讲的钉子，钉不进去前面白讲。FDE 的杠杆，不来自打字快，来自两样东西：结构化能力 + 平台固化。

先说结构化能力。康养项目最难的一步是把 102 个乱糟糟的业务事件，收敛成 16 簇、压成 7 个域。这一步没有任何模型能替你做判断——模型可以帮你把 102 件事列出来、可以帮你写候选归类，但’该归成 16 簇还是 20 簇、这个域的边界划在哪’，是 FDE 的结构化判断。模型只能加速你做完，不能替你做对。这是杠杆的支点：你结构化能力越强，模型放大的倍数越大；你结构化能力是零，模型放大零还是零。

再说平台固化。7 个域能在同一天并行编译、7/7 零悬空引用，靠的不是个人手速，是 studio-planner（事件风暴）→ domain-model（限界上下文）→ clife-onto-engine（本体）→ citations 治理 → 可研报告生成 这一条固化管线（Astra Studio）。方法论一旦固化进平台，就不再依赖’这个人今天状态好不好’。没有工程化平台的 FDE，只是“更累的架构师”——他能做对，但做不快、做不稳、复制不了。

所以杠杆 = 结构化能力（决定能不能做对）× 平台固化（决定能不能做快做稳）。打字快，在这个乘式里连一项都不是。"

口播 · Vibe Coding 的真相（对应 §六 ③ 末尾的 🎯 段）

"上一页那句’模型只能加速你做完、不能替你做对’，不是我编的口号，是我们方法论文集里一篇《AI 时代的 FDE》的第一手结论。作者用 AI 辅助，3 小时手搓了一个本体引擎原型；他复盘’这 3 小时里 AI 到底干了多少活’，得出一张清单——

  • AI 能干的：给了明确规格后，把伪代码变 Python、处理文件读写、生成测试、格式化输出——10 分钟搞定。共同特征：给明确规格，AI 快速生成代码。
  • AI 不能干的：规则写入前还是后执行？日志存快照还是只存改变？Schema 用 YAML 还是 Python？多规则违反时短路还是收集？——这些是工程判断，不是编码问题。AI 只会给’常见做法’，不一定符合你的设计原则。

一句话结论，请记死——‘AI 能把“想清楚的事”快速变成代码，但不能代替“想清楚”这件事本身。’ ’想清楚’指的就是：数据规模 vs 决策治理、规则 vs 前置条件、可追溯性要什么、业务人员要审查什么、边界条件怎么处理——这些判断都发生在写代码之前。

所以’认知杠杆’的真相是：AI 把“实现”变便宜了，但没把“判断”变容易。 谁的判断力强，谁的杠杆就大；没有判断，AI 放大的是一堆能跑但错的代码（方法论 06 原话：没有蓝图的 Vibe Coding 会失控，一处改动带出三处 bug）。再补一句同篇的判断——‘平台越来越便宜，本体模型越来越值钱；会建模型的人，不会被替代，而是被放大。’"

两句难听话（收口用，各甩一句）：

讲 1：“你以为你在’对接需求’，其实你只是在’转述需求’——把上一道工序的话原样递给下一道，中间那些没写进文档的判断，从你手上又蒸发了一层。你不是断层的受害者，你就是断层本身。”

讲 2：“你之所以觉得 AI 就是’帮你写得快一点’，是因为你自己的活里，就没有多少需要结构化判断的成分——你一直在做搬运，所以你只能想象一个’搬得更快’的 AI。杠杆放大的是判断力，你没有判断力，AI 放大的就是你的空白。”
