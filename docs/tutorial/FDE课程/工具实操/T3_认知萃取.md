# T3 · 认知萃取（studio-insight）

> 目标：把 T1 的项目描述，压成**人、路径、机会**三类结构化产物。**120′**（知识注入 30′ + 实操 70′ + checkout 20′）
> 知识（讲什么）：**栈① 产品设计**——Persona / 用户旅程 / 机会矩阵（讲义已并入本手册第六节，讲师不必另开文件）
> 主案例：**教育督导项目**（全部项目里 personas / journeys / processes **三件唯一齐全**的）
> 工具：`studio-insight` v0.2.0，**6 个 skill 各自独立可跑**，零插件依赖

## 〇、先说清楚一件事：T3 和 T4 会"做两遍"吗

不会重复，但**确实会碰同一批产物**，先讲明白，否则学员到 T4 必困惑：

| | T3（本步） | T4（下一步） |
|---|---|---|
| 怎么跑 | **手动单跑** 6 个 insight skill | `/studio-planner:plan` 一条命令串 5 步 |
| 目的 | **看清每个产物长什么样、为什么这么长** | 体会**流水线**：事件风暴自动调用 persona/journey/process |
| 关系 | 学"零件" | 学"装配线" |

> `/studio-planner:plan` 的 event-storm 步骤内部会调用 `studio-insight` 的 persona-insight / journey-map / process-flow。**T3 先手动跑一遍，是为了让学员知道 T4 那条流水线里到底发生了什么**——否则 plan 跑完，学员只会说"它自己生成了一堆文件"。

## 一、六件套：命令、产物、确认点

| 命令 | 参数提示 | 产物路径 | 用户确认点 |
|---|---|---|---|
| `/studio-insight:persona-insight` | `[用户描述 或 工作区路径]` | `studio/changes/{name}/personas/{slug}.md`（多个时另出 `personas/README.md` 索引） | **2** |
| `/studio-insight:journey-map` | `[persona + 场景描述]` | `journeys/{persona-slug}-{scenario-slug}.md` | 1 |
| `/studio-insight:process-flow` | `[流程描述]` | `processes/{process-slug}.md` | **2** |
| `/studio-insight:domain-canvas` | `[领域描述 或 工作区路径]` | `domain-canvas.md` | 1 |
| `/studio-insight:behavior-matrix` | `[领域描述 或 工作区路径]` | `behavior-matrix.md` | 1 |
| `/studio-insight:opportunity-brief` | `[领域描述 或 工作区路径]` | `opportunity-brief.md` | 1 |

**六个 skill 内部结构完全同构，都是三段**：

```
① Expert Discovery（专家发现，五步）
    ↓
② 主体分析（各自不同）
    ↓
③ Expert Review（专家评审：派子代理逐个评审草稿）
    ↓
④ Validate（向你提 3–4 个问题）
    ↓
⑤ Write Output（这时才落盘）
```

**关键**：**先评审、再问你、最后才写文件**。学员看到"它在反复确认"不是卡住了，是设计如此。

## 二、专家发现机制（这一节讲透，学员才不会被"静默覆盖"坑）

### 五步查找顺序

1. **固定加载主角色** —— persona / journey / opportunity 三个用 `product-manager.md`；process / canvas / matrix 三个用 `architect.md`
2. `Glob studio/agents/*.md` —— **项目级自定义专家，先扫**
3. `Glob {插件内置}/agents/*.md` —— 内置专家，**"skip any already loaded from project"**
4. 按相关性匹配：拿专家的 `## Your Domain` 段与你的主题比对，**选 1–3 个**
5. **跳过 `_domain-expert-template.md`**（它是模板不是专家）

**第 3 步那句 skip 就是覆盖生效点**：`studio/agents/product-manager.md` 存在时，内置那份**根本不会被加载**。

### 内置的 11 个专家

| 通用 6 个 | 领域 5 个 |
|---|---|
| `product-manager` 用户视角，是否解决真问题 | `child-nutrition-expert` 0–12 岁营养 |
| `architect` 结构、边界、可持续性 | `child-exercise-expert` 0–12 岁运动发育 |
| `ux-researcher` 人**实际**怎么做，而非嘴上怎么说 | `elderly-nutrition-expert` 60+ 慢病膳食 |
| `data-analyst` 可度量性、指标与基线 | `elderly-rehab-exercise-expert` 60+ 康复与防跌倒 |
| `compliance-officer` 规则、风险与问责 | `skincare-expert` 护肤 |
| `operations-manager` 日常怎么落地、能否规模化 | |

> 老年营养 + 老年康复运动这两个内置专家，**正是康养项目沉淀下来的**。这就是讲 5「平台=固化物」在**专家层**的体现——上一个项目的领域知识，变成了下一个项目开箱可用的评审视角。

### ⚠️ 翻车点 1：同名专家静默覆盖

学员在 `studio/agents/` 放了个自己写的 `product-manager.md`，内置那份就不加载了。**产出的画像会走味，而且没有任何报错。**
**处置**：跑之前先 `ls studio/agents/`，心里有数。要定制就用 `/studio-core:create-expert customize product-manager`，别手搓同名文件。

> ⚠️ 另注：插件文档里有处写 `/studio-insight:create-expert` —— **这个命令不存在**，正确的是 **`/studio-core:create-expert`**。

## 三、六个产物长什么样（手册要给学员看样子）

### persona 卡
ASCII 卡片：Role / Age range / Tech level / Context / **Goals(1–3)** / **Pain points(1–3，带 高·中·低 severity)** / Current tools / Success looks like
\+ 共情图四象限：**Thinks / Sees / Hears / Does**
\+ 结尾两行 `Pain:` / `Gain:`

### journey
元数据（persona、scenario、trigger、end state）
\+ 逐阶段表，行标签固定：`Stage / Actions / Touchpoints / Thoughts / Emotion(带 emoji) / Pain points`，**4–7 个阶段列**
\+ 情绪曲线文字图
\+ **痛点机会表 5 列**：`# | Stage | Pain Point | Severity | Opportunity`
\+ Key insights

### process
元数据（name / trigger / end states / frequency）
\+ 文字流程图，**五种符号**：`[事件]` `◇ 问题？` `→` `├─` `(Actor)`
\+ **决策点表 5 列**：`ID | Decision | Condition | True path | False path`
\+ 并行说明 + 泳道图 + Key observations

### domain-canvas
每域一张卡：**Owns / Does NOT own / Key actors / Key events**
\+ **分类表**：`Domain | Type | Rationale`（Type = Core / Support / Generic）
\+ 关系表（`──▶ 喂入` / `◀──▶ 共享` / `· · · 独立` / `══▶ 编排`）
\+ 整张 canvas ASCII 图 + build strategy 建议

> **`Does NOT own` 这一行是精华**：定义一个域最有效的方式是说清它**不管什么**。这条直接喂给 T4 的域切分。

### behavior-matrix
Actor 清单（Type = User / AI Agent / System / External）
\+ 动作表 / 事件表 / 数据表
\+ **主矩阵 5 列**：`Actor | Action | Event | Data In | Data Out`
\+ 数据实体表 + **Gaps** + **Automation opportunities** + Skill mapping hints

> 主矩阵是 **T5 五要素的直接前身**：Actor→Action 的 actor，Action→Action，Data In/Out→Object 与 Link。T5 会回来用它。

### opportunity-brief
证据来源表 + 候选表（ID 形如 `OP-1`）
\+ **Impact × Feasibility 5×5 星阵**：★★★ Build first / ★★ Build next / ★ Consider / 空 Defer
\+ 工作量表 + 排名块（**Score = 两轴相乘**）+ Recommendation

> ⚠️ 它**明确拒绝给工期估算**（"Do NOT give time estimates"）。学员问"那什么时候能做完"——**这不是这个工具该回答的**，工期要等 T4 域切分和 T8 技能拆解之后才谈得上。

## 四、实操（70′）

### 🔔 先做一件事：把 T1 的输入包喂进去

> 六件套的第一个输入，就是 **T1 产出的 `_INPUT.md`**——不是让学员现场再口述一遍命题。
> **⭐ 这是对 T1 的一次真实验收**：如果跑出来的画像很空洞、或者术语每次都不一样，**回 T1 看输入包的②口径层缺了什么**，别怪工具。

### 🔔 任务
用本组命题跑完六件套，产出：**画像 ≥3、旅程 ≥2、流程 ≥2、热点分层一份**。

### 建议顺序与时间盒

| 序 | 命令 | 时长 | 输出 |
|---|---|---|---|
| 1 | `persona-insight` | 20′ | ≥3 张画像卡 + README 索引 |
| 2 | `journey-map` ×2 | 20′ | 2 条旅程（选**最能暴露痛点**的场景，不是最典型的） |
| 3 | `process-flow` ×2 | 15′ | 2 个流程（含决策点表） |
| 4 | `opportunity-brief` | 15′ | 热点排名（可当场推翻评分，见下） |

**domain-canvas 与 behavior-matrix 本步不强制跑** —— 它们在 T4 的 `/studio-planner:plan` 完整模式里会自动带出来。时间充裕的组可以跑 `behavior-matrix` 提前感受一下 T5 的五要素雏形。

### 🔔 难点/注意

**① 画像必须按「行为」切，不能按「人口属性」切。**

> 康养项目基线：7 个画像不是"60 岁以上老人""空巢老人"这种切法，而是
> **"熟人获客接受度 77.59%"**、**"智能监护接受但要简单式 84.48%"** ——按行为倾向切，且每条都有 368 份问卷校准。
> **判据**：两个画像如果目标、痛点、使用频率没有显著差异，就**不该拆成两个**。建议 2–3 个起步，超过 4 个说明你的范围划大了。

**② `opportunity-brief` 的评分可以推翻。**
skill 明确允许你**以业务理由否决它的排序**。这正是 C7「价值判断」不可外包的具体落点——模型能算 Impact×Feasibility，但"这个季度必须先啃硬骨头给客户看到东西"这种判断，只能人做。

**③ 没有工作区时产物会散落。**
六个 skill 都能脱离 `studio/` 独立跑，此时会写到**当前目录**或让你选路径。**先确认 `/studio-core:init` 跑过**，否则文件会撒得到处都是。

## 五、💡 启发范例 · 教育督导项目（点开看"做对了长什么样"）

> 素材：`Plugins/kindergarten-bench-plugins/studio/changes/saihan-preschool/`
> **成熟度诚实标注**：教育督导项目已完成建模 + 方案 + 47 页 Mock demo（数据是真的、AI 是 Mock），**本体未编译**（`status.json` phase=planning）。

**它的三件套长这样：**

| 类型 | 文件 | 看点 |
|---|---|---|
| personas | `p1-li-keke`（区教育局科长）/ `p2-zhang-yuanchang`（园长）/ `p3-wang-laoshi`（教师） | **三层视角**：监管者 / 管理者 / 执行者。同一件事在三个人眼里完全不同 |
| journeys | `j1-li-gap-to-okr`（从差距到 OKR）/ `j2-zhang-task-to-class`（从任务到班级）/ `j3-wang-upload-qc`（上传到质检） | **三条旅程首尾相接**：李科长的产出是张园长的输入，张园长的产出是王老师的输入 |
| processes | `pf1-district-gap-okr` / `pf2-park-task-decompose` / `pf3-upload-qc-loop` | 与旅程一一对应，把"人的体验"翻译成"系统的流程" |

**⭐ 最值得学的一点**：三个画像不是并列的三类用户，而是**一条责任链上的三环**。旅程也因此能首尾相接。
**给学员的问题**：你的命题里，那几个角色是并列的，还是有责任传递关系的？**如果是链，就按链来做旅程。**

**⚠️ 同时带一个 B-5 活体**：教育督导项目的园所数在源材料里**不一致**——event-storm 写 99 所、热点评估写 124 园、数据样本是 79 园。
**正确处置是三个数都标"待区教育局核实"，不替它选一个。** 学员最爱的动作是"挑一个看起来最靠谱的写上去"——那就是编造的开始。

**⚠️ 反面对照 · 学前教育项目**：那个项目交出了 653KB 可研和完整送审报价包，**但它没有 persona、没有 journey**，只做到 event-storm + 本体总纲。
**说明什么**：可研写得出来，不等于认知萃取做过了。**跳过 T3 也能交付，但交付的是"我们理解的业务"，不是"客户实际在做的业务"。**

## 六、知识（讲什么）· 栈① 产品设计（产品经理的方法论，30′）

> 这一节是讲 4「七角色知识栈」里的 **栈①**，能力位 **C1 认知萃取**。
> **【这个角色原本是谁】** 产品经理 / 产品设计师——负责把模糊的客户意图变成"要做什么"。传统模式里他一个人占着这个位置，交接给架构师时信息就衰减一次。**FDE 把这套方法论装进自己脑子**，从事件一路跑到机会矩阵，中间不换人。

### 6.1 核心命题

> **FDE 的核心资产不是"会用 AI"，是把客户的模糊意图压成可执行的结构。**
> 证据：康养项目 **102 个业务事件 → 16 事件簇 → 7 域限界上下文**。这一步没有任何模型能替你做判断，模型只能加速你做完。

产品设计**不是"画原型"**。它在这门课里的定义只有一句：**一条把"客户想要点什么"逼成可归域结构的方法论管线**——`事件 → 画像 → 旅程 → 机会矩阵`。管线的出口直接插进 T4 的限界上下文。

### 6.2 方法论内核：五个把模糊意图变结构的具体方法

| 方法 | 要点 | 本步对应的 skill |
|---|---|---|
| **Persona 用户画像** | 按**行为 / 目标 / 动机 / 痛点**定义真实用户，**不是人口属性堆砌**。画像是整条旅程的地基——Figma 的说法是 persona 让旅程"反映真实用户视角" | `persona-insight` |
| **User Journey Map 用户旅程图** | Figma 五要素框架：① 用户（persona）② 场景与目标 ③ **旅程阶段**（通用 awareness→consideration→decision→purchase→retention，可按业务定制）④ **行为·态度·情绪**（每阶段的正负情绪）⑤ **机会点**（从摩擦/痛点里长出来）。五步做法：研究数据定 persona 与目标 → 找触点 → 可视化阶段 → 逐阶段记录行为与情绪 → 用真实反馈校验迭代 | `journey-map` |
| **Opportunity Matrix 机会矩阵** | 把旅程里暴露的痛点**排优先级**——按影响 × 可行性 × 频率打分、ROI 排序，决定先做哪个 | `opportunity-brief` |

> ⚠️ **方法论与工具实现有一处差异，要当场说明**：机会矩阵在方法论上是**三因子**（影响 × 可行性 × 频率），但 `opportunity-brief` 这个 skill **只算两轴**——`Score = Impact × Feasibility`，5×5 星阵，**频率不进公式**。
> **不是工具做错了**：频率信息在旅程里（"每天都遇到" vs "一年一次"），工具把它留给你做最后判断。所以工具给的排序**本来就该被你以业务理由推翻**——这正是下面第三条要讲的。
> **别让学员对着两个数字发懵**，也别自己动手改工具的算法。
| **Event Storming 事件风暴** | 把业务事件全量铺开、再归簇，**喂给后面的限界上下文（栈②/T4）** | T4 `event-storm` |
| **产品思维（梁宁）** | 给上面这些方法补一层"人和情绪"：① **同理心**——看懂用户情绪、把需求分成**痛点/痒点/爽点**（画像和旅程里的"痛点"就从这来）② **机会判断·点线面体**——别做一个没有势能的孤点 ③ **用户体验五层**（战略存在/能力圈/资源结构/角色框架/感知层）——产品不止"感知层好看"，底下四层才决定成败 | 贯穿全部六件套 |

> **画像 → 旅程 → 机会矩阵是有先后的**：画像不真，旅程就是编的；旅程不暴露痛点，机会矩阵就没有原料。**这条顺序不能倒**，也是本步实操时间盒的排法依据。

### 6.3 业界经典（要补这一栈，就啃这几本）

| 来源 | 补什么 |
|---|---|
| **《设计冲刺 Sprint》**（Jake Knapp，Google Ventures） | 五天从问题到可测原型；HMW（How Might We）、用户测试是骨架 |
| **Figma User Journey Map 资源库** | 旅程图五要素与五步做法的权威框架（本步 `journey-map` 产物结构的出处） |
| **梁宁《产品思维 30 讲》**（得到） | 同理心 / 点线面体 / 用户体验五层，补足"情绪与势能"维度 |
| **内部《场景化产品设计》**（刘亚蒙，2018） | 它的"建立共同的认知约定：名词/概念/流程/节奏"**就是本课程锚定口径机制的原型**；"场景七要素"**就是后面 T5 五要素里 Action 的前身** |

> ⭐ 最后一条要当场点破：**产品栈和本体栈本是一条血脉。** 学员到 T5 会以为五要素是凭空长出来的本体概念——不是，它在产品栈的"场景七要素"里就有雏形。这也是为什么 T3 做得糙，T5 一定难受。

### 6.4 方法论 → 工具：这一栈已经被固化了

这些方法在 C-Life **不是靠手画白板，是固化成 studio 技能**：`persona-insight` · `journey-map` · `process-flow` · `opportunity-brief` · `behavior-matrix` · `domain-canvas`，加上 T4 的 `event-storm`。

> 这跟 T5 本体锚到 `clife-onto-engine` 是**对称的**：产品栈锚到 Astra Studio planner/insight 工具链——**方法论被平台固化**（呼应 T2 讲的"平台 = 方法论的固化物"）。
> 记住因果方向：**工具是果，管线是因**。不是因为有了这六个 skill 才这么做事，是因为先有这条管线，工具才长成这个样子。

### 6.5 康养项目完整链条（背下来，这是量级标尺）

```
102 业务事件 → 16 事件簇 → 7 角色画像（368 份问卷校准）
    → 7 条用户旅程 → 5 条业务流程 → 10 个热点（P1–P5 分层）→ 7 域限界上下文
```

**每一段都有一个 skill 对应**：`event-storm` 出 102 事件 / 16 簇 → `persona-insight` 定 7 画像 → `journey-map` 画 7 旅程 → `process-flow` 出 5 流程 → `opportunity-brief` 排 10 热点 P1–P5。**这条链就是本步实操要复刻的东西**，只是规模小一号。

### 6.6 三件事讲透

1. **画像的真假之分（本步唯一的核心教学点）** —— 假画像是人口统计（"60 岁以上、退休、有慢病"），真画像是**行为倾向 + 证据**（"熟人获客接受度 77.59%""智能监护接受但要简单式 84.48%"）。前者从常识就能编，**后者必须去问**——康养项目那 7 个画像背后是 **368 份问卷校准**，每条特征都能指回一份数据来源。
   > **判据**：两个画像如果目标、痛点、使用频率没有显著差异，就不该拆成两个。
2. **旅程要选"最暴露痛点"的场景，不是最典型的场景** —— 典型场景大家都顺，看不出机会在哪。
3. **热点分层是给决策者看的，不是给自己看的** —— Impact × Feasibility 打分的意义不在于分数本身，在于**逼你说清"凭什么这个先做"**。

### 6.7 同一套方法跨行业成立 · 教育督导项目的印证

教育督导项目用的是**完全同一套 planner/insight 方法**：3 画像（李科长 / 张园长 / 王老师）+ journey + `opportunity-brief` ROI 排序（material-qc / standard-decode / gap-diagnose 排 P0）。

> **康养和幼教，行业不同、交付模式不同，认知萃取这一栈的做法一模一样。** 这就是 C1 认知萃取**迁移力**的底座——也是为什么这一栈值得单独花 30 分钟：它是你换一个行业还带得走的东西。

### 6.8 ⚠️ 反例 B-7（旅程建模过重）

康养项目长者旅程的初版做的是**"夜间急救"**——场景很戏剧、很打动人，但**过重且偏离营收主线**，最后返工改成会员飞轮。

> **原则**：建模要服务于业务优先级，不是求全。**返工成本要记在方法论账上**，不能假装没发生过。
> **落到本步**：选旅程场景之前，先回头看 T1 写的商业模式——**那三条收入线在哪条旅程上？** 就做那条。

### 6.9 自学 / 自评到"能独立交付"

**练法**：对一个熟悉业务，限时做一张**含五要素（persona / 阶段 / 情绪 / 痛点 / 机会）的旅程图**，再从痛点排一张机会矩阵。

**自评三条（够到就是能交付）**：
- 能独立主持一场事件风暴，产出**可归域**（不是流水账）的事件集；
- 能做一张**情绪与机会点齐全**的 journey map；
- **每个画像特征都能指到一份数据来源**——康养项目 368 份问卷就是这条纪律的样板，指不出来源的特征就是编的（这正是 B-5「数据张冠李戴」的上游防线）。

## 七、知识（讲什么）· 认知杠杆：为什么工具能顶几个人（15′）

> **讲这一节的时机很关键：放在实操之后。** 学员刚亲手用六件套在 55 分钟里产出了传统要几天的东西——**这时候讲「认知杠杆」他有实感；开课就讲，他只当是口号。**
> 本节吸收讲义「第 2 讲 · 大模型时代 FDE 交付 vs 传统交付」。**口播稿在末节讲师包，5 段可照读。**

### 认知杠杆 = 结构化能力 × 平台固化（这一页是钉子，钉不进去前面白讲）

```
认知杠杆 = 结构化能力（决定能不能做对） × 平台固化（决定能不能做快做稳）
                    ★ 打字快 ∉ 这个公式
```

- **结构化能力**：把 102 个乱糟糟的业务事件收敛成 16 簇、压成 7 个域，**没有任何模型能替你做判断**。模型能帮你把 102 件事列出来、写候选归类，但"该归成 16 簇还是 20 簇、边界划在哪"是 FDE 的判断。**模型只能加速你做完，不能替你做对。** 你结构化能力越强，模型放大的倍数越大；**你结构化能力是零，模型放大零还是零。**
- **平台固化**：7 域同日并行编译、7/7 零悬空，靠的是 `studio-planner → domain-model → clife-onto-engine → citations 治理 → 可研生成` 这条固化管线（详见 T2 §六）。**没有工程化平台的 FDE，只是"更累的架构师"**——能做对，但做不快、做不稳、复制不了。

**顺带把"交付物形态"讲了**（学员以为 AI 只是让你写得快，交付物还是老三样，错）：

| | 传统 | FDE |
|---|---|---|
| 方案与系统 | Word 方案 ⟂ 系统（**两张皮**） | 11 章可研 ‖ 3835 行骨架（**同源**，7/7 py_compile） |
| 一致性 | **不可校验**（你怎么校验一份 Word 的内部一致性？） | A 结构 7/7 零悬空、B source 治理 7/7 零空 source |
| 规模与深度 | 5 人数周产不出，产出来也无法保证内部一致 | 14 类知识库 / 8 个知识图谱 / 约 350 万三元组 |

**节奏也变了**：传统是**串行接力**（总时长 = 各段之和），FDE 是**并行铺开**（35 个分节并行写作、26 图与写作同步、7 域同日编译）。

> ⚠️ **并行有代价，要诚实说**：各写各的，**口径会散**。康养项目的处置是先立一份 `_WRITING_BRIEF.md`（术语表 + 核心数据表 + 观点主张 + 协作纪律）当**唯一真相源**，**35 节全部引用不重算**，再用结构校验器兜底。
> **这条纪律就是本手册 §四 B-11 的上位规则**——"数字锚在单点、引用不重算"，在写作期叫 BRIEF，在调研期就叫"**换模板必须清空所有数字**"。

**🎯 Vibe Coding 的真相（一句话记死）**

| AI 能干 | AI 不能干 |
|---|---|
| **给了明确规格后**，把伪代码变 Python、处理文件读写、生成测试、格式化输出——10 分钟搞定 | **工程判断**：规则写入前还是后执行？日志存快照还是只存改变？Schema 用 YAML 还是 Python？多规则违反时短路还是收集？ |

> **"AI 能把'想清楚的事'快速变成代码，但不能代替'想清楚'这件事本身。"**
> **AI 把"实现"变便宜了，但没把"判断"变容易。** 没有蓝图的 Vibe Coding 会失控，一处改动带出三处 bug。
> **落到 T1**：这份项目描述，就是那份"蓝图"。**你在这一步偷的懒，AI 会在后面七步替你放大。**

### 口播 · 开场：为什么是"角色合体"，不是"技能清单"

**（用在：全课第一次讲"知识栈"时——本步是七栈的第一站，这段开场只在 T3 讲一次，T4/T5a/T6 不再重复。原话稿，出自讲义 04 §3.0）**

### 口播 · 栈①的角色定位与内核

**（用在：第六节 6.1–6.2，进入方法表之前。讲述要点（非原话稿），出自讲义 04 §3.1）**

> "这一栈原本是谁的活？产品经理、产品设计师——负责把模糊的客户意图变成'要做什么'。但产品设计不是'画原型'，它的核心是四件**可照做的方法**，一步步把'客户想要点什么'逼成可归域的结构：Persona 按行为、目标、动机、痛点定义真实用户，**不是人口属性堆砌**；User Journey Map 有五要素——用户、场景与目标、旅程阶段、行为态度情绪、机会点，机会点是从摩擦和痛点里长出来的；机会矩阵把痛点按影响乘可行性乘频率排出优先级；事件风暴把业务事件全量铺开再归簇，喂给后面的限界上下文。再加梁宁那套产品思维，补上'人和情绪'这一层——痛点、痒点、爽点，点线面体，用户体验五层。这五样合起来，才是这一栈。"

### 口播 · 画像必须按行为切（本步唯一的核心教学点）

**（用在：第六节 6.6 第 1 条 + 实操第①个难点，学员开始跑 `persona-insight` 之前。讲述要点（非原话稿），出自讲义 04 §3.1 康养项目段）**

> "康养项目 `persona-insight` 定出 7 个画像，是 368 份问卷校准过的，而且**是按行为聚类的**——不是按'60 岁以上老人'这种人口属性切，是按'熟人获客接受度 77.59%''智能监护接受但要简单式 84.48%'这种**行为倾向**切。差别在哪？人口属性那种画像，你坐在办公室里凭常识就能编出来，编出来还看不出错；行为倾向这种，**你必须去问**，问完还得留下数据来源。所以我给你们的验收标准只有一条：**每个画像特征，都要能指到一份数据来源。** 指不出来的，就是你编的。"

### 口播 · 同一套方法跨行业成立

**（用在：第六节 6.7 或第五节教育督导项目范例讲完时。讲述要点（非原话稿），出自讲义 04 §3.1 教育督导项目段）**

> "教育督导项目用的是同一套——3 个画像：李科长、张园长、王老师，加 journey，加 `opportunity-brief` 的 ROI 排序，material-qc、standard-decode、gap-diagnose 排 P0。康养和幼教，行业不同、交付模式也不同，但**认知萃取这一栈的做法一模一样**。这就是为什么这一栈值得单独花三十分钟：它是你换一个行业还带得走的东西。"

### 口播 · 人力对比，一次真实的实证（对应 §六 ③ 开场）

"上一讲我说'一个人贯通消除断层'，肯定有人心里嘀咕：一个人扛得动吗？还是嘴上好听、实际累死？今天我用康养项目的账，一笔一笔算给你看。

同一条交付链——从需求调研到 7 域数智本体建模、到 3835 行可运行插件骨架、到 100+ 页对客可研——两种模式的投入是这样：

**传统模式**：产品经理 + 架构师 + 行业顾问 + 方案经理 + 美工，**5 人以上，数周**。而且这 5 个人之间有至少 4 道接缝，每道接缝都在漏（第 1 讲讲过）。

**FDE 模式**：**1 名 FDE + 智能体编队**。0 接缝。

这不是'省了 4 个人'这么简单。是**交付的组织形态变了**——从'按工种分人、靠流程串起来'，变成'按认知链分给一个人、靠智能体扩手脚'。"

### 口播 · 交付物形态的根本变化（对应 §六 ③ 的对照表）

"再看**交出去的东西**变了没有。很多人以为 AI 只是让你'写得快',交付物还是老三样。错。康养项目的交付物形态是传统模式**根本产不出**的：

第一，**方案与代码同源**。传统模式里，可研报告是方案经理写的 PPT/Word，跟真正的系统是两张皮。康养项目不是——11 章可研背后，是 3835 行可运行的 Python 插件骨架 + 21 个 YAML，**7/7 py_compile 通过**。方案里写的每个域，都有能编译的结构撑着。方案不再是"说说而已"，是"已经建好了骨架的说明书"。

第二，**结构可校验**。7 域五要素 OAG：Object 76 / Link 75 / Function 38 / Rule 47 / Action 54，A 结构校验 7/7 零悬空引用，B source 治理 7/7 零空 source。传统方案没有"校验"这个概念——你怎么校验一份 Word 的内部一致性？

第三，**规模与深度**同时在线：14 类知识库 / 8 个知识图谱 / 约 350 万三元组。这个体量,传统 5 人团队数周产不出，产出来也无法保证内部一致。"

### 口播 · 节奏与质量控制的根本变化（对应 §六 ③ "节奏也变了"）

"节奏也变了。传统模式是**串行接力**：需求做完交设计，设计做完交开发，一棒接一棒，总时长是各段之和。FDE 模式是**并行铺开**：一个人在同一时间，指挥智能体编队并行跑多条支线。

康养项目可研的写作阶段就是活样本：**35 个分节并行写作**，不是一节一节写。制图 26 张与写作**同步跑**。7 个域**同一天并行编译**。这不是把串行加速，是把串行**改成了并行**——这是节奏上质的差别。

但并行有个致命风险：**各写各的，口径会散**。所以质量控制的方式也跟着变了。传统靠'评审会'事后抓错；FDE 靠**锚定口径 + 结构校验**事前防错。康养项目的做法是先立一份 `_WRITING_BRIEF.md`（术语表 + 核心数据表 + 观点主张 + 协作纪律）当**唯一真相源**，35 节全部引用不重算,再用结构校验器兜底。

我要诚实说一句：**并行不是没代价的**。散了口径就要收口。下一讲会讲到康养项目栽过的跟头——图目计数漂移、章节编号冲突——那都是并行的账。但账是可控的，靠的是纪律，不是靠不并行。"

### 口播 · 杠杆到底来自哪里（对应 §六 ③ 公式，**全讲的钉子，别讲偏**）

"最后这页是全讲的钉子，钉不进去前面白讲。**FDE 的杠杆，不来自打字快，来自两样东西：结构化能力 + 平台固化。**

先说**结构化能力**。康养项目最难的一步是把 102 个乱糟糟的业务事件，收敛成 16 簇、压成 7 个域。这一步**没有任何模型能替你做判断**——模型可以帮你把 102 件事列出来、可以帮你写候选归类，但'该归成 16 簇还是 20 簇、这个域的边界划在哪'，是 FDE 的结构化判断。模型只能**加速你做完**，不能**替你做对**。这是杠杆的支点：你结构化能力越强，模型放大的倍数越大；你结构化能力是零，模型放大零还是零。

再说**平台固化**。7 个域能在同一天并行编译、7/7 零悬空引用，靠的不是个人手速，是 studio-planner（事件风暴）→ domain-model（限界上下文）→ clife-onto-engine（本体）→ citations 治理 → 可研报告生成 这一条**固化管线**（Astra Studio）。方法论一旦固化进平台，就不再依赖'这个人今天状态好不好'。**没有工程化平台的 FDE，只是"更累的架构师"**——他能做对，但做不快、做不稳、复制不了。

所以杠杆 = 结构化能力（决定能不能做对）× 平台固化（决定能不能做快做稳）。打字快，在这个乘式里连一项都不是。"

### 口播 · Vibe Coding 的真相（对应 §六 ③ 末尾的 🎯 段）

"上一页那句'模型只能加速你做完、不能替你做对'，不是我编的口号，是我们方法论文集里一篇《AI 时代的 FDE》的第一手结论。作者用 AI 辅助，**3 小时**手搓了一个本体引擎原型；他复盘'这 3 小时里 AI 到底干了多少活'，得出一张清单——

- **AI 能干的**：给了明确规格后，把伪代码变 Python、处理文件读写、生成测试、格式化输出——10 分钟搞定。共同特征：**给明确规格，AI 快速生成代码。**
- **AI 不能干的**：规则写入前还是后执行？日志存快照还是只存改变？Schema 用 YAML 还是 Python？多规则违反时短路还是收集？——这些是**工程判断，不是编码问题**。AI 只会给'常见做法'，不一定符合你的设计原则。

一句话结论，请记死——**'AI 能把"想清楚的事"快速变成代码，但不能代替"想清楚"这件事本身。'** '想清楚'指的就是：数据规模 vs 决策治理、规则 vs 前置条件、可追溯性要什么、业务人员要审查什么、边界条件怎么处理——**这些判断都发生在写代码之前。**

所以'认知杠杆'的真相是：**AI 把"实现"变便宜了，但没把"判断"变容易。** 谁的判断力强，谁的杠杆就大；没有判断，AI 放大的是一堆能跑但错的代码（方法论 06 原话：没有蓝图的 Vibe Coding 会失控，一处改动带出三处 bug）。再补一句同篇的判断——**'平台越来越便宜，本体模型越来越值钱；会建模型的人，不会被替代，而是被放大。'**"

> **讲 1**："你以为你在'对接需求'，其实你只是在'转述需求'——把上一道工序的话原样递给下一道，中间那些没写进文档的判断，从你手上又蒸发了一层。**你不是断层的受害者，你就是断层本身。**"
